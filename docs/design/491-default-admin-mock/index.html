The problem#484's warning has a blind spot

The everyone-is-an-admin warning (#484) shows when nobody is mapped to a role and no admin list is set — ssoRBACCheck in internal/api/setup_checks.go. It does not check the other way admin becomes universal: WARDYN_OIDC_DEFAULT_ROLE=admin. When that variable is set, every sign-in the role map does not match falls through to admin (deriveRole, internal/auth/oidc/derive.go), and validDefaultRole (cmd/wardynd/boot_deps.go) permits it.

A role map being set is exactly the condition that today reads ok and hides the banner — so a deployment can have named role-map rows, a default role of admin, and still hand admin to everyone the map does not name, with no warning anywhere. Proposal: warn whenever the default role is admin, whether or not a role map is set. Same banner, same title, same CTA — three small copy additions for this state: a banner body sentence, and the matching setup-row detail and fix. No new title, no new surface.

DecisionsThree, each drawn as recommended.
  1. Same banner, or a distinct one? Drawn: the existing EveryoneAdminBanner component and the existing sso_rbac setup row, unchanged in shape — only the warn condition widens and the body sentence is chosen per-case. The other option is a second banner/row dedicated to the default-role case.

    Recommended: same banner. Both cases are the same fact from the person signing in — every unmatched identity becomes admin — and Q457-4 already established one banner shows this fact to admins everywhere. A second banner risks both showing at once when a deployment has neither a role map nor an admin list AND a default role of admin.

  2. Does the sentence name the env var? Drawn: no. The banner sentence stays in the same register as today's — "signs in", "identity provider", never a variable name — and reads a setup-check fix string, not the banner body, for the operator-facing detail. Compare the banner page's two body sentences to decide.

    Recommended: no. #484's frozen strings never name WARDYN_OIDC_OPERATOR_EMAILS either; the setup row's fix field is where a chart variable is named (see tls_cookie_posture's fix, which does name one), consistent with the existing split between banner (what/why) and setup detail (how to fix).

  3. Does the setup check turn warn, or stay ok with the banner only? Drawn: the setup check turns warn too — the check exists to catch exactly this configuration mistake, and Q457-6's canon already treats Blocking: true as the row's own concern, not the banner's. The other option is to leave the row ok (a role map is configured) and let only the banner carry the new warning.

    Recommended: warn. A setup row that reads ok while every unmapped person becomes admin is the exact gap #491 reports; hiding it behind the banner alone reintroduces the "row says fine, nothing else shows" failure #484 was built to close.
