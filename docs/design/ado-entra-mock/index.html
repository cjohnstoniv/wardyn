What a run may do here

Two lists, and the difference between them matters: the ceiling is what a run may ever ask for, the defaults are what it starts with.

Capability ceiling

What a run may ever ask for. Anything not ticked here is refused outright — nobody can approve it, not the person and not you.

Read

Clone, fetch, and read work items, pipelines and policies.

 Push

Push commits, and create or move a branch no policy protects.

 Pull requests

Open, update, comment on and complete a pull request.

 Branch policies

Create, change or delete a branch policy.

 Push past a branch policy

Move a policy-protected branch, or complete a pull request with its policies bypassed.

 Run pipelines

Queue a build or a release.

 Repository settings

Rename, fork, or change a repository's own settings.

 Work items

Create and edit work items.

 Wiki

Create and edit wiki pages.

 Anything Wardyn does not recognise

Off: a write Wardyn can't name is refused and can't be approved. On: it can be asked for, named by its address. Leave it off unless a tool you need is being refused.

Where this is enforced

Three different things, held by three different parties. Wardyn states all three because only two of them are Wardyn's.

Who a run acts asAzure DevOps. It is that person's own sign-in, so their own Azure DevOps permissions apply and a repository they can't read stays unreadable. Every commit and every API call is recorded under their name.
What a run may doWardyn. Every Azure DevOps request is read at the proxy and refused if this run hasn't been granted it. This check is what bounds the run — not the token.
The token's own reachNobody narrows it. A Microsoft Entra sign-in token carries every Azure DevOps permission that person has consented to, and asking for less changes nothing. Switch Token to “One Azure DevOps mints per run” to have Azure DevOps bound it too.
Always refused, on every Azure DevOps rowCreating or revoking tokens, service hooks, and installing extensions. They are not on the ceiling, they can't be approved, and no change here allows them.
Only the GitHub App lane keeps its token outside the sandbox — a PAT or SSH key enters it for the clone, then is wiped. Public repos clone with no credential at all.
