# Wardyn 0.8.6 — git_pat narrowing (GPAT)

An adopter that reaches GitLab-style forges with a `git_pat` grant asked for the grant to be
narrowable: to a set of repositories, to read-only, and with or without the forge's API. Today a
`git_pat` grant names a host and a stored secret and nothing else. Every run that holds it can
clone, fetch and push any repository the PAT itself can reach on that host.

Wardyn cannot narrow the PAT. It is a long-lived credential the forge issued with whatever
scope the operator chose. Wardyn can narrow the **run**. With the PAT broker on (the default
since 0.7), the PAT never enters the sandbox, and every git request to the forge passes through a
proxy route that Wardyn controls. A refusal at that route is therefore a real boundary. 0.8.6
uses it.

0.8.6 first closes a hole in that boundary (lane `gpat-g0`, which ships first). It then adds
four scope axes, `repos`, `access`, `api` and `forge`, and makes the governance bounds understand
them **before** anything enforces them. Last come the broker enforcement, the console and the
forge API door.

This record is the design for epic GPAT and its five lanes (`gpat-g0` to `gpat-g4`). Every code
reference is to `origin/main` at `e0efee625` (v0.8.5).

## What exists today

**The scope.** A `git_pat` scope is `{host, secret_name, username?}`. It is decoded in three
places that are kept in agreement by hand:

- `gitPATScopeFields` (`internal/api/runs_scm.go:429-442`), with a lenient `json.Unmarshal`;
- the broker's `gitPATScope` (`internal/broker/broker.go:810-815`), decoded by `mintGitPAT`
  (`internal/broker/broker_mint_kinds.go:105-112`);
- composer's `grantPairingOf` (`internal/composer/grantbound.go:88-92`).

Unknown keys are ignored everywhere. A policy written today with `"repos": [...]` in a `git_pat`
scope is accepted, and the field does nothing.

**The broker lane.** With `WARDYN_GIT_PAT_BROKER` on (`docs/ENV.md:225`, `internal/api/server.go:479-492`),
dispatch:

- withholds the grant ids from the sandbox env (`internal/api/runs_dispatch_mounts.go:453-466`);
- tells `agent-run` which hosts to route through `/wardyn/git/<host>/` (`WARDYN_GIT_PAT_BROKER_HOSTS`);
- hands the proxy a per-host map, `ProxyConfig.PATGrants` (`internal/egress/proxy/config.go:83-103`),
  built by `patBrokerGrants` (`internal/api/runs_dispatch.go:955-968`).

The proxy's `handlePATBroker` (`internal/egress/proxy/pat_broker.go:89-191`) then runs these steps
in order:

1. Look up the host (`:98`).
2. Refuse an unsafe path (`patForwardSafe`, `:116`) or a non-smart-HTTP verb (`validGitRest`,
   `internal/egress/proxy/git_broker.go:509-518`).
3. Hand an Azure DevOps host to its own lane (`:123-126`).
4. Apply branch-namespace and push content rules (`:128-161`).
5. Mint the PAT through `patToken` (`:163`).
6. Forward with Basic auth (`:174-191`).

The comments state the current position plainly: the allowlist is "per-HOST (a per-repo key would
imply a confinement the credential doesn't have)" (`pat_broker.go:12-15`, `config.go:97-102`).

**The raw-mint hole.** The proxy relays `POST /wardyn/v1/credentials/mint` from the sandbox to the
control plane with the run token attached (`internal/egress/proxy/local_routes.go:115-139`). It
refuses a body that names one of the run's **GitHub** broker grants (`isBrokeredGitGrant`,
`git_broker.go:247-276`), and nothing else. The proxy's own broker mint goes to the same control-plane
endpoint with the same run token (`mintGitToken`, `git_broker.go:375`). The control plane therefore
cannot tell the two callers apart.

A `git_pat` grant id is documented as non-secret (`runs_dispatch_mounts.go:449-450`). It appears in
audit rows and run detail. A sandbox that learns one can mint the PAT raw through the relay, so the
"never resident" posture rests on the secrecy of an id that is not secret. On an approval-gated,
single-use grant, the sandbox's mint also burns the broker's one mint.

The control plane's own check, `brokeredForgeMintKind` (`internal/api/internal_mint.go:158-205`),
refuses a `git_pat` mint only for a **GitHub-brokered** forge host (`:192-195`).

**Shadowed and withheld grants.** `persistRunGrants` writes every eligible grant row
(`internal/api/runs_create.go:468-478`). It then builds a host→id map that keeps only the last grant
per host (`:517`) and skips vetoed lanes with `continue` (`:512-515`). Dispatch later drops
brokered-forge hosts (`dropBrokeredGrants`, `runs_dispatch.go:252-253`). Every one of those grant
rows can still be minted by id. `credential_grants` is insert-only (`internal_mint.go:156-158`), so
`ListGrantsByRun` is the complete set.

**The governance bounds know host and secret only.**

| Seam | Code | What it compares for `git_pat` |
|---|---|---|
| Pairing identity | `grantPairingOf` (`composer/grantbound.go:88-92`) | `(host, secret_name)` |
| Clamp dominance | `grantDominatedBy` (`composer/clamp.go:419-430`) | approval, TTL, GitHub scope only |
| Clamp meet | `clampGrants` (`composer/clamp.go:445-469`) | GitHub scope intersected (`:465-469`); nothing for `git_pat` |
| Write and resolve | `governanceGrantWithinCeiling` (`internal/api/governance_grantbound.go:143`), called at profile write (`internal/api/governance.go:208`) and at resolve (`reintersectGovernanceGrants`, `governance.go:909-916`) | approval, `owner_only`, TTL, GitHub scope (`:207`) |
| Create | `composer.Clamp` (`internal/api/inline_policy.go:71`, `internal/api/profile.go:135`) | as Clamp |

Adding `repos`/`access`/`api`/`forge` to the struct without touching these seams would let a member
take a ceiling grant narrowed to `team/app` read-only, and propose:

- the same pairing with `team/other`;
- `access: write`;
- `api: true`;
- the field left out.

Each proposal would survive Clamp, write validation and resolve-time re-intersection, and the proxy
would then enforce the member's widened scope.

**There is no REST door on this lane.** The threat model says so: "The GitHub App and `git_pat`
lanes have no REST door" (`threatmodel/THREAT-MODEL.md:3269-3276`). The Azure DevOps REST gate is
the only forge API Wardyn governs. It sits on the MITM path (`gateADO`, `internal/egress/proxy/ado_gate.go:82`,
called from `serveMITMRequest`, `internal/egress/proxy/mitm.go:374`). It refuses content writes it
cannot read (`internal/egress/proxy/ado_content.go:38-60`). It judges the effective method, with
`X-HTTP-Method-Override` applied (`THREAT-MODEL.md:3255-3258`).

**File-size budget.** `inline_policy.go` is 988 and `runs_dispatch.go` 968 of 1000 lines
(`scripts/check-file-size.sh`). New code goes in new files.

## Decisions

### D1. Close raw mint first, in the proxy (`gpat-g0`)

While `p.PATBroker` is on, dispatch exports the **complete** set of the run's `git_pat` grant ids as
a new `ProxyConfig` field, `brokered_pat_grant_ids`. `handleBrokerMint` refuses any body whose
`grant_id` is in that set (`isBrokeredPATGrant`, beside `isBrokeredGitGrant`). It answers `403` and
emits a `brokered:mint` deny decision (`local_routes.go:47`), the same shape as the GitHub refusal at
`:129-134`.

The set is read at dispatch from `ListGrantsByRun`, keeping every `GrantGitPAT` row. It therefore
includes:

- a grant shadowed by a later grant for the same host (`runs_create.go:517`);
- a grant whose lane was vetoed (`:512-515`);
- a grant withheld for a brokered forge (`runs_dispatch.go:252-253`, `runs_dispatch_mounts.go:453`);
- an Azure DevOps owner-only grant (`runs_create.go:463-466`).

A list failure with the broker on fails the dispatch closed. Decoding mirrors the control plane
exactly, as `isBrokeredGitGrant` does. An undecodable body still passes to the control plane, which
answers `400`; the reasoning at `git_broker.go:256-259` applies unchanged.

With the broker off, the field is empty and legacy grants mint exactly as today. That is the
documented posture of `WARDYN_GIT_PAT_BROKER=off`.

Revive reloads the rendered proxy config (`internal/api/run_revive.go:590-612`). When it drops a
denied host's lane (`:606-611`), it leaves the id set untouched. A dropped lane's grant stays
refused. A config rendered before 0.8.6 carries no set, so with the broker on revive recomputes it
from `ListGrantsByRun` with the dispatch helper and overwrites the loaded value; a list failure
refuses the revive, as `reassertProxyCeiling` refuses a ceiling it cannot honour.

*Rejected:* a control-plane refusal. The control-plane mint endpoint cannot tell the proxy's own mint
from the sandbox's: same route, same run token (`git_broker.go:375`, `local_routes.go:137`). Refusing
there would break the broker itself.

*Rejected:* threading the set from `persistRunGrants`. That would need one more field on
`grantWiring` and `dispatchParams`, and every dispatch caller that does not come through
`persistRunGrants` would miss it. The grant table is insert-only and complete, so one read at
dispatch is the single answer.

*Rejected:* deriving the set from `PATGrants`. That map keeps one id per host, after vetoes and
drops, which is exactly the incomplete set this lane exists to fix.

### D2. Wardyn narrows the run, not the PAT

The scope gains four axes:

| Field | Values | Omitted means |
|---|---|---|
| `repos` | list of repository paths on the grant's host; an entry may end in one `/*` segment | every repository the PAT reaches (unnarrowed) |
| `access` | `read` \| `write` | `write` |
| `api` | bool | `false` |
| `forge` | `gitlab` \| `bitbucket_server` \| `gitea` \| `generic` | `generic` |

These omission defaults are the contract (D4). An omitted field never means "whatever the ceiling
says". `access` defaults to `write` and `repos` to all, so every grant stored before 0.8.6 means
exactly what it meant in 0.8.5. `api` defaults to `false`, which is also today's behaviour, since
the lane has no REST door.

`forge` defaults to `generic`, the strictest path identity (D6), so leaving it out can never make two
distinct repositories compare equal.

A grant is **narrowed** when it sets `repos`, sets `access: read`, or sets `api: true`. Only a
narrowed grant is affected by D7's dispatch refusals.

*Rejected:* a per-repo grant kind. A second kind would double every seam in the table above, and the
pairing identity `(host, secret_name)` would still be shared between the two.

*Rejected:* auto-narrowing to the run's declared workspace repos (Q-GPAT (b)). The declared clone set
is chosen by the person launching, not by the operator. Using it as the bound would let the launcher
pick the narrowing. Narrowing stays an operator-authored field.

### D3. One scope type, decoded once, strict at write

A single typed scope, with `Decode` and `Normalize`, replaces the three hand-kept decoders
(`runs_scm.go:429`, `broker.go:811`, `grantbound.go:88`). It lives in `internal/types`, so api,
broker, composer and the dispatch half all read one definition. `Normalize` applies the omission
defaults of D2 and returns a value in which an absent `repos` (all) is distinct from an empty
`repos` (none). The same file holds the one repository-key function of D6,
`types.PATRepoKey(forge, path) (key string, ok bool)`, used by the composer contract (D4) and the
proxy's path extraction (D5) alike.

Every caller moves to the typed scope:

- `internal/api/policy.go:537,661`;
- `internal/api/inline_policy.go:787,895`;
- `internal/api/runs_create.go:463,506,571`;
- `internal/api/internal_mint.go:192`;
- `internal/api/compose_setup.go:191,394`;
- `internal/api/run_revive.go:606-611`: no scope decoding here, only the `PATGrants` ceiling loop (the one gpat-g0 touches); unchanged by this lane;
- `internal/api/approvals_push.go:152`, found while writing this record.

**At write,** a `git_pat` scope is decoded strictly: an unknown key is a `400`. Strict decoding
runs on request bodies (`policies.go:48`, `governance.go:145`, `inline_policy.go:224`,
`presets.go:166`, `policy_grade.go:47`) and on the boot policy file (`LoadPolicySpec`, which already
uses `DisallowUnknownFields`; the CHANGELOG upgrade line names the `--policy` file). Record-mode
synthesis from stored grant specs (`profile.go:136`) stays lenient. A typo such as
`"repo"` would otherwise read as an omission, and an omission means unnarrowed. Reads stay lenient,
so a stored row with an unknown key still loads and runs as it did. Write-time validation also
covers:

- each `repos` entry: non-empty, no `..`, `?`, `#`, backslash or control character (the
  `patForwardSafe` set, `pat_broker.go:72-86`), at most one trailing `/*`;
- `access` and `forge`: inside their enums;
- `api: true`: refused unless `forge` is `gitlab` or `gitea` (or `bitbucket_server`, under Q-GPAT
  (a)), and refused outright as "not yet available" until `gpat-g4` merges;
- a narrowed scope on an Azure DevOps host (`adoGrantHost`): refused, naming that host's own lane
  (D7 is the authoritative check).

*Rejected:* strict decode on read. It would turn a stored policy carrying a stray key into a run
that cannot launch after upgrade.

### D4. One PAT dominance and intersection contract, used at every bound

Two exported functions in `internal/composer` sit beside `GitHubScopeWithin`/`clampGitHubScope`:

- `PATScopeWithin(g, cg)` reports whether ceiling grant `cg` dominates proposal `g` on **every**
  PAT axis:
  - `repos`: `g.repos ⊆ cg.repos` under the forge's identity rule (D6). An omitted `cg.repos`
    dominates anything. An omitted `g.repos` is dominated only by an omitted `cg.repos`. A
    `group/*` in `g` is covered only by the same `group/*`, or by an omitted `cg.repos`.
  - `access`: `read ≤ write`.
  - `api`: `false ≤ true`.
  - `forge`: equal after normalisation **only when `cg` sets `repos` or `api: true`**. There a
    forge change changes path identity or the API table, so differing forges never dominate. When
    `cg` leaves `repos` out and has `api: false`, the forge axis is free and `PATScopeMeet` keeps
    `g`'s forge. Every ceiling written before 0.8.6 has no `forge` key (it reads as `generic`), so
    without this a narrower proposal on any other forge could never sit under it.
- `PATScopeMeet(g, bounds)` intersects `g` with every bounding ceiling grant. It is
  order-independent. If the `repos` intersection is **empty**, the grant is **dropped** with a
  warning. It is never kept with an empty list that would read as "all", the same trap as an empty
  method list meaning every method. Forges that disagree also drop the grant, except against a bound
with no `repos` and `api: false`, where `g`'s forge is kept.

**One ceiling grant must dominate every axis.** Two same-host ceiling grants, one wide on `repos` and
one wide on `access`, do not combine into a proposal wide on both. This matches the existing rule
that identity, then a single dominating grant, decides (`clamp.go:432-460`).

The contract is wired into every seam that bounds a grant:

| Seam | Change |
|---|---|
| write | `governanceGrantWithinCeiling` (`governance_grantbound.go:143`), beside the GitHub check at `:207`, refuses with a sentence naming the axis; `validatePolicySpec` (`policy.go:537`) and the inline path (`inline_policy.go:787,895`) validate the scope |
| create and preflight | `grantDominatedBy` (`clamp.go:419`) checks the PAT axes; `clampGrants` (`:445`) applies `PATScopeMeet` beside the GitHub meet (`:465-469`) |
| resolve | `reintersectGovernanceGrants` (`governance.go:909-916`) inherits the write check, because it calls the same function |
| composition and GOV4 `Leq` | COMP's single base-dominance contract, `composer.GrantWithin` (design 0.8.6-comp, "Grants: one base-dominance contract"), is `governanceGrantWithinCeiling` moved by `comp-d2`, so it calls `PATScopeWithin`. That is why `comp-d2` is blocked by this lane. `owner_only` in that contract is COMP's, not this lane's |

**Two `git_pat` grants for one host in one run policy, where either is narrowed,** are refused at
write and at create (`422`). The proxy holds one grant per host (`pat_broker.go:98`).

*Rejected:* a union, which would let one grant's PAT reach the other grant's repositories.

*Rejected:* today's last-wins, which makes the narrowing depend on list order (`runs_create.go:517`).

Unnarrowed duplicates keep today's behaviour, unchanged.

*Rejected:* enforcing the new axes in the proxy first and the bounds later. Until the bounds
understand an axis, the proxy would faithfully enforce a scope a member had widened.

### D5. Enforcement in the broker, before any mint (`gpat-g2`)

`ProxyConfig.PATGrant` (`config.go:403-406`) gains the normalised `repos`, `access` and `forge` (and
`api`, read by `gpat-g4`). `patBrokerGrants` (`runs_dispatch.go:955`) takes only a host→id map, so
it holds no scope. The scope comes from the `ListGrantsByRun` rows `gpat-g0` already reads at
dispatch: for each host's winning grant id, that row's typed scope (`Decode` + `Normalize`). There is
no second read and no new `dispatchParams` field. A winning id with no row fails the dispatch closed.
The D7 refusals read the same rows.

`handlePATBroker` runs two checks **after** `patForwardSafe`/`validGitRest` (`pat_broker.go:116-120`)
and the Azure DevOps hand-off (`:123-126`), and **before** the push rules (`:128`) and `patToken`
(`:163`). They sit after the hand-off because a host on the Azure DevOps lane may have no `patGrants`
entry (`:98-100`), so `grant` is the zero value there; past `:126` the request is on the `granted`
path, the grant is the real one, and nothing has been minted yet:

- `patRepoAllowed(grant, rest, verb)` extracts the repository path from `rest` with the forge's
  path table (D6) and requires a match in `grant.repos`. An unnarrowed grant passes, as today.
- The **read-only check**, for `access: read`, refuses both receive-pack doors:
  - `GET …/info/refs?service=git-receive-pack`, the ref advertisement a push starts with;
  - `POST …/git-receive-pack`.

  Refusing only the `POST` would still advertise refs for a push the run can never make, and a
  future verb change could open the second door.

A refusal is a `403` with a new decision-log rule source: `brokered:git-pat:repo` or
`brokered:git-pat:read-only`. Both are documented in `docs/AUDIT-ACTIONS.md`'s rule-source table,
which `TestAuditActionsDocEnumeratesEveryRuleSource` guards. Because both checks run before
`patToken`, a refused request consumes nothing: an approval-gated single-use grant still has its
one mint for the next allowed request.

The comments at `pat_broker.go:12-15` and `config.go:97-102` are rewritten. The PAT still cannot be
narrowed; the run now can.

*Rejected:* checking after the push rules. The push-rule path may read the forge
(`brokered:git:forge-read`) and may hold for review, both of which spend the credential.

### D6. Repository identity is the forwarded path

`forwardBrokeredGit` forwards `rest` as the upstream path (`pat_broker.go:197-205`). The identity
check must compare against **what is forwarded**, or two names that the check folds together reach
two different repositories. git-http-backend serves different repositories for `Team/App.git` and
`team/app.git`, and for `team/foo` and `team/foo.git`.

- **`generic`:** the path is preserved **exactly**. There is no case-folding and no `.git`
  stripping. `repos: ["team/app"]` matches `/team/app/info/refs` and nothing else. `team/app.git` is
  a different entry.
- **`gitlab`, `gitea` and `bitbucket_server`:** each has a path table: the accepted request forms
  and the repository key. Canonicalisation (for example an optional `.git`) applies **only** where
  the proxy then forwards the canonical form, so the checked string and the forwarded string are one
  value. That is the rule `patForwardSafe` already states (`pat_broker.go:65-71`). A forge that
  would serve the original form differently from the canonical one gets no canonicalisation.
- **One function.** These rules live in `types.PATRepoKey` (D3) and nowhere else. The composer's
  comparison and the proxy's extraction both call it, so the identity the bound compares is the
  identity the proxy forwards.
- **One trailing `/*`** matches exactly one further path segment. `group/*` matches `group/app` and
  not `group/sub/app`. Subgroups need their own entry.
- **Encoding.** `handlePATBroker` reads the decoded path (`:90`). A request whose escaped path
  decodes to a different segment structure, such as an encoded `/`, is compared on the decoded form
  that `forwardBrokeredGit` rebuilds. Tests pin that the compared form and the forwarded URL path
  agree.

*Rejected:* universal case-folding and `.git` stripping. It aliases distinct repositories on a
generic git-http-backend while the proxy forwards the original path.

### D7. Dispatch refuses a narrowing it cannot enforce (`gpat-g2`)

Three cases fail the dispatch, with a reason the run's failure shows:

- **A narrowed grant with the broker off.** With `WARDYN_GIT_PAT_BROKER=off`, the PAT is resident
  in the sandbox (`runs_dispatch_mounts.go:467-471`), and a narrowing would be fiction. Reason:
  `git_pat_narrowing_needs_broker`.
- **A narrowed grant alongside an `ssh_key` grant for the same host.** SSH is a second push path the
  broker cannot see. Reason: `git_pat_narrowing_ssh_conflict`. This case is also refused at policy
  write, following `validateGrantLaneExclusivity` (`policy.go:595-673`). An `ssh_key` grant is
  accepted only for `github.com`/`ssh.github.com` and `dev.azure.com` (`sshOver443Endpoint`,
  `runs_scm.go:527`), so the reachable case is GitHub; tests use `github.com` and `ssh.github.com`.
- **A narrowed grant on a host whose own lane ignores the narrowing.** `handlePATBroker` hands any
  host the run's Azure DevOps gate covers to `serveADOGit` (`pat_broker.go:123-126`) before the
  D5 checks, and that lane is chosen at dispatch from site config (`resolveADOEntraRun`,
  `runs_dispatch.go:344`), not from the policy. A grant for a GitHub-brokered forge host is withheld
  (`dropBrokeredGrants`). Either way `repos`/`access`/`api` would be fiction. A narrowed grant whose
  host the run's Azure DevOps gate covers, that is an Azure DevOps host (`adoGrantHost`,
  `ado_shared_retire.go:100`), or that is a brokered-forge host (`brokeredForgeHost`,
  `runs_dispatch_gitbroker.go:297`) fails with `git_pat_narrowing_unsupported_host`.

Dispatch is the authoritative seam for the broker case, because the broker posture is
deployment-wide and can change after the policy was written. Preflight mirrors all three refusals
(`TestPreflightMirrorsLaunchGates`, `internal/api/preflight_launch_gate_parity_test.go:74`). The
reasons go in `internal/api/reasons.go` and `docs/sdk.md` (`TestReasonDocsMatchReasonsGo`).

### D8. The forge API door is a closed operation table (`gpat-g4`)

`api: true` opens a governed REST door to the grant's forge. It follows the Azure DevOps precedent:

- requests reach the forge on the MITM path, through a gate at the `serveMITMRequest` seam
  (`mitm.go:374`), with the MITM host wiring in `internal/egress/proxy/inject.go` and
  `internal/egress/egress.go` and a lazy mint (below);
- the gate authorises the request against a **closed operation table**, then injects the PAT. An
  unmatched request is refused before mint and before anything is sent upstream.

Each row of the table names:

- a method, judged on the effective method with `X-HTTP-Method-Override` applied;
- a path template;
- every **body field that names a target**, for example GitLab create-merge-request's
  `target_project_id`.

Every target the request names, in the path, the query string **or** the body, must be in `repos`.
The gate reads target-bearing fields from the query string and from JSON, form-urlencoded and
multipart bodies. It refuses (fail closed) a `Content-Encoding` other than identity, a content type
it does not parse, and a body over the peek cap, as `adoPeekBody` and `adoscope.Request.RawQuery`
do (`ado_gate.go:166-174,283-306`). `access: read` admits the read rows only.

The read rows are enumerated, not a prefix: merge/pull request list, get, changes and notes; issue
list, get and notes; branches; tags; commits; compare; pipeline and job status; repository tree,
files, raw and archive reads. Any other `GET` under the project path is refused. That keeps out
project metadata (GitLab returns `runners_token` to a maintainer), variables, hooks, deploy keys and
tokens, access tokens, secure files, members and export.

The door mints lazily, through `patToken` → `brokeredToken` (`pat_broker.go:253`,
`git_broker.go:300`), only after the table admits the request. It never registers the PAT as an
`InjectionConfig` entry, which would mint at proxy start (`inject.go:39-43`) and spend an
approval-gated single-use mint before any request is gated. It strips sandbox credentials first
(`stripSandboxCredentials`), sets the forge's header (GitLab `PRIVATE-TOKEN`, Gitea
`Authorization: token`) and registers the value with the mask registry as
`registerBasicAuthCredential` does. The MITM host is the grant's host exactly, never a derived host.

The plain forward lane (`servePlain`, `plain_lane.go:43-48`) skips every MITM gate, so it refuses
every request to a host with `api: true`, before evaluation or injection, as `refuseADOPlain` does.

| Admitted, with target checks | Refused |
|---|---|
| merge/pull-request creation | merge |
| comments on a merge/pull request or issue of a granted repository | auto-merge, including create or update requests that set it |
| the enumerated read rows under a granted repository's own path (above) | opaque content writes (repository files and commits APIs); these bypass the receive-pack content and branch checks, as `ado_content.go:38-60` explains for Azure DevOps |
| | GraphQL, search and any endpoint not under a granted repository |
| | numeric project ids in a path; a body target the gate cannot map to a granted path, such as a present `target_project_id`; a cross-repository head |
| | the `generic` forge entirely |

GitLab and Gitea ship. Bitbucket Server ships behind an opt-in deployment flag that is off by
default (Q-GPAT (a)). wardynd is the only reader of the flag. Policy and governance write refuse
`api: true` on `bitbucket_server` while it is off, and dispatch refuses a stored such grant with
`git_pat_api_forge_disabled` (mirrored in preflight), so turning the flag off after a write still
holds. The proxy gate reads no env; it enforces the forge carried on the `PATGrant`.

With `api: true`, the forge's API host joins the run's MITM hosts for that grant only. The
`THREAT-MODEL.md:3269` sentence is rewritten to describe the door.

*Rejected:* a per-repository path prefix check alone. A merge request's target lives in the body. A
merge, or an auto-merge set at creation, changes protected content without passing through
receive-pack.

*Rejected:* a plain-HTTP broker path like `/wardyn/git/`. Forge CLIs and libraries call the API host
directly, so a second route would leave the direct call ungoverned.

### D9. Honesty copy names what cannot be narrowed

The console (`gpat-g3`), `docs/POLICIES.md` and the threat model say plainly what narrowing does
**not** do:

- the PAT itself is exactly as broad as its issuer made it, everywhere outside Wardyn;
- on the API door, numeric ids, GraphQL, search and the generic forge's API cannot be narrowed, so
  they are refused rather than passed;
- with the broker off, nothing is narrowed, and such a run is refused.

## Data model

There is no migration. A `git_pat` scope is JSON inside a stored policy, a governance profile's
ceiling and a `credential_grants` row's spec. The new keys are additive, and their omission defaults
reproduce 0.8.5 behaviour.

The new `ProxyConfig` fields are:

- `brokered_pat_grant_ids` (`gpat-g0`);
- `repos`, `access`, `api` and `forge` on each `pat_grants` entry (`gpat-g2`).

## API and wire

- The policy, governance profile and run-create bodies accept the four scope keys. A write with an
  unknown `git_pat` scope key, an out-of-enum value, or `api: true` before `gpat-g4` answers `400`.
- A grant beyond its ceiling answers `422` at governance write, with the axis named. At create, Clamp
  narrows it with a warning, or drops it when the intersection is empty.
- New refusal reasons: `git_pat_narrowing_needs_broker`, `git_pat_narrowing_ssh_conflict`,
  `git_pat_narrowing_unsupported_host` and, from `gpat-g4`, `git_pat_api_forge_disabled`.
- New decision-log rule sources: `brokered:git-pat:repo`, `brokered:git-pat:read-only` and, from
  `gpat-g4`, the API door's allow and deny sources. The G0 refusal reuses `brokered:mint`.
- The UI wire types (`ui/src/app/lib/types/policy.ts`) keep `scope` free-form, so
  `wire-parity.test.ts` needs no new Go-mirrored type. The editor reads the four keys explicitly.

## Environment and chart

No new wardynd or proxy env var for `gpat-g0` to `gpat-g3`. `WARDYN_GIT_PAT_BROKER`
(`docs/ENV.md:225`) gains a sentence: a narrowed grant needs it on.

`gpat-g4` adds the Bitbucket Server opt-in flag if Q-GPAT (a) keeps it flagged. Its row goes in
`docs/ENV.md`, and the chart carries it through `extraEnv`, so no chart template changes. Only
wardynd reads it.

## Security model

**What becomes a boundary.**

- **With the broker on:** the sandbox can no longer mint any of its run's `git_pat` grants raw. A
  narrowed grant's git traffic reaches only its `repos`, and a read-only grant cannot push.
- **With `api: true`:** only the table's operations reach the forge API, against granted targets.

**What does not.**

- The PAT's own reach is unchanged outside Wardyn.
- An unnarrowed grant behaves exactly as in 0.8.5.
- Broker-off legacy grants mint raw, as documented. A narrowed one cannot be used with the broker
  off, because dispatch refuses the run.

**Residual risks.**

- **Direct egress to the forge.** A run whose policy also allows the forge host directly can reach
  it without the PAT, with whatever credential the sandbox has of its own. That is the standing
  "by name" caveat of the broker lanes (`docs/POLICIES.md:151-153`), not a new one.
- **Same-repository reach is coarse.** `repos` narrows which repositories, not which branches. Branch
  confinement remains `WARDYN_GIT_BROKER_ENFORCE_BRANCH_NS`'s `pat` scope, off by default for this
  lane (`docs/ENV.md:358`). Content remains `push_rules`.
- **Forge path tables can lag a forge.** A request form a table does not list is refused. A forge
  that later serves a new alias of an existing path is outside the table until someone adds it. The
  failure is a refusal, not a pass.
- **Cross-project merge requests** are refused under narrowing.
- **Upgrade window.** An older proxy image refuses the new config strictly
  (`config.go:245-248`, `DisallowUnknownFields`), so a run with the new fields fails at proxy start.
  That fails closed. Operators upgrade the proxy image together with wardynd, as for `owner_only`
  (`docs/POLICIES.md:676`).
- **Downgrade.** A 0.8.5 control plane ignores the new keys. A stored narrowed policy would run
  **unnarrowed**. The CHANGELOG says this.

## Upgrade and compatibility

- **Stored policies and profiles** are not rewritten. Without the new keys they keep 0.8.5 meaning.
  A stored scope that already carries one of the four key names (accepted and ignored before 0.8.6)
  starts being enforced on upgrade. The CHANGELOG names this, and a release-note line tells
  operators to search their policies for those keys first.
- **Strict write.** Re-saving a stored `git_pat` scope that carries any other unknown key now answers
  `400` until the key is removed.
- **Proxy and wardynd** upgrade together (above).
- **`forge` is a scope field, not a git-provider kind.** GitLab and Bitbucket as provider kinds
  remain a later minor (`docs/design/0.8/PLAN.md`, "What the repository already promised").

## Verification

Each lane's check runs `make lint && make staticcheck`, its scoped `go test -count=1 -p 4`, and
`go test -count=1 ./cmd/wardynd/`. UI lanes run scoped vitest and their own `scripts/run-ui-e2e.sh`
specs.

**gpat-g0:**

- A proxy test POSTs the mint route with each id in `brokered_pat_grant_ids` and gets `403` with a
  `brokered:mint` deny, and the control plane is never called. An id outside the set is relayed. An
  undecodable body is relayed.
- A dispatch test with the broker on puts every `GrantGitPAT` id into the set:
  - two grants on one host, in both orders;
  - a lane-vetoed grant;
  - a grant withheld for a brokered forge;
  - an Azure DevOps owner-only grant.
- With the broker off, the field is absent and the legacy mint still succeeds.
- A `ListGrantsByRun` failure with the broker on fails the dispatch.
- Revive that drops a denied host's lane keeps that grant's id in the set.
- Revive of a stored config without the field, with the broker on, carries every `GrantGitPAT` id;
  a list failure refuses the revive.

**gpat-g1:**

- Table tests of `PATScopeWithin` and `PATScopeMeet` over every axis, including omission on either
  side. These run against an independent oracle: a hand-written expected verdict per row, not the
  comparator itself.
- Each of the following is refused at governance write, narrowed or dropped by Clamp at create, and
  removed at resolve:
  - repository substitution;
  - `read → write`;
  - `api false → true`;
  - a field omitted against a narrowed ceiling;
  - a forge change against a ceiling that sets `repos` or `api`.
- A ceiling grant with no `repos` and no `forge` dominates `{forge: gitlab, repos: [team/app],
  access: read}`, and Clamp keeps it unchanged.
- Same-host multiple ceiling grants, in both orders: a proposal that needs two grants to dominate is
  refused.
- An empty `repos` intersection drops the grant and never yields an unnarrowed one.
- A write with an unknown scope key or `api: true` answers `400`. A stored row with an unknown key
  still loads. `LoadPolicySpec` with a stray key fails naming the key; synthesis from a stored grant
  with a stray key succeeds. A narrowed scope on an Azure DevOps host answers `400`.
- Two same-host grants where one is narrowed are refused at write and at create.
- Every caller listed in D3 compiles against the typed scope, and no `gitPATScopeFields` or broker
  `gitPATScope` remains.

**gpat-g2:**

- Per-forge path-table tests, each asserting the compared key **and** the forwarded upstream path:
  - `Team/App.git` vs `team/app.git`, and `team/foo` vs `team/foo.git`, are distinct on `generic`;
