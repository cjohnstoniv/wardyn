# Wardyn 0.8.6 — denials name the policy, its owner and how to request a change

A member refused by a governance profile today learns the profile's name and nothing else. The
attach refusal, for example, says "attaching is not allowed under the governance profile %q this run
was launched under" (`internal/api/governance_run_doors.go:79-80`). A sandbox refused at the egress
proxy learns even less: the body is "egress denied by policy" and the headers name the host and the
rule class (`internal/egress/proxy/policy.go:642-669`, `internal/egress/proxy/egress_headers.go:30-53`).
Neither says who owns the rule or how to ask for a change, so the refusal becomes a support ticket
routed by guesswork. An adopter running a central identity team and many governed groups asked for
both.

This epic gives every governance profile an optional **contact**: an owner, an email address, a
request link and a short request text. It gives the deployment a `policy_help` block for runs and
people that no profile binds. Every refusal caused by the governing ceiling then carries a structured
`policy` reference, and the sandbox's egress and broker refusals carry the same reference as headers
and one added sentence in the body. The console shows a "Request access" link beside the refusal.

The work is tracked on the `0.8.6` milestone under the epic "[Epic] 0.8.6: Denials name the policy and
how to request a change", as lanes `deny-f1` to `deny-f4`. All file:line references are to
`origin/main` at `e0efee625` (v0.8.5).

## Goals and scope

- A profile can carry `contact: {owner, email, request_url, request_text}`. The site config can carry
  `policy_help` with the same shape, for the no-profile case.
- Every refusal whose cause is the resolved ceiling carries `policy` in its JSON error body, through
  the one refusal emitter (`internal/api/refusal.go:39`).
- `GET /me` carries `governance_contact`: the contact of the profile that binds the caller.
- The egress proxy's policy refusals, the git and PAT broker refusals and the Azure DevOps gate's
  refusals add `X-Wardyn-Policy` and `X-Wardyn-Policy-Request` headers and one sentence in the body.
- The SDK's `APIError` and the CLI project the remedy, so a refused `wardyn run` prints where to ask.
- The console renders a "Request access" link beside a refusal (mock packet M10), and the profile
  editor gains the contact fields (mock packet M3).

**Not in scope.** No new refusal reason, no new audit action, no new environment variable, no change
to any frozen member sentence, and no change to who may be refused or why. The SSH gateway's
authentication refusal stays opaque (see residual risks). Approval routing to a profile's contact is
the NOTIFY epic's lane `notify-e3`, which reads this epic's data.

## What exists today

- **Refusals carry a name in prose only.** `denyUserGovernance` (`internal/api/runs_create_validate.go:512-565`),
  the autonomy doors (`internal/api/runs_autonomy.go:137-211`), the drive door
  (`internal/api/user_drives_run.go:252-262`) and the live-run doors
  (`internal/api/governance_run_doors.go:72-97`) all build a sentence containing the profile name and
  send it through `refuse`. Those sentences are frozen member copy: "the console never rewords a
  server refusal" (`internal/api/runs_create_validate.go:509-511`, `internal/api/user_drives_run.go:256-257`).
- **The wire envelope** is `errorBody{Error, Reason, Provider, Kind}` (`internal/api/http.go:204-213`).
  `Provider` and `Kind` already show the pattern this epic follows: a structured field beside the
  sentence, present only on the refusals it is about.
- **The decision type** is `authz.Decision` (`internal/authz/authz.go:81-104`). It is pure data; its
  audit projection `authz.Datum` (`internal/authz/authz.go:179-209`) copies an explicit allowlist of
  keys, so a new `Decision` field never reaches an audit row unless `Datum` is changed.
- **Hidden doors.** `WireReason` (set by `Decision.AsIf`, `internal/authz/authz.go:133-140`) makes a
  Hidden-effect refusal byte-identical to a genuinely missing resource. `refuse` swaps it in at
  `internal/api/refusal.go:49-52`.
- **A validated help precedent.** The site's sign-in help is validated on write and re-validated on
  the anonymous read, dropping a value that no longer passes (`internal/api/site_config_signin_help.go:36-66`,
  `internal/api/healthz.go:175-187`). `unsafeHelpRune` refuses C0/C1 controls and invisible formatting
  characters (`internal/api/site_config_signin_help.go:32-38`).
- **Profiles** are rows of `governance_profiles` (`internal/db/migrations/0052_governance_profiles.sql`),
  typed as `types.GovernanceProfile` (`internal/types/governance.go:283-291`), written by one upsert
  that keeps JSON keys this binary does not declare (`internal/store/governance.go:39-70`). Profile
  authoring is security-admin only (`internal/api/governance.go:53-61`, mounted at
  `internal/api/routes.go:582`). A member cannot read any profile.
- **The proxy config** is built once at dispatch (`internal/api/runs_dispatch.go:468`, marshalled by
  `internal/runner/sandbox.go:170-199`) and decoded strictly by the sidecar: an unknown key fails its
  startup (`internal/egress/proxy/config.go:229-251`).
- **The console** labels a rule source with `ruleSourceLabel` (`ui/src/app/components/wardyn/audit-decision.tsx:71`)
  and renders the chip on the run detail (`ui/src/app/components/screens/run-detail.tsx:869`). The
  console's error type carries `reason`, `org`, `provider` and `kind` (`ui/src/app/lib/api/core.ts:112-138`).

## Decisions

**D1. A structured `policy` field beside the sentence, never a longer sentence.** The refusal body
gains `policy`; `error` is byte-for-byte unchanged. *Rejected:* appending "contact X at Y" to the
sentence. It would break the frozen member copy and its pinning tests, and it would put
admin-authored text inside a string that clients treat as opaque.

**D2. The contact lives on the profile row.** One nullable JSONB column, `governance_profiles.contact`.
*Rejected:* a contact on each assignment. The same profile assigned to five groups would carry five
contacts that drift, and the person who owns the rule is a property of the rule. *Rejected:* a
separate contacts table keyed by profile. It adds a join to every read for four short strings.

**D3. One allowlisted, leaf-only DTO.** Every surface serves the same type, `policyref.Ref`:
`{source, name, owner, email, request_url, request_text}`. `source` is `profile` or `deployment`;
`name` is the leaf profile's name and is absent for `deployment`. It never carries a profile id, the
ceiling, limits, a base profile, assignment subjects or priorities. *Rejected:* serving the
`GovernanceProfile` row with fields blanked. A field added to the row later would leak by default.

**D4. Leaf identity and contact stay separate from effective content.** Under profile composition
(COMP epic), the effective ceiling is composed from bases, but `policy` names only the leaf profile
that binds the person or run. A contact is never inherited from a base. A leaf with no contact
falls back to the site's `policy_help`, because disclosing a base's contact would disclose the
base. This is the COMP design's rule; this epic is where it is enforced on the wire. *Rejected:*
inheriting a base's contact, which leaks the profile graph to members.

**D5. Hidden doors never carry it.** `refuse` copies `Decision.Policy` into the body **except when
`WireReason != ""`**. As a second guard, it never copies it on an `EffectHidden` decision. A hidden
door must stay byte-identical to a missing resource, and a `policy` block would reveal that the
resource exists. *Rejected:* letting each door decide. One rule in the one emitter cannot be
forgotten by a door written later.

**D6. Validated on write, re-validated on read.** The write refuses a bad value with a 400. Every
read projection (refusal, `/me`, run detail, proxy config) runs the same validator and drops, field
by field, any value that no longer passes. A value can fail on read if an older binary wrote it, if
it was written directly to the database, or if a rule tightened. This is the sign-in help pattern
(`internal/api/healthz.go:175-187`). *Rejected:* trusting the stored value. The header fields are
written into an HTTP response a sandbox reads.

**D7. One small package holds the type and the validator.** New package `internal/policyref`,
depending only on the standard library and `internal/hostrules`. It holds `Contact`, `Ref`,
`Validate`, `Project` (the read-side re-validation), `HeaderValues` and `Ref.RequestRoute()`, the one
place the request route is chosen. `unsafeHelpRune` moves
there as `UnsafeRune`, and `internal/api/site_config_signin_help.go` calls it unchanged. `authz`,
`types`, `internal/api`, the proxy and the SDK all import it. *Rejected:* a validator in
`internal/api` plus a copy in the proxy. Two copies of a header-safety rule drift, and the proxy is
the side that writes the header.

**D8. The proxy learns the attribution at dispatch.** `proxy.Config.Attribution` (a `policyref.Ref`)
is filled at dispatch from `run.GovernanceProfileID` (`internal/types/types.go:143`). It is the
run's leaf profile, or the site's `policy_help` when the run has none. It is frozen for the run's
lifetime. *Rejected:* the proxy asking wardynd per refusal. That adds a control-plane round trip to
a refusal path that must stay fast, and fails open or closed on an outage for a field that is only
advice.

**D9. Only refusals the policy decided are attributed.** At the proxy that means `policy:denied`,
`policy:default-deny`, `policy:method`, `approval:denied`, and the broker refusals (git broker
"repository not granted", PAT broker "host not granted", the branch-namespace and push-rule
refusals, and the Azure DevOps gate's refusals). `builtin:private-ip`, `builtin:resolve-failed`,
`builtin:dial-failed` and `policy:evaluator-error` are faults, not policy, and stay as they are
(`internal/egress/proxy/policy.go:657-667`). `approval:denied` is decided inside `evaluate`
(`internal/egress/proxy/proxy.go:692`) and so reaches the same `writeEgressDeny` callers as the
`policy:*` reasons (`internal/egress/proxy/proxy.go:801`, `plain_lane.go:67`, `mitm.go:362`).
*Rejected:* attributing every 403. Sending someone to
the policy owner for a DNS failure costs that owner a ticket that is not theirs.

**D10. The header value is ASCII.** Profile names allow any printable Unicode
(`internal/api/governance.go:142`, `internal/api/permissions.go:145`). `X-Wardyn-Policy` therefore
carries `profile; name="<percent-encoded name>"` or `deployment`. `X-Wardyn-Policy-Request` carries
`Ref.RequestRoute()`: `request_url`, else `mailto:<email>` only after it re-passes the `request_url`
mailto rule, else nothing. The header, the CLI and the egress body never build the fallback ad hoc. Both are restricted at write to printable ASCII
with no spaces. *Rejected:* raw UTF-8 in a header, which several HTTP clients mangle or refuse.

**D11. The contact never enters an `authz.denied` row.** `authz.Datum` is unchanged, so owner and
email (personal data) stay out of the hash-chained audit log, and the AR epic's erasure has nothing
to find there. The profile-write row (`governance.profile.write`, `internal/api/governance.go:229-235`)
records `contact_fields` (which of the four fields are set) and the `request_url` itself. The URL is
where members are sent, so a reviewer must be able to see when it changed. *Rejected:* recording the
whole contact, which writes a person's name and email into an append-only chain.

**D12. `/me` never fails because of the contact.** `governance_contact` is computed with
`effectiveCeiling` (`internal/api/governance.go:768`). A resolver error, a stale group snapshot or an
operator caller gives `null`, and `/me` answers as it does today. *Rejected:* a 500 on `/me`, which
is the console's most-polled route (`internal/api/me.go:100-104` explains why it avoids extra store
reads).

**D13. The run detail carries the run's own policy.** `GET /runs/{id}` gains `policy`, projected
after `getRunAuthorized` (`internal/api/runs_policy.go:212`, `internal/api/helpers.go:500`). A caller
who may not read the run gets the same 404 a missing run gets, before any profile is looked up.
That is hidden-404 parity by construction. The console needs this projection to put a "Request
access" link beside the run's egress refusals. *Rejected:* using `/me` for that link. `/me` names the
viewer's current profile, which is wrong for a run launched under a profile since reassigned, and
wrong when an admin views someone else's run.

## Data model and migration

### `policyref.Contact`

| Field | Type | Rule |
|---|---|---|
| `owner` | string | ≤ 200 characters (runes); no `UnsafeRune`; free text, e.g. a team name |
| `email` | string | ≤ 254 bytes; exactly one bare address (`net/mail.ParseAddress` must return the input unchanged, so no display name and no list); local part restricted to `[A-Za-z0-9._%+-]+` and domain to `hostrules.ValidApprovedHost`, so that `"mailto:" + email` passes the same mailto rule as `request_url` (no `?`, `#`, `&`, `,`, `;`, `/`, quotes, spaces). `ParseAddress` alone accepts `x?cc=evil@example.com` unchanged |
| `request_url` | string | ≤ 2048 bytes; printable ASCII, no spaces; scheme `https` or `mailto` only. `https`: no userinfo, and the host passes `hostrules.ValidApprovedHost` (as `internal/api/site_config_signin_help.go:65` does). `mailto`: exactly one address and no query or fragment, so `cc=` and `body=` can't be smuggled in |
| `request_text` | string | ≤ 1000 characters (runes), the sign-in help cap (`internal/api/site_config_signin_help.go:19`); no `UnsafeRune` |

All four are optional. A contact with every field empty is stored as NULL. The caps are this
design's choice; the sign-in help values are the precedent.

### Migration (next free number)

One migration, numbered origin/main's max + 1 when the lane is cut (`0107_` today) and renumbered by
the steward at merge (`scripts/check-migration-numbers.sh`, `TestMigrationPrefixesNoGapsOrDupes`):

```sql
ALTER TABLE governance_profiles ADD COLUMN contact JSONB NULL
  CHECK (contact IS NULL OR (jsonb_typeof(contact) = 'object' AND octet_length(contact::text) <= 8192));
```

The CHECK is a backstop for direct writes. The closed field set lives in the Go type, as `limits`
does (`internal/db/migrations/0052_governance_profiles.sql:31-37`). Because it ALTERs an older table,
it needs ownership, so the lane adds its row to `docs/OPERATIONS.md`'s migrator rationale
(`scripts/test-claims-match-code.sh` C8c). Adding a nullable column with a CHECK that is trivially
true for NULL scans nothing on PostgreSQL 13+, so the upgrade cost is a brief lock.

### Absent, null and empty on `POST`/`PUT /governance/profiles`

| Field | Absent on PUT | `null` | `{}` or all-empty |
|---|---|---|---|
| `contact` | keep the stored value | clear | stored as NULL |

On `POST`, absent means NULL. This matches the COMP design's table for its own fields, so an older
client that does not send `contact` can't wipe it. The upsert gains a presence flag, so its SET
clause keeps `governance_profiles.contact` when the request omitted the key
(`internal/store/governance.go:51-58` is the statement that changes). The request type
(`internal/api/governance.go:106-110`) decodes `contact` as `json.RawMessage` to tell absent from
`null`.

### Site config `policy_help`

`types.SiteConfig` gains `PolicyHelp *policyref.Contact` (`json:"policy_help,omitempty"`), beside
`SignInHelpText` (`internal/types/site_config.go:95`). It is validated by `policyref.Validate` at
`PUT /site-config` and keeps its stored value when absent from the document, as the sign-in help pair
does (`internal/api/site_config.go:634-638`). Unlike sign-in help, it is **not public**. `/healthz`
does not publish it. It reaches a signed-in member only through `policy` and `governance_contact`.
The site-config write audit row records `policy_help_fields` and `policy_help_request_url`, the
same D11 rule. It is set through the site-config document (API, CLI or MDM); a console field for it is
not in this epic.

## Wire

### API refusals

- `policyref.Ref` (D3), on the wire as:

  ```json
  {"error": "attaching is not allowed under the governance profile \"Team A\" …",
   "reason": "governance_profile",
   "policy": {"source": "profile", "name": "Team A", "owner": "Platform security",
              "email": "platform-security@example.com",
              "request_url": "https://help.example.com/access",
              "request_text": "Ask in the access-requests queue; include the run id."}}
  ```

- `authz.Decision` gains `Policy *policyref.Ref` (`json:"policy,omitempty"`), beside `WireReason`
  (`internal/authz/authz.go:100`). `Decision.WithPolicy(ref)` sets it. `Datum` does not read it (D11).
- `errorBody` gains `Policy *policyref.Ref` (`json:"policy,omitempty"`) (`internal/api/http.go:204-213`).
- `refuse` (`internal/api/refusal.go:39-56`) passes `d.Policy` to the writer unless
  `d.WireReason != ""` or the reason's effect is `EffectHidden` (D5).
- `governanceCeiling` (`internal/api/governance.go:629-639`) gains `policyRef()`. For a ceiling
  with a `Profile`, it returns the leaf profile's projected ref. For a member bound by the
  deployment, it returns a `deployment` ref whose contact is read from the site config
  (`siteConfigSnapshot`, `internal/api/setup.go:523`) only when a refusal is written, so resolving a
  ceiling costs no extra read. For an operator it returns nil: nothing binds them.
- For the live-run doors, which read the run's profile rather than the caller's ceiling
  (`internal/api/governance_run_doors.go:36-50`), `runPolicyRef(run)` projects the run's leaf. Under
  COMP it reads the leaf identity from `resolveProfileByID`'s result, never a base.

### The ceiling-door census

Lane `deny-f2` attaches `policy` at every refusal whose cause is the resolved ceiling. The known
sites:

| Door | Site |
|---|---|
| create: `runs.task_mode`, `runs.interactive_start`, `runs.interactive`, `runs.seed_auto_tools`, `runs.agent` | `internal/api/runs_create_validate.go:519-562` |
| create: run quota (`run_quota`, 422) | `internal/api/runs_create_validate.go:601` |
| autonomy ladder, same five targets | `internal/api/runs_autonomy.go:137-211` |
| user drive (`runs.drive`) | `internal/api/user_drives_run.go:252-262` |
| live attach (`runs.attach`) and UI gateway (`runs.ui_apps`) | `internal/api/governance_run_doors.go:72-97` |
| Record Mode and step-run ceiling limits (`errRecordCeilingLimit`) | raised at `internal/api/workspace_run_launch.go:376,385` (in `stepRunCeilingLimits`, `:364-387`); written at `internal/api/record.go:428-429` (Record Mode launch) and `internal/api/provider_signin.go:237-238` (provider sign-in launch) |

The `errRecordCeilingLimit` door does not go through `refuse` or `authz.Decision`: both writers call
`writeErrorReason` (`internal/api/http.go:234`) with `reasonRecordCeilingLimit`
(`internal/api/reasons_routes.go:433`), so `Decision.WithPolicy` cannot reach it. Its mechanism:

- The two raise sites wrap the ceiling's `policyRef()` into the error, as a `recordCeilingError{err,
  ref}` whose `Unwrap` returns the existing `fmt.Errorf("%w: …", errRecordCeilingLimit, …)` value.
  `errors.Is(err, errRecordCeilingLimit)` keeps matching, and `Error()` stays byte-identical.
- Both writers take the ref with `errors.As` and call a new
  `writeErrorReasonPolicy(w, status, reason, sentence, ref)`, which fills `errorBody.Policy`. Status,
  reason and sentence are unchanged.

A source-scan guard test in `internal/api`, in the style of `reason_coverage_guard_test.go`, fails
when a `governance_profile` or `run_quota` refusal reaches the writer without `WithPolicy`, and when
`reasonRecordCeilingLimit` reaches `writeErrorReason` rather than `writeErrorReasonPolicy`. It closes
the list for doors written later. Drops (`recordRefusal` with `authz.Drop`,
`internal/api/governance_run_doors.go:113`) have no response, so nothing is attached.

### `GET /me`

`governance_contact` is added to the body built at `internal/api/me.go:46`. It holds the caller's
`policyRef()` or `null` (D12). An operator gets `null`. A security admin, who is bound like anyone
(`internal/api/routes.go:574-577`), gets their own profile's contact. An admin in the user view gets
the contact the view resolves to. The deployment arm on `/me` returns `{source: "deployment"}` without
reading site config, so a member bound by the deployment adds no store read to `/me`; the
deployment's contact reaches members through refusals and `GET /runs/{id}`.

### `GET /runs/{id}`

`policy` is added to the projection struct at `internal/api/runs_policy.go:236-249`. It holds
`runPolicyRef(run)`: the leaf profile's ref, the deployment's `policy_help` when the run has no
profile or its profile was deleted, or omitted when neither has anything to say. A store failure
omits it and logs, as `ui_apps` does at `internal/api/runs_policy.go:222-233`.

### SDK and CLI

- `client.APIError` (`pkg/client/apierror.go:14-25`) gains `Policy *policyref.Ref`, parsed once in
  `NewAPIError` (`pkg/client/apierror.go:33-41`), so the SDK transport and the CLI's raw calls both
  get it.
- The CLI prints one more line after the error, beside `dialHint` (`cmd/wardyn/main.go:36-40`), when
  the error carries a policy: `wardyn: governed by the profile "Team A" — to request a change:
  https://help.example.com/access`. Precedence for the route is the same as the header: URL, then
  `mailto:`, then the request text. Exit codes (`cmd/wardyn/main.go:94-115`) do not change.

## Environment and chart

No new environment variable and no chart value. `policy_help` is site configuration, not
deployment configuration, because the people who own access policy are rarely the people who own
the Helm release.

Move the proxy image pin in the same step as wardynd. From 0.8.6, wardynd writes `attribution` for
every run launched under a governance profile (contact or not) and for every run when `policy_help`
is set; a 0.8.5 sidecar refuses that key at startup (`internal/egress/proxy/config.go:229-251`) and
the run fails to launch. The proxy image must therefore be the 0.8.6 image before wardynd is upgraded
on any deployment that assigns a governance profile. This is the same constraint every proxy-config
key added since that rule carries. The upgrade notes say it, and operators who pin
`WARDYN_PROXY_IMAGE` or `k8s.proxyImage` by digest move the pin with wardynd, unconditionally.

## Security model and residual risks

**What a member can learn.** The leaf profile that binds them or their run: its name (already in
today's refusal sentences) and its contact. Not another profile, not a base, not the ceiling, not an
assignment, its subject or its priority. A member who can't read a run gets the missing-run 404
before any lookup. Hidden doors carry nothing (D5). The `authz_test.go` `chi.Walk` matrix is extended
so that a member under profile A, calling every door that can refuse them, never receives profile B's
name or contact.

**What a sandbox can learn.** Its run's profile name and request route (Q-DENY). That is
information the run's owner already has, delivered to the process acting for them. Anything the
sandbox can read, it can send to any host its policy allows. So the contact should contain nothing
the run's owner may not share, and the editor's helper text says so (M3).

**Admin-authored text reaching people and sandboxes.** The request link is where members are sent,
which makes it a phishing lever for whoever can edit a profile. Mitigations: it is restricted to
`https:` and single-address `mailto:`; its value is in the profile-write audit row (D11); and under
the GOV4 epic's four-eyes switch, which exempts only "metadata, or changes proven narrowing by their resolved
effect", this design proposes that a contact edit counts as neither, so it needs a second person
(Q-DENY c). Request text is shown to a sandbox; a profile
author is already trusted with that run's ceiling.

**Header and body injection.** Header-bound fields are printable ASCII without spaces at write, the
name is percent-encoded, and both the API read and the proxy load re-validate (D6, D7). Body text
refuses controls and invisible formatting characters (`UnsafeRune`).

**Residual risks, accepted:**

- **The `policy_help` request link is a `/site-config` write.** GOV4 leaves `/site-config`
  single-human in 0.8.6, so this route is gated only by the super-admin tier and by the
  `policy_help_request_url` audit field; it is not under four-eyes (Q-DENY c asks whether this
  acceptance stands).
- **The attribution is frozen at dispatch.** A contact edited mid-run reaches the console and the API
  at once, but reaches the sandbox only on a new run. A revive reads the old sidecar's config back
  (`docs/AUDIT-ACTIONS.md:128`), so it keeps the old attribution too.
- **It names the governing profile, not the layer that refused.** A host may be refused because the
  run's own selected policy omitted it, even though the profile would allow it. The sentence says
  "governed by", never "the profile forbids", and does not claim more.
- **The SSH gateway stays opaque.** A `deny_interactive` refusal at SSH authentication
  (`internal/api/sshgateway.go:308-316`) is an authentication failure with no channel for a remedy,
  and naming a profile before authentication completes would disclose it. The console attach and the
  CLI attach carry the remedy.
- **Profile names written before 0.8.6** may contain invisible formatting characters, because the name
  rule is `controlCharFree` only (`internal/api/permissions.go:145`). They already appear in today's
  sentences. The header percent-encodes them; the body shows them as stored.
- **Stale `/me`.** `governance_contact` is as fresh as the console's last `/me` read.

## Upgrade and compatibility

- **Additive on the wire.** `policy`, `governance_contact`, the run's `policy` and the two headers
  are new and omitted when empty. Clients that ignore unknown fields (the SDK, the console, `curl`)
  see no change. The `authz/v1` decision schema is additive by its own rule (`internal/authz/authz.go:17-18`).
- **Off by default.** With no contact on any profile and no `policy_help`, the only visible change is
  `policy: {source: "profile", name: …}` on refusals that already named the profile in prose, plus the
  `X-Wardyn-Policy` header on attributed egress refusals. Every governed run's proxy config still
  carries `attribution`, so the proxy image moves first (Environment and chart).
- **Older clients writing profiles.** An older SDK or console omits `contact` and so keeps it (the
  absent rule above).
- **Proxy image.** It moves with wardynd (Environment and chart).
- **Downgrade.** A 0.8.5 wardynd reading a 0.8.6 database ignores the extra column, because the
  store's SELECT names its columns.

## Interactions with other 0.8.6 epics

- **COMP.** `comp-d3` is blocked by `deny-f1`. Its resolver returns the leaf's contact beside the
  effective content, and its absent/null/empty table includes `contact` with the same rules as here.
- **NOTIFY.** `notify-e3`'s `profile_contact` target reads `contact.email` through `policyref.Project`,
  so it re-validates on read the same way. It is blocked by `deny-f1`.
- **GOV4.** A contact edit is a profile write, and it is queued under four-eyes (Q-DENY c). gov4-b1
  queues any PUT whose stored `contact` changes, even when the `Leq` proof holds.
- **AR.** No contact reaches an `authz.denied` row (D11). The profile-write row's `request_url` is not
  personal data. `owner` and `email` live only in the profile row, which an erasure does not
  rewrite: they describe a role, not a subject.
