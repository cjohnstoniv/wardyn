# Wardyn 0.8.6 — auto-preflight and Launch gating

The New Run screen has a preflight: a dry run of the exact request Launch would send, which
answers with the real launch refusals, the enforced confinement class, the risk grade and a setup
checklist. Today a person has to press a button to get it. Once they have it, nothing on the
screen acts on it. Launch stays enabled over a refusal the server has just given for the same
body. The checklist row that says this host cannot enforce the chosen barrier is fetched and
thrown away. A person whose agent run has no model to reach can launch a sandbox whose first
model call fails. An adopter whose first runs on a shared cluster failed in exactly these ways
asked for a first run that succeeds or explains itself before it starts.

This record designs that for 0.8.6. Preflight runs on its own as the body settles. Launch is
blocked on a fresh refusal for the current body. A sign-in that a preflight asked for re-checks
and never launches. The server gains the two things an automatic caller needs: a per-person rate
limit, and audit rows that tell a dry run apart from a launch and do not grow by one row per
keystroke. It is the PF epic (lanes `pf-pf1` to `pf-pf4`). It also carries three first-run lanes
that the automatic preflight depends on: `f-f3`, `f-f4` and `f-f5`.

Every file:line reference is to `origin/main` at `e0efee625` (the v0.8.5 tree).

## What exists today

- **One body, two calls.** `use-launch.ts` builds the request once (`buildRunInput`,
  `ui/src/app/components/screens/new-run/use-launch.ts:105-126`) and sends it to both
  `POST /runs` and `POST /runs/preflight`. A verdict is shown only while it was graded from the
  body Launch would send now: `preflightIsCurrent` compares the serialised body
  (`use-launch.ts:165-175`). That rule is enforced by construction, not by remembering to clear
  state. The e2e `ui/e2e/new-run.spec.ts:260-281` pins byte-identical bodies.
- **Preflight is manual.** The only trigger is the "Preflight" button on the Policy panel
  (`ui/src/app/components/wardyn/policy-panel.tsx:531-546`), wired at
  `ui/src/app/components/screens/new-run/new-run-screen.tsx:649-651`. `preflight()` sets no
  credential-refusal state; any error becomes the rail's alert (`use-launch.ts:177-201`,
  `new-run-rail.tsx:609-620`).
- **Launch ignores the verdict.** Launch is disabled only by the panel's local `problem` chain,
  `workspaceUnavailable` and `noBarrier` (`new-run-launch-panel.tsx:196-235`,
  `new-run-rail.tsx:553`). A preflight 4xx for the current body leaves Launch enabled.
- **The sign-in door relaunches.** When Launch gets the 422 `model_credential`, the rail opens
  that provider's door with `onSignedIn: () => onLaunchRef.current()`
  (`new-run-rail.tsx:304-322`). The click is consumed on first evaluation, and `autoOpened` is
  reset only by the Launch button's own click (`new-run-rail.tsx:555`). The door's `close()`
  clears `onSignedIn`, so a cancelled door never fires it
  (`ui/src/app/components/wardyn/model-access-context.tsx:232-239`). The rail's own rule, stated
  at `new-run-rail.tsx:288-303`, is that Launch is the server's decision and nothing is
  pre-checked on cached status that can be five minutes stale.
- **`setup_items` has no console consumer.** The server derives a `backend` row that says whether
  the runner advertises the enforced class (`internal/api/compose_setup.go:490-545`). Preflight
  deliberately reports this instead of repeating launch's hard 422
  (`internal/api/preflight.go:96-99,246-251`; launch's 422 is at `internal/api/runs_create.go:368-373`).
  The UI type says outright that nothing reads it (`ui/src/app/lib/types/runs.ts:744-751`). The
  field is consumed elsewhere: the CLI's `--dry-run` table (`cmd/wardyn/commands.go:247-250`), the
  SDK (`pkg/client/runs_create.go:235`), `docs/CI.md:596-599` and `scripts/ci-run.sh:310-313`.
- **The model warning is advisory.** The rail warns when an agent run has no model path:
  `showModelWarning={isAgent && llmReady === false}` (`new-run-screen.tsx:771`, `llmReady` from
  `/setup/status` at `:227`). That is true for interactive agent sessions too. The server's own
  rule exempts interactive, exec and sign-in bodies (`runNeedsModelWarning`,
  `internal/api/runs.go:712-725`), and its launch-time check only warns (`runs.go:557-566`).
- **Preflight writes a row per refused call.** Every gate preflight reproduces is the real gate,
  so a refused dry run writes the gate's `authz.denied` row through the one emitter
  (`internal/api/refusal.go:39-96`). The handler's own comment admits the cost: a member editing
  against a closed door can write a row per keystroke, and "the run_id NULL is what tells those
  apart" (`internal/api/preflight.go:80-94`; the same text in `docs/OPERATIONS.md:2808-2823`). That
  last claim is wrong: launch refusals before a run row exists also carry `run_id` NULL, so the
  NULL distinguishes nothing.
- **No limit on preflight.** `POST /runs/preflight` is open to every authenticated person
  (`internal/api/routes.go:197`) with no rate limit. A per-key token bucket already exists,
  `principalLimiter` (`internal/api/directory_search.go:177-250`), used by directory search (its
  zero value in `directory_search.go`) and by the two device limiters, enrolment and ingest
  failures (`internal/api/server.go:815-816`). Its 429 reasons live in
  `internal/api/reasons_routes.go:664` and are documented in `docs/sdk.md:409`.
- **Preflight does not spend credentials.** Provider liveness runs with `refresh=false`
  (`internal/api/run_model_provider.go:306`); the Bedrock arm treats an expired but renewable
  session as live on a dry run and never spends the one-use refresh token
  (`internal/api/provider_bedrock.go:84-93`). The host-capacity check runs with audit off and
  answers 503 `host_capacity_refused` (`preflight.go:313-318`, `internal/api/writeservererror.go:75-85`).
  `adoStandingAtDoor` is pure in-memory logic over the spec, site config and ceiling
  (`internal/api/runs_ado_standing.go:30-56`).
- **The structural parity guard.** `TestPreflightMirrorsLaunchGates`
  (`internal/api/preflight_launch_gate_parity_test.go:74`) requires every gate launch calls before
  minting a run identity to be called by preflight too, unless it is a listed exception. It does
  not check the reverse direction.

## Goals and scope

- A person learns about a launch refusal before pressing Launch, without pressing anything else.
- Launch cannot be pressed over a refusal the server gave for this exact body less than a minute
  ago, unless that refusal is one a sign-in or a retry repairs.
- A sign-in that a preflight asked for never launches a run nobody clicked.
- A host that cannot enforce the chosen barrier blocks Launch with the server's own row.
- An unattended agent run with no model to reach cannot be launched; an interactive session stays
  advisory.
- An automatic caller cannot flood the server or the audit log.
- Unchanged: Launch remains the server's decision. Every refusal the client acts on is still
  enforced by `POST /runs`. The `setup_items` wire field stays (the owner rejected deleting it in
  #172). No migration.

Not in scope: new preflight gates (P7's capacity check is its own lane in the P epic, and it
rides this design's blocking rule unchanged); the refusal sentences themselves (DENY).

## Decisions

**Preflight runs on its own, debounced on the body.** `use-launch.ts` re-checks 800ms after the
body last changed, aborting any check still in flight. It also re-checks when the window regains
focus and after the sign-in door closes. It fires only when Launch would otherwise be pressable: a
body exists, the panel's local `problem` is empty, and neither `workspaceUnavailable` nor
`noBarrier` is set. This sends no request for a form that is still obviously incomplete. The
manual button stays, relabelled "Check again". Rejected: a fixed polling interval, which sends
requests for a body nobody is editing and still lags an edit; and preflight on Launch click only,
which is what launch already does.

**Launch is blocked on a fresh refusal.** One predicate, `preflightBlock`:

> the verdict was graded from the current body ∧ it is less than 60s old ∧ the answer was a 4xx ∧
> its reason is not `model_credential` or `preflight_rate_limited`.

- `model_credential` is excluded because the sign-in door repairs it (F3), and the door opens on
  its own.
- `preflight_rate_limited` is excluded because it says nothing about the body.
- Host capacity is excluded because it is transient. No `host_capacity` reason exists on the
  wire: it is a 503 whose `error` is `host_capacity_refused` and whose `reason` is the refusal's
  own (`writeservererror.go:83`). The exclusion is therefore keyed on status: host capacity is a
  503 and never blocks (5xx clause).
- 5xx and network failures never block.

The 60s bound keeps the rail's no-stale-status rule (`new-run-rail.tsx:288-303`): a verdict is a
statement about one body at one moment, and an old one is re-checked, not trusted. PF3 also folds
F4's missing-backend arm and F5's missing-`llm_access` arm into the same predicate, so they too
stop blocking at 60s.

Rejected: blocking on any preflight error, which would let a rate limit or an outage disable
Launch; and an unbounded freshness window, which turns a refusal an admin has since lifted into a
lock that only a reload clears.

**A preflight-origin sign-in re-checks, never launches** (review finding 28). Today the rail's
door always relaunches on sign-in. Making preflight automatic would reuse that path and launch a
run nobody clicked. A focused test confirmed this against the baseline rail. F3 separates the two
intents:
- A preflight 422 `model_credential` (background or manual) opens that provider's door with
  `onSignedIn` = re-run preflight on the current body. It never launches. It opens at most once
  per body and provider, and never over a door someone else opened (the existing
  `door.open` rule, `new-run-rail.tsx:311`).
- Only an explicit Launch click arms launch-after-sign-in. The armed intent lives inside the
  `onSignedIn` closure passed at open time and captures the body Launch was clicked for. When it
  fires, it launches only if that body still equals the current body (read through a ref) and it
  has not fired before. Otherwise it re-runs preflight. `onClosed` is not used to disarm: it also
  fires on a successful sign-in, before `onSignedIn` runs (`model-access-context.tsx:232-247`). A
  cancelled door already cannot fire, because `close()` clears `onSignedIn`.
- An armed intent that is still valid launches exactly once. The existing behaviour of a relaunch
  that completes after the person left the page (#146, `new-run-rail.tsx:301-303`) stays for a
  click-armed intent.

Rejected: suppressing the door for background checks and showing only the inline line. That
leaves the person to find the sign-in themselves, which is the trip the door exists to save.

**Preflight's `setup_items` render, and a missing `backend` row blocks Launch** (F4). This is the
only row whose launch counterpart is a hard 422 (`runs_create.go:368-373`). It becomes a new
`problem` arm in `new-run-launch-panel.tsx`:
`preflightIsCurrent && preflightResult.setup_items.some(i => i.kind === "backend" && i.status === "missing")`.
The rail renders the server's row: its label and detail, the same strings the CLI prints. Other
`missing` rows render as advisory lines and never block. `llm_access` in particular is warn-only
at launch and exempt for interactive runs (`runs.go:561-562,719-725`); gating on no model access
is F5's job. An `unverified` backend row (the capability probe failed,
`compose_setup.go:520-524`) does not block. Rejected: deleting `setup_items`, which four consumers
outside the console read; and blocking on every `missing` row, which would refuse interactive
sessions that the server admits.

**No model reachable gates Launch for bodies that need one** (F5; review finding 29). The gate
mirrors `runNeedsModelWarning` (`runs.go:719-725`): the body is an agent run that is not
interactive. Exec bodies are the Shell run type (`isAgent` false), and the sign-in body is
server-set and never authored here. "Not reachable" means `preflightIsCurrent` and preflight's
`setup_items` has a `llm_access` row with status `missing`. That row is the server's own
`runLLMAccess` (`preflight.go:351-362`, `compose_setup.go:96-125`), the same verdict as the
launch-time warning. The arm applies only when `isAgent && !isInteractive`. `llmReady` is not used:
it is global and read once at mount, so it misses a per-agent gap and would lock Launch until a reload.
It is a new `problem` arm, not a reuse of `showModelWarning`, which is true for interactive
sessions as well (`new-run-screen.tsx:771`). An interactive body with no model keeps today's
advice and stays launchable, so "start with a shell" still works. Rejected: gating on
`showModelWarning` directly, which blocks exactly the case F4 says remains allowed.

**A per-person rate limit on preflight** (PF1). `POST /runs/preflight` gets its own
`principalLimiter` (`directory_search.go:177-250`): 20 per minute with a burst of 5, keyed by
`principalFromRequest`, for `ActorHuman` callers only: every admin-bearer caller shares the
constant `admin-token` principal, so limiting it would pool all CI jobs into one bucket. It is checked first in `handlePreflightRun`, before decoding and before
any gate, so a limited call does no work and writes no audit row. The refusal is 429 with the
wire reason `preflight_rate_limited`. It is not an `authz.denied` reason: like `run_quota` and
`event_stream_cap`, it is a caller who is authorised and hit a limit, so it goes in
`internal/api/reasons_routes.go` and `docs/sdk.md`'s reason table (`TestReasonDocsMatchReasonsGo`),
not in `internal/authz/registry.go`. The bucket map is capped for a deployment's people rather
than its admins, with the limiter's existing evict-one rule. `WARDYN_PREFLIGHT_RATE_PER_MIN` sets
the rate; `0` turns the limit off. `POST /runs` is not limited by this. Rejected: a global limit,
where one person's editor starves everyone's; and limiting in the client only, which the CLI and
SDK bypass.

At 800ms debounce, sustained typing produces at most one request per pause, well inside 20 per
minute. The client treats a 429 as "not checked": it shows no error alert, does not block Launch,
and does not retry on its own. The next edit, focus or "Check again" retries.

**Dry-run rows are marked, and repeats are summarised by appending** (PF2). Every audit row
written while serving `POST /runs/preflight` carries `dry_run: true`. The handler marks its
request context before any gate runs, and the mark is stamped in one place for every writer, the
way `audit.DelegationRecorder` stamps `via` (`internal/audit/delegation.go:38-66`, wired at
`cmd/wardynd/boot_deps.go:151,200`). `dry_run` joins `authz`'s `reservedDatumKeys`
(`internal/authz/authz.go:173`), so no door's detail can forge or clear it. Launch rows never
carry it.

A coalescer in the same recorder chain handles only marked rows. The first row for a key (actor,
action, target, reason, outcome) is passed through in full, as it is today. Further identical rows
within 10 minutes are counted and not written. When the window closes, one summary row is
**appended**: action `preflight.denial.coalesce`, `outcome` `denied`, the same actor and target,
and fixed-shape data `{dry_run: true, reason, count, suppressed, first_at, last_at}`. `count`
includes the first row, so three identical refused dry runs give one full row plus a summary with
`count=3`. A window with no repeats writes no summary. No chained row is ever updated or deleted.
The coalescer's map is bounded; when full, it closes its oldest window early and writes that
summary, never dropping a count. A graceful shutdown flushes every open window.

Rejected:
- Updating the first row's count in place, which breaks the append-only chain.
- Emitting the summary as `authz.denied` with a count, which breaks "one row, one refusal" for
  every SIEM rule counting that action.
- Suppressing dry-run denials entirely, which drops the record that this person was refused this
  capability. That record is the reason preflight audits at all (`preflight.go:87-91`).
- Using `run_id` NULL as the marker, which launch refusals share.

The new action needs the verb `coalesce` in `docs/AUDIT-ACTIONS.md`'s closed verb list
(`TestAuditActionsDoc_Grammar`, `cmd/wardynd/audit_actions_doc_guard_test.go:626`) and a row in
the action table.

**`adoStandingAtDoor` gets a no-outbound regression assertion.** It is pure in-memory today
(`runs_ado_standing.go:30-56`), so there is nothing to audit. The risk is a later change that adds
a network call to a function an automatic preflight now calls on every pause in typing. PF2 adds
a test that runs a preflight through it with every outbound client replaced by one that fails the
test on use. Rejected: auditing its outbound calls, since it makes none.

## Data model and migrations

None. The dry-run marker is a key in the existing audit `data` JSON. The coalescer's state is in
memory. The summary row is an ordinary audit event.

## Security model

- **The server stays authoritative.** `preflightBlock`, F4's arm and F5's arm are conveniences.
  `POST /runs` enforces every refusal they mirror. A client that ignores them gets the same
  answer at launch. None of them widens what any caller can do.
- **No launch without a click.** After F3, the only path to `createRun` from a sign-in is an
  intent armed by a Launch click for the body still on screen.
- **No credential is spent by checking.** Auto-preflight uses the dry-run liveness path
  (`refresh=false`, `run_model_provider.go:306`; `provider_bedrock.go:84-93`). F2, a separate lane,
  keeps preflight's `renew=false` when it makes create renew. `adoStandingAtDoor` gains the
  no-outbound assertion.
- **Audit fidelity.** The first dry-run refusal per key per window is always written in full and
  goes through the same masking, spool and sinks as today. Repeats are summarised, not hidden.
  The coalescer acts only on rows that carry the marker, and only the preflight handler sets it,
  so a launch refusal can never be folded into a summary. The marker is a reserved datum key, so
  a door's detail cannot set or clear it.
- **The limiter is load protection, not a boundary.** It sits behind authentication. Evicting a
  bucket when the map is full fails open for that one person, which is acceptable for a dry run
  that changes nothing.

### Residual risks

- **Per replica.** The limiter and the coalescer are in-process. With N replicas, one person can
  reach N × 20 per minute, and a key can produce up to N full rows per window. This matches the
  HA epic's documented per-replica limiters (Q-HA3).
- **A crash loses the count.** The first row of a window is durable; the summary of the repeats
  after it is lost if the process dies before the window closes.
- **Up to 60s of a lifted refusal.** If an admin grants a capability, Launch stays blocked until
  the verdict ages out, the window regains focus, or the person presses "Check again".
- **Aborted requests may still run.** Aborting in the browser does not guarantee the server
  stops. The limiter counts the request either way, and the coalescer bounds its rows.
- **The signed-out hold.** A background `POST` must not raise the sign-in prompt on its own while
  the console's signed-out hold is set (`ui/src/app/lib/api/core.ts:226-228`). Auto-preflight is
  skipped while the hold is on.

## Upgrade and compatibility

- **New 429.** CLI and SDK callers of `POST /runs/preflight` can now get 429
  `preflight_rate_limited`. `scripts/ci-run.sh:310-313` already treats a failed preflight as a
  warning and continues, and one CI job sends one request. A script that loops `--dry-run` faster
  than 20 per minute per person needs to slow down or set `WARDYN_PREFLIGHT_RATE_PER_MIN=0`.
- **Audit consumers.** Rows written by preflight now carry `dry_run: true`. Rows written before
  0.8.6 do not, and history is not rewritten. A SIEM rule that counts `authz.denied` per person
  sees fewer dry-run rows and a new `preflight.denial.coalesce` action carrying `count`. The
  OPERATIONS.md paragraph that claims a NULL `run_id` marks a dry run is corrected.
- **Wire.** `setup_items` is unchanged. `preflightResponse` gains nothing.
- **Console.** The "Preflight" button becomes "Check again". Launch can now be disabled by a
  fresh preflight refusal, a missing backend row, or an unattended agent body with no model.
- **No migration, no chart change.**
