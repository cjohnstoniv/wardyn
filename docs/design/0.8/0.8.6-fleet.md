# Wardyn 0.8.6 — fleet capacity view, and operability without kubectl

An adopter runs Wardyn on a shared, multi-tenant Kubernetes cluster where the platform team
holds kubectl and the Wardyn administrators do not. Two questions follow from that. How much of
the cluster is Wardyn holding right now, for whom, and what is stuck waiting for room? And is
the control plane's link to the substrate healthy, and are its background sweeps still running?
Today the console answers neither, so both turn into a ticket to the platform team.

This record covers three pieces of work under the `0.8.6` milestone:

- the epic "0.8.6: Fleet capacity view", with four lanes `fleet-fl1` to `fleet-fl4`;
- operability rows filed beside it: `o-o1` (an opt-in `ServiceMonitor`), `o-o2` (substrate and
  sweep health, with `/readyz` unchanged) and `o-o2b` (the admin banner that reads `o-o2`'s row).

Every file:line below is `origin/main` at e0efee625 (v0.8.5).

## What is true today

**Nothing records what a run reserves.** The one resource value a run row keeps is the
ephemeral-disk cap. Dispatch writes it with a scoped update once it is resolved
(`internal/api/runs_dispatch.go:402-412`, `internal/store/store.go:239-245`). CPU and memory are
never written down:

- The defaults are compiled constants, 2000m and 4096Mi (`internal/runner/sandbox.go:33-34`).
- They are filled in three separate places: `composer.Clamp` (`internal/composer/clamp.go:139-146`),
  the Kubernetes driver (`internal/runner/k8s/naming.go:164-185`) and the Docker driver
  (`internal/runner/docker/hardening.go:487-500`).
- On Kubernetes the agent's requests equal its limits (`naming.go:175-181`). The proxy pod has a
  fixed 500m/256Mi envelope, also with requests equal to limits (`naming.go:258-270`). So one
  default run reserves 2500m/4352Mi, not the 2000m/4096Mi a reader of the policy would assume.
- On Docker there is no reservation at all, only caps. The proxy has a 256 MiB memory cap and no
  CPU cap (`hardening.go:33`, `:466-477`).

**The scrape surface has no live view of the fleet.** `/metrics` counts runs once they reach a
terminal state (`wardyn_runs_total{state}`, `internal/api/metrics.go:405-408`). Its only live
gauges are `wardyn_store_up` and the audit-spool gauges (`metrics.go:503-525`). Nothing counts
active runs, the oldest active run, or the runs waiting for a node.

**The per-run resource reading execs inside the sandbox.** `GET /runs/{id}/resources` runs a script
in the sandbox over `ExecStream` (`internal/api/run_resources.go:10`, `:49`, `:200`). That is fine
for one run page. Fanned out across a fleet, it would put one exec into every live sandbox per
refresh.

**The security tier already sees every run.** `GET /runs?view=admin` is granted to
`isSecurityOperator` (`internal/api/runs_list_filter.go:88-89`), so an owner-by-owner capacity
breakdown tells a security admin nothing they cannot already list.

**A substrate fault is invisible from the console.**

- `/readyz` pings Postgres and nothing else (`internal/api/security_headers.go:119-140`). The chart's
  readinessProbe targets it (`deploy/helm/wardyn/templates/deployment.yaml:541-558`).
- The `runner` row on `/setup/status` is derived from the runner's advertised classes
  (`internal/api/setup_checks.go:70-115`). It does not probe whether the substrate still answers,
  or whether the ServiceAccount token is still accepted.

**No background sweep reports its own progress.**

- The idle reaper (`internal/lifecycle/lifecycle.go:151-160`, single-flight through `reapTickLock`,
  `cmd/wardynd/adapters.go:631-645`).
- The terminal-sandbox sweep (`cmd/wardynd/terminal_sandbox_sweeper.go:94`).
- The approval expiry sweeper (`adapters.go:820`).
- The run-secret sweeper (`adapters.go:866`).
- The credential expiry sweeper (`adapters.go:893`).
- The recording retention sweeper (`adapters.go:930`).
- The run-watcher sweeper (`internal/api/reconcile.go:507`).
- The orphaned-build sweeper (`reconcile.go:314`).

A sweep that has stopped looks exactly like one with nothing to do.

**The chart ships no ServiceMonitor.** `deploy/helm/wardyn/README.md:977-1002` documents scraping
through the NetworkPolicy with a pod annotation, and says the chart deliberately ships no
`ServiceMonitor`. The scrape credential is the admin bearer (`internal/api/routes.go:39-46`,
`docs/operations/monitoring.md:5`, `:67-68`).

## Goals

- An administrator can see, in the console and on a scrape, what the fleet holds. That means
  active runs by state, their configured CPU and memory reservations per runner kind, how old
  they are, who holds the most, and which runs are waiting for room. The figures come from what
  Wardyn asked the substrate for, recorded at the moment it asked.
- No number is invented. A run dispatched before 0.8.6 has no recorded reservation and is counted
  as "unknown".
- A broken substrate or a stalled sweep shows on a gauge, on a `/setup/status` row and in an
  admin banner, while `/readyz` keeps answering 200 so the console stays reachable.
- A cluster that runs the Prometheus Operator can scrape Wardyn by turning on one chart value.

## Non-goals

- **Observed allocation.** The figures are configured reservations. Reconciling them against what
  the runner actually holds is deferred (Q-FL (b)).
- **Free cluster capacity.** Co-tenant pods in other namespaces are invisible to Wardyn. P7's
  admission check (`p-p7`) owns the "will it fit" advisory, and the scheduler stays authoritative.
- **A metrics-only credential.** Under current auth the scrape credential has full admin authority.
  A dedicated metrics-reader token class is a follow-up, not 0.8.6 scope.
- **Changing `/readyz`.**

## Decisions — fleet capacity

**F-D1. Persist the configured reservation at dispatch, from the same function the drivers use.**
At dispatch, `runner.EffectiveResources(res)`, built on `runner.EffectiveLimits()` (owned by the `p-p2` lane),
resolves four things for the run from its resolved `policy.Resources`, applying the
deployment default only to zero fields:

- the agent's effective CPU and memory **requests and limits**, after defaults and P3's request
  ratio;
- the **proxy envelope**, which P2 turns into a value;
- the **runner kind** that will create it.

Dispatch writes all of these to the run row. The driver applies exactly these values, and a
parity test across both drivers pins that. The console labels the sums **"configured
reservations"**.

*Rejected:*
- Summing agent limits. That misses the proxy pod, double-counts on Docker, and goes wrong the
  moment P3 separates requests from limits: a ratio change moves what the scheduler reserves
  without changing any stored limit.
- Recomputing from today's configuration at read time. That rewrites history every time an
  operator turns a knob.
- Asking the runner. The per-run reading execs into the sandbox, and a substrate-side list needs
  the reconciliation deferred under Q-FL.

**F-D2. Columns on `agent_runs`, written by one scoped update, kept out of the run DTO.** The new
columns sit beside `disk_mib` and, like `SetRunDiskMiB` (`store.go:239-245`), are written by one
scoped `UPDATE`, best-effort, at the site that already persists the disk cap
(`runs_dispatch.go:402-412`). They are **not** added to the run struct, its scan columns or
the `AgentRun` wire type. Only the capacity aggregate reads them.

Unlike `SetRunDiskMiB`, which sets `updated_at=now()` (`store.go:244`), this write does not bump
`updated_at`. That column is the idle clock lifecycle stop reads, and P5 defines its contract.

The write and the read are **optional store capabilities**, asserted at the call site. The
precedent is `runStatusDetailSetter` (`internal/api/runs_status_detail.go:30-37`), so the test
doubles that embed `store.Store` keep compiling.

*Rejected:*
- Widening `AgentRun`. Every run column is threaded through several scan-bound places and the
  console's wire mirror, and none of those readers needs these numbers.
- A side table keyed by run id. It needs its own foreign key and deletion path for a value that
  lives and dies with the run row.

**F-D3. Record the runner kind with the numbers, beside the existing `runner_target`.**
`runner_target` is the configured target, stamped at create for every row since `0001_init.sql`
(`internal/api/runs.go:300`). Because it is never NULL, it cannot mark a row whose reservation was
never recorded. The new `runner_kind` is written in the same statement as the numbers, so a row
has both or neither. The write happens at `runs_dispatch.go:402-412`, before `CreateSandbox`
(`:593`), so the kind comes from `Config.RunnerTarget` (`internal/api/server.go:227-230`). That is
exact today: one process runs exactly one substrate (`cmd/wardynd/boot_deps.go:284`,
`orchestrator.New(sub)`), so the configured target is the kind that will create the sandbox.

*Rejected:* reusing `runner_target`. It would make legacy rows indistinguishable from recorded
ones. Both carry the same value on a recorded row; only `runner_kind` is NULL where nothing was
recorded.

**F-D4. One basis per runner kind, and never one sum across kinds.**
- Kubernetes rows sum **requests**: what the scheduler sets aside and what `ResourceQuota` charges.
  Limits are reported beside them.
- Docker has no reservations, so Docker rows report **caps**. The Docker proxy's CPU is uncapped,
  recorded as NULL with `runner_kind` set, and shown as "no cap".
- `by_runner` carries a `basis` field (`requests` | `caps`), and the gauges carry a `runner` label.

*Rejected:* one unlabelled "held" total. It would add Docker caps to Kubernetes requests and
mean neither.

**F-D5. State inclusion is written down, not implied.**

| Row | Counted as holding | Why |
|---|---|---|
| `STARTING`, `RUNNING`, `WAITING_FOR_CONFIRMATION` with `lost_at` NULL | yes | its pods exist or are being created |
| paused (`paused_at` set, migration `0097`) | yes | a paused sandbox keeps its pods, memory and proxy (`internal/types/types.go:153`) |
| unschedulable (`STARTING`, status reason `Unschedulable`) | yes, **and** listed separately | `ResourceQuota` charges a Pending pod. The node never ran it |
| kept (`RUNNING` with `lost_at` set) | no; counted as `kept` | its sandbox is gone (`types.go:144`, `cmd/wardynd/adapters.go:587-588`) |
| `PENDING` | no; counted in `states` | nothing is dispatched yet |
| terminal | no | see residual R-F2 |

Non-terminal is `types.NonTerminalRunStates` (`internal/types/types.go:81`), the same positive list
the per-person quota counts (`store.go:128-155`).

"Unschedulable" means a `STARTING` row whose `status_detail` reason token, parsed by
`statusDetailReason` (`runs_status_detail.go:217-224`), is in `runner.CapacityBlockerReasons`, a
new exported closed set `{"Unschedulable"}` that `fleet-fl2` adds. `p-p6` decides its capacity
wait against the same variable.

**F-D6. Unknown is a count, never a zero.** A holding row with `runner_kind` NULL adds 1 to
`unknown` and nothing to any sum. There is no backfill. Legacy rows leave the count as they end.
A failed best-effort write also leaves the row unknown, and dispatch carries on, exactly as a
failed disk-cap write does today. A `STARTING` row is unknown for the moment between its create
and the dispatch write. The docs say so.

**F-D7. The read is `GET /api/v1/admin/runs/capacity`, on the security tier.** It is registered in
`adminRoutes` (`internal/api/routes.go:793-831`, mounted at `:270`) on `securityOps`, because Q-FL
(a) recommends that `security_admin` may read it. If the owner rules otherwise, it moves to
`operatorOnly` beside `/admin/runs/proxy-window` (`routes.go:829`).

The route matrix row (`internal/api/authz_test.go:331` region) and the OPERATIONS.md tier-table
row, which `internal/api/operations_tier_doc_test.go:39-60` pins, move with it.

*Rejected:*
- Member visibility. Fleet volume is the disclosure that keeps `/metrics` gated
  (`routes.go:39-45`).
- An `operatorOnly` default. It withholds from the security tier a figure it can already
  reconstruct from `GET /runs?view=admin`.

**F-D8. Gauges come from a 15-second cached snapshot, with no owner label.** The scrape reads one
aggregate at most every 15 seconds per replica, single-flight across concurrent scrapes. The gauge
families:

- `wardyn_runs_active{state}`;
- `wardyn_runs_unschedulable`;
- `wardyn_runs_cpu_millis_held{runner}`;
- `wardyn_runs_memory_mib_held{runner}`;
- `wardyn_runs_oldest_active_seconds`.

Every replica computes the same Postgres-derived values, so the docs say to aggregate with `max()`,
never `sum()`. If the snapshot cannot be refreshed, the capacity families are **omitted** from that
scrape; they are not written as zero.

*Rejected:*
- An owner label. It is unbounded cardinality, and `/metrics` carries no per-run detail by charter
  (`docs/operations/monitoring.md:5-9`).
- Emitting zeros on a store error. A dead store and an empty cluster would then scrape the same,
  which is the exact asymmetry `writeHealthGauges` exists to remove (`metrics.go:491-502`).

**F-D9. No fan-out to `/runs/{id}/resources`.** The capacity view never execs into a sandbox.

## Decisions — operability (O1, O2)

**O-D1. `ServiceMonitor` is opt-in and takes a reference to an existing Secret.**

- `metrics.serviceMonitor.enabled` (default `false`) renders one `ServiceMonitor` for the chart's
  Service. It targets the named `http` port (`templates/service.yaml:40`) and the base path
  `/metrics` is served under.
- `metrics.serviceMonitor.bearerTokenSecret.{name,key}` names a Secret the operator creates in the
  release namespace.
- `metrics.serviceMonitor.labels` exists so the Prometheus `serviceMonitorSelector` can match.
- `metrics.serviceMonitor.interval` is optional.
- With the flag off, the render is byte-identical to today's. This reverses the "ships no
  ServiceMonitor" stance in `README.md:1000-1002` only for an operator who asks for it.

*Rejected:*
- The chart creating the Secret from a value. That puts an admin-authority credential in a values
  file and in Helm release history.
- Gating the object on `.Capabilities.APIVersions`. An offline `helm template` or a GitOps render
  would silently drop it.

**O-D2. The scrape credential's authority is disclosed, not narrowed.**
`/metrics` is `humanOrAdminAuth` plus `requireOperator` (`routes.go:46`). Any credential that
scrapes it is therefore a full admin credential: the shared admin token, or a personal API token
whose owner is an admin.

The README says so in plain words, and names two more things:
- The follow-up: a metrics-reader token class.
- The two ways a personal token scrape stops working: I1's `expires_at` / `WARDYN_API_TOKEN_MAX_TTL`,
  and I2's `WARDYN_ROLE_STAMP_TTL`, which refuses the token with `role_stamp_stale` until its owner
  signs in again. In both cases the Secret is rotated.

The selector section covers two ways to drop a scrape:
- The chart's NetworkPolicy admits only peers named in `networkPolicy.ingress.from`
  (`README.md:977-1000`), so the Prometheus namespace has to be admitted.
- The `ServiceMonitor`'s own labels have to match the Prometheus selector.

Either one, missed, reads as "target down".

**O-D3. `/readyz` stays store-only.**
- The readinessProbe targets it (`deployment.yaml:541-558`).
- Pulling every replica out of the Service on a substrate fault would hide the console, and the
  console is the adopter's only diagnostic surface.
- Substrate health is reported, not enforced.

**O-D4. A per-replica runner probe, cached with a TTL and read lazily.**
- The runner gains an optional health capability, modelled on the optional `DriveProber`
  (`internal/runner/runner.go:408-416`).
- On Kubernetes it makes one authenticated namespaced read the Role already grants: `list` pods
  with a limit of 1 (`templates/rbac.yaml:181-183`). That shows whether the API server answers and
  whether the ServiceAccount token is accepted, and needs no new verb (the R-02 guard in
  `scripts/test-claims-match-code.sh:27-30`).
- On Docker it is a daemon ping.
- The result is classified (`ok` | `unreachable` | `unauthorized` | `forbidden`). It is cached per
  replica with a short TTL and a single flight, in the shape of `capsCacheTTL`
  (`orchestrator.go:35`). Each replica reports its own probe, because a token or route can fail on
  one pod and not another.

*Rejected:* a background ticker. It would be another goroutine to lead-gate, and it would need its
own liveness gauge.

**O-D5. Sweep progress lives in a shared row and separates an attempt from a success.**
- A new `sweep_ticks` table holds one row per sweep.
- `attempted_at` is set when a tick starts real work: the replica that won the tick lock, or under
  HA the leader.
- `succeeded_at` is set when the tick finishes without error.
- Writes use `GREATEST` so a late replica cannot move either column backwards.
- Every replica reads the same row. Under HA, followers report the leader's ticks and never look
  stale, and a stopped leader shows as stale on every replica.
- The label set of `wardyn_sweep_last_tick_seconds{sweep,result}` is closed. `sweep` is one of
  `idle_reaper`, `terminal_sandbox`, `approval_expiry`, `run_secret`, `credential_expiry`,
  `recording_retention`, `run_watcher` and `orphaned_build`. `result` is one of `attempt` and
  `success`.

*Rejected:* per-replica in-memory timestamps. A follower that never wins the lock would report a
sweep as dead.

**O-D6. One `/setup/status` row and one admin banner, never blocking.**
- The row is `substrate_health`. It has `Cause` values `runner_unreachable`, `runner_auth` and
  `sweep_stale`, using the existing machine-key field (`setup_checks.go:57-64`).
- It reports `fail` for a failed runner probe and `warn` when a sweep's last success is older than
  three of its intervals.
- Only a sweep this install started can be stale. Five of the eight start only under a condition,
  and recording retention is off by default:
  - `idle_reaper`: a runner exists and the autostop interval is above 0
    (`cmd/wardynd/boot_serve.go:131`);
  - `approval_expiry`: its interval is above 0 (`boot_serve.go:167`);
  - `recording_retention`: the recording store can sweep and `WARDYN_RECORDING_RETENTION_DAYS` is
    above 0, default 0 (`boot_serve.go:176`, `boot_flags.go:406`);
  - `terminal_sandbox`: a runner exists (`boot_serve.go:207-208`);
  - `run_watcher`: a runner exists (`internal/api/reconcile.go:107-115`);
  - `orphaned_build`: the image builder implements `ImageBuildSweeper` (`reconcile.go:104`).

  Each replica registers every sweep whose start condition holds on this install, whether or not
  this replica holds the sweeper leader lock. The staleness grace runs from this process's start.
  A sweep whose start condition does not hold is omitted from `wardyn_sweep_last_tick_seconds` and
  never contributes to `sweep_stale`. A registered sweep with no `sweep_ticks` row, or with no
  success yet, warns only once three of its intervals have passed since this process started.
  So a default install, with recording retention off, never carries a standing `sweep_stale`.
- It never sets `Blocking` (`setup_checks.go:31-49`): confiscating the console on a substrate fault
  is the outcome O-D3 exists to avoid.
- Members never see it, because `redactSetupStatusForUser` empties `Checks`
  (`internal/api/setup.go:459-462`).
- The banner mounts in the shell's banner stack beside `EveryoneAdminBanner`
  (`ui/src/app/components/screens/app-shell.tsx:877`). It renders only for a resolved admin and
  reads the row, never re-deriving it.
- The row's detail carries the classified state, never raw substrate error text.

## Data model and migrations

Both migrations take the next free number at merge: `0107` against today's main, where the
highest is `0106_attach_ticket_authority.sql`. The steward renumbers them in merge order
(`scripts/check-migration-numbers.sh`, `TestMigrationPrefixesNoGapsOrDupes`).

**`fleet-fl1`: `NNNN_agent_runs_reservation.sql`.**

```sql
ALTER TABLE agent_runs
    ADD COLUMN IF NOT EXISTS runner_kind              TEXT CHECK (runner_kind IN ('docker','k8s')),
    ADD COLUMN IF NOT EXISTS agent_cpu_request_millis INTEGER,
    ADD COLUMN IF NOT EXISTS agent_cpu_limit_millis   INTEGER,
    ADD COLUMN IF NOT EXISTS agent_memory_request_mib INTEGER,
    ADD COLUMN IF NOT EXISTS agent_memory_limit_mib   INTEGER,
    ADD COLUMN IF NOT EXISTS proxy_cpu_millis         INTEGER,  -- NULL with runner_kind set: no CPU cap (Docker)
    ADD COLUMN IF NOT EXISTS proxy_memory_mib         INTEGER;
```

- Every column is nullable, with no default. On PostgreSQL 13 and later, adding such a column is a
  catalog-only change with no table rewrite.
- `agent_runs` was created in `0001_init.sql`, so this migration ALTERs a table an earlier release
  created. Its number therefore goes into the migrator/app-role rationale in `docs/OPERATIONS.md`,
  which check C8c of `scripts/test-claims-match-code.sh:157-188` enforces.
- The aggregate filters on the existing `agent_runs_state_idx` (`0001_init.sql:22`). No new index
  is added.

**`o-o2`: `NNNN_sweep_ticks.sql`.**

```sql
CREATE TABLE IF NOT EXISTS sweep_ticks (
    sweep        TEXT PRIMARY KEY,
    attempted_at TIMESTAMPTZ,
    succeeded_at TIMESTAMPTZ,
    replica      TEXT NOT NULL DEFAULT ''
);
```

This creates a new table and needs no C8c row. It holds no personal data, so erasure does not
touch it.

## API

`GET /api/v1/admin/runs/capacity` returns:

- `generated_at`, and `basis: "configured_reservations"`;
- `states`: counts for each non-terminal state, plus `paused` and `kept`;
- `totals`: `holding`, `unknown`, and the summed request, limit and proxy fields. Kubernetes and
  Docker are never mixed in one figure: `totals` carries the deployment's current runner kind,
  and the other kind appears only under `by_runner`;
- `age_buckets`: holding runs by age since `created_at`, in the bounds under 1h, 1–8h, 8–24h, 1–7d
  and over 7d;
- `by_runner`: one entry per kind, each with `basis`, its sums and its own `unknown` count. Legacy
  rows are attributed through `runner_target`;
- `by_owner`: the top 50 owners, ordered by held CPU and then by run count, with
  `by_owner_truncated` set when more exist;
- `unschedulable`: at most 20 runs, the oldest first, each with id, owner, how long it has waited,
  the reason and its recorded reservation, plus `unschedulable_total`.

The response is computed on request from one query over the non-terminal rows. The gauges reuse
the same aggregate function behind their 15-second cache.

## Security model and residual risks

- **The capacity read discloses per-owner usage to the security tier.** That tier already lists
  every run with its owner (`runs_list_filter.go:88-89`). The gauges carry no owner, and `/metrics`
  stays admin-only.
- **R-F1: the figures are configured, not observed.** A run whose pod was evicted and recreated
  smaller or larger by something outside Wardyn is reported at what Wardyn asked for. The card and
  the docs say "configured reservations" every time.
- **R-F2: a failed teardown is invisible.** A terminal run whose sandbox outlived it still holds
  real capacity, and the card does not count it. The terminal-sandbox sweep reaps such sandboxes
  (`routes.go:807-827`). The view only becomes exact once runner reconciliation lands, which Q-FL
  (b) defers. The docs name this gap.
- **R-F3: Docker caps are not reservations.** The Docker figure is an upper bound on what the
  sandboxes may take, not what the host has set aside.
- **R-O1: the scrape credential is a full admin credential (O-D2).** Anyone who can read the
  referenced Secret in the release namespace holds admin authority over the API. The Operator
  copies it into the Prometheus configuration Secret and pod in the Prometheus namespace, so
  everyone with Secret read or exec there, and the Operator's ServiceAccount, holds admin authority
  over the API. The README says to mint a dedicated personal API token for a dedicated admin
  identity, with a TTL under I1 (`WARDYN_API_TOKEN_MAX_TTL`), never the shared `auth.adminToken`,
  so a leaked scrape credential is revoked by deleting that one token. This stays a residual until
  the metrics-reader token class exists.
- **R-O2: the runner probe proves reachability and authentication, not capacity or scheduling.** A
  cluster with a full node pool probes healthy. P6's waits and the unschedulable list carry that
  signal.
- **R-O3: `sweep_ticks` shows progress, not correctness.** A sweep that succeeds while doing the
  wrong thing still reads green. Its own tests and audit rows remain the evidence.

## Upgrade and compatibility

- **Additive schema.** Rows dispatched before the upgrade read as `unknown` until they end. Nothing
  is backfilled.
- **No wire change to `AgentRun`.** The capacity endpoint is new. Older clients never call it.
- **`/readyz` and the readinessProbe are unchanged.** The new row is advisory and is redacted for
  members.
- **The chart renders byte-identically with `metrics.serviceMonitor.enabled=false`**, which is the
  default.
- **Under HA, aggregate with `max()`.** Each replica serves the same fleet gauges, so a `sum()`
  multiplies them by the replica count. `wardyn_runner_up` is per replica, and an alert should fire
  when any replica reports 0.
- **Downgrade.** As for any migration, an older binary refuses a database that carries a migration
  it does not know.
