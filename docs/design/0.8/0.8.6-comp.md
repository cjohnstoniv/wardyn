# Wardyn 0.8.6 — profile composition

A governance profile today is a whole ceiling with replacement semantics: an assigned profile *is*
the person's ceiling, and with no assignment the person falls through to `Config.DefaultPolicy`
byte for byte (`internal/types/governance.go:272-279`, `docs/OPERATIONS.md:2613`,
`docs/design/governance-prompt.md:156-158`). An organisation with one baseline and many teams has
to copy the baseline into every team profile and keep the copies in step by hand. When the baseline
narrows, a copy that was missed keeps the old, wider walls. An adopter with a central identity team
and many tenants asked for profiles that say "the baseline, minus this".

This record designs that: a profile may name a **base** (another profile, or the deployment
default) and carry an **overlay** that can only narrow it. It also carries the prerequisite fix that
stops a profile's `resources` escaping the deployment's sandbox size (G1, which this epic calls D0).

Every file:line below is `origin/main` at e0efee625 (v0.8.5). Owner decisions are marked
**accepted at the recommended defaults (owner ruling 2026-10-03)**, and the recommended default applies unless the owner overrides it.

## Goals and scope

- A profile may be **standalone** (today's shape, unchanged byte for byte) or **composed**: a base
  plus a presence-typed overlay. The effective ceiling is `ApplyOverlay(effective(base), overlay)`,
  resolved whenever authority is read.
- An overlay can only narrow. That holds against what the proxy, the composer and dispatch actually
  enforce, not only against a comparator.
- Every reader of profile authority, including the doors that bind runs already going, sees the
  composed answer. A base that cannot be read fails closed.
- `composer.Leq(a, b)` ("a is at most as permissive as b") is exported for the four-eyes design
  (GOV4), which exempts proven-narrowing changes from second-person approval.
- The SDK and CLI can export a composed graph from one install and apply it to another.

**Not in scope.** Multiple bases per profile, widening overlays, a cross-request ceiling cache,
and any change to how a profile is *assigned* (tiers, priority and user types are unchanged).
`DefaultPolicy` stays a non-floor: the adopter does not ask to forbid widening by standalone
profiles, so a standalone profile may still be wider than the deployment.

## Prerequisite (D0 = G1): resources cannot escape the deployment

Measured on an adopter's install: an admin gets 1000m, a member with no profile 1000m, a member
whose profile omits `resources` **2000m**, and a member whose profile sets 64000 **64000m**. The
2000m comes from the platform constant (`internal/runner/sandbox.go:33-34`) that `composer.Clamp`
and the runners fall back to when a ceiling carries no `resources` (`internal/composer/clamp.go:139-150`).
`ceilingFromProfile` hands the profile's spec through as is (`internal/api/governance.go:855-867`),
and the commonest member launch (no policy at all) uses the ceiling itself as the run's spec with
no clamp (`resolvePolicy` at `internal/api/inline_policy.go:258`, and the scoping note at `:295-298` that confines the member clamp to a selected row at `:316`).

G1 fixes this in three parts. It builds on P2's `runner.EffectiveLimits()`, which owns the
effective default, so it is stacked on that lane.

- **(a)** A profile that omits `resources`, or leaves a field of it zero, inherits the deployment's
  value for that field in `ceilingFromProfile`: `DefaultPolicy.Resources`, else
  `runner.EffectiveLimits()`.
- **(b)** `GovernanceLimits` gains `MaxCPUMillis` and `MaxMemoryMiB` (`max_cpu_millis`,
  `max_memory_mib`; 0 is unlimited, negatives refused beside the existing checks at
  `internal/api/governance.go:174-189`). They fold into `composer.Clamp` the same way
  `MaxEphemeralDiskMiB` does (`internal/api/inline_policy.go:71`, `internal/api/profile.go:135`,
  `internal/api/runs_dispatch_ceiling.go:68`). The no-policy path gets the same bound through a
  **resource-only helper**, not full `Clamp`, because `Clamp` drops workspace mounts
  (`internal/composer/clamp.go:198-200`). The sign-in sandbox keeps its own smaller size
  (`internal/api/harnesscred.go:409-420`).
- **(c)** `validatePolicySpec` (`internal/api/policy.go:54`) range-checks `Resources`, so the
  `Resources` row of `internal/api/policy_field_coverage_guard_test.go:78` flips to validated. The
  editor shows an advisory when a profile omits `resources` (copy in mock packet M10), and the
  "profiles narrow by omission" paragraph (`docs/OPERATIONS.md:2615-2617`) is corrected.

Rejected: making the deployment a floor for every profile. It would break standalone profiles that
deliberately widen, and nobody asked for it.

## Decisions

**A single base and an overlay, not a free composition of profiles.** A profile names at most one
base. Rejected: composing an arbitrary set of profiles (multiple inheritance). With several parents
a person can't tell which wall came from where, and the meet of several partial overlays has no
single reading of "absent". Rejected: copy-on-write templates (copy the base at creation). They
reproduce the drift this feature exists to remove.

**A new meet in `internal/composer/meet.go`, not `Clamp`.** `Clamp` is not a lattice meet
(`internal/types/governance.go:276-279`). It drops workspace mounts, replaces `llm_inspection`
wholesale with the operator's mode (`internal/composer/clamp.go:98-116`) and defaults unnamed tools
to hold. It exists to bound an untrusted proposal against an operator ceiling. A meet of two
operator-authored ceilings is a different operation and gets its own function, with its own rules
per field (the table below). Rejected: reusing `Clamp` with the base as ceiling. It would silently
lose mounts and be order-dependent.

**Resolved at read time, not materialised.** The effective ceiling is computed when authority is
read, from one consistent read of the chain. Rejected: writing the effective ceiling into the
child's `ceiling` column whenever a base changes. The deployment base is environment-borne
(`WARDYN_DEFAULT_POLICY`), so a redeploy would leave every materialised child stale, which is the
exact hazard `reintersectGovernanceGrants` exists for (`internal/api/governance.go:891-907`). A base
edit would also have to fan out writes to every descendant.

**Strict at write, meet at resolve.** A write is refused when an overlay names something its base
does not permit, such as a domain outside the base, a method the base excludes, or `allow_all_egress`
on a base without it. At resolve time the base may have narrowed since, and the meet then drops what
is no longer covered, with a warning on the 201 `clamp_warnings` list. This is the asymmetry the
grant re-intersection already uses and defends: a write is the author's own act and can be sent back,
but a base edit is someone else's act arriving between two runs. Rejected: a silent meet at write.
It would hide an author's mistake, and a later widening of the base would then quietly activate it.

**Unrepresentable results are refused, never encoded as "no restriction".** Several fields use the
empty value to mean "everything". An empty `allowed_methods` allows every method in the proxy
(`internal/egress/proxy/policy.go:411-418`), and an empty `azure_devops_capabilities` means the
provider row's default profile. A meet that would produce an empty set from two non-empty sets
never becomes `[]`:

- at write, the overlay is refused (400 `governance_overlay_invalid`);
- at a base write, a change that would empty a descendant's meet is refused (409
  `governance_overlay_unsatisfiable`, naming the descendant);
- at resolve, which is reachable only when the environment-borne deployment base changed under a
  profile, launches under that profile are refused with the authz reason
  `governance_overlay_unsatisfiable`, audited. That is the explicit deny-all state.

**One domain matcher.** "Covered by the base" for `allowed_domains` uses the proxy's own matcher.
`classifyDomain`'s pattern logic (`internal/egress/proxy/policy.go:273`, called from `CompilePolicy`
at `:96`, with `matchWild`/`matchWildPort` at `:346,357` and `evalHost` at `:369`) is extracted into
one exported function that both the proxy and `meet.go` call. `internal/composer` does not import
the proxy today (its non-test imports are `internal/adoscope`, `internal/runner` and
`internal/types`), and the proxy does not import composer, so either direction is cycle-free. The
pattern logic moves to a small leaf package, `internal/egress/domainmatch` (`Classify`, `MatchWild`,
`MatchWildPort`), that both `proxy.CompilePolicy` and `meet.go` import, so composer does not take the
whole proxy (`hoptls`, `contentscan`, `gitpack`, `ipguard`, `secretmask`) as a dependency. Only the
oracle tests (`_test.go`) import the proxy from composer. Rejected: a second matcher kept in agreement by a
test. The repository has paid for dual matchers before.

**One resolver for every authority read.** See "Resolution" below. Rejected: composing only in
`effectiveCeiling`. Live doors, revive, reclamp and end extension read stored profiles directly
today, so a child that inherits `deny_interactive` would launch a task run and then attach through
the child's raw, empty limits.

**Depth at most 3, one parent, no cycles.** The depth of a profile is the number of profiles on its
path to the deployment, itself included. A standalone or deployment-based profile has depth 1. A
write that would create a cycle, or push any existing descendant past depth 3, is refused. Rejected:
unbounded chains. Resolve cost and readability both degrade, and nobody asked for more than a
baseline, a division and a team.

**Leaf identity and contact are separate from effective content.** The leaf profile's id, name and
`contact` (added by DENY F1) are what a denial and `/me` disclose. A base's name, overlay and contact
never reach a member. The effective *content* is composed. `contact` is never inherited from a base:
a leaf with no contact falls back to the site's `policy_help`, because disclosing a base's contact
would disclose the base. Rejected: inheriting contact, which leaks the graph.

**An update that omits the composition fields keeps them.** A `PUT` on a composed profile that omits
`base_profile_id`, `overlay`, `overlay_limits` or `contact` keeps the stored value. Only an explicit
`null` clears one. An older client that does not know the fields therefore can't flatten a profile
by accident.

## Meet and normalisation, per field

Every field has an explicit **unset** reading (what the runtime does with zero or absent), a
**top** (least restrictive) and a **bottom** or unsatisfiable state. Values pass through the
runtime's own default normalisers *before* the meet, and the result is written back explicitly. A
"smaller positive" over raw values would widen whenever the runtime gives zero a finite meaning.
For example, with an active push rule `max_inspect_pack_mib=0` means 32 MiB
(`internal/egress/proxy/push_rules.go:99`), so `meet(0, 64)` taken raw would be 64.

`ApplyOverlay(base, overlay)`: for each field present in the overlay, the result is
`meet(norm(base), norm(overlay))`. An absent field inherits the base unchanged.

### `RunPolicySpec` (`internal/types/policy.go:120-207`)

| Field | Unset means | Meet |
|---|---|---|
| `allowed_domains` | nothing allowed (default deny) | Every overlay entry must be covered by the base's own `allowed_domains` under the one matcher (`internal/egress/domainmatch`), whether or not the base sets `allow_all_egress`; an uncovered entry is `governance_overlay_invalid`. `allow_all_egress` on the base never covers an entry: an exact entry reaches private literal IPs and `internal_hosts` names and enrols credential injection, which allow-all does not (`internal/egress/proxy/policy.go:391-407,606-615`) |
| `denied_domains` | none | union |
| `allow_all_egress` | false | AND. An overlay may set it only false |
| `first_use_approval` | `always_deny` (`Normalize`) | stricter by `firstUseApprovalRank` (`internal/composer/clamp.go:344`) |
| `first_use_hold_seconds` | 30 s | smaller after normalising (Q-COMP a) |
| `max_holds` | 16 | smaller after normalising |
| `allowed_methods` | all methods | intersect non-empty sets. Empty on one side yields the other. Disjoint is unsatisfiable, never `[]` |
| `min_confinement_class` | required | higher (`confinementRank`, `clamp.go:22`) |
| `eligible_grants` | none | the overlay's grants pass through unchanged; the resolver re-intersects them against the **resolved base** with `reintersectGovernanceGrants` (next section) |
| `auto_stop_after_sec` | ≤0 never reaped | smaller positive (≤0 counts as unbounded) |
| `workspace_mounts` | none | intersect by (source, target). Read-only if either side is |
| `workspace_repos` | none | intersect by identity |
| `llm_inspection` | none | present on one side yields that side. Both present and unequal is refused (Q-COMP c) |
| `ui_apps` | none | intersect by (name, port), as `clampUIApps` (`clamp.go:322`) |
| `resources` | deployment value (G1(a)), else `runner.EffectiveLimits()` | smaller per field after normalising |
| `tool_rules` | unnamed tool = hold, `*` default (`ceilingToolEffect`, `clamp.go:672`) | per tool named on either side, plus `*`: stricter by `toolStrictness` (`clamp.go:660`), emitted explicitly |
| `git_push_any_branch` | false | AND |
| `push_rules.deny_paths`, `.require_review_paths` | none | union |
| `push_rules.max_inspect_pack_mib` | 32 MiB when the result has any rule | smaller after normalising |
| `push_rules.hold_seconds` | 120 s | smaller after normalising (Q-COMP a) |
| `push_rules.max_file_size_mib` | off | smaller positive (off counts as unbounded) |
| `push_rules.deny_new_executables` | false | OR (reserved: validation refuses `true` today, `internal/types/policy.go:234-238`) |
| `azure_devops_capabilities` | the row's default profile | intersect non-empty lists. Empty on one side yields the other. Disjoint is unsatisfiable |

### `GovernanceLimits` (`internal/types/governance.go:42-117`)

| Field | Unset means | Meet |
|---|---|---|
| `deny_task_mode_exec`, `deny_interactive`, `deny_ui_apps`, `deny_user_drive` | false | OR |
| `max_concurrent_runs`, `max_ephemeral_disk_mib`, `max_drive_size_mib`, `max_cpu_millis`, `max_memory_mib` | 0 = unlimited | smaller positive |
| `autonomy_rubric` | nil caps nothing | per field, the lower level. A field set on one side only takes that side. nil+nil stays nil |
| `max_end_ahead_sec` | 0 = no limit | smaller positive |
| `default_end_sec` | 0 = `max_end_ahead_sec` | smaller after normalising, then clamped to the resulting max |
| `max_wait_sec` | 0 = the deployment's approval expiry | smaller after normalising |
| `default_wait_sec` | 0 = the deployment's approval expiry | smaller after normalising, then clamped to the resulting max |
| `allow_no_end`, `user_changes_limits` | false | AND |
| `pause_idle_after_sec` | 0 = pause only runs waiting for a decision | smaller positive (0 counts as unbounded for idleness) |

The `RunLimits` bound fields use the same tightening as live-run reclamp: comp-d1 moves
`tightenRunLimits`/`tighterSec` (`internal/api/run_limits_reclamp.go:99-117`) into
`internal/composer`, so a running child is reclamped to the bounds a new run gets.

The result of the limits meet must pass `runLimitsRefusal` and `governanceLimitsRefusal`. A result
they would refuse counts as unsatisfiable.

**Field coverage guard.** A recursive guard walks `RunPolicySpec` and `GovernanceLimits`, including
the nested `PushRulesSpec`, `ResourceLimits`, `AutonomyRubric`, `RunLimits` and `GrantSpec`, and
fails on any field with no meet rule and no `Leq` rule. It is modelled on
`internal/api/policy_field_coverage_guard_test.go`. A new policy field therefore cannot ship
unhandled.

## Grants: one base-dominance contract

The single-grant dominance comparator already exists: `governanceGrantWithinCeiling`
(`internal/api/governance_grantbound.go:143`). It checks kind and pairing identity,
`requires_approval`, `owner_only` (`:192-198`), TTL after normalising and the GitHub scope, and GPAT
G1 wires the git_pat scope axes (`repos`, `access`, `api`, `forge`) into it with their explicit
omission defaults. `reintersectGovernanceGrants` (`internal/api/governance.go:909`) calls it at
resolve, today against the **deployment** only. For a composed profile that is not enough, because
the base may be narrower than the deployment. (`grantDominatedBy`, `internal/composer/clamp.go:419-430`,
omits `owner_only`; it is not this contract.)

There is no new comparator. comp-d2 moves `governanceGrantWithinCeiling`'s logic into
`internal/composer` as exported `composer.GrantWithin(g, ceiling []GrantSpec) error`, and the api
function becomes a one-line wrapper. The one contract is used in three places:

- at overlay write, where a grant not within the base is refused;
- in the resolver, where `reintersectGovernanceGrants` re-intersects the overlay's grants against
  each step's **resolved base** (the meet itself passes grants through unchanged);
- in `Leq`.

The existing deployment re-intersection still runs at the root of the chain, so every composed
grant is transitively within the deployment.

## `Leq`

`composer.Leq(a, b RunPolicySpec, la, lb GovernanceLimits) bool` reports whether `a` is at most as
permissive as `b` under the normalisers above. It is **conservative**: a field the rules don't cover,
or a change it can't prove narrowing, returns false. GOV4 uses it to exempt proven-narrowing writes
from second-person approval. A false negative only means an extra approval, never a silent widening.
D2's exemptions need the complete git_pat algebra, so D2 is blocked by GPAT G1.

## Data model and migration

One migration, at the next free number when it merges (0107 on `origin/main` today; the steward
renumbers), ALTERs `governance_profiles` (`internal/db/migrations/0052_governance_profiles.sql`):

```sql
ALTER TABLE governance_profiles
  ADD COLUMN base_profile_id UUID NULL REFERENCES governance_profiles(id) ON DELETE RESTRICT,
  ADD COLUMN overlay         JSONB NULL,
  ADD COLUMN overlay_limits  JSONB NULL,
  ADD CONSTRAINT governance_profiles_base_needs_overlay
      CHECK (base_profile_id IS NULL OR overlay IS NOT NULL),
  ADD CONSTRAINT governance_profiles_no_self_base
      CHECK (base_profile_id IS DISTINCT FROM id),
  ADD CONSTRAINT governance_profiles_limits_need_overlay
      CHECK (overlay_limits IS NULL OR overlay IS NOT NULL),
  ADD CONSTRAINT governance_profiles_overlay_objects
      CHECK ((overlay IS NULL OR jsonb_typeof(overlay) = 'object')
         AND (overlay_limits IS NULL OR jsonb_typeof(overlay_limits) = 'object')),
  ADD CONSTRAINT governance_profiles_composed_has_no_raw_ceiling
      CHECK (overlay IS NULL OR (ceiling = '{}'::jsonb AND limits = '{}'::jsonb));
```

- `overlay IS NULL` means standalone: today's row, read exactly as today.
- `overlay` not NULL with `base_profile_id IS NULL` means composed on the deployment default.
- `overlay` not NULL with a base id means composed on that profile.
- A composed row stores no raw ceiling or limits, so nothing can mistake its columns for authority.
- `ON DELETE RESTRICT` makes deleting a base that still has children a 409, as the assignment FK
  already does for assigned profiles (`internal/store/governance.go:80-100`). The message names the
  children.
- All columns are nullable with no default and no backfill. Every existing row satisfies every CHECK.
- Because it ALTERs an older table, the migration gets a row in OPERATIONS.md's migrator rationale
  (checked by `scripts/test-claims-match-code.sh` C8c).

**Absent, null and empty**, for `POST`/`PUT /governance/profiles`:

| Field | Absent on PUT | `null` | Empty |
|---|---|---|---|
| `base_profile_id` | keep | the deployment is the base (composed rows only) | n/a |
| `overlay` | keep | the row becomes standalone, and the request must carry a valid `ceiling` | `{}` is a composed alias of the base (valid, no narrowing) |
| `overlay_limits` | keep | no limit narrowing (stored NULL) | `{}` is stored as NULL |
| `contact` (DENY F1) | keep | clear | `{}` is stored as NULL |

On `POST`, absent means NULL. Overlay field presence is typed: `CeilingOverlay` and `LimitsOverlay`
mirror `RunPolicySpec` and `GovernanceLimits` with pointer fields, decoded strictly. A present empty
list is a value. For example, `allowed_domains: []` narrows to no domains, while
`allowed_methods: []` is refused because it would mean "all".

**Graph writes are serialised.** Create, update and delete take one transaction-scoped advisory lock
for the profile graph. Inside the transaction they re-read the chain and the descendants' heights,
refuse a cycle (409 `governance_profile_cycle`) or a depth overflow (409 `governance_profile_depth`),
and re-resolve every descendant, refusing a base change that would make one unsatisfiable. Profile
writes are rare and the graph is small, so one lock costs nothing that matters.

## Resolution

New file `internal/api/governance_compose.go`, because `governance.go` is at 925 of 1000 lines
under `scripts/check-file-size.sh`.

- **`resolveProfileByID(ctx, id) (ResolvedProfile, error)`** reads the leaf and its ancestors in one
  statement (a recursive CTE bounded at depth 3), composes from the deployment down, and returns
  `ResolvedProfile{ID, Name, Contact, Chain, Ceiling, Limits, Warnings}`. The leaf's identity and
  contact sit beside the effective content.
- **`resolveAllProfiles(ctx)`** composes every profile from one `ListGovernanceProfiles` read, for
  the readers that scan the list.
- **A base that fails to read fails closed.** The resolver returns the error, never a partial chain,
  and every caller takes its existing store-failure branch: `ceilingFromProfile`'s real-error check
  (`internal/api/governance.go:856-858`), 503 `owner_profile_unreadable` at revive and end
  extension, and `governance_unavailable` on `/me` as the drive door already reports
  (`internal/api/user_drives_resolve.go:170`).

**Every authority reader is routed through it.** On `origin/main` the raw reads are:

| Reader | Raw read | What it binds |
|---|---|---|
| `resolveEffectiveCeiling` / `ceilingWithUnusableGroups` | `governance.go:824,835` | create, preflight, dispatch (through the per-request memo, `governance.go:768-789`) |
| `runProfile` | `governance_run_doors.go:40`, used at `:61,87` | the live attach/SSH and UI-app doors |
| `ownerProfile` | `run_owner_authority.go:237`, used by revive (`run_revive.go:560`) and owner revalidation (`run_owner_authority.go:463`) | revive and the owner's authority |
| run-limit reclamp | `run_limits_reclamp.go:38` | tightening live runs' limits |
| end extension | `run_end_wait.go:189` | `PATCH /runs/{id}` end and wait |
| run policy view | `run_policy_view.go:241` | `GET /runs/{id}/policy` |
| governance list and preview | `governance.go:79,534` | the admin view and `POST /governance/preview` |
| user-drive preview | `user_drives_preview.go:332` | the drive naming preview |

`ceilingFromProfile` takes a `ResolvedProfile`. `reintersectGovernanceGrants` runs at each step
against that step's resolved base and at the root against the deployment. `droppedPushRulesWarning`
applies to standalone profiles only, since a composed profile inherits its base's push rules.

**A guard enforces the census.** A source-scanning test fails if anything in `internal/api`
outside `governance_compose.go` calls `Store.GetGovernanceProfile`, `ListGovernanceProfiles` or
`ResolveGovernanceProfile`. The store's row type and the resolved type are distinct Go types, so
anything a refactor leaves on the raw row stops compiling instead of reading empty limits. The
census and the write door that accepts `overlay` land in the same pull request: composition is
never writable while any reader is raw.

**API.** `GET /governance` and the write responses add `base_profile_id`, `overlay` and
`overlay_limits`, plus `effective: {ceiling, limits}`. `ceiling` and `limits` stay exactly the
stored columns, which are `{}` for a composed row. These routes are security-admin only
(`mountGovernanceRoutes` is called with `securityOps`, `internal/api/routes.go:98-99`). Member-facing surfaces (`GET /policies/default`, `/me`, denial
bodies) serve the leaf DTO and the effective content, never the chain. `POST /governance/preview`
answers with the effective ceiling.

**Wire reasons.** New wire reasons go in `internal/api/reasons.go` and `docs/sdk.md` (guarded by
`TestReasonDocsMatchReasonsGo`): `governance_overlay_invalid`, `governance_profile_cycle`,
`governance_profile_depth` and `governance_overlay_unsatisfiable`. The launch-time refusal registers
`governance_overlay_unsatisfiable` in `internal/authz/registry.go` and documents it in OPERATIONS'
denial table (`TestAuthzDeniedReasonsAreDocumented`). Because the same value is used on both
surfaces, it is listed in `reason_docs_guard_test.go`'s duplicate set. **Audit.**
`governance.profile.write` (`docs/AUDIT-ACTIONS.md:301`) gains `base_profile_id` and
`overlay_fields` (the names of the overlay fields that are present, never their values). No new
action is added.

## Environment and chart

None. Composition is a data feature with no switch: a deployment that writes no composed profile
behaves exactly as today. G1 adds no variable either, because the default-size knob is P2's
(`WARDYN_SANDBOX_DEFAULT_CPU_MILLIS/_MEMORY_MIB`).

## SDK and CLI (D6)

`ApplyGovernance` creates profiles in document and name order, remaps only assignment ids
(`pkg/client/families.go:711-760`), and compares only `ceiling` and `limits`
(`pkg/client/families.go:661-663`). Applied to a composed graph from another install, that would
create a child before its base, or carry over a base UUID from the source install. The changes:

- profiles are written in topological order (bases before children);
- every graph reference (`base_profile_id`, assignment `profile_id`) is remapped through the
  name-to-id map;
- every new field is preserved and compared, and `effective` is never written back;
- under GOV4 a write may return 202. A child whose base is pending, and an assignment whose profile
  is pending, are deferred and reported, not sent with a dangling id;
- prune deletes descendants before bases.

`cmd/wardyn/governance.go` passes these results through unchanged.

## Security model and residual risks

- **Narrowing holds against enforcement.** Each meet rule is tested against the enforcer, not
  against `Leq`. The tests compile base, overlay and result with `proxy.CompilePolicy` and probe hosts
  and methods; run `composer.Clamp` against each ceiling; and read the broker's effective push
  bounds. The result must refuse whatever either side refuses. Property tests (`testing/quick`:
  narrowing, idempotence, order independence) come on top of those, not in place of them.
- **No reader sees raw authority.** This is enforced by the type split and the census guard. The
  plan-level test is a running child after its base is edited: attach/SSH, UI apps, revive, reclamp
  and end extension honour the inherited restrictions, and fail closed when the base read fails.
- **Disclosure.** Members see the leaf name and contact only. The `authz_test.go` `chi.Walk` matrix
  gains composed-profile rows, and a test asserts that a member never sees another profile's policy
  or a base's name.
- **Residual: running proxies keep their dispatched egress.** A base edit narrows a whole subtree at
  once, but as today a profile edit reaches an already-running proxy only through the denies
  re-asserted at revive or restart (`docs/AUDIT-ACTIONS.md:128`). Composition makes the blast radius
  of one edit larger. It does not change this property, and the docs say so.
- **Residual: a deployment change can strand a subtree.** A redeploy that narrows `DefaultPolicy`
  can make an overlay unsatisfiable, and launches under it are then refused with a named reason
  rather than widened. Operators see it on the profile's `effective` and in the denial stream.
- **Residual: one matcher, no independent second opinion.** Sharing the proxy's matcher removes
  drift, but a matcher bug now affects both sides alike. The oracle tests probe a fixed host corpus
  through `evalHost` to bound this.
- **Residual: `Leq` is conservative.** Some narrowing edits will still need a second approver under
  GOV4. That is the safe direction.
- Operators (`isOperator`) still resolve no profile (`internal/api/governance.go:795-798`). CADM C1
  changes that predicate, not this design.

## Upgrade and compatibility

- The migration is additive. Every existing profile is standalone and resolves byte for byte as on
  0.8.5, pinned by a golden test over the existing ceiling fixtures.
- An older SDK or CLI against 0.8.6 sees `ceiling: {}` on a composed profile and doesn't know
  `effective`. A re-apply it makes compares equal and sends nothing. A PUT it does send omits the
  composition fields, which are kept, so it can't flatten a profile. Documented in `docs/sdk.md`.
- **Rollback.** A 0.8.5 binary refuses a database with an unknown migration applied, and
  converting composed profiles to standalone first changes nothing it sees. The only way back is to
  restore the pre-upgrade dump, which holds no composed profile. The upgrade notes state this.
- G1(a) can **narrow** members whose profile omitted `resources`: they get the deployment's size
  instead of 2000m. This is the fix, and the upgrade notes call it out next to P2's new default.
