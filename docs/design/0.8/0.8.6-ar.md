# 0.8.6 design: audit retention and erasure (AR)

Status: proposed for 0.8.6. Owner decisions Q-AR1 to Q-AR5 are accepted at the recommended defaults (owner ruling 2026-10-03); each carries the
recommended default the lanes build to unless it is overridden. Every file:line below is on
`origin/main` at e0efee625 (v0.8.5).

## Why

An adopter running Wardyn under a records-retention schedule needs two things the audit log cannot do
today. The first is **retention**: delete audit history older than the schedule allows, in a way an
auditor can check afterwards. The second is **erasure**: remove a leaver's personal data on request,
without breaking the evidence that the log was never edited.

Both collide with what makes the log trustworthy. `audit_events` is append-only (0001's
`audit_events_no_update`, 0004's `audit_events_no_truncate`) and hash-chained: every row commits to the
one before it (`internal/db/migrations/0047_audit_hash_chain.sql:36-90`), the chain trigger allocates
`seq` under one advisory lock (`0056_audit_chain_serialize.sql`, `internal/db/advisory_locks.go:87-99`),
and `VerifyAuditChain` walks every row in `seq` order (`internal/store/auditchain.go:157`). A plain
`DELETE` is refused; a plain `DROP` of old rows is indistinguishable from tampering.

This design keeps the chain as the evidence and makes both operations attested:

- **Retention** drops whole monthly partitions, oldest first, through one database function that checks
  a digest the operator supplies, records a chained event and an anchor, and only then drops. Verify then
  starts from the newest anchor.
- **Erasure** encrypts each personal field under a per-person key before the row is hashed, so the row
  hash covers ciphertext. Destroying the key makes the field unreadable and leaves the chain verifiable.

## Goals and non-goals

Goals:

- monthly retention with an attested, verifiable drop, and verification that still detects an
  unattested removal anywhere in the retained history, including the newest tail;
- per-person erasure of personal audit fields, run tasks, run output, optional recordings and every
  other copy of a person's data that 0.8.6 introduces, reported complete only when every copy is gone;
- an upgrade from a populated 0.8.5 chain that never leaves the table unguarded.

Non-goals:

- **Erasing audit rows written before 0.8.6.** They hold plaintext, and the shipped chain hashes that
  plaintext. Only retention (or the legacy split, Q-AR5, plus a drop) removes them. This is disclosed.
- Zero-downtime upgrade. The conversion is a stopped-writer upgrade.
- Postgres 12. 0.8.6 requires Postgres 13 or newer.
- Removing an interior range of the chain. Only the oldest partition can be dropped.

## Decisions

Each decision names the alternative it rejects.

**D1. Partition on a new server-assigned `recorded_at`, not on `time`.** The spool replays a failed
write at-least-once and keeps the event's original `ev.Time` (`internal/store/store.go:684-688`), so
`time` can be hours older than the row's chain position. Partitions keyed on `time` would put a late row
into an old month, and dropping that month would remove an interior link. *Rejected:* partitioning on
`time`.

**D2. The database owns the append, through one function.** `now()` is the transaction start time. A
transaction that began before a month boundary can take the chain lock after one from the new month, so
a column `DEFAULT now()` produces `seq 1 / new month, seq 2 / old month`, and dropping the old month
removes an interior link. Assigning the timestamp in the existing BEFORE ROW trigger is too late,
because partition routing has already happened. So every audit insert goes through one
`SECURITY DEFINER` function, `audit_append(…)`. Under the chain lock it allocates `seq` from a standalone
`audit_events_seq` and sets `recorded_at := greatest(clock_timestamp(), <high-water recorded_at>)`, which
stays monotonic under a clock step backwards, then inserts with those explicit values. Routing therefore
happens on values decided in chain order, and **every monthly partition is a contiguous prefix of chain
order**. *Rejected:* `DEFAULT now()`; a trigger-assigned `clock_timestamp()`.

**D3. No DEFAULT partition.** Once a row lands in a DEFAULT partition of an append-only table, the
matching month can never be attached again (attach would have to move the row). Instead months are
created twelve ahead, at every boot and daily, and an insert into a missing month fails and is held by
the spool until the month exists. *Rejected:* a DEFAULT partition as a safety net.

**D4. A bounded, canonical digest, not `string_agg`.** Concatenating 64-character hashes reaches
Postgres's 1 GB field limit near 16 million rows (about six events a second over a 30-day month); such a
partition could never be dropped, and every later drop would be blocked behind it. The digest is a
streaming fold in `seq` order through a cursor, constant memory:
`d_0 = sha256(manifest_header)`, `d_i = sha256(d_{i-1} || row_hash_i)`. *Rejected:* `string_agg`,
which also returns NULL for an empty partition.

**D5. The drop is a database function that checks a digest and leaves an anchor.** Retention must leave
evidence that the removed rows were exported and accounted for. *Rejected:* a Go-side `DROP`, which a
crash could leave without its chained event or anchor; and `DELETE`, which the append-only guard refuses
by design.

**D6. The conversion commits with working guards.** The migrator commits each file on its own and runs
`ensureAuditTriggers` only after all of them (`internal/db/db.go:169-196`). A conversion split across two
files (drop guards in one, create them in the next) leaves a crash window with an unprotected table. So
the conversion migration M-A creates functioning parent and leaf guards before it commits; M-A2 is only
the replayable definition. *Rejected:* creating the guards in a later file.

**D7. A stopped-writer upgrade; no 0.8.5 compatibility.** 0.8.5 inserts directly into `audit_events`
with no `seq` or `recorded_at`. After the conversion the chain trigger refuses those rows, so a 0.8.5
writer still running would push every event to its spool. The chart is already `Recreate`
(`deploy/helm/wardyn/templates/deployment.yaml:117-136`), so the default path (Migrate at the new pod's
boot) is the stopped-writer path. *Rejected:* an online conversion that old binaries could write
through.

**D8. Postgres 13 floor.** BEFORE ROW triggers on a partitioned table, which the parent-level chain and
append-only guards rely on, exist from Postgres 13. *Rejected:* keeping 12 with per-partition-only
triggers, which would leave the parent unguarded between a partition's creation and its trigger.

**D9. Seal personal fields, per field, under per-person keys in `principal_keys`.** `data` is queried by
key in SQL, so sealing the whole object would break those queries: the mint ledger reads
`data->>'jti'` and `data->>'grant_id'` (`internal/broker/pgx.go:50-59`), device ingest reads
`data->'device_origin'` (`internal/store/store_devices.go:399-404,497-503`), and the filter uses
`data @>` (`internal/store/auditfilter.go:182-183`). Keys live in the one per-subject key table
`principal_keys(purpose='audit-seal')` that KEY's SK0 creates; there is no separate `audit_subjects`
table. Ciphertext is `kek.Seal` (AES-256-GCM, `internal/secretstore/kek/kek.go:113`), because the
adopter's cipher allowlist excludes age. *Rejected:* whole-row encryption; a second key table; age.

**D10. Seal between masking and spooling.** The recorder chain is
`DelegationRecorder → maskingRecorder → spoolingRecorder → fanoutRecorder(store, sinks)`
(`cmd/wardynd/boot_deps.go:169-200`). A new `sealingRecorder` goes between `maskingRecorder` and
`spoolingRecorder`, so the spool, the store and the row hash all see ciphertext, and nothing personal is
ever written in clear. **The SIEM sinks (file, webhook, syslog) therefore receive ciphertext for sealed
fields.** SIEM rules key on `actor`, `source_ip` and the action, which stay clear under `fields`.
*Rejected:* sealing at the store, which would leave plaintext in the spool and the sinks.

**D11. One erasure orchestrator with explicit scopes.** `erasure.Orchestrate(ctx, person, scopes)` is the
single entry point. Scopes are independent: `credentials`, `audit_personal_fields`, `run_tasks`,
`run_outputs`, `recordings`, `mask_copies`. The existing `DELETE /people/{principal}/credentials`
(`internal/api/routes.go:751`, `internal/api/credential_erase.go:49-118`) keeps meaning **credentials
only**: resetting a credential never destroys run or audit history. `POST /people/{principal}/erasure`
and SCIM purge opt into the record scopes. *Rejected:* widening the credential route.

**D12. Pre-upgrade history: ship a legacy split (Q-AR5, accepted at the recommended defaults (owner ruling 2026-10-03), recommended (b)).** All pre-0.8.6
rows land in one legacy partition `[MINVALUE, cutover)`, droppable only once the cutover itself ages past
retention. (b) ships `wardynd -audit-split-legacy` to split it into monthly, seq-contiguous ranges.
*Alternative (a):* disclose and wait.

### Tables

- **`audit_events`** becomes a range-partitioned parent on `recorded_at`, primary key
  `(seq, recorded_at)`, `recorded_at timestamptz NOT NULL DEFAULT now()` (the default is never used by an
  in-tree writer; the trigger refuses a row `audit_append` did not allocate). Partitions are
  `audit_events_legacy` and one per month.
- **`audit_partition_meta`**, one row: the cutover (`T0 + 1µs`); the **high-water mark** (`seq`,
  `recorded_at`, `row_hash` of the newest row), updated by `audit_append` under the chain lock; the
  **expected partition manifest** (each partition's name and bounds), maintained by
  `audit_ensure_partitions` and the drop; and, from ar-l1.3, the retention policy (effective days,
  pending decrease and the date it takes effect).
- **`audit_chain_anchors`**: one row per attested drop or legacy split, told apart by
  `kind text NOT NULL CHECK (kind IN ('drop','split'))`: partition name, `seq` range,
  `recorded_at` range, row count, digest, the dropped tail's last `row_hash`, actor, time, and the
  `seq` of the chained `audit.retention.partition_dropped` event. Written only inside the drop function
  (and by `-audit-split-legacy`). `REVOKE INSERT, UPDATE, DELETE, TRUNCATE` from PUBLIC and from the app
  role.

The row hash is unchanged. `audit_row_hash` (0047) does not cover `seq` or `recorded_at`; position is
bound by the `prev_hash` link. Existing rows therefore verify without rehashing, and `recorded_at` is
protected by the trigger check below rather than by the hash.

### M-A: the conversion (one transaction)

The L1.1 upgrade test runs this exact order against a 0.8.5 schema with a seeded chain.

1. **Version gate** is the separate first file (above).
2. `T0 := transaction_timestamp()`, captured in a PL/pgSQL `DO` block. `ADD COLUMN recorded_at
   timestamptz NOT NULL DEFAULT '<T0 literal>'`: a fast default, every existing row gets `T0`.
3. Move `seq` to a standalone `audit_events_seq` starting after the identity's `last_value`, then
   `DROP IDENTITY` (0001 declares `seq BIGINT GENERATED ALWAYS AS IDENTITY`,
   `0001_init.sql:60-61`).
4. Drop the three triggers, one statement each, built with
   `EXECUTE format('DROP TRIGGER %I ON %I.audit_events', <name>, <schema>)` inside a `DO` block with the
   name passed as a parameter. **The literal `TRIGGER audit_events_chain` never appears in M-A**,
   because `replayTriggerMigrations` re-executes every file containing it (`internal/db/db.go:547-612`),
   and re-running the conversion would refuse boot. M-A creates its own guards the same way.
   `CREATE OR REPLACE FUNCTION audit_events_chain()` is safe (no `TRIGGER ` precedes the name).
   `DROP CONSTRAINT audit_events_pkey`. Rename the table to `audit_events_legacy` and each of its indexes
   with a `_legacy` suffix.
5. `ALTER TABLE audit_events_legacy ADD CONSTRAINT legacy_bound CHECK (recorded_at < '<T0>' +
   interval '1 microsecond')`, so ATTACH skips its own scan. This statement validates by scanning the
   legacy table once.
6. Create the partitioned parent with PK `(seq, recorded_at)`. Create its indexes under new names,
   **never `IF NOT EXISTS`**: the equivalents of 0001's run and time indexes
   (`0001_init.sql:73-74`), 0017's `(action, seq DESC)`, 0023's `(run_id, seq)`, 0047's chain-head
   partial index (`0047_audit_hash_chain.sql:33-34`) and 0078's device-origin expression index
   (`0078_audit_events_device_origin_idx.sql:28-30`). 0047's index statement is re-run by
   `replayTriggerMigrations`, so parent index names must not collide with it, and the replay test
   asserts the parent's index set is the same before and after a replay. (The plan also named an
   "`audit.go:115` expression index": on origin/main `internal/api/audit.go:113-116` is a comment about a
   possible future `data->>'session_id'` index, not an index, so there is nothing to recreate. An index
   an operator built out of band stays on `audit_events_legacy`; the upgrade note says so.)
7. `ATTACH PARTITION audit_events_legacy FOR VALUES FROM (MINVALUE) TO (T0 + 1µs)`. Postgres builds the
   `(seq, recorded_at)` unique index on legacy: the one index build (measured 1.35 s at 3M rows, 7.3 s at
   12M).
8. **Copy `relacl` grants** from the old table to the parent.
9. Persist the cutover in `audit_partition_meta`. Create the first live partition
   `FROM (cutover) TO (next month start)`, then `audit_ensure_partitions(12)`.
10. **Install working guards before commit**: the chain trigger, the append-only row trigger on the
    parent (cloned to partitions), and a TRUNCATE trigger on the parent and on each partition, plus the
    privilege model below. M-A commits with no window in which an unchained append, a mutation or a
    truncate is possible.

`audit_ensure_partitions` always continues from the highest existing upper bound, never from
`date_trunc(now())`.

### M-A2: the replayable trigger definition

A separate idempotent file: `CREATE OR REPLACE FUNCTION audit_events_chain() …`, then
`DROP TRIGGER IF EXISTS … ; CREATE TRIGGER audit_events_chain …` on the parent, the row and TRUNCATE
triggers, and the per-partition TRUNCATE triggers. It drops any interim trigger name M-A used, so
`auditForeignTriggers` (`internal/db/db_audit_triggers.go:92`) never sees a foreign one.

The chain function does not allocate. It **verifies** the `seq` that `audit_append` allocated (one
allocator), and never calls `pg_get_serial_sequence(TG_RELID)`, which is NULL on a partition.

Guard tests: `triggerMigrationFiles("audit_events_chain")` (`db.go:589`) **excludes M-A and includes
M-A2**; `replayTriggerMigrations` on a converted database is idempotent; and the counterfactual: drop the
trigger after M-A, run `ensureAuditTriggers`, expect it restored. `internal/db/db_audit_triggers.go`
walks partitions through `pg_inherits` and handles clone triggers (`tgparentid <> 0`).

## The append protocol and privileges

`audit_append(id, time, run_id, actor_type, actor, action, target, outcome, source_ip, data)` returns
`(seq, recorded_at, prev_hash, row_hash)`. Under `AuditChainLockKey` it allocates `seq` from
`audit_events_seq`, reads the high-water `recorded_at` from `audit_partition_meta` (never from the head
row, so a stray row cannot drag the clock), sets `recorded_at := greatest(clock_timestamp(), hw)`, sets
a transaction-local setting holding the allocated `seq`, inserts with explicit values, and advances the
high-water mark.

**All five direct insert sites are converted:** `internal/store/store.go:645` (`InsertAuditEvent`),
`internal/broker/broker.go:981` (the in-transaction `credential.mint` row, `broker.go:597`),
`internal/db/db.go:250` (the boot canary: it calls `audit_append` and is still rolled back, so the
app-pool canary proves the new path), `internal/store/store_devices.go:354` (federated device rows) and
`internal/store/store_reauth.go:88`. Callers keep their bounded lock wait
(`db.AuditChainLockTimeoutSQL()`).

**The chain trigger's check is caller-independent.** It refuses a row whose `seq` differs from the
transaction-local `seq` (or when that setting is unset), whose `seq` is not above the high-water `seq`,
whose `recorded_at` exceeds `clock_timestamp()` plus a small skew, or whose `recorded_at` is below the
high-water mark. A multi-row `INSERT` is therefore refused after its first row.

**Privilege model, per deployment shape:**

- **Split role** (`WARDYN_PG_MIGRATE_DSN` set, `cmd/wardynd/boot_flags.go:353`). M-A derives the grantees
  **from the catalog**: every role holding INSERT on `audit_events` in `relacl` (via `aclexplode`) is
  granted EXECUTE on `audit_append` and the other callable functions in the same transaction, and only
  then is INSERT revoked from it. Later AR migrations grant EXECUTE to the roles that hold EXECUTE on
  `audit_append`. Functions are owned by the migrator role. The OPERATIONS recipe gains
  `ALTER DEFAULT PRIVILEGES … GRANT EXECUTE ON FUNCTIONS` and an explicit GRANT line in the upgrade note.
- **Single role** (the default, one DSN). Direct INSERT cannot be revoked from the owner. The trigger
  check is the control, and a boot posture line reports "app role can INSERT directly", beside the
  existing single-DSN notice (`cmd/wardynd/boot_deps.go:130`).
- **Boot check on the serving pool:** `has_function_privilege(current_user, 'audit_append(…)',
  'EXECUTE')` must be true, or boot refuses with a named remedy. The L1.1 upgrade test runs with a split
  role whose name is **not** `wardyn_app`.

**Default privileges cannot re-grant writes.** Right after every CREATE or ATTACH of a partition, and of
`audit_chain_anchors` and `audit_partition_meta` (in M-A and in `audit_ensure_partitions`), in the same
transaction: REVOKE ALL from every non-owner grantee in its `relacl`, then GRANT only SELECT where needed.

**Function hardening reuses 0058**, not `search_path = pg_catalog, public`
(`0058_audit_chain_schema_qualified.sql:4-103` explains why: an app-owned temporary table can shadow an
unqualified relation, and a non-`public` install resolves wrongly):

- every table, sequence, function and dynamic target is qualified with the **actual schema**, discovered
  from the catalog at apply time, and the pinned path ends with `pg_temp` last;
- partition OIDs are validated against the intended parent before any DETACH, DROP or digest;
- each function gets `REVOKE ALL ON FUNCTION … FROM PUBLIC` and `GRANT EXECUTE` to the app role in the
  same transaction;
- a boot posture line, beside `AuditDDLProtected` (`internal/db/db_audit_ddl.go:34`), reports any PUBLIC
  EXECUTE on these functions.

## Partition lifecycle

**Lock profile.** `audit_ensure_partitions()` creates each month as a standalone table, adds
`CHECK (recorded_at >= lo AND recorded_at < hi)`, hardens its privileges, then ATTACHes it. ATTACH takes
SHARE UPDATE EXCLUSIVE on the parent, and the CHECK lets it skip the validation scan. It never uses
`CREATE TABLE … PARTITION OF`, which takes ACCESS EXCLUSIVE. The drop must DETACH non-concurrently,
because a SQL function runs inside a transaction: a brief ACCESS EXCLUSIVE with no scan. Both functions
`SET lock_timeout = '5s'`; callers retry with backoff, and the audit spool absorbs inserts blocked
meanwhile.

**Keeping months ahead.** `audit_ensure_partitions(12)` runs inside Migrate at every boot, before the
listener, and daily in the leader sweeper (HA L2.3's `SweeperLeaderLockKey`; on a single replica, the one
process). Gauge `wardyn_audit_partitions_ahead`, and a `/setup/status` warning below 3 months. An insert
into a missing month fails; the spool keeps the row (with its `ev.Time`) and replays it once the
partition exists.

**Closed partitions.** A partition is closed once the high-water `recorded_at` is at or past its upper
bound: no row can route into it again (D2). Digests are computed only for closed partitions, **outside**
the chain lock; the lock is taken only for the drop.

**Digest.** `manifest_header` binds the partition name, `seq` range, `recorded_at` range and row count,
canonically encoded the way `audit_row_hash` encodes (JSON array, integer microseconds). An empty
partition's digest is `d_0`. Rows from before the chain began (NULL `row_hash`, 0047's legacy rows) fold
`audit_row_hash(NULL, …)`. Tests run past the 1 GB limit with streamed synthetic input, and cover the
empty case.

**Export.** `GET /audit/export?partition=<name>` streams the partition in `seq` order and writes the
manifest header and the digest, computed by the same fold while streaming, in its footer. It has two
forms. The **readable** export unseals what it can (erased fields read as erased). The **raw archive**
carries the stored, hash-covered ciphertext, the `seq`, `prev_hash` and `row_hash` fields and the
manifest, so an operator can recompute every row hash and the digest independently of Wardyn.
`?partition=` is honoured only for a security operator; any other session gets the same empty export
`auditScope` gives a member, and the partition is never read. `?partition=` with any other filter is
refused (`audit_export_partition_filter`), so the footer digest always covers the whole partition.

**Attested drop.** `audit_retention_drop(p_partition, p_digest, p_actor)` is `SECURITY DEFINER` and
refuses unless the partition is the **oldest** retained one, is closed, is past the effective retention
window, and holds no rows of a run that is still live (retention keeps the operational facts live runs
need: revocation reads `credential.mint` rows, `internal/broker/pgx.go:50-59`; provenance is the run's
own audit trail, read by `run_id` in `seq` order, `internal/store/pagination.go:425-429`). It recomputes the digest
and refuses on a mismatch. Then, under `AuditChainLockKey`:

1. it inserts a chained `audit.retention.partition_dropped` event (through `audit_append`);
2. it inserts the `audit_chain_anchors` row;
3. DETACH, then DROP.

**Verify.** `VerifyAuditChain` starts from the newest `kind='drop'` anchor: the first retained row's
`prev_hash` must equal the anchor's recorded tail hash. A `split` anchor is manifest evidence only: each
range it names must be present or accounted for by a later `drop` anchor. It inspects **every** retained row. A gap with no anchor still
reads "rows removed without an attested retention drop". Because the chain alone cannot see a removed
newest tail, verify also checks that the newest row matches the high-water mark in
`audit_partition_meta`, and that every partition in the expected manifest is present unless an anchor
accounts for it.

## Retention policy

- `WARDYN_AUDIT_RETENTION_DAYS`, default `0` (forever). The value is persisted at boot. An increase takes
  effect at once. A **decrease takes effect 30 days after the boot that first saw it**, and the pending
  value and its date are persisted, so restarts do not reset the cooldown. Changing `0` to any finite
  value is a decrease. The boot that records a change writes an audit row. The policy is written only
  through `SECURITY DEFINER audit_retention_set_policy(p_days)`, which computes the effect inside the
  database from `clock_timestamp()` and never resets an existing pending decrease; the app role holds no
  write privilege on `audit_partition_meta`, and `audit_retention_drop` reads the window only from it.
- `WARDYN_AUDIT_RETENTION_AUTODROP`, default false. When true, the leader sweeper drops eligible oldest
  partitions itself, as the system actor, computing the digest in the database. Documented as
  **unattested**: no operator verified an export before the drop.
- `GET /audit/retention` reports the effective and pending policy, the cutover, the partitions with
  their row counts, state and eligibility, and months ahead.
- `POST /audit/retention/drop` takes `{partition, digest}`; the operator exports first, checks the
  archive, then submits its digest.
- Who may drop (Q-AR1, accepted at the recommended defaults (owner ruling 2026-10-03)): one `security_admin` acting alone, with the 30-day cooldown on
  decreases as the brake.

## Sealing and erasure

**Mode.** `WARDYN_AUDIT_SEAL=off|fields|full`, default `off`. `fields` seals personal `data` fields.
`full` additionally stores the human `actor` as `subject:<uuid>` (ar-l1.5, flagged and off by default,
Q-AR3); it changes what SIEM rules keyed on `actor` see, and actor filters resolve through the subject
mapping.

**What is sealed.** A closed list of personal `data` keys (`internal/audit/sealkeys.go`): `task, prompt,
message, reason, comment, note, email, display_name, query, command`, finalised by auditing every emit
site. Sealing is **action- and path-aware**: the list is per action and JSON path, not by leaf name, so
machine reason codes (a `reason` carrying a refusal code) stay clear for SIEM and UI classification. The
design PR for ar-l1.4 enumerates every retained personal field per action. Not sealed: federated device
rows (their hash binds the device's own claim, `store_devices.go:497-503`); agent-actor mints; the
`actor` and `source_ip` columns (`actor` only under `full`). Whether `source_ip` is sealed is the
adopter's policy decision (Q-AR2), not an established exemption.

**Subject attribution.** Each sealed field is sealed under the subject it describes. A multi-person event
(requester and approver, actor and target person) seals each person's fields under that person's key.
Aliases (email forms, the `entra:` principal) resolve to one subject through SCIM's
`principal_identities`. A sealed value records the subject, the key version and the ciphertext; its
additional authenticated data binds the event id, action, JSON path, subject and key version, so a
ciphertext cannot be moved to another event or field.

**Keys.** Subject keys are `principal_keys(owner, purpose='audit-seal', version, domain, …)` through
SK0's `internal/secretstore/subjectkey` (generate, wrap, unwrap, a bounded 5-minute LRU that zeroises on
evict, `Destroy`). One reserved platform boot key, `wardyn-audit-pending-key`, exists only to seal
`pending_subject` spool lines. It is minted with `loadOrCreateSecret`
(`cmd/wardynd/boot_keys.go:85`) and added to the three reservation maps (`internal/api/secrets.go:45`,
`internal/broker/broker.go:849`, `internal/secretstore/secretstore.go:137`), which
`TestPlatformSecretsAreReservedEverywhere` (`cmd/wardynd/platform_secrets_test.go:109`) enforces. The
seal key source is threaded through **every** `buildAuditChain` caller: `cmd/wardynd/main.go:216`,
`rewrap.go:101`, `rekey.go:114` and `migrate_secrets.go:69`.

**Sealing failure.** If a cold subject-key lookup fails before spooling, the event is written to the
spool **sealed under `wardyn-audit-pending-key` with a `pending_subject` marker**. The drain recorder,
today the raw store recorder (`boot_deps.go:164-168`, `internal/api/auditspool.go:262-269`), becomes
`sealingRecorder{inner: storeRec}` in replay mode: for a pending line it resolves the subject key and
re-seals; on failure it returns an error, so `Drain` keeps the line rather than re-spooling it. The event
is never dropped and never written in clear.

**Reads.** Audit reads and the readable export unseal with the subject key; a destroyed key reads as
"erased". `data @>` filters do not match inside sealed fields; the docs say so.

**The orchestrator.** `erasure.Orchestrate(ctx, person, scopes)`:

- `credentials`: the credential-erase path as key-l3.2 leaves it (`eraseLocked` plus destroying the
  credential principal key); `handleErasePersonCredentials` calls `Orchestrate(ctx, person,
  {credentials})`, so one code path erases credentials;
- `audit_personal_fields`: `Destroy(owner, 'audit-seal')` for every version;
- `run_tasks`: blanks `agent_runs.task` (`0001_init.sql:13`) for the person's runs;
- `run_outputs`: calls OUT O-2's `EraseRunOutputs(ctx, runIDs)` for the person's runs (below);
- `recordings`: deletes recordings, opt-in (Q-AR4);
- `mask_copies`: calls HA L2.0's manifest erasure primitive; ha-l2.1 and ha-l2.4 extend it.

The orchestrator lives in `internal/erasure/`. The person resolves through `resolveSecretOwner`, and the
operator namespace is refused for every scope before anything runs. `scopes` must be a non-empty list of
known names (`erasure_scope_unknown`). Erasing oneself is refused for every scope except `credentials`
(`erasure_self_refused`, the principal-and-email comparison `requireSecondHuman` makes); the admin token
is allowed and audited. `person.erasure` and `credential.erase` rows are fully unsealed, so the record of
an erasure survives the key it destroys.

**Each erasure integration lands with the table it covers.** ar-l1.4 covers every table present on the
batch branch when it merges: `run_outputs` from out-o2 and `run_mask_manifest` from ha-l2.0 (W1),
both of which merge before it, so ar-l1.4 wires their erasers. A lane that adds such a table after
ar-l1.4 has merged adds its eraser to the orchestrator in the same lane: ha-l2.1 (`mask_values`),
ha-l2.4 (`run_output_chunks` and ADO run-PAT values).

**Completion fences.** Erasure is reported complete only once every copy for the requested scopes is
gone. Two durable fences make that true across replicas. Both are owned by other lanes; the
orchestrator only calls them:

- **key revocation** is key-sk0's: every cache fill and every use reads the version's durable
  `destroyed_at`, so a follower's 5-minute LRU cannot keep decrypting after `Destroy` commits, whether
  or not a notification arrives;
- the **per-run output-erasure tombstone** is out-o2's `EraseRunOutputs`, checked by output reads,
  UPSERTs and retries (and by ha-l2.4's chunk writes); local tail buffers are zeroed, and in-flight
  finalisers are fenced.

The orchestrator is idempotent: a partial failure returns an error naming the scopes not yet done, and a
retry finishes them. Callers: `POST /people/{principal}/erasure` (body names the scopes) and SCIM purge.
Both erasure and drop routes are `securityOps` in `adminRoutes`
(`internal/api/routes.go:62-70`), audited as `person.erasure` and `audit.retention.partition_dropped`.

## Upgrade and compatibility

- **Postgres 13+ required.** `deploy/helm/wardyn/README.md:94,110` change from 12+ to 13+; CHANGELOG
  carries "Postgres 13+ required". On Postgres 12 the version gate refuses and records nothing, so 0.8.5
  can be restarted unchanged.
- **The conversion is one-way.** The OPERATIONS upgrade runbook gains "take a dump first". A 0.8.5
  binary refuses the converted schema at boot (`unknownAppliedMigrations`, `internal/db/db.go:129-140`).
  Under the break-glass `WARDYN_ALLOW_UNKNOWN_MIGRATIONS` it would boot, and the chain trigger would
  refuse every one of its direct inserts, which then sit in its spool; a failure-injection test pins
  that an old binary plus the migrator never yields an unchained row.
- **Stopped writers.** With `Recreate`, Migrate at the new pod's boot is the stopped-writer path. ar-l1.0
  adds `wardynd -migrate-only` (schema only, defined exit codes, honours `WARDYN_PG_MIGRATE_DSN`), for a
  one-off Job **only after** `kubectl scale deploy/wardyn --replicas=0`. It acquires and holds the
  single-instance lock (`SingleInstanceLockKey`, `internal/db/advisory_locks.go:52`) for the whole
  migration, and also refuses while `pg_stat_activity` shows any other client backend on the database,
  because no replica holds the lock under `-allow-multi-instance` (the chart's `allowMultiReplica`) or
  `WARDYN_HA=true`; there, scaling to zero is the only pre-step that stops writers. An adopter without
  cluster access uses the default path.
- **Boot budget.** `WARDYN_MIGRATE_TIMEOUT` defaults to 5m (`cmd/wardynd/boot_flags.go:354`). The chart
  startupProbe is a literal `periodSeconds: 5`, `failureThreshold: 90` (450 s,
  `deployment.yaml:560-573`); it becomes a chart value derived from the migrate timeout plus the fixed
  30 s connect. The conversion's cost is the CHECK scan, the one index build and the lock waits; the
  upgrade notes give rows-to-seconds figures measured by the L1.1 test.
- **Exercised on Postgres 13** as well as 16 and 17.
- **Rows written before 0.8.6 stay plaintext**, so erasure cannot reach them; only retention, or the
  legacy split plus a drop, removes them.
- **SIEM payloads change** when sealing is turned on: sealed fields arrive as ciphertext.
- **Default behaviour is unchanged**: retention is forever, autodrop is off, sealing is off.

## Legacy split (ar-l1.7, if Q-AR5 = b)

`wardynd -audit-split-legacy` is a one-shot offline tool, run with writers stopped, under
`AuditChainLockKey`. It splits the legacy partition into **seq-contiguous ranges** whose boundaries are
where `time` first crosses each month **in `seq` order**. It never routes by `time`, because a
spool-replayed row's `time` can be older than its `seq`. Each range gets strictly increasing
`recorded_at` bounds below the cutover, so partitions remain contiguous prefixes of chain order.
`row_hash` is preserved (it does not cover `recorded_at`). A range's drop eligibility uses the maximum
`time` within it. The tool verifies each range's digest against the source, then swaps out the legacy
partition and writes a `kind='split'` anchor listing the ranges. It takes the same stopped-writer guards
as `-migrate-only` and runs only on the migrator DSN, since the app role cannot write anchors or
DETACH/ATTACH.

## Security model and residual risks

What this protects: no caller chooses a row's position, timestamp or hash; retention removes only a
whole oldest prefix, with a chained event, an anchor and a digest the operator could check; a removed
interior range, a removed newest tail or a missing partition fails verify; a destroyed subject key
leaves sealed fields unreadable everywhere they were copied (store, spool, sinks, exports) while the
chain still verifies.

Residual risks, disclosed:

- **A database owner can still rewrite history.** In single-role mode the app role owns the table and
  can drop triggers (already disclosed, `boot_deps.go:130`); it can also set the transaction-local
  allocation setting itself, so the trigger check binds out-of-tree and mistaken writers, not a hostile
  owner. An owner who edits both the tail and the high-water mark is caught only by the head hash already
  shipped off-box to a SIEM (0047's design).
- **Crypto-erasure is complete only after backups expire** or the wrapping key version is retired, the
  same horizon as threat-model residual 48 (`threatmodel/THREAT-MODEL.md:2062-2085`).
- **Pre-0.8.6 rows are plaintext.**
- **A compromised wardynd process** can read every subject key it can unwrap.
- **Autodrop is unattested.**
- **`source_ip` and, under `fields`, `actor` stay clear** unless the adopter chooses otherwise.
- **Spool loss.** A spool on an emptyDir is lost with its node (disclosed under HA).

## Verification

Every PG lane starts its own throwaway Postgres container and asserts the suite ran rather than
skipped. Upgrade tests run on Postgres 13 and on 16/17.

- **Upgrade:** from a 0.8.5 schema with a seeded chain, the conversion passes: verify OK, grants copied,
  `seq` continues, `pg_indexes` present on the parent and on a fresh partition; total conversion time
  measured.
- **Append protocol:** interleaved spool replay, delayed transactions across a month boundary,
  multi-row inserts and repeated drops all keep every partition a contiguous chain prefix; verify
  inspects every retained row.
- **Guards:** a forged `recorded_at` is refused; a partition TRUNCATE is refused; failure injected after
  M-A and during M-A2 leaves, seen from a second connection, no possible unchained append, mutation or
  truncate; an old binary plus the migrator writes no unchained row.
- **Privileges:** a CONNECT-only role gets `permission denied for function`; temp-table shadowing of the
  anchor, meta and audit tables fails; a non-`public` schema install works; under the documented
  `ALTER DEFAULT PRIVILEGES`, a new partition gives the app role no INSERT, UPDATE or DELETE.
- **Drop:** a bad-digest drop and a non-oldest drop are refused; an attested drop verifies from its
  anchor; a manual DROP fails verify; a removed newest tail fails verify.
- **Digest:** past the 1 GB limit with streamed input; the empty partition is `d_0`.
- **Triggers:** drop the chain trigger, reboot, it is restored; the replay is idempotent on a converted
  database.
- **Erasure:** after a shred, verify still passes and the export shows erased; after erasure the
  person's `run_outputs` 404; a cold seal failure, then the store returns, then the drain re-seals, then
  after erasure the event shows erased; a warm follower cache, a lost notification, a Postgres outage,
  blocked writers and finalisers and restarts all leave the export erased and the output 404.
- **Credential route:** `DELETE /people/{principal}/credentials` still erases credentials only.
