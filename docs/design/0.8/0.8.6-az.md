# Wardyn 0.8.6 — Azure Foundry provider with per-person Entra sign-in

An adopter that runs its model traffic through Azure wants each person's runs to reach an Azure
Foundry deployment under that person's own Entra identity, not under a resource key the whole
organisation shares. This design adds a model-provider kind, `azure_foundry`, whose credential is a
per-person Entra sign-in captured for exactly one resource audience, injected by the proxy, and
spendable only on a closed set of inference routes for a pinned set of deployments. It also fixes
today's `codex-cli` wiring (row CX0), which the Azure lane builds on and which is broken on 0.8.5
for every provider.

All file:line references are to `origin/main` at `e0efee625` (v0.8.5).

### Terms used in this record

- **Messages harness.** The harness-catalog entry for the Anthropic-dialect command-line tool, whose
  image pins version 2.1.231 (`deploy/images/<messages-harness>/Dockerfile:182`). Its catalog id is
  written `<messages-harness>`, and its environment prefix `<MESSAGES_HARNESS>` (the id upper-cased,
  `-` as `_`).
- **Responses harness.** `codex-cli`, pinned at codex 0.149.1 (`deploy/images/codex-cli/Dockerfile:152`).
- **Foundry host.** The `azure.com` subdomain that Microsoft Learn names as the Foundry resource
  audience. It is written `<foundry-host>` below; the literal comes from the A0 record and lives in
  code.
- **Foundry audience** is `https://<foundry-host>/.default`; the **Cognitive Services audience** is
  `https://cognitiveservices.azure.com/.default`.

## Goals and scope

- A new provider kind, `azure_foundry`, configured in site config. One provider row serves one
  route and one audience.
- A per-person Entra sign-in per row, captured through the console's existing Entra login
  application, stored sealed under the person's namespace, and redeemed by the proxy at run time.
  No key or token enters the sandbox.
- A proxy route gate that admits only the inference calls the row's harness needs, for the row's
  pinned deployments, and refuses everything else **before** the token is attached, on all three
  proxy doors.
- The sandbox wiring for both harnesses: the Messages harness against Foundry's `/anthropic` route,
  the Responses harness against Azure OpenAI v1 (`/openai/v1`).
- **CX0:** the Responses harness on 0.8.5 is pointed at its route by variables codex 0.149.1 never
  reads. This is fixed for every provider in W0, and the Azure wiring reuses the same helper.

### What this is not

- Not a key-based Azure kind. A resource key already works through `custom_endpoint`; that key is
  resource-wide, which is the problem this design solves.
- No on-behalf-of exchange. Wardyn keeps no login tokens, so there is nothing to exchange.
- No sovereign clouds (Azure Government, Azure China) in 0.8.6 (Q-AZ, accepted at the recommended defaults (owner ruling 2026-10-03)).
- No multi-audience refresh tokens. A person never holds a token for a resource their row does not
  use.
- No inspection of the OpenAI Responses body. `/openai/v1/responses` stays an honest
  `uninspected_channel`, exactly as `api.openai.com` is today.
- No WebSocket transport for the Responses harness. It is refused by design and the harness falls
  back to HTTP.
- The Messages harness is never wired to an OpenAI-family deployment, and the Responses harness is
  never wired to the `/anthropic` route. Both pairings are refused with a sentence.

## Decisions

**D1. A new kind, `azure_foundry`, in site config; no migration.** `ModelProvider` gains `Azure
*AzureSettings{Endpoint, Route}`, the sibling of `Bedrock`. The deployment name is the existing
`ProviderHarness.Model`, required for this kind as it is for Bedrock. `ProviderHarness` gains one
optional field, `FastModel`, used by the Messages harness only. Rejected: re-using `custom_endpoint`
with an Entra auth mode, which would put identity semantics on a kind whose contract is "the admin's
endpoint, the person's own token", and would give the route gate no route to pin.

**D2. One row, one route, one audience.** `Route ∈ {anthropic, openai_v1}`. A deployment that serves
both harnesses configures two rows. Rejected: one row serving both routes, which needs a refresh
token spanning two resources or two captures per row, and would put a token for a resource on
people whose runs never use it.

**D3. A closed, dot-anchored host suffix list.** `openai.azure.com`, `services.<foundry-host>` and
`cognitiveservices.azure.com`, matched as `host == s || strings.HasSuffix(host, "."+s)`. Sovereign
clouds are deferred (Q-AZ). Rejected: any HTTPS host, which would let an admin typo or a hostile
config point a person's Entra token at a host that is not Azure; and an unanchored suffix match,
which admits `evilopenai.azure.com.attacker.example`-shaped hosts.

**D4. The app identity is the console's Entra login application.** `azure_foundry` rows always sign
in through `LoginClientID`/`LoginTenantID` and its secret (`internal/api/ado_entra.go:165-170`).
There is no per-row tenant or client, so a deployment without Entra console login cannot use the
kind, and the validator says so. The admin prerequisite is to grant that application the delegated
permission for the row's audience resource, with admin consent. Rejected: per-row app
registrations, which multiply client secrets for no gain in narrowing.

**D5. Generalise the Azure DevOps capture rather than fork it.** A1 turns `ado_entra.go`,
`ado_entra_login.go` and `ado_entra_store.go` into a generic `entraCapture{kind, scopes, secretName,
donePath, rowUID}` with a per-kind scope policy. Azure DevOps behaviour stays byte-identical,
including its `/.default` refusal, now expressed as that kind's policy. Rejected: a copy of the
capture for Azure, which doubles the state-cookie, refresh and single-flight code that already
took several releases to get right.

**D6. The console-login door stays Azure DevOps only.** `LoginScopes`, `CaptureLoginGrant` and
`adoEntraForLogin` are never widened for `azure_foundry`. Entra refuses a login request whose scopes
name two resources (AADSTS700022), so mixing an Azure audience into the login would break every
sign-in. `azure_foundry` is captured only by its own per-row door, which requests `<resource>/.default
offline_access openid` and nothing else. Rejected: piggy-backing the login, as Azure DevOps does.

**D7. For `azure_foundry` the ceiling is a resource, not a scope literal.** Entra answers a
`<resource>/.default` request with the delegated permissions it expands to (for the Foundry audience,
`https://<foundry-host>/user_impersonation`), never with the `.default` string. So the per-kind policy
owns three things: the request (`<resource>/.default offline_access openid`); the capture (store the
`resp.Scope` entries prefixed `<resource>/`; none means `unusable_grant`); and the consent check at
redemption (pass when the blob holds at least one scope under `<resource>/`; redeem `<resource>/.default`).
Azure DevOps keeps its exact-literal intersect. Exact scope normalisation follows the A0 evidence.
Rejected: storing the literal `.default`, which no real authority returns, so every redemption would
fail its consent check.

**D8. Keyed by row uid, under one redirect URI.** The sign-in start route takes the row uid, stores
it in the one-time state cookie beside the random state, and the callback resolves the row from the
cookie, never from the query. The credential is `wardyn-provider-<uid>-entra`. Rejected: a callback
path per row, which needs an app-registration edit for every new row; and a uid in the callback
query, which a crafted link could swap.

**D9. The audience rides the dispatch snapshot.** The injection snapshot carries `{OwnerSubject,
ProviderUID, Audience}`, and `injection_azure.go` redeems that audience. The proxy injector stays
host-keyed. Rejected: re-deriving the audience at redemption from the current row, which lets a row
edit between dispatch and refresh change what a running sandbox's token can reach.

**D10. Activation is gated on the route gate.** A2's validator refuses the `azure_foundry` kind
until A5's gate is merged, through one package-level `var`, `azureFoundryGateReady`, whose literal
A5 flips. A3 is stacked on A5. No tree on `main` can therefore write an Azure row, let alone dispatch one, without
the gate. The validator is the boundary because site-config provider writes stay available through
the API whatever the console shows. Rejected: relying on the console editor (A4, W4) to hide the
kind, which is not a security boundary; and landing A2/A3 before A5 with a "do not use" note, which
leaves an intermediate tree where a resource-wide Entra token rides the host-only injector to every
path on the host.

**D11. The Azure host is a channel host, never an `LLMUpstreams` entry.** `LLMUpstreams` also feeds
`llmUpstreams`, so registering Azure there would make the brokered `/wardyn/llm/*` route forward
origin-form sandbox requests to Azure with the person's token and no path or model gate. A new
per-run carrier, `ProxyConfig.LLMChannelHosts {host: vendor}`, compiles into its own proxy map,
`channelHosts`, consulted by `isLLMHost` and `channelForHost` beside `gatewayVendor`. It never feeds
`gatewayVendor` (which enrols hosts in the relaxed-vet set) or `llmUpstreams`. The brokered route
keeps dialing the public vendor host, where this run holds no credential. Rejected: the
`LLMUpstreams` path, for the reason above.

**D12. A route gate, not a body-field check.** The Azure data plane chooses the deployment from the
URL path (`/openai/deployments/{id}/…`) and also serves files, fine-tuning and images. So the gate
is a method-and-path allowlist per row, then a deployment-identity check, then fail-closed body
handling, enforced on the MITM lane, the plain absolute-form lane and the brokered route. Rejected:
checking only the body's `model`, which a path-addressed deployment or a non-inference API bypasses.

**D13. The `InjectionRule` pin grows to a method-and-path set.** `allowsInjection` then withholds
the token on every other request on both the MITM lane and the plain forward lane. The AWS SSO rule
still pins GET only. Rejected: an Azure-only branch inside the injector, which would leave the
plain lane relying on a second, separate check.

**D14. A dedicated inference-body cap with an aggregate budget charged before the read.** 32 MiB for
`/anthropic` (the vendor maximum) and the Azure OpenAI v1 limit as A0 records it, never
`adoscope.MaxBodyPeek`. A per-proxy 128 MiB weighted semaphore, a sibling of `scanRetained`, is
acquired before the body is read. The budget fits the existing proxy memory default, or Azure runs
alone get a per-run override; the deployment-wide default is never raised for it. Rejected: the 256 KiB REST peek, which refuses ordinary prompts;
and charging after the read, which lets sandbox-controlled chunked bodies pin memory before the
budget sees them.

**D15. The codex base URL and auth go through config the harness actually reads (CX0).** Dispatch
sets `WARDYN_CODEX_BASE_URL` and `CODEX_API_KEY=wardyn-proxy-injected`; one shared prep helper in the
image writes `openai_base_url` (and, for Azure, `model`) into the user-layer config.toml and runs
`codex login --with-api-key` with the sentinel for the interactive tool. Rejected: continuing to set
`OPENAI_BASE_URL`, which codex 0.149.1 ignores; and project-local config, which codex's loader
denylist forbids for `openai_base_url`.

## CX0: today's codex wiring (W0)

**Base URL.** Dispatch sets `WARDYN_CODEX_BASE_URL` to the brokered route plus the path the final
upstream needs. For the public OpenAI upstream that is `<proxy>/wardyn/llm/openai/v1`: codex appends
`responses`, the proxy strips `/wardyn/llm/openai`, and the upstream receives `v1/responses`
(`internal/egress/proxy/openai_bare_path_test.go:42`). When a configured gateway (`LLMUpstreams`)
already contributes its own path prefix (`llm_routes.go:62-70,179`, `egress_target.go:294`), no
extra `/v1` is added. Copying today's URL unchanged would send `api.openai.com/responses`, a 404
behind an allow-shaped decision-log row.

**Auth.** Dispatch sets `CODEX_API_KEY=wardyn-proxy-injected` for task mode. For the interactive
tool, prep runs `printf '%s' "$CODEX_API_KEY" | codex login --with-api-key`, so `auth.json` holds
only the inert sentinel. The proxy replaces it on the wire, as today.

**The shared prep helper.** One function in the codex image, run by both task mode
(`agent-run:283-296`) and `--idle` (`:150-154`) before `prep-done` (`:167`):

- `cfg_dir="${CODEX_HOME:-$HOME/.codex}"; mkdir -p "$cfg_dir"` (`CODEX_HOME` is unset in the image,
  and `set -u` is on).
- Each key is written only when its variable is non-empty (`[[ -n "${VAR:-}" ]]`).
- For each key the helper writes, and only for that key, the existing top-level line is deleted and
  the new one inserted **before the first `[` table**, because codex writes `[projects."<path>"]`
  tables into the same file and a revive must not duplicate keys. `model =` is touched only when
  `WARDYN_CODEX_MODEL` is non-empty (A3); a run without it keeps the person's own `model =`, which
  codex 0.149.1 persists from its model picker.
- With neither variable set, config.toml and `auth.json` are untouched.

The 0.8.5 variables `OPENAI_BASE_URL` and `OPENAI_API_KEY` stay set, inert for 0.149.1, so an
operator image carrying an older codex keeps its behaviour. The comments at
`deploy/images/codex-cli/Dockerfile:15-27` and `agent-run:40-43` are corrected.
`runs_dispatch_provider_test.go:197` asserts the new variable, and `docs/ENV.md` gains a
`WARDYN_CODEX_BASE_URL` row beside `WARDYN_SEED_AUTO_TOOLS` (`:442`).

## The provider kind (A2)

- `types.ModelProviderAzureFoundry = "azure_foundry"`; `AzureSettings{Endpoint, Route}` on
  `ModelProvider.Azure`; optional `ProviderHarness.FastModel`.
- `validateModelProviders` gains `validateProviderAzure`:
  - refuses the kind while `azureFoundryGateReady` is false (D10);
  - `Endpoint` is `https://<host>` with a host in the closed suffix list (D3): no path (a trailing
    `/` is trimmed), no port, no userinfo, query or fragment; the host is lower-cased in
    `normalizeModelProviders` (`internal/api/model_providers.go:145-158`) and refused with a
    trailing dot;
  - `Route` is one of the two values;
  - harness compatibility: the Messages harness only on `anthropic`, the Responses harness only on
    `openai_v1`, each other pairing refused with a sentence naming the right route;
  - `ProviderHarness.Model` is required; `FastModel` only on the Messages harness;
  - Entra console login must be configured (D4), and the refusal names the admin prerequisite.
    `validateModelProviders` gains that configuration (client and tenant set or not) and an
    injected resolver as inputs, passed from both write doors;
  - `Bedrock`, `BaseURL` and `Auth` are refused on this kind, as `Azure` is on every other.
- **Purge trigger.** `providerAddressChanged` and `providerAddressDigest`
  (`internal/api/model_providers_api.go:223,243`) gain `Azure.Endpoint` and `Azure.Route`, so an
  endpoint or route change purges every person's `-entra` blob; a `Model`/`FastModel` change is not an
  address change.
- **Private endpoints.** The validator returns an advisory, not an error, only when the endpoint host
  resolves to a private address and no `InternalHosts` entry covers it: a `model_provider_warnings`
  field on both write responses, modelled on `dangling_secret_refs` (`site_config.go:930,948`), and
  printed by `wardyn site-config set`. It does not warn on `NoProxy`. The row's help text
  documents the two separate knobs: `InternalHosts` lifts the private-IP SSRF guard
  (`internal/types/site_config.go:63-72`); `UpstreamProxyNoProxy` matters only when a corporate
  proxy is configured (`:33-42`).

## Sign-in and storage (A1)

- **Generic capture.** `entraCapture{kind, scopes, secretName, donePath, rowUID}`, with a per-kind
  scope policy:
  - **Azure DevOps** refuses any `/.default` (today's `adoEntraCheckRequestedScopes`), enforced at
    validation, login-request parsing and every redemption, and keeps its exact-literal intersect.
  - **`azure_foundry`** admits exactly the one audience literal its row's route names, plus
    `offline_access openid`, and refuses every other `/.default`. Its ceiling is the resource (D7).
- **Per-route audience table.** Filled from the A0 record, not fixed in this design. Microsoft
  Learn's Foundry pages give the Foundry audience for `/anthropic` and the Cognitive Services
  audience for `/openai/v1`; a newer lifecycle page shows the Foundry audience for `/openai/v1` too.
  A0 tests both audiences on both routes; if one audience serves both, the narrower one is used.
- **Per-row door.** A sign-in start route that takes the row uid, and one shared callback that
  resolves the row from the state cookie (D8). The cookie is HttpOnly but unsigned, and the row can
  change between start and callback, so start stamps `rowUID`, the route-derived audience literal and
  `providerAddressDigest(row)` beside the random state, and the callback re-reads the row by uid from
  the current site config under `siteConfigMu` and refuses (audit `failure`, nothing stored) unless
  the row exists, is `azure_foundry`, and its digest and audience equal the stamped values, as the
  provider sign-ins already do (`internal/api/provider_signin.go:67,127,354`). Redemption refuses a
  snapshot `Audience` that is not one of the two closed audience literals. The redemption single-flight keeps the owner-and-row key of
  `internal/api/ado_entra_store.go:335-344`; ha-l2.2 later promotes it to a cross-replica lock.
- **The secret name is sealed and enumerated.** `providerEntraPart = "entra"` joins both
  `providerSignInSecret` (sealed beside `-oauth` and `-sso`) and `providerSecretParts`.
  `providerCredentialName` gets an `azure_foundry` arm. Purge on endpoint or route change (A2 extends
  the comparator), row deletion,
  `connectedPeople` and the credential inventory therefore all see the blob. Because the name is
  sealed, `sinkReservedSecret` (`internal/api/secrets.go:116`), `reservedBrokerSecret`
  (`internal/broker/broker.go:871`) and the secrets API all refuse writes to it.
- **The kind constant lands in A1, outside the closed set.** Capture, purge and inventory need to
  name the kind before A2 makes it writable; it joins `ClosedModelProviderKinds` in A2, and A2's
  validator refuses it until A5.
- **test/entrafake** gains `.default` expansion: a `<resource>/.default` request is consented iff
  the fixture holds a scope under `<resource>/`, and the response `scope` lists those scopes, never
  the literal. It also refuses a scope string naming two resources with AADSTS700022.
- **Audit.** A capture writes one audit row (success or failure, `owner`, `provider`, `source`; never
  a token), modelled on `ado.signin.capture`, and the lane names and documents it in
  `docs/AUDIT-ACTIONS.md`. Azure DevOps keeps `ado.signin.capture` unchanged.

## Dispatch and the sandbox (A3)

**The snapshot and the injector.** Dispatch authors an injection grant for the row's endpoint host with `snapshot{OwnerSubject, ProviderUID, Audience}`. `injection_azure.go` (modelled on
`injection_awssso.go` and `injection_ado.go`) resolves it: snapshot equality and a host pin, as
`adoResolveHostPinRefusal` does (`internal/api/injection_ado.go:56,241`); a 423 hold on
`invalid_grant` or `interaction_required`, through the existing mid-run reauth path
(`credential.reauth.request`); and refresh before expiry. The proxy replaces `Authorization` with
`Bearer <token>` and strips any sandbox `api-key` or `x-api-key` header on the pinned host
(`stripSandboxCredentials`).

**Conditional Access.** The supported policies are named in the docs from the A0 evidence (a
refresh from the control-plane address is part of A0). An unsupported challenge gives an actionable
failure that says which policy class blocked the refresh; generic continuous-access-evaluation
support is not promised.

**The Messages harness** gets:

- `<MESSAGES_HARNESS>_USE_FOUNDRY=1`, the harness's own Foundry switch;
- `ANTHROPIC_FOUNDRY_BASE_URL=<endpoint>/anthropic`;
- `ANTHROPIC_FOUNDRY_AUTH_TOKEN=wardyn-proxy-injected`;
- `ANTHROPIC_MODEL=<deployment>`, `ANTHROPIC_DEFAULT_OPUS_MODEL` and `ANTHROPIC_DEFAULT_SONNET_MODEL`
  set to the deployment, and `ANTHROPIC_DEFAULT_HAIKU_MODEL` set to `FastModel`, or the deployment
  when unset. Every alias the harness emits then resolves inside A5's pinned set; A0 records the
  aliases it observed.

It does **not** take the existing `ANTHROPIC_API_KEY` arm (`runs_dispatch_provider.go:442-446`):
without a Foundry token variable the harness falls back to the Azure SDK default credential chain,
which fails closed in the sandbox.

**The Responses harness** gets `WARDYN_CODEX_BASE_URL=<endpoint>/openai/v1`,
`WARDYN_CODEX_MODEL=<ProviderHarness.Model>` and `CODEX_API_KEY=wardyn-proxy-injected`, through CX0's
helper and write semantics. Project-local config cannot override `openai_base_url` (codex's loader
denylist). As belt and braces, `-m` is passed at the two argv sites only when set:
`if [[ -n "${WARDYN_CODEX_MODEL:-}" ]]; then seed_argv+=(-m "$WARDYN_CODEX_MODEL"); fi` at
`agent-run:240`, and the same guarded array at the exec site (`:340`). Every non-Azure codex run is
therefore unchanged, and only the bare first-attach `codex` relies on config.toml. The docs say
plainly that a repo config or the interactive model picker can still change the body's model, and
the route gate then refuses it.

**The per-run CA.** The Azure lane is a CA consumer: the condition at `runs_dispatch_llm.go:459`
gains `azureInject`. Like `authorADOEntraInjection`, authoring refuses dispatch with
`no_run_certificate_authority` when the CA is absent.

**Egress and MITM.** Dispatch appends the endpoint host (bare host, port 443) to the run's exact
egress allowlist **and** to `ProxyConfig.MITMHosts`, as a fourth producer at `runs_dispatch.go:484`,
modelled on `adoEntraLane.mitmHosts`. Without the MITM entry the CONNECT would be a blind tunnel and
nothing could be gated. `TestDispatch_RedirectMITMHostsCarryNoDuplicateBareHost`
(`internal/api/dispatch_redirect_proxy_boot_test.go:145`) is extended.

**Inspection.** Dispatch authors `ProxyConfig.LLMChannelHosts` (D11) and `ProxyConfig.AzureGates`
(below). Inspection then covers `/anthropic/v1/messages` (scan summary). `/openai/v1/responses`
stays `uninspected_channel`, and fail-closed inspection refuses it. Parser and scanner peak memory
are sized together with the body budget (D14).

## The proxy route gate (A5)

**Carrier.** `ProxyConfig.AzureGates []AzureGateConfig{Host, Route, Models []string, BodyCap int64}`,
authored by dispatch beside `ADOGrant` (`runs_dispatch.go:505`) and consumed by `isAzureLane(host)`,
modelled on `isADOLane`. The `InjectionRule` carries only the method-and-path set.

**Rule level, both lanes.** The `InjectionRule` pin grows from "a GET of `PinPath`" to a
method-and-path set, so `allowsInjection` withholds the token on every other request, on the MITM
lane and on the plain absolute-form forward lane (`servePlain`/`handlePlain`). The change lands in
the strict scope decoder (`runs_scm.go:377-401`); the AWS SSO rule still pins GET only
(`runs_dispatch_sso_inject.go:226-234`).

**Plain lane.** Any absolute-form request to an `azure_foundry` host is refused with
`azure_route_refused` (model: `refuseADOPlain`), and so is a CONNECT the proxy will not terminate
(`refuseADOTunnel`'s equivalent). Azure traffic flows only through the terminated tunnel.

**MITM lane.** The gate runs before injection (the `gateADO` slot, `mitm.go:374`, before `:426`):

1. **Method-and-path allowlist per row.**
   - Messages harness: `POST /anthropic/v1/messages`, `POST /anthropic/v1/messages/count_tokens`.
   - Responses harness: `POST /openai/v1/responses` and `POST /openai/v1/responses/compact` (remote
     compaction is on by default in codex 0.149.1), plus whatever A0 observes; each addition is
     listed in the lane.
   - WebSocket is never allowlisted. codex 0.149.1 tries Responses-over-WebSocket first: a `GET` with
     `Upgrade: websocket` on `/openai/v1/responses` is refused with `azure_route_refused` and no
     token, and codex falls back to HTTP. A0 records the fallback and whether a user-layer
     `supports_websockets = false` is honoured, which would avoid the refused first request.
   - The method and the full decoded path match exactly (no prefix match). Before matching, a path
     containing `..`, `//`, `\`, `;`, a `%` in the raw path, or a control character is refused with
     `azure_route_refused`, following `adoCheck` (`ado_gate.go`). The query string is ignored for
     matching.
   - Every other path on the host is refused with `azure_route_refused`, before injection, so a
     refused request never carries the token.
2. **Deployment identity, in depth.** A path segment after `/openai/deployments/` outside the pinned
   set (main plus `FastModel`) is refused even if a later allowlist edit admits such a path; this
   step never admits a path step 1 refuses. The JSON body's top-level `model` must be in the pinned
   set, decoded with `walkUnique`, so two `model` keys are refused.
3. **Fail closed** on a missing `model`, an unparseable body, a body over the cap, or a non-identity
   `Content-Encoding`. The body is buffered and replayed like `adoPeekBody`, with a chunked or absent
   `Content-Length` bounded by a `LimitReader`.
4. **Aggregate bound, charged before the read.** The 128 MiB weighted semaphore is acquired by
   `Content-Length` when present and within the cap (above the cap is refused unread), otherwise by
   the full cap, with the over-charge released once the real size is known. When it is exhausted the
   gate answers 503 `azure_inflight_budget` rather than queueing on sandbox-controlled input, and
   releases after the upstream round trip.
5. `RequireTLS=true` on the rule.

**The brokered route.** `proxyLLMRequest` honours `allowsInjection` (withhold and strip) like the
other two lanes. Because the Azure host is never an `LLMUpstreams` entry, `/wardyn/llm/*` on an
Azure run dials the public vendor host, where the run holds no credential, and answers 404
`no_llm_credential`.

**Decision log.** The gate's allow and refusal rows get their own `rule_source` pair, modelled on
`brokered:ado` and `brokered:ado:denied` (`docs/AUDIT-ACTIONS.md:357`), documented in the
`rule_source` table that `cmd/wardynd/audit_actions_doc_guard_test.go:686` checks.

**File size.** `internal/egress/proxy/proxy.go` is exactly 1000 lines, the
`scripts/check-file-size.sh` threshold, so `channelHosts`, the gate and the budget go in new files.

  stays at the p-p2 default.

## Security model

- **What the token can reach.** A person's Azure token is scoped to one resource audience
  (D2, D7), and the resource is resource-wide inside it. The route gate is therefore the boundary:
  only the listed inference calls, for the pinned deployments, on a host in the closed list, through
  the terminated tunnel. Every refusal happens before injection, on every door.
- **Where the token lives.** Sealed in the person's namespace; redeemed by the control plane on the
  proxy's request; held in proxy memory; never in the sandbox env, config or files. The sandbox holds
  only the sentinel `wardyn-proxy-injected`.
- **What the sandbox can try.** Another path, deployment, body `model`, encoding, transport
  (WebSocket, plain absolute-form, unterminated CONNECT) or the brokered route: each is refused
  without the token. A huge or slow body is bounded per request and in aggregate before the read.
- **Activation.** Unreachable until the gate exists (D10).

### Residual risks

- Inside the pinned deployments the token is resource-wide: any inference the allowlist admits is
  admitted for any prompt. The gate narrows the API surface, not the content.
- `/openai/v1/responses` is uninspected, as `api.openai.com` is today. A deployment that requires
  inspection must refuse it (fail-closed inspection does).
- A repo config or the interactive model picker can change the requested model. The gate refuses it,
  so the run fails rather than escapes; the docs say so.
- The audience table rests on the A0 record. If Microsoft changes which audience a route accepts,
  sign-ins fail closed until the table is updated.
- Conditional Access policies outside the named set fail with an actionable message, not silently.
- The first WebSocket attempt of each Responses session is refused and logged by design.
- Until ha-l2.2 lands, the redemption single-flight is per process, as Azure DevOps' is today.

## Upgrade and compatibility

- No migration and no default change. Existing provider rows, including a `custom_endpoint` pointed
  at Azure with a resource key, are untouched.
- CX0 changes every codex run's wiring: it adds `WARDYN_CODEX_BASE_URL` and `CODEX_API_KEY` and a
  config.toml write. Runs that were silently skipping the brokered route on 0.8.5 start using it. An
  operator image with an older codex still sees `OPENAI_BASE_URL`.
- Azure DevOps sign-in behaviour is byte-identical, pinned by its existing tests plus A1's.
- The kind cannot be written on any tree before A5 merges.
