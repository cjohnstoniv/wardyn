# Wardyn 0.8.6 — shared masking registry and supported multiple replicas

Wardyn runs one `wardynd` per database today, and the pin is a safety control rather than a
preference. The secret-masking registry is an in-process map that fails open, so a second
replica, or a single replica that restarts mid-run, can persist a session recording with live
credentials in it and audit the upload as a `success`. An adopter running Wardyn on a shared,
regulated Kubernetes platform asked for node-failure tolerance. This record designs the way
there: an immutable per-run masking manifest that makes a registry miss fail closed, a
Postgres-backed registry every replica reads, cross-replica locks for the work that must not
run twice, one elected leader for the sweepers, the remaining live state moved into Postgres,
and a chart that renders more than one replica only when all of that is in place.

It is one of the fifteen 0.8.6 design records. The work is tracked under the epic
"[Epic] 0.8.6: Shared masking registry and supported multi-replica" as six task issues,
`ha-l2.0` to `ha-l2.5`. Every file and line reference below is to `origin/main` at
`e0efee625` (v0.8.5).

## Where we are

**The registry is process-local and fails open.** `secretmask.Registry` holds per-run values in
`perRun` and owner-keyed globals in `current`/`retired`, all in memory
(`internal/secretmask/secretmask.go:38-65`). Values are registered by whichever request mints or
injects them: dispatch's workspace and inspection secrets (`internal/api/runs_dispatch_secrets.go:99,197`),
the Azure DevOps run token in its three renderings (`internal/api/runs_dispatch_ado_pat.go:178-180`),
and the AWS SSO and Azure DevOps sign-in tokens as per-owner globals
(`internal/api/awssso_refresh.go:528`, `internal/api/ado_entra.go:650,708`). The recording
upload masks through `buildMaskingBody` (`internal/api/recording.go:140,190`) and the live
attach cast and exec tail through `liveMaskWriter` (`internal/api/attach.go:747`,
`internal/api/run_output.go:111`). With an empty snapshot both pass bytes through unchanged. The
threat model states this residual, including the single-replica restart case
(`threatmodel/THREAT-MODEL.md:343-357`).

**The pin has two halves.** The chart refuses `replicas > 1` unless `allowMultiReplica` is set
(`deploy/helm/wardyn/templates/deployment.yaml:81-82`, `values.yaml:51`). wardynd takes the
single-instance advisory lock at boot and refuses to start when another instance holds it,
unless `-allow-multi-instance` is passed (`cmd/wardynd/single_instance.go:29-56`, passed by the
chart at `deployment.yaml:198-209`). The strategy is `Recreate` for the same reason
(`deployment.yaml:117-136`). OPERATIONS.md "One replica, by construction" lists the state that
is still per-process (`docs/OPERATIONS.md:6012`).

**Six things are already Postgres-backed**: attach tickets, compose results, the lifecycle
reaper's tick lock, run watcher leases, `pg` session recordings, and the ground-truth token
rotator's leader lock (same section). The terminal-sandbox sweep is tick-locked
(`internal/db/advisory_locks.go:73-85`).

## Goals

- A secret that reached a run is masked in every artefact Wardyn persists or relays for that
  run, whichever replica serves the request and whether or not any replica restarted.
- When Wardyn cannot prove that, it refuses the door instead of passing bytes through.
- Two or more replicas on Kubernetes tolerate the loss of a node, with every background job
  that must run once running once, and every refresh of a rotating credential spending the
  credential once.
- Erasure and key custody reach every new persisted copy of a secret.

### What this is not

- **Not zero-downtime upgrades.** The strategy stays `Recreate`. HA here means tolerating a
  node failure, not rolling a new version under live traffic.
- **Not a shared Docker engine.** HA is supported on the Kubernetes substrate only. The Docker
  driver's sandbox tracking maps (`agentExecs`, `pending`, `mainProc`, `creating`,
  `internal/runner/docker/driver.go:125-131`) are per-process by design, and a teardown served
  by a replica that did not create the sandbox cannot see them.
- **Not stronger masking.** Masking stays verbatim-only, as `secretmask.go:1-16` states. SSH
  exec, SFTP and direct-tcpip were never masked (`internal/api/sshgateway_channels.go:668-676`),
  and the docs now say so in the HA section too.
- **Not fleet-wide limits.** Connection caps, rate limiters and debounce caches stay
  per-replica, so the effective cap is the per-replica cap times the replica count (Q-HA3).

## Design

### 1. Fail closed on a registry miss: the run masking manifest (`ha-l2.0`)

Re-resolving a run's secrets by name after a restart is wrong. Dispatch with secret `X=v1`,
rotate `X` to `v2`, restart: the lookup succeeds, `v2` is registered, and the sandbox still
holds `v1`, which is now unmasked. The registry must instead recover the exact bytes the run
received.

**The manifest.** At dispatch, in the dispatching transaction's path and before the sandbox can
see any value, wardynd commits the run's masking manifest: the exact bytes of every rendering
the run received, then `complete = true` last. That covers the workspace and inspection secrets
(`runs_dispatch_secrets.go:99,197`) and the Azure DevOps run token in its three renderings
(`runs_dispatch_ado_pat.go:178-180`). Today's `ado_run_pats` table holds metadata only
(`internal/store/store_ado_run_pats.go:21-34`), so the manifest is the first place a token
value is persisted. A run token minted after dispatch — renewal, widening, or a resume after a
pause (`runs_dispatch_ado_pat.go:327,371`) — appends its renderings to the manifest in the mint
path before the token is returned. A failed append fails the mint, as a failed `Add` fails the
injection.

**Sealing.** Each value row is sealed with `kek.Seal` (AES-256-GCM,
`internal/secretstore/kek/kek.go:113`) under the run owner's `cred` subject key from
`principal_keys` (KEY's `key-sk0`), in the owner's key domain. The run owner is
`runIdentitySubject(run.CreatedBy)`, the same subject dispatch resolves through, even when a
value came from the operator namespace by fallback: custody follows the person whose run it
is. The AAD binds the run id, the rendering's ordinal and the key version. This is why
`ha-l2.0` is stacked on `key-sk0`. A platform key would have been simpler and was rejected: it
would leave decryptable copies of a person's credentials after that person's key is destroyed,
which breaks both domain custody and erasure.

**Coverage.** `Covered(runID)` is true when this process holds the run's complete manifest and
the run's manifest row is present and not fenced in Postgres. Any serving replica can load and
certify a manifest; it never needs the watcher lease. That makes the ordinary case work:
replica A healthy and holding the lease while the upload lands on B. `ReconcileOnBoot`
(`reconcile.go:102`) loads the manifest of every live run it walks, so coverage comes back
without waiting for the first door. Injection-time `Add`s never mark a run covered: they add
values, they do not prove the corpus is whole.

**Pre-upgrade runs** have no manifest and stay honestly uncovered.

**Doors refused while uncovered.** Five doors relay or persist sandbox output. Each one checks
`Covered` and refuses when it is false:

- the recording upload (`handleUploadRecording`/`handleUploadRecordingPart`,
  `recording.go:84,95`): `503` with the new reason `mask_state_unavailable` and a denied audit
  row;
- the live attach (`handleAttachWS`, `attach.go:149`) and its recorded tail (`attach.go:747`);
- the exec relay, the masked writer dispatch hands the runner (`run_output.go:105-121`);
- the SSH shell (`bridgeSSHShell`, `sshgateway_channels.go:413`);
- the live output read (`readExecOutput`, `run_output.go:126`). Serving terminal output from
  its persisted `run_outputs` row, with OUT's erasure tombstone checked on read, is `out-o2`'s
  (W2); it is not rebuilt from a live registry here.

Audit events for an uncovered run record `"mask_scope":"globals_only"`.

**Erasure.** The lane provides one primitive: fence a run's live consumers (end its attaches,
SSH shells and relays, and refuse new ones), then delete a subject's manifest rows. The fence is
a durable row every replica honours, not an in-process flag: `run_mask_manifest.fenced_at` is
set in the same transaction that deletes the subject's value rows. `Covered` is re-read from
Postgres at each door's admission (never served from the cache alone), every in-flight consumer
re-checks it per chunk or beat and ends on a fence, and a replica drops its cached manifest and
values when the row is fenced or gone. AR's `erasure.Orchestrate` calls it from its
`mask_copies` scope: `ar-l1.4` covers every HA table
present on its branch when it merges, and this lane (W1) merges before it (W2), so the wiring
lands in `ar-l1.4`, not here. Because the rows are sealed under the person's `cred` key,
destroying that key also leaves them undecryptable.

**Release note and Q-HA1.** After any restart, runs that predate the manifest are refused at
attach, the SSH shell, the exec relay and the recording upload. Runs dispatched by 0.8.6
survive restarts.

**DONE WHEN (`ha-l2.0`):**

- rotation, delete and recreate of a secret after dispatch → `v1` is still masked after a
  restart;
- healthy A plus an upload to B → masked;
- an incomplete manifest is refused at all five doors;
- an injection after a restart does not cover an unmarked run;
- a legacy Azure DevOps run token from before the upgrade is honestly uncovered;
- the erasure primitive, called directly, fences then deletes a subject's manifest rows;
- a fence issued on B ends an attach held on A, and a new attach on A is refused.

Terminal output readable after every replica restarts is `out-o2`'s DONE WHEN.

### 2. The shared registry (`ha-l2.1`)

The manifest proves what a run received at dispatch. The registry also holds values registered
later, at injection, and the per-owner globals. `ha-l2.1` moves all of it into Postgres.

**Three buckets, an `owner` column on every row.** The new `mask_values` table holds:

- **per-run values**, sealed under the run owner's `cred` subject key;
- **per-owner globals**, registered through `AddGlobal`/`MergeGlobal` with an owner — today the
  AWS SSO and Azure DevOps sign-in access and refresh tokens. They are sealed under **that
  owner's** `cred` subject key, and deleted by `EvictGlobal` and by erasure;
- **shared-credential globals** (owner `""`). None exist today. If one appears, it is sealed
  under a new platform boot key `wardyn-mask-key`, minted through `loadOrCreateSecret`
  (`cmd/wardynd/boot_keys.go:85`) and added to the three reservation maps
  (`internal/api/secrets.go:46`, `internal/broker/broker.go:850`,
  `internal/secretstore/secretstore.go:138`), which `TestPlatformSecretsAreReservedEverywhere`
  enforces. The lane builds this bucket only if such a value exists when it lands.

**Write-through before return.** `Registry.Add*` and `Evict*` commit to Postgres before they
return, so a value is registered before the agent can see it. An `Add` that fails, fails the
injection. The in-memory maps remain as each replica's cache of the committed corpus.
Dispatch-time registrations and run-token mints that `ha-l2.0` commits to the manifest are not
written again: the per-run bucket holds only post-dispatch injection values, and each replica's
per-run corpus is the manifest plus the per-run rows. Per-run rows reference `agent_runs` with
`ON DELETE CASCADE`.

**A generation cursor that is a complete committed prefix.** Each registering or evicting
transaction allocates its generation with `UPDATE mask_gen SET gen = gen + 1 RETURNING gen`.
The row lock is held until commit, so commit order equals generation order. A plain sequence
is rejected: with a sequence, transaction T1 takes generation 1 and pauses, T2 commits
generation 2, a reader advances its cursor to 2, and when T1 commits its value is never read.
Evictions write tombstones with their own generation: `Evict`, `EvictGlobal` and retirement
(`SweepGlobals` past `RunSecretGrace`) set `tombstone = true` and `sealed = NULL` in one
statement, and the prune job deletes tombstone rows older than the horizon. After commit the transaction issues
`pg_notify('wardyn_mask', gen)`, which carries ids only, never a value.

**Sync.** Each replica keeps a cursor and reads every row and tombstone above it. A consumer
that is about to mask a chunk waits for a sync that *started after* the chunk arrived. Syncs
are coalesced to at most one every 50ms per replica. NOTIFY is only a hint: a reconnected
listener, and a cursor older than the tombstone prune horizon, both resync from the table
(full reload in the second case), and both are correct with no notification at all.

**Retention.** A leader-gated pass (on `ha-l2.3`'s `SweeperLeaderLockKey`) runs `SweepGlobals`
against Postgres and deletes the per-run rows and the manifest rows of runs terminal past
`RunSecretGrace`, writing tombstones so every replica's cache drops them. Each replica's own
run-secret sweeper keeps dropping its local cache.

**Fail closed.** If Postgres is unreachable, a consumer cannot prove its corpus is current, so
the recording upload answers `503`, a new attach is refused, and a live chunk is replaced by the
placeholder, the same rule the masker already applies to a recovered panic
(`secretmask.go:13-16`).

**Erasure.** `erasure.Orchestrate`'s `mask_copies` scope deletes by owner across the per-run
and per-owner-global rows, after fencing the person's live consumers. `ha-l2.1` lands after
`ar-l1.4` so this integration lands with the table, not later. Erasure is reported complete
only once every copy is gone, including the manifest rows and the run-token rows (§5).

**Single-replica installs.** The Postgres registry is the only registry once this lane lands,
whether or not HA is on. It also closes the restart case for per-owner globals at
`replicas: 1`. A mode switch was rejected: it would double the masking test matrix and keep
the fail-open path alive for the topology most installs run.

**Tests:** out-of-order commits; eviction tombstones; missing notifications; registration
failures. Values registered on A mask a recording uploaded to B. A person's AWS SSO and Azure
DevOps refresh tokens registered as globals on A cannot be decrypted after that person's
erasure. Purge on B with values registered on A, then restart both: no live credential-bearing
table can be decrypted with the remaining platform keys, and a delayed refresh or reconcile
cannot recreate the values.

### 3. Cross-replica locks (`ha-l2.2`)

Six in-process mutexes become Postgres advisory locks: the per-run operation lock
(`run_oplock.go:29`), the site-config writers (`server.go:660-671`, whose own comment asks for
this promotion), capability enforcement (`server.go:672-681`), the audit chain verify sweep
(`server.go:623-627`), and the two refresh single-flights (`awssso_refresh.go:227-233`,
`ado_entra_store.go:335-344`). The last two are what makes HA safe for rotating credentials, and
they are where 0.8.6's create-time renewal (`f-f2`) lands its single-flight, so this lane is
stacked on `f-f2` and on `az-a1`, which share those files.

**The helper needs work first.** `AdvisoryLockKeyed` allows one keyed hold per process
(`internal/db/advisory_lock_keyed.go:73`), and when the pool cannot spare a connection it
returns `ErrAdvisoryLockNoCapacity`, which callers treat as "proceed unlocked"
(`advisory_lock_keyed.go:46-52`). Both are wrong for these locks. The credential erase already
nests one refresh lock inside another (`credential_erase.go:141-146`: the AWS lock, then the
Azure DevOps lock), which a one-hold gate turns into a timeout, and proceeding unlocked through
a refresh is exactly the double spend the lock exists to prevent. The lane defines:

- **Lock order.** Run operation, then the Azure DevOps per-run run-token mint/revoke lock
  (`ha-l2.4`), then person credential locks (AWS SSO before Azure DevOps sign-in, matching the
  erase), then document locks (site config, capability enforcement).
  The audit chain lock is always taken last and never held while waiting on another. A test
  takes every documented nesting and fails on any inversion.
- **Pool capacity.** Locks are held on a small dedicated lock pool rather than the request
  pool, and a nested lock reuses its caller's lock connection instead of pinning a second one.
  The pool size is documented beside `pool_max_conns` in `docs/ENV.md`.
- **No unlocked fallback for these locks.** For the run-operation, refresh, erase and document
  locks, no capacity means refuse (`503`, retry), never proceed; the sweep side keeps
  `tryLockRunOp` semantics and skips the run. The sign-in supersede lock keeps its
  documented behaviour.
- **Loss behaviour.** A session-level lock dies with its connection, for example on a Postgres
  failover. The holder watches its lock connection and cancels the guarded work's context when
  it is lost. The refresh's final `Put` is a compare-and-set on the stored blob's version, so a
  holder that lost its lock cannot overwrite a newer refresh token.

**DONE WHEN (`ha-l2.2`):** a concurrent AWS SSO refresh on two servers sharing one database
spends the refresh token once; the same holds for the Azure DevOps sign-in refresh; the nested
erase completes under the new helper; a lock-pool exhaustion refuses rather than proceeding, including on the per-run operation lock
(the revive is refused); a lock lost mid-refresh does not overwrite a newer token.

### 4. Leader-gated sweepers and fencing (`ha-l2.3`)

The approval, recording, credential and pause sweepers, and the always-egress reconcile, run on
one elected leader. The credential sweeper is already per-row locked
(`cmd/wardynd/adapters.go:888-893`) and is gated only to avoid duplicate passes. The run-secret
sweeper (`boot_serve.go:189`) stays on every replica, because it drops that replica's own
in-memory cache (`runs_lifecycle.go:458`). A new `SweeperLeaderLockKey` in
`internal/db/advisory_locks.go` is held for the process lifetime, the pattern the ground-truth
rotator already uses (`advisory_locks.go:27-37`). Followers retry it.

**Advisory locks can briefly overlap.** On a Postgres failover the old leader's session lock is
released while the old leader is still running (`advisory_locks.go:39-52` states this ceiling).
So every leader action is idempotent **and fenced**:

- **A lease epoch.** Each acquisition bumps a durable epoch. The leader monitors its lock,
  and on loss it cancels and joins its sweeps before anything else runs. Multi-step run
  operations and their compensations carry the epoch and re-check it at each write.
- **The pause repair.** `pauseRun` freezes, then marks the run paused with a compare, and on a
  failed mark thaws (`run_pause.go:607-634`). With two stale leaders, both freeze, the second
  loses the compare, and its compensating thaw undoes the winner while the database says
  paused. The compensation must re-read the run under the epoch and thaw only when no newer
  pause holds it.

**O2.** Operability's `o-o2` reports sweep health. Under HA it must distinguish an attempted
sweep from a successful one, include each replica's own substrate and auth probe, and show
followers the leader's last tick so they never look stale. Those requirements are carried by
`o-o2`; this lane gives it the leader identity.

**DONE WHEN (`ha-l2.3`):** with two servers on one database, exactly one runs each sweeper;
killing the leader hands every sweeper to the other within one retry interval; the
two-stale-leaders pause schedule leaves the run frozen and marked paused; the recording
sweeper deletes once per tick across both; a run terminal past `RunSecretGrace` whose values
were loaded on the follower is gone from the follower's registry after one secret-sweep
interval.

### 5. Live state into Postgres (`ha-l2.4`)

- **The exec tail.** Live output moves to its own table, `run_output_chunks(run_id, seq,
  replica, bytes_masked, at)`. Chunks are masked by the dispatching replica's `liveMaskWriter`
  before insert, and its holdback is flushed on finalize. Any replica serves the live read.
  OUT's `out-o2` owns `run_outputs`, one final row per run; the two tables stay separate. The
  lane extends `erasure.Orchestrate` to delete `run_output_chunks`, and chunk writes honour
  OUT's per-run erasure tombstone.
- **The attach lease.** The attach holder (`attach_holder.go:294-315`) becomes a Postgres
  lease. Attach input, resize and release are fenced by lease identity, so a replica whose
  lease was taken over cannot write into the PTY. This lane follows the terminal lanes that
  change attach admission (`term-t7`, `term-t15`, `term-t14`). `attach.go` is 953 lines, so new
  code goes in new files (`scripts/check-file-size.sh`).
- **NOTIFY fan-out.** The run-events hub publishes each event to every replica, and a kill
  reaches the replica running that run's `CreateSandbox`. NOTIFY is not durable, so neither
  depends on it: the events stream already re-reads the store every beat
  (`run_events.go:32-36`), and a lost kill is still caught by the existing kill-race guard
  (`runs_dispatch.go:650-673`), which tears the sandbox down when the STARTING→RUNNING compare
  fails, so there is no new re-read code.
- **The Azure DevOps run-token cache and the sign-in ends counter** move to Postgres, and the
  per-run mint/revoke single-flight (`adoRunPATCache.lock`, `ado_run_pat_cache.go:69`) becomes a
  keyed lock under `ha-l2.2`'s helper, after the run-operation lock and before the person
  credential locks, with no unlocked fallback. Run-token
  rows hold token values, sealed with `kek.Seal` under the run owner's `cred` subject key, with
  AAD binding the run id and the rendering. Erasure deletes them with the person's other
  copies.

**DONE WHEN (`ha-l2.4`):** output written through A is readable live from B; after A crashes, B
serves the tail written before the crash, and OUT's capture-gap marker covers what A could not
flush; an attach whose lease was taken over cannot send input or resize; a run token cached by
A is served to a proxy that asks B; a kill served by B cancels A's in-flight `CreateSandbox`
within 2s, and with the NOTIFY dropped the run still ends `KILLED` with its sandbox torn down; a
lost NOTIFY for an event still delivers the ended event on the next beat; two servers resolving
one run's token concurrently mint exactly one PAT, and a pause revoke on A with a resume on B
leaves no unrevoked PAT on a paused run; after a person's erasure their chunk rows and run-token rows
are gone and no late write recreates them.

### 6. Chart, boot and status (`ha-l2.5`)

**The chart.**

- `ha.enabled` sets `WARDYN_HA=true`. It replaces `allowMultiReplica` and
  `-allow-multi-instance` as a documented clean break: a values file that still sets
  `allowMultiReplica` is refused with a pointer to `ha.enabled`.
- It lifts the `replicas > 1` refusal (`deployment.yaml:81-82`) when `ha.enabled` is set.
- It refuses to render with HA unless `WARDYN_RECORDING_STORE` is `pg` (or recording is
  `off`), and refuses FS persistence. The chart today derives the store from
  `persistence.enabled` (`deployment.yaml:382-398`); the guard scans **both** `env` and
  `extraEnv`, because `extraEnv` can set the same key.
- It adds a PodDisruptionBudget (`minAvailable: 1`) and pod anti-affinity. The audit spool
  already lives on the per-pod `tmp` emptyDir whenever persistence is off
  (`WARDYN_AUDIT_SPOOL=/tmp/audit-spool.jsonl`, `deployment.yaml:407-419,617-619`); a
  `helm template` case asserts HA renders it there, and HA refuses an `env`/`extraEnv`
  `WARDYN_AUDIT_SPOOL` outside `/tmp`. The strategy stays `Recreate` (Q-HA2).

**wardynd.** `WARDYN_HA=true` replaces `-allow-multi-instance` at boot: the single-instance lock
is not taken, and the process refuses to start in HA unless its runner is the Kubernetes
substrate and its recording store is `pg` or `off`. The chart refusal is render-time only, so
this boot refusal is the half that holds when someone edits the Deployment by hand, the same
two-half shape the single-instance lock has today (`single_instance.go:15-23`). The old flag is
refused with a pointer. Without `WARDYN_HA`, boot is unchanged: one instance, lock taken.

**`/setup/status`** gains three rows: `ha_mode`, `recording_store_shared` and
`mask_registry_shared`. `mask_registry_shared` is ok when this replica's LISTEN connection is
up and its mask sync cursor is within one sync of `mask_gen`, and fails otherwise. Their copy
goes into mock packet M10 beside CADM's `/setup/status` row
(CONSOLE-RULES §12), or the maintainer's waiver is recorded on `ha-l2.5`.

**Docs.** OPERATIONS.md "One replica, by construction" is rewritten as the HA section, carrying

## Security model and residual risks

**What changes.** Secret values now exist at rest in Postgres: the manifest, `mask_values` and
the run-token rows. Every one is sealed with AES-256-GCM through `kek.Seal`, under the subject
key of the person it belongs to, in that person's key domain. A database dump alone reveals
none of them. NOTIFY payloads carry generations and ids only.

**Erasure and custody** reach every copy: destroying a person's `cred` key leaves their rows
undecryptable, and `erasure.Orchestrate`'s `mask_copies` scope deletes them after fencing live
consumers. Erasure is reported complete only after the manifest, `mask_values`, chunk and
run-token rows are gone.

**Residual risks, disclosed in OPERATIONS.md and the threat model:**

- Masking is verbatim-only; encoded or narrated values are not caught (unchanged).
- SSH exec, SFTP and direct-tcpip were never masked (`sshgateway_channels.go:668-676`).
- Runs that predate 0.8.6 are uncovered and refused at the five doors after any restart.
- Masking now depends on Postgres: when it is unreachable, uploads and new attaches are refused
  and live chunks are replaced by the placeholder. That trades availability for never
  persisting a credential.
- On a Postgres failover, advisory locks can overlap briefly. Leader actions are idempotent and
  epoch-fenced, and the refresh `Put` is compare-and-set, but a refresh already in flight on
  the old holder can still race a new holder's redeem in that window and lose the credential;
  the person signs in again.
- The audit spool is a per-pod emptyDir. A node failure loses whatever that pod had spooled
  and not yet drained.
- Per-replica caps (SSH and UI connections, rate limiters, debounce caches, the events stream
  cap) multiply by the replica count.
- A compromised wardynd process still sees every value it masks.
- Shredding is complete only after backups expire or the wrapping key version is retired.

## Upgrade and compatibility

- **Default installs are unchanged in shape:** one replica, `Recreate`, the single-instance
  lock taken. They gain the manifest and the Postgres registry.
- **Live runs at upgrade** have no manifest. After the restart they are refused at attach, the
  SSH shell, the exec relay and the recording upload, and the live output read; terminal output
  persisted by OUT is still served. The release note says so (Q-HA1).
- **`allowMultiReplica` and `-allow-multi-instance` are removed** as a documented clean break,
  refused with a pointer. An install that set them was running an unsupported topology.
- **HA needs the `pg` recording store.** The chart's default today is `fs` with persistence on
  and `off` without; an HA install sets `WARDYN_RECORDING_STORE=pg` and leaves persistence off.
- **Migrations are additive** and run in the existing stopped-writer upgrade.

## Verification

**Per lane:** `make lint && make staticcheck`; the lane's scoped `go test` plus
`go test ./cmd/wardynd/`; for a migration lane, the Postgres suites against a fresh database of
its own, and the check fails if those suites skipped (`go test -count=1 -v ./internal/db/` must
not print `WARDYN_TEST_PG not set`); `helm lint` and `helm template` for `ha-l2.5`. Each lane's
DONE WHEN is above.

**Tests the design requires**, in addition to the DONE WHEN bullets:

- `ha-l2.0`: rotation, delete and recreate after dispatch; a value resolved through the
  operator fallback and then shadowed by the owner's own secret; a kept run revived after a
  restart; a legacy run-token upgrade; a cross-replica fence.
- `ha-l2.1`: out-of-order commits under the generation counter; eviction tombstones and the
  prune horizon; missing notifications and listener reconnect; a failed registration failing
  the injection; Postgres down at upload, attach and chunk.
- `ha-l2.2`: every documented lock nesting; lock-pool exhaustion; lock loss mid-refresh.
- `ha-l2.3`: two stale leaders on the pause schedule; leader loss mid-sweep.
- `ha-l2.4`: delayed final bytes; A → crash → B with output before, during and after handoff;
  lease takeover during input; lost NOTIFY for an event and for a kill (the kill as a
  regression test of the existing guard); concurrent run-token mint and pause/resume across two
  servers.

**End to end, two replicas on kind** (`ha-l2.5`, run by the release lead):

- a secret registered on A is masked in a recording uploaded to B;
- with Postgres down, the upload gets `503`;
- the leader sweeper hands over when the leader pod is deleted;
- a concurrent AWS SSO refresh on two replicas spends the token once.
