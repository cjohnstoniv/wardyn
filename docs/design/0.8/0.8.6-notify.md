# Wardyn 0.8.6 — approval notification, routing and escalation

A pending approval today waits in the console until someone happens to open the Approvals page.
Nothing tells the approver it exists, nothing routes a push review to the people who own the
policy, and nothing escalates an approval that has sat for an hour. An adopter running a shared
deployment with a central security team asked for exactly that: approvals delivered to the team's
chat and mail, routed by what is being asked and under which profile, and escalated when nobody
answers. This record designs it for 0.8.6. It is the NOTIFY epic; its five lanes are `notify-e1`
to `notify-e5`.

Every file:line reference is to `origin/main` at `e0efee625` (the v0.8.5 tree).

## What exists today

- **Two insertion seams and no third.** Every approval row is written by one of two statements,
  and a grep of non-test Go for `INSERT INTO approvals` finds exactly these two:
  - `store.PG.CreateApproval` (`internal/store/store.go:468`, the INSERT at `:476`), reached
    through `approval.RequestApproval` (`internal/approval/approval.go:48`), which the console
    adapter `approvalService.Request` calls (`cmd/wardynd/adapters.go:300`). Every API raise goes
    through it: the internal raise door (`internal/api/internal.go:473`), the AWS SSO re-auth hold
    (`internal/api/injection_awssso.go:404`), the Azure DevOps sign-in and capability doors
    (`internal/api/injection_ado_signin.go:166`, `internal/api/injection_ado_capability.go:326,399`).
    The write is a single autocommit `QueryRow` on the pool, not a transaction. A concurrent
    duplicate loses on the partial unique index and is mapped to `ErrDuplicatePending`
    (`store.go:488-490`), which `RequestApproval` treats as a dedup signal and re-reads the winner
    (`approval.go:71-81`).
  - The broker's credential path: `MintForGrant` calls `ensureApproval` (`internal/broker/broker.go:402`),
    which opens its own transaction (`internal/broker/sql.go:62`) and inserts with
    `ON CONFLICT … DO NOTHING` (`sql.go:89-92`), then re-selects the winner. This path never
    touches the `approvalService` adapter.
- **Five kinds**, a closed set: `credential`, `egress_domain`, `tool_call`, `credential_reauth`,
  `push_content` (`internal/types/types.go:237-254`).
- **The adapter's extra interfaces.** `approvalService` (`adapters.go:296-374`) also carries the
  optional paging and attention reads the API type-asserts for (`ListApprovalsPage`,
  `ListApprovalsPageByRunCreator`, `ListApprovalsPageByRun`, `ListPendingApprovalsForRuns`,
  `CountPendingApprovals*`). They stay as they are.
- **Response-time projection.** `projectHolds` (`internal/api/approvals_decidable.go:26`) sets
  `held`/`held_until` on every row a `GET /approvals` returns, through the single wrapper
  `withHoldProjection` (`:45`) used at all four list call sites (`internal/api/approvals.go:113,133,139,144`).
  The wire type is `types.ApprovalRequest` (`types.go:330`).
- **The audit sinks are lossy by design.** The SIEM webhook sink drops events when its buffer is
  full (`internal/audit/sinks/webhook.go:148-161`) and after retry exhaustion; the loss is counted in
  `wardyn_audit_sink_drops_total` (`internal/api/metrics.go:551`). That is right for a telemetry
  stream and wrong for "tell a human an approval is waiting".
- **Outbound HTTP precedent.** The audit webhook refuses a bearer token over plain HTTP and never
  echoes a URL that may carry credentials (`webhook.go:104-114`). Credential-bearing clients refuse
  to follow redirects (`internal/api/awssso_refresh.go:655`, `internal/api/ado_pat_client.go:141`).
  `WARDYN_TRUSTED_CA_FILE` installs a corporate CA by mutating the process-global
  `http.DefaultTransport` (`cmd/wardynd/trusted_ca.go:114-116`), and that transport honours
  `HTTPS_PROXY`.
- **No row-claiming worker exists.** Nothing in `internal/` or `cmd/` uses `FOR UPDATE SKIP LOCKED`.
- **Who owns a run.** `agent_runs.created_by` is the principal; `people.email` holds the address
  (`internal/db/migrations/0090_people_and_token_minted_by.sql:9-15`). The run's governance profile
  is `agent_runs.governance_profile_id` (`0072_agent_runs_run_limits.sql:20`).

## Goals and scope

- Every new approval produces a durable notification record in the same transaction that creates
  the approval, so no crash can leave an approval nobody was told about.
- Delivery to a generic signed webhook, a Teams Workflows Adaptive Card, a Slack incoming webhook
  and SMTP over verified STARTTLS.
- Routing by approval kind and by the run's governance profile; escalation tiers that fire after a
  configured delay while the approval is still pending; recipients that can be the run owner or the
  profile's named contact.
- The approver sees the SLA: when the next escalation fires and which tier is in force.
- Operators see failures: an audit row, a metric, a Settings card and a `/setup/status` warning.

**Not in 0.8.6:** deciding an approval from the channel (buttons in Teams or Slack); per-person
subscription preferences; a console-editable channel list; a test-send button; implicit-TLS SMTP
(port 465). Each is either a security decision below or a later minor.

**Off by default.** With `WARDYN_APPROVAL_NOTIFY` unset, no outbox row is written, no worker runs
and every response is byte-identical to 0.8.5 except that `CreateApproval` runs inside a
transaction.

## Design

### 1. The outbox and the atomic enqueue

A new table `approval_notifications` holds one row per (approval, tier, channel). It is written
**in the same transaction as the approval row**, at both seams, and never by a wrapper after commit.
An independent review of the plan found that a wrapper around `approvalService.Request` would miss
the broker's direct insert entirely, and would return after the approval had committed, so a crash
between the two writes leaves an approval with no notification and no retry can repair it (the
dedup returns the existing row and "only when new" never fires again). The requirement this design
carries is therefore: every actual insertion enqueues atomically; a dedup loser enqueues nothing;
delivery identity is idempotent; the adapter keeps its paging and attention interfaces and is not
the enqueue point.

- **`store.PG.CreateApproval` becomes transactional.** Inside one transaction it reads the run's
  `governance_profile_id`, inserts the approval, asks the planner for the rows to enqueue, inserts
  them, and commits. A unique violation on the approval insert rolls the whole transaction back and
  still returns `ErrDuplicatePending`, so `RequestApproval`'s dedup path (`approval.go:71`) is
  unchanged and the loser enqueues nothing.
- **`ensureApproval`'s INSERT becomes a CTE on the inserted row:**
  `WITH ins AS (INSERT INTO approvals … ON CONFLICT … DO NOTHING RETURNING id, requested_at)
  INSERT INTO approval_notifications (…) SELECT ins.id, p.tier, p.channel, ins.requested_at + p.after …
  FROM ins CROSS JOIN unnest($tiers, $channels, $afters) AS p(…)`.
  When the insert loses the race, `ins` is empty and the second statement inserts nothing. The
  profile id is read in the same transaction before the statement.
- **One planner.** `notify.Plan(kind, profileID) []Planned` is a pure function of the boot config.
  Both seams call it, so the two cannot drift. With no config it returns nothing.
- **A per-run budget.** The sandbox agent decides how many distinct approvals its run raises (up to
  `maxApprovalsPerRun = 4096`, `internal/api/internal.go:381`), so a flood of chat cards could bury
  the one real approval. Inside the enqueue transaction, at both seams, the planner enqueues nothing
  when the run already has 25 or more tier-0 outbox rows created in the last hour. A suppressed
  raise increments `wardyn_approval_notify_suppressed_total{channel}` and writes one
  `approval.notify.suppressed` audit row per run per hour. The console still lists every approval.
- **A source guard.** A test lists every non-test `INSERT INTO approvals` in the tree and fails if
  any site other than the two above appears, so a third seam cannot be added without its enqueue.
- **Why not the audit sinks.** They drop on overflow (`webhook.go:148`), and their retry state lives
  in memory. A notification that must survive a restart needs a row.

### 2. The worker (`internal/notify/`)

- **Every replica runs it** when the config is set. Each tick (every 15 s) claims at most 50 due rows
  with `SELECT … FOR UPDATE SKIP LOCKED`, marks them `sending` with `lease_until = now() + 60s` and
  `attempts = attempts + 1`, commits, and only then sends. Rows in `sending` whose lease has passed
  are claimable again, so a replica that crashed mid-send loses nothing. `SKIP LOCKED` alone is not
  crash recovery; the lease is.
- **Sends run concurrently**, one goroutine per claimed row, each with a 10 s timeout, so one wedged
  endpoint cannot stall the others. The lease (60 s) is longer than the longest send (10 s).
- **Re-read before send.** The worker re-reads the approval. A row whose approval is no longer
  `PENDING` moves to `cancelled` without sending. Escalation rows for an approval decided before
  their due time are cancelled the same way when they come due.
- **Finalising** a row is a compare-and-set on `(id, lease_until)`, so a replica whose lease was
  reclaimed cannot overwrite the new claimant's result. Every finalise (sent, retry, dead,
  cancelled) sets `last_attempt_at = now()`, the time the status card and `/setup/status` read (§9).
- **Retries.** Network errors, timeouts, HTTP 408, 429 and 5xx retry with back-off of 30 s, 1 m, 2 m
  and 4 m. Any other 4xx, a 3xx, or a configuration error is not retryable. A row becomes **dead**
  after its fifth failure, on the first non-retryable failure, or when it is still unsent one hour
  after its `due_at` (`expired`; a reminder that arrives hours late is noise).
- **A dead row** writes one `approval.notify.failed` audit row and increments
  `wardyn_approval_notify_failed_total{channel}`.
- **Housekeeping.** Each tick deletes at most 500 terminal rows (`sent`, `cancelled`, `dead`) whose
  `last_attempt_at` is older than 30 days. The rows hold no personal data (§6), so this is size control, not retention policy.

### 3. Delivery semantics

- **At least once, with expiry.** A crash after a successful send and before finalising resends on
  reclaim. Every delivery carries a stable `delivery_id` (the outbox row id) in the body and in an
  `X-Wardyn-Delivery` header, so a receiver can drop duplicates.
- **Stable destination ids.** Each channel has an operator-chosen `id`; the outbox stores that id,
  never the URL. Rotating a webhook URL under the same id keeps pending rows deliverable.
  `UNIQUE (approval_id, tier, channel)` makes the enqueue idempotent.
- **Redirects are not followed.** The client uses `CheckRedirect` returning
  `http.ErrUseLastResponse`, the existing precedent (`awssso_refresh.go:655`). A 3xx is a
  non-retryable failure, `redirect_refused`. Following a redirect would hand the body, signature
  and any URL-embedded credential to a host the operator never named.
- **Errors are redacted to a class.** The stored `last_error`, the audit row and the log carry a
  class and a code only: `http_status:503`, `timeout`, `tls_verify`, `dial`, `redirect_refused`,
  `smtp_reply:550`, `no_recipient`, `expired`. Never the URL (a Go `*url.Error` prints the full URL,
  including a Teams workflow signature or a Slack hook path), never a response body, never an SMTP
  server's reply text.
- **Transport.** The client clones `http.DefaultTransport` after boot has applied
  `WARDYN_TRUSTED_CA_FILE`, so a corporate TLS-inspecting proxy and `HTTPS_PROXY` work as they do for
  the OIDC and audit clients, and nothing the notifier does can mutate the shared TLS config.

### 4. Channels

The config names channels by `id` (`[a-z0-9_-]{1,32}`, unique; it is also the metric label, so the
label set is bounded by config). Types:

- **`webhook`**: `POST` of the `wardyn.approval.v1` JSON body (§5). Optional `hmac_secret` and
  `bearer_token`. HTTPS is required when either is set or when the URL carries userinfo or a query
  string; a plain-HTTP URL with none of those is allowed, matching the audit webhook rule
  (`webhook.go:104-114`).
- **`teams`**: a Teams Workflows trigger URL; the body is an Adaptive Card message built from the
  same allowlisted fields. The URL carries its signature in the query string, so HTTPS is always
  required.
- **`slack`**: a Slack incoming-webhook URL; the body is Block Kit. The URL path is the credential,
  so HTTPS is always required.
- **`smtp`** (lane E5, last): `host`, `port`, `from`, optional static `to`, optional
  `username`/`password`. **STARTTLS is mandatory and verified**: the client refuses a server that
  does not advertise STARTTLS, verifies the certificate against the system roots plus the trusted
  CA file with `ServerName` set to `host`, and only then authenticates. There is no plaintext
  fallback and no option to skip verification. The body is plain text only, so no markup can be
  injected. Header values are built from validated fields; a CR or LF anywhere is refused.

### 5. Payload `wardyn.approval.v1`

**Allowlisted fields only:**

| Field | Source |
|---|---|
| `schema` | the literal `wardyn.approval.v1` |
| `delivery_id` | outbox row id |
| `event` | `raised` (tier 0) or `escalated` (tier ≥ 1) |
| `tier` | the row's tier |
| `approval.id`, `approval.kind`, `approval.requested_at` | the approval row |
| `approval.sla_due_at` | the next tier's due time, when one exists |
| `run.id` | the approval row |
| `profile.id`, `profile.name` | the run's leaf governance profile (admin-authored) |
| `requester.principal`, `requester.email` | the run owner (`agent_runs.created_by`, `people.email`); omitted on a channel with `redact_requester` |
| `recipients[]` | `{role, email}` from the tier's `notify` targets (§7) |
| `console_url` | `<console_url>/approvals`, from config; omitted when unset |

**Never sent:** `requested_scope` (it holds the host, tool arguments and push paths), the reason
text, the run title, any diff, any credential. Those are written or influenced by the sandbox
agent, and a message that arrives in Teams under the deployment's name with agent-chosen text is a
phishing channel into the approving team. The approver reads the details in the console, signed
in, where the four-eyes and second-human rules apply.

- **Masking.** Every string field passes through the run's `secretmask` masker
  (`internal/secretmask/secretmask.go:319`) before encoding. No allowlisted field is sandbox text, so
  this is defence in depth against an identifier that happens to equal a registered secret.
  Masking fields rather than the encoded body keeps the JSON well-formed and lets the signature
  cover the final bytes.
- **Escaping.** Requester and profile strings are stripped of control characters, capped at 256
  bytes, and escaped for the target markup: Slack `plain_text` objects (no mrkdwn
  interpretation) and Adaptive Card text with Markdown control characters and `& < >` escaped. The
  only link in any message is `console_url`, from config, never from approval data.
- **Signature.** With `hmac_secret` set, `X-Wardyn-Signature: t=<unix seconds>,v1=<hex>`, where
  `v1 = HMAC-SHA256(secret, t + "." + body)`. The timestamp bounds replay; a receiver should
  reject a `t` more than five minutes old. A published test vector pins the format.
- **Fixed text.** The human-readable title is `Approval waiting: <kind label>` for tier 0 and
  `Approval still waiting (escalation <n>): <kind label>` above it. Kind labels: `credential`
  "Credential", `egress_domain` "Network access", `tool_call` "Tool call", `credential_reauth`
  "Sign-in needed", `push_content` "Push review". The body lines are the run's short id, the
  requester (unless redacted), the request time in UTC and the console link. SMTP uses the same
  title as its subject, prefixed `[Wardyn] `. Changing these strings changes this record.

### 6. Schema and migration

Migration `0107_approval_notifications.sql` (the next free number on today's main; the steward
renumbers in merge order):

```sql
CREATE TABLE IF NOT EXISTS approval_notifications (
    id              UUID PRIMARY KEY,
    approval_id     UUID NOT NULL REFERENCES approvals(id) ON DELETE CASCADE,
    tier            SMALLINT NOT NULL CHECK (tier BETWEEN 0 AND 4),
    channel         TEXT NOT NULL CHECK (channel ~ '^[a-z0-9_-]{1,32}$'),
    due_at          TIMESTAMPTZ NOT NULL,
    state           TEXT NOT NULL DEFAULT 'pending'
                      CHECK (state IN ('pending','sending','sent','cancelled','dead')),
    attempts        SMALLINT NOT NULL DEFAULT 0,
    next_attempt_at TIMESTAMPTZ NOT NULL,
    lease_until     TIMESTAMPTZ,
    last_error      TEXT NOT NULL DEFAULT '',
    last_attempt_at TIMESTAMPTZ,
    sent_at         TIMESTAMPTZ,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (approval_id, tier, channel)
);
CREATE INDEX IF NOT EXISTS approval_notifications_due_idx
    ON approval_notifications (next_attempt_at) WHERE state IN ('pending','sending');
```

- It creates a table and alters none, so it needs no row in the migrator rationale that
  `scripts/test-claims-match-code.sh` C8c checks. A lane that later adds an index or column on
  `approvals` must add that row.
- **No personal data is stored.** The payload is rendered at send time from the approval, the run
  and the people row, and is never persisted. `last_error` is a class. Erasure needs no
  integration: deleting a run cascades to its approvals and from there to these rows.
- The state set is a closed Go enum checked against the DB CHECK, the same pattern as
  `types.ApprovalKinds`.

### 7. Routing and escalation (lane E3)

```json
{
  "console_url": "https://wardyn.example.com",
  "channels": [
    {"id": "sec-teams", "type": "teams", "url": "https://…"},
    {"id": "hook", "type": "webhook", "url": "https://hooks.example.com/wardyn",
     "hmac_secret": "…", "redact_requester": true},
    {"id": "mail", "type": "smtp", "host": "smtp.example.com", "port": 587,
     "from": "wardyn@example.com", "username": "…", "password": "…"}
  ],
  "routes": [
    {"kinds": ["push_content"],
     "tiers": [{"after": "0s",  "channels": ["sec-teams"]},
               {"after": "30m", "channels": ["sec-teams", "mail"], "notify": ["profile_contact"]}]},
    {"profiles": ["<profile uuid>"],
     "tiers": [{"after": "0s", "channels": ["mail"], "notify": ["run_owner"]}]},
    {"tiers": [{"after": "0s", "channels": ["hook"]}]}
  ]
}
```

- **Matching.** A route matches on `kinds` (members of `types.ApprovalKinds`) and `profiles`
  (governance profile ids); an absent key matches anything. The first matching route wins; no match
  means no notification. With `routes` absent (lane E1's shape), every approval goes to every
  channel at tier 0.
- **Profiles by id, not name.** A rename must not silently re-route. The id is the run's **leaf**
  profile as bound at dispatch; under profile composition the contact and identity stay the leaf's,
  separate from the effective content.
- **Tiers.** At most five; `after` strictly ascending from ≥ 0. All tiers are enqueued at insertion
  with `due_at = requested_at + after`; the worker sends a row only when it is due and the approval
  is still pending. Boot warns when a tier's `after` is at or beyond `WARDYN_APPROVAL_EXPIRY_AFTER`
  (default 24 h, `docs/ENV.md:218`), because the approval will have expired first.
- **`notify` targets** fill `recipients[]` and, on an SMTP channel, the envelope recipients
  (together with the channel's static `to`):
  - `run_owner`: the run owner's `people.email`;
  - `profile_contact`: the leaf profile's `contact.email`, from the DENY epic's `ProfileContact`
    (lane `deny-f1`), passed through deny-f1's `policyref.Project`, which re-validates it; the
    returned `Ref.Email` is used and no contact rule is re-implemented here. This is why
    `notify-e3` is blocked by `deny-f1`.
  
  A target with no address is skipped; an SMTP send left with no recipient is dead with
  `no_recipient`.
- **Boot refuses:** malformed JSON or an unknown field; a duplicate channel id; a route naming an
  unknown channel; an unknown kind; non-ascending tiers; `notify: run_owner` on a channel with
  `redact_requester` (the owner is the requester, so the two contradict); a Teams, Slack or
  secret-bearing webhook URL that is not HTTPS; a `console_url` that is not `https://` or carries
  userinfo, a query or a fragment; a channel type whose lane has not landed. Every refusal names
  the channel `id` and the rule it broke and nothing else: never a URL, secret, token or field
  value (the `malformed url (redacted)` precedent, `webhook.go:107-109`). The config is never logged.

### 8. SLA on the approval list (lane E4)

- `types.ApprovalRequest` gains two response-time fields, never stored on the approval:
  - `escalation_tier`: the highest tier whose `due_at` has passed;
  - `sla_due_at`: the earliest `due_at` still in the future, i.e. when the next escalation fires.
  Both appear on `PENDING` rows only, like `held`.
- They are projected inside `withHoldProjection`, the single projection point for every list read
  (`approvals_decidable.go:45`). The projection is one batched read over the page's ids, exposed by
  `approvalService` as another optional capability (the `ListPendingApprovalsForRuns` pattern,
  `adapters.go:358`). A backend without it projects nothing.
- They are computed from the outbox rows, not from the current config: the rows record what was
  actually scheduled when the approval was raised, so a config change after a raise cannot make the
  chip disagree with what was sent.
- The TypeScript type in `ui/src/app/lib/types/approvals.ts` mirrors them (the wire-parity test
  reads the Go struct).
- The approvals cards show an "escalated" chip and an "escalates in" chip. Their copy waits for
  mock packet **M6**.

### 9. Operator visibility

- **Audit:** `approval.notify.failed`, actor `system` (`wardyn/approval-notify`), target the
  approval id, keyed to the run so it lands in the run's evidence rail. Fields: `approval_id`,
  `channel`, `tier`, `attempts`, `error` (the class). Added to `docs/AUDIT-ACTIONS.md`, which
  `cmd/wardynd/audit_actions_doc_guard_test.go` enforces. Successful sends are not audited: a
  notification is a pointer, not a decision; the chain records decisions, which already have
  `approval.decide`, `approval.expire` and `approval.cancel`.
- **Metric:** `wardyn_approval_notify_failed_total{channel}` in `internal/api/metrics.go`, documented
  in `docs/operations/monitoring.md`. Per replica, like every counter there.
- **Settings card** (admin Settings, `ui/src/app/components/screens/settings/admin-settings-screen.tsx`):
  read-only. Per channel it shows id, type, destination host only, last success time, last error
  class and time, and failures in the last hour, plus a line saying the list is configured by
  `WARDYN_APPROVAL_NOTIFY`. It reads a new `GET /api/v1/approval-notify/status` mounted on the
  `securityOps` tier (`internal/api/routes.go:191`), with a row in the `authz_test.go` `chi.Walk`
  matrix. Copy waits for **M6**.
- **`/setup/status`:** a non-blocking `SetupCheck` (`internal/api/setup_checks.go:51`) with id
  `approval_notify`, present only when notifications are configured: `warn` when any channel
  produced a dead row in the last hour, `ok` otherwise. Its id joins the setup-check id test.

## Decisions and rejected alternatives

- **Transactional outbox at both insertion seams.** Rejected: a notifying wrapper around
  `approvalService` (misses the broker path; leaves a crash window after commit); the audit sinks
  (lossy by design); `LISTEN/NOTIFY` (not durable — a listener that is down misses the event).
- **Lease-based claims, all replicas.** Rejected: a leader-only worker. `SKIP LOCKED` plus a lease is
  already safe with several replicas and creates no dependency on the HA epic's leader election.
- **At-least-once with a stable `delivery_id`.** Rejected: exactly-once. Without the receiver's
  cooperation it is impossible over HTTP and SMTP; a stable id lets the receiver deduplicate.
- **Render at send time, store ids only.** Rejected: storing the payload. It would put requester
  identity in a second table that erasure must then reach, and a payload rendered at raise time
  could not honour a decision made before the escalation fired.
- **No free text in the payload.** Rejected: including the host or the run title "for context". Both
  are reachable by the sandbox agent; the console link carries the context behind sign-in.
- **No action buttons.** Rejected: approve or deny from Teams or Slack. A channel click carries no
  Wardyn session, so it would bypass the second-human rule, self-approval refusal and role checks
  that `POST /approvals/{id}/approve` and `/deny` enforce (`internal/api/routes.go:261-262`).
- **Do not follow redirects.** Rejected: following with credentials stripped. The signature and the
  body still go to the new host, and a Teams or Slack URL is itself the credential.
- **Config by environment only.** Rejected: a console-editable channel list. The URLs are secrets,
  and a destination writable over the API would let a stolen admin session redirect approval
  traffic. The `_FILE` twin lets the config come from a secret store.
- **SMTP STARTTLS, verified, no fallback.** Rejected: opportunistic TLS and a skip-verify switch. A
  downgrade would expose the SMTP password and the requester's identity on the wire.
- **Housekeeping of terminal rows (an addition to the approved scope).** Each tick deletes at most
  500 `sent`, `cancelled` or `dead` rows older than 30 days (§2). Rejected: keeping every row, which
  grows the table without bound on a busy install. The whole feature is off by default.
- **Escalation rows enqueued up front.** Rejected: a scheduler that computes the next tier on the
  fly. Up-front rows make the SLA projection a read and survive restarts with no extra state.

## Configuration

**Environment.**

- `WARDYN_APPROVAL_NOTIFY` 🔒 — JSON (§7). Unset or empty means off. Read once at boot; a change
  needs a restart.
- `WARDYN_APPROVAL_NOTIFY_FILE` — its `_FILE` twin, added to `secretFileSettings`
  (`cmd/wardynd/secret_file.go:28`), with the same refusals as every other twin.
- Both documented in `docs/ENV.md` beside `WARDYN_AUDIT_SINKS` (`docs/ENV.md:170`).

**Chart.**

- `WARDYN_APPROVAL_NOTIFY` joins the both-forms refusal list in
  `deploy/helm/wardyn/templates/secret.yaml:63`. It is delivered through `extraEnv` with a
  `secretKeyRef`, or through `env.WARDYN_APPROVAL_NOTIFY_FILE` from a Vault or CSI mount, as the
  `values.yaml` comments describe for the audit sinks.
- wardynd's NetworkPolicy is default-deny for egress. An operator adds a rule for the notification
  endpoints, the SMTP relay or the corporate proxy through `networkPolicy.egress.extra`
  (`deploy/helm/wardyn/templates/networkpolicy.yaml:181`), exactly as for SIEM sinks. The
  operations page says so.

**Compose.** `deploy/compose/docker-compose.yaml` passes `WARDYN_APPROVAL_NOTIFY` through with an
empty default, which boot treats as unset.

## Security model and residual risks

**What it protects.**

- Every new approval yields a notification or a recorded failure, even across a crash.
- No sandbox-authored text reaches a chat or mail channel.
- No credential leaves through a redirect.
- No destination secret appears in logs, audit rows, the Settings card or `/setup/status`.
- SMTP is never sent in clear.
- Approval authority stays in the console.

**Residual risks.**

1. **Duplicates.** At-least-once means a crash between send and finalise resends. Receivers that care
   deduplicate on `delivery_id`.
2. **A late "waiting" message.** The approval can be decided between the worker's re-read and the
   send. The message then points at an approval the console shows as decided. Bounded by one
   send's latency.
3. **Requester identity in a shared channel.** The payload carries the run owner's principal and
   email unless `redact_requester` is set on that channel (Q-NOT, accepted at the recommended defaults (owner ruling 2026-10-03)).
4. **Masking per replica.** Until the HA epic's shared masking registry lands, a replica that never
   saw a run's secrets masks with an empty set. No payload field is sandbox text, so the exposure
   is an identifier that coincides with a secret. Stated, not fixed here.
5. **The channel's own security.** A Teams workflow or Slack hook URL that leaks lets anyone post
   lookalike messages into that channel. Wardyn messages carry only one link, to the configured
   console, and approvals are decided only there. Operators should treat the URLs as secrets, which
   the `_FILE` path supports.
6. **Webhook receivers that skip verification.** A receiver that ignores `X-Wardyn-Signature` accepts
   forged events. The signature is documented with a test vector; checking it is the receiver's job.
7. **The SMTP password lives in the JSON config.** Same custody as the SIEM bearer token in
   `WARDYN_AUDIT_SINKS`. No new at-rest storage is introduced, so no new `kek.Seal` use arises.

## Upgrade and compatibility

- The migration only adds a table. The 0.8.5 binary refuses a database that has applied it (the
  standard unknown-migration refusal, `WARDYN_ALLOW_UNKNOWN_MIGRATIONS`, `docs/ENV.md:118`), so a
  downgrade is a restore from the pre-upgrade dump, as for every 0.8.6 migration.
- Unset config: no rows, no worker, no new response fields with values (`escalation_tier` and
  `sla_due_at` are `omitempty`). Older SDKs and CLIs ignore the new fields.
- Approvals that are pending at upgrade time get no notifications; only approvals raised after
  the config is set are enqueued.
- `CreateApproval` moving into a transaction changes no return value or error mapping; the
  existing approval tests pin that.

## Verification

- **Golden payloads.** For every kind, on every channel type, with a registered secret embedded in
  `requested_scope` and in the reason, the rendered body contains neither the secret nor any byte
  of the scope. The goldens are checked in.
- **Atomic enqueue.** Every kind through `store.PG.CreateApproval`, and `credential` through the
  broker's `ensureApproval` CTE, writes its outbox rows in the approval's transaction. A failure injected at the approval write, and one at the outbox write, each leave
  neither row. A crash at commit leaves neither. Concurrent duplicate raises leave exactly one
  approval and one set of outbox rows. The source guard finds exactly two insert sites.
- **Two workers.** `SKIP LOCKED` with two workers on one database delivers 100 rows exactly once
  when nothing crashes. A claim whose lease expired is reclaimed and sent. A stale finaliser loses
  its compare-and-set.
- **HMAC vector.** A fixed secret, timestamp and body produce the published `v1` value.
- **Delivery rules.** A 3xx is not followed and is recorded as `redirect_refused`. A URL with a
  signature in its query never appears in `last_error`, the audit row or the log. Five retryable
  failures produce one dead row, one audit row and one metric increment.
- **Escalation.** A tier-1 row is not sent before its `due_at`, is sent after it while pending, and
  is cancelled when the approval was decided first. `escalation_tier` and `sla_due_at` match the
  outbox rows.
- **SMTP.** A server without STARTTLS, and one with an unverifiable certificate, are both refused
  with no `AUTH` sent. A CR or LF in any header field is refused.
- **Off by default.** With the config unset, the approval suites see no outbox rows and no worker
  goroutine.
