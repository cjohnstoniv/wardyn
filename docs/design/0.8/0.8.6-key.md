# Wardyn 0.8.6 — key custody: AKV platform split, principal and domain keys

An adopter whose organisation mandates key custody asked three things of Wardyn's credential
storage: that the platform's own keys and people's credentials never share one key or one
identity, that each person's data sit under a key of its own that can be destroyed, and that a
tenant's data sit under a key the tenant controls. This record designs those three, plus two small
posture items from the same request: a deployment switch that refuses to boot without a key service,
and a FIPS build variant. It is the design record for the 0.8.6 key-custody epic; each lane below is
one task issue on the `0.8.6` milestone.

Every file:line below is `origin/main` at e0efee625 (v0.8.5).

## What already exists, and what does not

Some of what the adopter asked for has shipped, and the reply to them says so. This design does not
rebuild it.

- **The Transit platform split.** `WARDYN_VAULT_TRANSIT_KEY_PLATFORM` (`cmd/wardynd/secret_store.go:324`)
  wraps the boot keys under a second Transit key reached as a second Vault role, and
  `buildPlatformKEK` (`cmd/wardynd/secret_store.go:432-464`) refuses a shared role, a shared key, a
  token-file login, or any `WARDYN_KEK` other than `transit`. The threat model records what the
  split buys and what it does not (`threatmodel/THREAT-MODEL.md:2109`, residual 49(c)).
- **AES-256-GCM at rest.** Every value and every local wrap goes through `kek.Seal`
  (`internal/secretstore/kek/kek.go:113`), with the nonce drawn inside Go's cryptographic module.
  age only seeds the `local` key and converts pre-envelope rows.
- **A FIPS boot path.** The envelope runs under `GODEBUG=fips140=only`, and store mode boots under it
  (`docs/operations/secrets-and-keys.md:192-205`). The build does not pin a module snapshot, and the
  diagnostic test helper only re-executes the same binary (`internal/secretstore/secretstoretest/fips.go:23`).

What does not exist:

- **No platform split under Azure Key Vault.** Boot keys and credentials share one Entra identity and
  one key pair (`threatmodel/THREAT-MODEL.md:2098`, residual 48(d)). `buildPlatformKEK` is Transit-only,
  and `-rewrap-retire-platform-key` requires the Transit setting (`cmd/wardynd/rewrap.go:77-78`).
- **No per-person key.** Each row has its own data key, but every data key is wrapped directly by the
  deployment's one credential KEK, so "destroy this person's key" has nothing to destroy.
- **No tenant boundary.** One credential KEK wraps every person's rows.
- **No custody floor.** A deployment that mandates a key service has no way to make wardynd refuse
  to start on the `local` key. The `/setup/status` rows (`internal/api/setup_checks.go:312-342`) only
  describe the posture. `Blocking` gates the console, not boot (`internal/api/setup_checks.go:31`).
- **No published FIPS artifact.** `go.mod:3-5` pins the toolchain, not a `GOFIPS140` snapshot.

## Decisions

### K1: a custody floor at boot, not a setup row

`WARDYN_KEK_REQUIRED` (chart `kek.required`) makes the **serving** boot refuse when the flag is set,
the pg store has no key service (`KeyService()` is empty, `internal/secretstore/pg/pg.go:266`), and
store mode does not hold the credentials, whether or not `WARDYN_AGE_KEY` or an OIDC issuer is set. With
no age key, `newSecretStore` generates an ephemeral local key (`cmd/wardynd/secret_store.go:158-171`),
which is the same posture and is refused too. The message starts "refusing to
start:" and names `WARDYN_KEK=transit|azurekv` and `wardynd -rewrap`, as `refuseIdleAgeKey` does
(`cmd/wardynd/secret_store.go:271-287`). A `/setup/status` row `kek_required_unmet` (status `fail`)
reports the same posture, but only reports it.

- The check sits in the serving path beside `refuseIdleAgeKey`, not in `newSecretStore`, which the
  maintenance modes also use (`cmd/wardynd/secret_store.go:152`). `wardynd -rewrap` is the named remedy,
  so it must still run with the flag set.
- Store mode (`WARDYN_SECRET_STORE=vaultkv|azurekv`) keeps the credentials in the organisation's store
  and holds no Wardyn key over them, so it meets the floor. Its pg store reports an empty
  `KeyService()`, so the predicate checks `StoresExternally()` too (`cmd/wardynd/secret_store.go:518`).
- `platform_shared` is unchanged. It is not emitted under a key service (`internal/api/setup_checks.go:316-325`).
- The chart has no `NOTES.txt` today. K1 adds `deploy/helm/wardyn/templates/NOTES.txt`, which warns at
  install when `kek.provider` is `local` (`deploy/helm/wardyn/values.yaml:311`).

Rejected: **changing the default to a key service.** Every install without Vault or Key Vault would
stop booting. Rejected: **a `Blocking` setup row.** It hides the console, which is the adopter's only
diagnostic surface, and it does not stop wardynd serving the API.

### K2: a FIPS image variant, with proof that it is one

A pinned `GOFIPS140=<frozen, validated module snapshot>` build of wardynd, published as an extra
`-fips` image tag and signed like the others. The snapshot name (for example `v1.0.0`) is taken from Go's
FIPS 140-3 documentation at build time, and the lane records which validation certificate it refers
to.

- **Build.** A `GOFIPS140` build argument in `deploy/compose/Dockerfile.wardynd` beside
  `GO_BUILD_TAGS` (`:128`), and a `wardynd-fips` row in the nightly multi-arch matrix next to `wardynd`
  (`.github/workflows/nightly.yml:607-612`), staged like it. In `release.yml`, a `wardynd-fips` row in
  both the `images` matrix (`:332`, the build path every tag push runs) and the `promote` matrix
  (`:693`), cosign-signed like the other images, with the `go version -m` assertion in the `images` job.
- **Metadata check.** In CI, `go version -m` on the built binary must show the pinned `GOFIPS140`
  build setting. Without this, an image tagged `-fips` could hold an ordinary binary.
- **Serving proof.** On kind, the `-fips` image boots with Transit custody and no age key under
  `GODEBUG=fips140=only`, and serves a run. Under `only`, age's X25519 is refused, so the variant is
  for non-age custody (Transit, Key Vault or store mode). That is already the documented boot
  behaviour (`docs/operations/secrets-and-keys.md:199-205`).
- **Docs.** Two separate statements: Wardyn's `-fips` image "uses a FIPS 140-3 validated Go
  cryptographic module", and "Wardyn itself is not certified". Nothing claims the second.

Rejected: **relying on `GODEBUG=fips140=only` at runtime.** It is a diagnostic. It does not select a
validated module snapshot, and the existing test helper passes for an ordinary build.

### L3.1: the Key Vault platform split mirrors Transit's

Three new settings: `WARDYN_AZURE_KEK_KEY_PLATFORM`, `WARDYN_AZURE_KEK_SIGNING_KEY_PLATFORM` and
`WARDYN_AZURE_CLIENT_ID_PLATFORM`. With them, the boot keys are wrapped and signed by a second key pair,
reached as a second Entra identity, and the credential identity reaches no boot key.

- `buildPlatformKEK` (`cmd/wardynd/secret_store.go:432`) gains a Key Vault arm that builds
  `azurekv.NewKEK` (`internal/secretstore/azurekv/kek.go:100`) with the platform keys and the platform
  client id. The KEK's boot self-test proves the pair, as it does for the credential pair.
- **Refusals.** Boot refuses when a platform key equals its credential-side counterpart (the wrapping
  key, the signing key or the client id), when the platform keys are set without
  `WARDYN_AZURE_CLIENT_ID_PLATFORM`, when they are set without `WARDYN_KEK=azurekv` (except under
  `-rewrap-retire-platform-key`, as for Transit at `cmd/wardynd/secret_store.go:437`), or when only one
  of the platform pair is set. Naming both a Transit and a Key Vault platform key refuses, as the
  credential side already does (`cmd/wardynd/secret_store.go:374-375`).
- **Rewrap.** `-rewrap-adopt-boot-keys` and `-rewrap-retire-platform-key` accept the Key Vault
  platform key (`cmd/wardynd/rewrap.go:77-78` names only the Transit setting today). The completion
  message stops assuming Transit: the platform version is reported through `retireStep`
  (`cmd/wardynd/rewrap.go:166-171`), not the Transit-only sentence at `:159`. The pg store already
  takes any `kek.KEK` as `PlatformKEK` (`internal/secretstore/pg/pg.go:103-110`), so the store
  needs no new mode.
- **Chart.** `kek.azurekv.keyPlatform`, `kek.azurekv.signingKeyPlatform` and
  `secretStore.azure.clientIdPlatform`, with render-time refusals next to the Transit ones
  (`deploy/helm/wardyn/templates/secret.yaml:273-280`). Under workload identity the second identity
  needs its own federated credential that trusts the same service account. The docs say so.

Rejected: **one identity, two key pairs.** A leaked credentials-side Entra token would still sign a
planted boot key, and that is the attack the split exists for (residual 48(d): `sign` is
credential-equivalent). Rejected: **requiring a second vault.** Key Vault RBAC can scope a role
assignment to a single key. A dedicated vault stays the recommendation in the docs, not a boot rule.

### SK0 and L3.2: one per-subject key table, used by credentials, audit sealing and masking

**One table, `principal_keys`**, keyed by `(owner, purpose, version)`. `purpose` is `cred` or
`audit-seal`. Each row's 32-byte key is wrapped under its key domain's KEK through the existing
`kek.KEK` interface, so local, Transit and Key Vault all work unchanged. There is no separate
audit-subjects table. The masking registry and the run masking manifest (HA) use the owner's `cred`
key too.

**Envelope v2 is on-disk `enc_version=3`.** Version 2 already means an external-store pointer
(`internal/secretstore/pg/external.go:21-31`): `open` dispatches it to `openExternal`, which parses
`kek_id` as `store:ref` (`external.go:51-55`), and `deleteLocked` and ordinary rewrap special-case
it (`external.go:195-221`, `pg.go:809`). A principal-key row with version 2 would read as a pointer
into a store called `pk`. So principal envelopes take version 3, with `kek_id="pk:v<n>"`, and every
v2 meaning is preserved. "Envelope v2" stays the design name, and the code says `enc_version=3`.

**Row data keys** are wrapped locally under the principal key with `kek.Seal`, with AAD
`Encode("wardyn/pk/v1", owner, name, version)`. The value under the data key keeps today's binding
(`secretAAD`, `internal/secretstore/pg/pg.go:341`).

**Principal-key wraps get their own canonical AAD.** Today every provider binds a wrap to
`Encode("wardyn/kek/v1", owner, name, kek_id)` (`WrapAAD`, `internal/secretstore/kek/kek.go:260-271`).
A principal-key wrap binds `Encode("wardyn/pk-wrap/v1", owner, purpose, version, domain, kek_id)`
instead, carried as new bind keys, so it changes in one place for all three providers. Because the label
differs, a principal-key wrap can never verify as a `secrets` row's wrap. A wrap moved to another
owner, purpose, version or domain does not unwrap.

**`WARDYN_PRINCIPAL_KEYS=off|on`**, default `off`, governs only `secrets` writes. With it off, 0.8.6
reads v3 rows and writes v1. The `subjectkey` package itself is always live, because HA's manifest and
AR's audit sealing write `principal_keys` rows whatever the flag says.

Rejected: **reusing `enc_version=2`** (it breaks or is broken by the external-pointer rows). Rejected:
**a `secrets` column for the owner key**, because audit sealing and masking need the same key outside
`secrets`. Rejected: **a table per purpose.** Two tables would mean two rotation inventories, and one
of them would be missed.

### SK0's cache, Destroy and generations

`internal/secretstore/subjectkey` offers generate, wrap, unwrap, a bounded LRU of unwrapped keys with
a five-minute lifetime, and `Destroy(owner, purpose)`, which `erasure.Orchestrate` (AR) calls.

- **The revocation check is durable and per use.** A cache fill and every use read that key version's
  `destroyed_at` (a primary-key read). A set `destroyed_at` evicts the entry and returns a data-loss
  error. This is the "durable revocation generation per subject-key version" the AR design requires.
  A warm cache on another replica stops decrypting at its next use, with no notification needed. If
  Postgres does not answer, the use fails closed. The cache saves the KEK round trip, not the check.
- **Destroy is a tombstone.** In one transaction it sets `destroyed_at` and clears `wrapped_key` on
  **every** historical generation of `(owner, purpose)`, and writes the audit row. Rows are never
  deleted, so a version number is never reused. The app role needs no `DELETE` on the table.
- **A new generation.** The first write after a Destroy creates version `max+1`. A partial unique
  index allows one live generation per `(owner, purpose)`. A concurrent first write is serialised by
  `INSERT … ON CONFLICT DO NOTHING` followed by a re-read.
- **Eviction** clears the key's byte slice. Go's runtime may already have copied it, so this is best
  effort, and the residuals say so.
- **Never a platform key.** `owner=""` (the operator namespace, which holds the boot keys) is refused,
  as `secretstore.EraseOwner` refuses it (`internal/secretstore/secretstore.go:267-270`). Boot keys stay
  on the platform KEK and are never erasable subject keys.

### Sequencing: root rotation covers `principal_keys` from the first row

The plan puts root-rotation coverage of `principal_keys` in L3.2. That leaves a window: `ha-l2.0`
(W1, stacked on `key-sk0`) and `ar-l1.4` (W2) write `principal_keys` rows wrapped under the root KEK
while credential rows are still v1. Today's `-rewrap` enumerates `secrets` only (`rewrapAll`,
`internal/secretstore/pg/pg.go:797-809`). It would rewrap every `secrets` row, report that every
older key version can be retired (`cmd/wardynd/rewrap.go:146-154`), and leave the principal keys under
the version it just called retirable. `LocalRows` (`internal/secretstore/pg/convert.go:118-126`) counts
`secrets` only, so `refuseIdleAgeKey` could tell the operator to unset an age key that still wraps
principal keys.

So the coverage lands with the table, in `key-sk0`:

- `RewrapKeys`/`Rekey` (`pg.go:561`, `:641`) rewrap `principal_keys.wrapped_key` for **every purpose
  and every domain**, each onto the latest version of **its own domain's** KEK, never across domains.
  The `secrets` rewrap skips v3 rows, whose data keys are under a principal key, not the root. Today
  `rewrap` aborts on any version other than 1 (`pg.go:885-886`).
- The safe-to-retire report (`RewrapResult.KeyVersion`, `rewrap.go:148-154`) names a version only when
  `secrets` **and** `principal_keys` are both at it, and `secret.rewrap` gains a `principal_keys`
  count.
- `LocalRows` counts `principal_keys` rows wrapped under a local key.

L3.2 keeps what belongs to the credential rows: the v3 format, the flag, the path audit and
`-rewrap-principal-keys`. That flag moves **credential rows into** principal envelopes. It is a
separate operation from rotating the root that wraps the principal keys.

### L3.2: every v3 path, named

Every reader, writer, delete, expiry, migration and rotation path is checked for v3:

| Path | Today | With v3 |
|---|---|---|
| `Put` (`pg.go:293`) | writes v1 | writes v3 when the flag is on |
| `open` (`pg.go:388-397`) | v0 refuses, v2 goes to external, any other version refuses | v3 unwraps the principal key, then the data key |
| `deleteLocked` (`external.go:195`), `DeleteEverywhere` (`pg.go:454`) | v2 deletes the external value first | v3 deletes the row; no external call |
| `DeleteExpired` (`internal/secretstore/pg/expiry.go:34`) | by row | unchanged, and reported as deletion |
| `Migrate`, `atTarget` (`external.go:250`, `:289`) | v1 to and from external | v3 opens through the principal key; moving to an external store leaves a v2 pointer |
| `Reconcile` (`external.go:442`) | v2 only | unchanged |
| `metadata` (`internal/secretstore/pg/meta.go:48-60`) | reads `split_part(kek_id, ':', 1)` | `pk` is reported as the principal-key format, not a store |
| `Rekey`, `RewrapKeys`, `rewrapAll`, `rewrap` (`pg.go:561`, `:641`, `:797`, `:881`) | abort on v3 | skip v3 `secrets` rows; rewrap `principal_keys` (SK0) |
| `LocalRows` (`convert.go:118`) | `secrets` only | also `principal_keys` (SK0) |
| `ConvertV0` (`convert.go:29`) | v0 only | unchanged |

Key lifecycle:

- **Erasing a person's credentials** (`handleErasePersonCredentials`, `internal/api/credential_erase.go:55`)
  destroys their `cred` principal key after the rows are gone.
- **Reconnecting** after an erase creates a fresh generation.
- **The erase report is honest about form.** v3 rows under a destroyed key are reported as
  crypto-erased. v1 rows, and rows written while the flag was off, are reported as deleted, which
  holds only to the backup horizon (residual 48(a)/(b)). External pointer rows are reported as deleted
  in the external store, with `purged`/`recoverable_days` as today.

### L3.3: key domains come from deploy config only

A **key domain** is a tenant: a name mapped to a Transit key and an optional Vault role, or to a Key
Vault key pair and an optional client id. Domains come **only** from `WARDYN_KEY_DOMAINS_FILE` and are
proven at boot. Each domain's KEK is built and runs its self-test (round trip, plus refusal under
another row's binding), as the credential KEK does.

Boot also refuses when:

- a domain names the same key as another domain, as the platform key or as the default credential KEK;
- a live `principal_keys` row names a domain the file no longer declares;
- a live row names a `kek_id` that its domain no longer reaches.

The `default` domain is the deployment's credential KEK (`WARDYN_KEK`). Until L3.3, every principal
key is in `default`.

**Membership** is set by API in `key_domain_assignments(subject_type, subject, domain, set_by, set_at)`,
using the governance subject vocabulary (`subject_type IN ('user','group','all')`,
`internal/db/migrations/0052_governance_profiles.sql:84`).

- A user assignment wins over a group assignment. Group-derived membership from IdP claims is preferred
  where the person's last verified login carries groups.
- Two group assignments that name different domains refuse the new generation by name rather than pick
  one. Fail closed.
- No match means `default`.
- **Assignment writes are covered by four-eyes** when `WARDYN_GOVERNANCE_SECOND_HUMAN` is on. `gov4-b2`
  owns that coverage (it adds `key_domain_assignment` to the GOV4 covered set); `key-l3.3` splits its
  write handlers into validate plus `apply` so they can be queued. Every change is audited.

**Domain binding is immutable per version.** A domain change applies to the **next generation**: the
next write after a reassignment creates a new generation in the new domain. Old generations stay in
their old domain and are never re-wrapped into another, because that would expose history to the new
domain's key holder. `-rewrap-principal-keys` can then re-seal the person's credential rows into the
new generation, which re-encrypts data keys and never moves the old principal key.

Rejected: **domains as database rows.** A database writer could then point new keys at a key the
attacker holds. Rejected: **re-wrapping a person's existing key into the new domain on reassignment.**
That would expose every historical row to the new domain's key holder.

## Data model and migrations

Numbers are "next free" at merge (origin/main's highest is `0106_attach_ticket_authority.sql`). The
steward renumbers in merge order. Neither migration ALTERs an older table, so no migrator-rationale row
is needed in OPERATIONS.

- **`key-sk0`, next free (0107 on origin/main today):** `principal_keys(owner TEXT NOT NULL CHECK
  (owner <> ''), purpose TEXT NOT NULL CHECK (purpose IN ('cred','audit-seal')), version INT NOT NULL,
  domain TEXT NOT NULL, kek_id TEXT NOT NULL, wrapped_key BYTEA, created_at, destroyed_at TIMESTAMPTZ,
  PRIMARY KEY (owner, purpose, version))`. A `CHECK` requires `wrapped_key` to be non-null exactly while
  `destroyed_at` is null. A partial unique index on `(owner, purpose) WHERE destroyed_at IS NULL`
  allows one live generation.
- **`key-l3.2`:** no schema change. `secrets.enc_version` is a `SMALLINT` with no `CHECK`
  (`internal/db/migrations/0069_secret_envelope_v1.sql:26`).
- **`key-l3.3`, next free:** `key_domain_assignments(subject_type TEXT NOT NULL CHECK (subject_type IN
  ('user','group','all')), subject TEXT NOT NULL, domain TEXT NOT NULL, set_by TEXT NOT NULL, set_at
  TIMESTAMPTZ NOT NULL, UNIQUE (subject_type, subject))`. `domain` is checked against the file in
  code, not in SQL, because the file is the authority.

Split-role installs grant the app role `SELECT, INSERT, UPDATE` on `principal_keys` and `SELECT,
INSERT, UPDATE, DELETE` on `key_domain_assignments`, per OPERATIONS "Splitting the migrator and app
roles" (`docs/OPERATIONS.md:5155`).

## API, audit and refusals

- **`key-l3.3` API**, on the `securityOps` tier: `GET /key-domains` (the declared domains and their
  boot proof, read-only); `PUT` and `DELETE /key-domains/assignments/{subject_type}/{subject}`. With
  four-eyes on (`gov4-b2`), a write returns `202` and a pending change.
- **New audit actions**, each added to `docs/AUDIT-ACTIONS.md`:
  - `principal_key.destroyed` (owner, purpose, generations; never key material);
  - `key_domain.assignment.set` and `key_domain.assignment.delete` (subject, old and new domain).

  Fields added to existing actions: `secret.rewrap` gains `principal_keys`; `credential.erase` gains
  the crypto-erased and deleted counts.
- **New refusal reasons**, registered in `internal/authz/registry.go` and documented: an unknown domain
  on assignment, and an ambiguous group membership at generation time.

## Custody inventory

A domain-custody or erasure claim is only as good as the list of places a person's secret is copied.
This is that list, and each copy is bound to the boundary named.

| Copy | Sealed under | Erased by |
|---|---|---|
| `secrets` rows, v3 | the person's `cred` principal key, in their domain | Destroy (crypto-erasure) |
| `secrets` rows, v1 / flag off | the domain-less credential KEK | row delete (to the backup horizon) |
| External pointer rows (v2) | the organisation's store | external delete, as today |
| `mask_values`, per-run and per-owner globals (HA L2.1) | the owner's `cred` principal key | `mask_copies` scope, after fencing consumers |
| `run_mask_manifest` (HA L2.0) | the run owner's `cred` principal key | erasure, after fencing that run's consumers |
| Sealed audit fields (AR L1.4) | the subject's `audit-seal` principal key | Destroy |
| ADO run-PAT value rows (HA L2.4) | must be the run owner's `cred` principal key | erasure; until then excluded from the claim |
| Shared-credential mask globals (`owner=""`) | the platform `wardyn-mask-key` | not a person's; outside domains |

The ADO run-PAT row is a requirement this design places on `ha-l2.4`. Its plan text says "sealed with
`kek.Seal`" and names no key. The tests that prove the claim (purge on replica B of values registered
on A, both restarted, and no live credential-bearing table decryptable with the remaining platform
keys) belong to the HA and AR lanes.

## Security model and residual risks

What principal and domain keys buy:

- **A database dump plus one domain's key exposes that domain only**, for rows written while the
  subject's membership was unchanged. Without any domain key, it exposes nothing beyond what residual
  48(c) already lists (metadata in the clear).
- **A person's destroyed key makes their v3 rows, sealed audit fields and masking copies
  undecryptable** on every replica at its next use, with no notification.
- **Forging a principal key needs the domain's KEK**: the same property F2 gives the root wrap. A
  planted `principal_keys` row under a key the attacker holds names a `kek_id` no domain reaches, and
  is refused.

What stays open:

- **Assignment rewrites.** A database writer who rewrites `key_domain_assignments` moves a subject's
  **future** writes into a domain whose key the attacker holds. Mitigations: four-eyes coverage of the
  API, an audited change, and a `/setup/status` row listing assignment changes in the last 30 days
  (L3.4). A database writer is already super-admin-equivalent (residual 48).
- **A compromised wardynd process still exposes everything.** It holds every domain's client.
- **Shredding is complete only after backups expire or the KEK version is retired.** A destroyed
  `principal_keys` row restored from a backup unwraps while its KEK version lives. This is residual
  48(a)'s shape.
- **The cache holds keys in process memory.** Clearing on evict is best effort under Go's runtime.
- **Credential erase versus live runs.** `credential.erase` does not reach into a running run
  (`internal/api/credential_erase.go:139-140`). Destroying the `cred` key makes that run's manifest
  undecryptable, so after a restart the run is honestly uncovered and refused at the HA doors. It fails
  closed and is disclosed.
- **The Key Vault platform split** has the same limits as Transit's (`threatmodel/THREAT-MODEL.md:2184-2192`).
  The process holds both identities. It holds only while the credential identity's role assignments
  leave the platform keys out, which Wardyn cannot check. Adoption and retirement are moments where
  one key vouches for the boot keys. Under workload identity, both client ids exchange the same
  projected token, so the split defends against a leaked Entra access token, not a leaked
  service-account token.
- **FIPS.** The `-fips` image uses a validated module. Wardyn is not certified. Paths that need
  non-approved primitives under `fips140=only` are listed by the K2 lane from its kind run.

Threat-model edits: residual 48(d)'s "there is no platform split like Transit's" is rewritten by
`key-l3.1`; residual 49 gains the Key Vault split; `key-l3.3` adds a residual for assignment rewrites
and the per-domain blast radius.

## Upgrade and compatibility

- Every switch here defaults to today's behaviour: `kek.required=false`, no platform keys,
  `WARDYN_PRINCIPAL_KEYS` left at its default (off), no domains file.
- `principal_keys` rows appear on upgrade only once HA's manifest or AR's sealing writes them. Root
  rotation covers them from the first row (SK0).
- **Rolling back below 0.8.6** after any v3 row exists makes those rows unreadable: 0.8.5 refuses an
  unknown `enc_version` by name (`internal/secretstore/pg/pg.go:48`, `:395-396`). Turning the flag off
  within 0.8.6 is safe, because 0.8.6 reads v3 with it off. The plan provides no v3-to-v1 tool. The
  release note says enabling principal keys is one-way across a downgrade. The upgrade itself is the
  stopped-writer Recreate upgrade the AR design defines.
- The `-fips` image is an additional tag. The default image is unchanged.
- Existing Key Vault installs keep one identity until they set the platform keys and run
  `wardynd -rewrap -rewrap-adopt-boot-keys` once.

## Verification

- **K1:** `go test ./cmd/wardynd/` has a table over the predicate. wardynd exits non-zero with the
  reason when the flag is set and neither a key service nor store mode holds the credentials (with and

  `-rewrap` runs with the flag set. `helm template ... | grep -q WARDYN_KEK_REQUIRED` shows the env
  wiring; `helm install --dry-run=server ... --set kek.provider=local` on kind prints the `NOTES.txt`

- **K2:** both a tag push (build path) and a promote dispatch publish a cosign-signed `-fips` tag. CI's
  `go version -m` check shows the pinned `GOFIPS140`. A kind boot with Transit under `GODEBUG=fips140=only` serves a run.

  - round trip;
  - cross-person and cross-purpose unwrap fails;
