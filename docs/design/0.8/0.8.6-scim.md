# Wardyn 0.8.6 — leaver deprovisioning (SCIM)

An adopter runs Wardyn behind a central Entra ID identity team whose joiner-mover-leaver process
provisions every application over SCIM. Today Wardyn has no way to hear that a person has left
or moved: an admin has to remember to cut their sessions, revoke their tokens, delete their SSH
keys and kill their runs, by hand, one route at a time. This design adds a SCIM 2.0 endpoint
whose only job is to **remove access** when the identity provider says so, durably and across
every replica.

All file:line references are to `origin/main` at `e0efee625` (v0.8.5).

## Goals and scope

- A SCIM 2.0 subset at `<base path>/scim/v2`: Users (GET with a filter, POST, PATCH, PUT,
  DELETE) and Groups (GET, POST, PATCH members, DELETE).
- **Suspend** (`active=false`): sessions cut, API tokens revoked, SSH keys deleted, the identity
  deactivated so no new sign-in completes, and every live run killed with its teardown confirmed.
- **Purge** (DELETE, or a fixed delay after suspension): suspend, then erase stored credentials
  through the one erasure entry point, reassign workspaces, delete user-subject grants and
  assignments, and list (not reclaim) drives.
- **Reactivate** (`active=true`): clears the deactivation and nothing else.
- **Movers**: removing a person from a group cuts their sessions and revokes that person's API
  tokens whose group snapshot holds that group.
- The deactivation is enforced at authentication on every replica, including against a sign-in
  that was already in flight when the suspension landed.

### What this is not

- **SCIM never grants.** A user or a group created over SCIM, and a group membership added over
  SCIM, are stored and grant nothing. Roles still come from the sign-in token and the role map.
- Not a directory sync, not just-in-time provisioning, not SAML.
- No `/ServiceProviderConfig`, `/Schemas`, `/ResourceTypes`, `/Bulk`, sorting or paging beyond
  what the Entra provisioning client sends. Filters are `attr eq "value"` only.
- Drives are listed on purge, never reclaimed.

## What exists today

- **People.** `people` (migration 0090) holds people an admin set up before their first sign-in;
  migration 0099 adds `issuer`, `tenant_id`, `object_id` so an Entra person can be keyed by
  object id. There is no deactivation column. `PersonStore` (`internal/store/store_people.go:21`)
  has create, get, list and mark-signed-in only.
- **Most Entra sign-ins have no `people` row.** Entra's `sub` is pairwise per application, so an
  ordinary sign-in keys by `sub` (`internal/api/people.go:289-322`). `PersonKeying.PrincipalFor`
  (`internal/auth/oidc/oidc.go:223-227`) can refuse a login, but only for a subject that names an
  object-id person this token does not carry, and only on an Entra issuer
  (`internal/auth/oidc/oidc.go:273-277`). No login path resolves a human by email.
- **Admission order.** The callback's `admit` (`internal/auth/oidc/oidc_callback.go:332`) runs the
  reserved-subject check, `resolvePerson` (`:347`), the email policy, then `deriveLogin` (`:379`).
  After admission, `OnLogin` (`:286`) and the login-grant capture (`:293`) run, then the cookie is
  stamped with `IssuedAt` and written (`:297-301`).
- **Session cutoff.** `SessionRevocations` is wired by default whenever OIDC is
  (`cmd/wardynd/boot_deps.go:417`). Middleware checks every cookie's `IssuedAt` against the cutoff
  for its sub and its email on every request and fails closed on a store error
  (`internal/auth/oidc/oidc.go:456`). `POST /sessions/revoke` calls `RevokeSub`
  (`internal/api/sessions.go:114`).
- **`OnLogin`** (`internal/auth/oidc/oidc.go:101`, wired at `cmd/wardynd/boot_deps.go:437`)
  re-stamps role, user type and groups on the person's SSH keys and API tokens. It is best-effort:
  a store error logs and the login proceeds.
- **Token and key removal.** `revokeAPITokensFor` (`internal/api/sessions.go:192`) and
  `deleteSSHKeysFor` (`internal/api/sshkeys_admin.go:43`) both take an `*http.Request`, so nothing
  without a request can call them. API tokens carry a `groups` snapshot (`0045_api_tokens.sql:62`) and a `groups_truncated` flag (`0052_governance_profiles.sql:110`).
- **Kill.** `killRunCascade` (`internal/api/runs_lifecycle.go:733`) wins the KILLED CAS, then tears
  down and revokes, and returns `(applied, errMap, err)`. A lost CAS returns `false` with nothing
  torn down. KILLED→KILLED is allowed precisely so a failed teardown can be repaired
  (`runs_lifecycle.go:772-779`, `internal/api/kill_rekill_test.go:44`). Nothing on the ordinary
  paths revisits a KILLED run whose teardown failed (`runs_lifecycle.go:811-831`).
- **Credential erasure.** `DELETE /people/{principal}/credentials`
  (`internal/api/credential_erase.go:55`) erases one person's namespace through `eraseLocked`
  (`:141`) under the three ordered locks (`:115-140`).
- **Workspace reassign.** `POST /workspaces/{id}/reassign` hands a member's workspace to the
  operator, idempotently (`internal/api/workspace_owner.go:43`, `SetWorkspaceOwner`,
  `internal/store/iface.go:78`).
- **Operator gate.** `isOperator` reads a request with no OIDC human as the admin token
  (`internal/api/http.go:561`), unless `neverOperator` (`internal/api/delegation.go:150`) says the
  caller is a device or a delegated portal (`http.go:558`, `:599`).
- **Shipped claims this changes.** `README.md:273`, `ROADMAP.md:157` and the boot log lines at
  `cmd/wardynd/boot_deps.go:450,465` say SCIM does not exist.

## Decisions

**1. SCIM only removes access.** Every SCIM write either records a projection or removes access.
A created user, a created group and an added member are stored and grant nothing; no authorisation
decision reads a SCIM table. *Rejected:* SCIM-driven role or group grants. They would make the
SCIM bearer token an admin credential, and the adopter's ask is the leaver path.

**2. The identity binding is immutable; `userName` and `emails` are a mutable projection.** Once
bound, an identity's issuer, tenant id, object id and principal never change. Entra updates
`userName` and `emails` on renames and domain changes, so those are accepted as projection
updates. A projection update never grants access and never rebinds an identity, and every old
value is kept as a historical **removal alias**. A PUT or PATCH that would change `externalId`
(the binding) on a bound identity is refused with 400 `invalidValue` and audited. *Rejected:*
refusing `userName`/`emails` changes on bound identities. That breaks the documented Entra rename
flow, stops Wardyn learning the new alias a later removal needs, and a combined update could take
`active=false` down with it.

**3. Removal outranks PATCH atomicity, and only removal.** A PATCH is pre-validated in full and
applied in one transaction. The one exception: when the only invalid operation is a refused
`externalId` change and the same PATCH sets `active=false`, the suspension still runs, and the
response is the 400 for `externalId`. *Rejected:* strict all-or-nothing, which would leave a
leaver active because of a mapping mistake; and silently accepting the binding change, which
rebinds an identity.

**4. Deactivation and the authority epoch live on `principal_identities`, not `people`.** Most
Entra sign-ins have no `people` row, so a new `principal_identities` table holds one row per
`(principal, issuer, tenant_id, object_id)`, created at first sign-in. A SCIM suspension for
someone who has never signed in **upserts** the row from the SCIM match, with the principal still
unbound; the first sign-in binds it. `people.deactivated_at` is also set where a people row
exists, for the People view and `PrincipalFor`. *Rejected:* deactivation on `people` alone, which
misses every sub-keyed sign-in.

**5. Matching order: `externalId` = object id, then `entra:<tid>:<oid>` people rows, then email.**
Admins map Entra's `objectId` to SCIM `externalId`; the docs say so and the endpoint treats it as
required. The tenant comes from the configured Entra issuer through `entraTenantFromIssuer`
(`cmd/wardynd/boot_posture.go:305-316`). That helper returns the issuer's raw first path segment,
so a multi-tenant issuer yields the literal `common`, `organizations` or `consumers`, not an empty
string, and the directory connector only refuses the empty case (`boot_posture.go:290-296`). SCIM
therefore refuses to mount (boot fails) when the derived tenant is empty or, case-insensitively,
`common`, `organizations` or `consumers`. Mounting on such a tenant would match `externalId`
against `entra:common:<oid>` people rows, while people rows are keyed by the token's real `tid`
(`internal/api/people.go:289-299`), so a leaver's suspension would silently miss. Email is used
only to fan **out** removals: an email match links a SCIM user to an identity
as a removal target only when that identity has no object id, and it never sets binding columns.
*Rejected:* matching by object id across tenants, and resolving a person by email for anything
but removal.

**6. Every issuer is gated; matching is specified for Entra.** The new per-principal check runs
for every issuer, not only Entra (today `resolvePerson` returns early for non-Entra issuers,
`oidc.go:275`). A non-Entra identity row has an empty tenant and object id and is keyed by
`(issuer, principal)`. The SCIM routes themselves mount only on a single-tenant, commercial-cloud
Entra issuer (Decision 5: `entraTenantFromIssuer` returns empty for any other host), so SCIM is
Entra-only and the docs say so; the gate still runs for every issuer, so a deactivated identity
row refuses sign-in whatever wrote it.

**7. A durable authority epoch, checked at authentication, and a serialised issuance.** A
cookie's `IssuedAt`-versus-cutoff check is not enough: a callback can pass admission, pause, and
finish after the suspension, stamping an `IssuedAt` newer than the cutoff.
- Each identity row carries `authority_epoch`, bumped by every suspension and never lowered.
- Session issuance re-checks deactivation and reads the epoch inside a transaction that holds the
  identity row `FOR SHARE`. Suspension takes the same row `FOR UPDATE`. So a callback either
  commits before the suspension (and its cookie carries the old epoch) or reads the deactivation
  and is refused.
- The cookie carries the epoch (`ae`, omitempty). Middleware compares it with the row's current
  epoch and deactivation in the same round trip as the existing revocation check, so a cookie
  minted before a suspension stops at its next request. API tokens (`internal/api/apitokens.go:98`)
  and SSH keys (`internal/api/sshgateway.go:258`) check the owner's identity row the same way.
- The login-grant capture (`internal/auth/oidc/login_grant.go:184`) writes conditionally on the
  epoch it was admitted under. Run create (`internal/api/runs.go:153`), dispatch
  (`internal/api/runs_dispatch.go:143`), stored-credential writers, API token creation
  (`POST /api/v1/me/tokens`) and SSH key registration (`POST /api/v1/me/ssh-keys`) re-check the
  owner's epoch inside their insert transaction, since `api_tokens` and `ssh_public_keys` carry no
  epoch of their own.
- The identity rows are **non-granting tombstones**: purge never deletes them and reactivation
  never lowers the epoch, so nothing minted before a suspension works again after a reactivation.
- Every check fails closed on a store error, as the cutoff check already does.
- Suspension writes the cutoff, the deactivation and the epoch bump in one transaction (step 1),
  before it sweeps tokens and keys (step 2), so every credential minted under the old epoch is
  either swept or refused.
*Rejected:* relying on `PrincipalFor` plus an atomic cutoff write, which a reproduction showed
still authenticates the late cookie.

**8. Deprovisioning is a durable job, and SCIM is acknowledged only after its effects.** A
`deprovision_jobs` table persists each pending step and target. A retry or a restart resumes the
failed tail, **including runs already KILLED whose teardown failed**: those are re-killed through
the KILLED→KILLED repair path. `killRunCascade`'s error map is inspected (a non-empty map leaves
the target pending), and a lost CAS re-reads the run rather than counting as success. The handler
returns 5xx until every required step succeeds, so Entra retries. *Rejected:* selecting only
non-terminal runs on each retry, which loses a KILLED run whose runner or broker cleanup failed.

**9. SCIM has its own authentication and can never be an operator.** `scimAuth` compares the
bearer against `WARDYN_SCIM_TOKEN` or `WARDYN_SCIM_TOKEN_NEXT` in constant time (over SHA-256
digests, so length does not leak). Requests it admits carry a context marker that `neverOperator`
answers true for; without it, `isOperator`'s no-human arm (`http.go:561`) would read the SCIM
caller as the admin token. *Rejected:* reusing the admin token or an API token, which would give
the IdP connector full admin authority; OAuth client credentials and mTLS (Q-SCIM4).

**10. Purge goes through the one erasure entry point.** Purge calls `erasure.Orchestrate` (AR
design) with the `credentials` scope, which keeps today's `eraseLocked` behaviour and locks, and
`mask_copies`, which removes the person's credential values held for masking. Record scopes
(`audit_personal_fields`, `run_tasks`, `run_outputs`, `recordings`) are not part of the
recommended default purge (Q-SCIM5). This deviates from the AR design, which says SCIM purge opts
into the documented record scopes; Q-SCIM5 puts the choice to the owner, and the purge's scope set
follows the ruling. *Rejected:* a SCIM-only erasure path, which would drift from the scoped,
fenced erasure every other caller uses.

**11. Group adds are not audited; group removals are.** Created groups and added members change
no access, so they are recorded in the SCIM tables and not in the audit log. A member removal
changes access and writes `scim.group.member_remove`.

**12. A refused sign-in shows the existing `sign_in_refused` code.** The browser gets
`sign_in_refused` (`internal/auth/oidc/oidc.go:544`), so no new console copy is needed and the page
does not disclose that an identity is deactivated. The audit row carries the specific reason.

## Protocol surface

All routes live under `<base path>/scim/v2`, outside `/api/v1`, with
`Content-Type: application/scim+json` and the RFC 7644 error envelope
(`urn:ietf:params:scim:api:messages:2.0:Error` with `scimType`).

| Route | Behaviour |
|---|---|
| `GET /Users?filter=…` | `userName`, `externalId` or `emails.value` `eq "v"`; any other filter, or no `filter`, is 400 `invalidFilter`. At most 100 resources with `totalResults`; `startIndex`/`count` ignored |
| `GET /Users/{id}` | `{id}` is a Wardyn-issued UUID, never a principal |
| `POST /Users` | Records the projection and links it to a matching identity (Decision 5). `active=false` on create suspends. Grants nothing. 201 |
| `PATCH /Users/{id}` | Entra's shapes (below). `active` false suspends, true reactivates; `userName`/`emails` update the projection and keep the old values as aliases; an `externalId` change on a bound identity is 400 `invalidValue` |
| `PUT /Users/{id}` | The same rules as PATCH on a full replacement. An omitted alias is never forgotten |
| `DELETE /Users/{id}` | Purge, immediately. 204 once every required step is done |
| `GET /Groups?filter=…` | `displayName` or `externalId` `eq "v"`; no `filter` is 400 `invalidFilter`. Same 100-resource cap |
| `POST /Groups` | Stored; grants nothing |
| `PATCH /Groups/{id}` | Member add (stored, grants nothing) and member remove (mover path) |
| `DELETE /Groups/{id}` | Every member is removed as a mover, then the group |

**Entra's non-RFC PatchOp shapes** the wire package accepts, each pinned by a golden payload
recorded from a real Entra provisioning job where Entra sends it (the scim-a0 record file lists
which shapes it actually sent):
- `active` as the string `"False"` / `"True"`;
- a case-insensitive `op` (`Replace`, `Add`, `Remove`);
- `replace` with no `path` and a value object;
- `remove` of group members with `path:"members"` and a `value` array of member refs (Entra's
  documented form), and with a filter path (`members[value eq "…"]`, the RFC 7644 form);
- `externalId` mapped from `objectId`, documented as required.

Entra updates users with PATCH only. PUT and the filter-path member remove are pinned by RFC 7644
fixtures named `rfc-*.json`, which the record file marks as not captured from Entra.

**Transport.** HTTPS only: with `WARDYN_SCIM_TOKEN` set, boot refuses unless wardynd serves TLS
itself or `WARDYN_TLS_TERMINATED=true` (`cmd/wardynd/boot_flags.go:358`). A per-request
`X-Forwarded-Proto` check was rejected because a client can set that header. Bodies are capped
with the same mechanism the API uses (`http.MaxBytesReader`, as `internal/api/approvals.go:551`
does), but at SCIM's own 64 KiB constant, not the API's 1 MiB `maxJSONBody`
(`internal/api/helpers.go:571`). Admitted requests are rate-limited per replica with the existing
`principalLimiter` (`internal/api/directory_search.go:188`), keyed by token slot, answering 429
with `Retry-After`. Refused requests (an invalid or missing bearer) have no slot, so they are
limited too: they share one process-wide bucket, and their `auth.fail` rows are rate-bounded by
the existing `authFailedLimiter` (`internal/api/auth_failed_coalesce.go:34`). Per-replica limits
are the documented HA position.

## Suspend, purge, reactivate, movers

**Suspend** (`active=false`). Every step is idempotent and recorded in `deprovision_jobs`; the
response is 5xx until all three succeed. Step 1 commits first; every other step is attempted on
every retry whether or not an earlier step failed.
1. One transaction: the session cutoff (`RevokeSub` for every principal bound to the identity, its
   `entra:<tid>:<oid>` people principal, and each email alias; the cutoff matches email
   case-insensitively), deactivation of the `principal_identities` row(s), the `authority_epoch`
   bump, and `people.deactivated_at` where a people row exists.
2. Revoke the API tokens and delete the SSH keys of those principals, after the bump, through
   `revokePersonCredentials`: the body of `handleRevokeSessions` (`internal/api/sessions.go:113-130`)
   extracted to take a context. It refuses an empty principal (on main an empty principal means
   everyone), and an unresolved key owner counts as zero keys.
3. `killRunCascade` on every non-terminal run those principals own, plus every KILLED run already
   recorded as a pending target. A target stays pending while the cascade's error map is non-empty
   or its CAS was lost and the re-read run is not yet torn down.

Fan-out targets skip a NULL principal, so suspending someone who has never signed in never reaches
another person's credentials. When no identity row binds a principal, the suspend resolves the
SCIM user's emails to subs through `api_tokens(principal, email)` and `people`, as
`resolveSSHKeyOwner` does, and runs every step under each resolved sub; an ambiguous key owner
leaves step 2 pending.

When the job completes, `scim.user.deactivate` and `person.deprovision` (with counts) are written.

**Purge** (DELETE, or once `WARDYN_SCIM_PURGE_AFTER` has passed since suspension):
1. Suspend, if not already complete.
2. `erasure.Orchestrate(ctx, person, scopes)`, with the scope set per Q-SCIM5 (recommended:
   `{credentials, mask_copies}`).
3. With `WARDYN_SCIM_LEAVER_WORKSPACES=reassign`, each workspace the person owns goes to the
   operator through `SetWorkspaceOwner(id, "")`, as the reassign route does.
4. Delete user-subject rows in `capability_grants` (0042) and `governance_assignments` (0052), by
   direct store calls audited in `person.deprovision`, never through the GOV4 apply path.
5. List the person's drives (`user_drives`, 0054) in the `person.deprovision` row; do not reclaim
   them.

The identity row stays as a tombstone with `purged_at` set. The sweeper runs each purge in a
transaction that takes the identity row `FOR UPDATE` and re-checks `deactivated_at IS NOT NULL AND
purge_after IS NOT NULL AND purge_after <= now()`, so a reactivation that committed first wins.

**Reactivate** (`active=true`) clears `deactivated_at` and `purge_after`. It does not lower the
epoch or restore tokens or keys. A row with `purged_at` set is a permanent tombstone: `active=true`
on it is 400 `invalidValue` with a denied `scim.user.write` row (`reason:"purged"`), and the sign-in
gate refuses it. A re-hired person needs a new identity (new object id). Purge deleted their deny
grants and assignments, so reviving the identity would hand it the deployment ceiling.

**Movers.** A group member removal (either remove shape) cuts the removed person's sessions, so
their next sign-in carries a fresh group snapshot. It also revokes the removed person's API tokens
(by every bound principal and email alias) whose `groups` snapshot contains
`lower(trim(scim_groups.external_id))`, the Entra group object id (never `display_name`; the
snapshot is the lowercased union of the roles and groups claims, `internal/auth/oidc/oidc.go:146-150`),
and the removed person's tokens whose snapshot is marked `groups_truncated`, since that snapshot
cannot prove the group's absence. No other person's token is touched.

## Data model and migrations

Every migration takes the next free number at merge (`0107` is origin/main's max + 1 today; the
AR design's PostgreSQL 13 gate migration stays first, and the steward renumbers in merge order).

- **scim-a1: `principal_identities` and `principal_identity_aliases`** (new tables).
  - `principal_identities(id uuid PK, principal text NULL, issuer text, tenant_id text,
    object_id text, email_lower text, scim_external_id text, scim_user_name text,
    deactivated_at timestamptz, authority_epoch bigint NOT NULL DEFAULT 0,
    purge_after timestamptz, purged_at timestamptz, created_at, last_login_at)`.
  - Unique `(principal, issuer, tenant_id, object_id)`; partial unique `(issuer, tenant_id,
    object_id)` where `object_id <> ''`; partial unique `(issuer, principal)` where `principal`
    is set.
  - `principal_identity_aliases(identity_id, kind 'email'|'user_name', value_lower,
    source 'login'|'scim', first_seen, last_seen)`, primary key `(identity_id, kind, value_lower)`.
  - Binding immutability is enforced in the store: every write that touches a binding column is
    `WHERE principal IS NULL`, pinned by a test. A database trigger was rejected: its
    `CREATE OR REPLACE FUNCTION` makes the migration ownership-requiring (`test-claims-match-code.sh`
    C8c) for no gain over the store guard.
- **scim-a4: `deprovision_jobs` and `people.deactivated_at`.**
  - `deprovision_jobs(id, identity_id, kind 'suspend'|'purge'|'group_remove', step, target, state
    'pending'|'done', attempts, last_error, created_at, updated_at)`, unique
    `(identity_id, kind, step, target)`.
  - `ALTER TABLE people ADD COLUMN deactivated_at timestamptz`. `people` was created by an earlier
    release (0090), so this migration gets its row in `docs/OPERATIONS.md`'s migrator rationale.
    C8c's derivation only flags tables from 0049 or earlier, so the shared rule, not the script,
    is what requires the row.
- **scim-a5: `scim_groups` and `scim_group_members`** (new tables). `scim_groups(id uuid PK,
  external_id, display_name, created_at)`; `scim_group_members(group_id, identity_id, added_at)`.

None of these tables holds a secret, so no `kek.Seal` is involved.

## Audit actions and refusal reasons

New rows in `docs/AUDIT-ACTIONS.md`:
- `scim.user.write`: a user created, a projection change, a reactivation, or (outcome `denied`,
  `reason:"external_id_immutable"`) a refused binding change. Actor `wardyn/scim`, with the token
  slot.
- `scim.user.deactivate`: a suspension completed.
- `scim.group.member_remove`: a mover removal completed, with the count of tokens revoked.
- `person.deprovision`: a suspend or purge job completed, with counts (sessions cut, tokens
  revoked, keys deleted, runs killed, credentials erased, workspaces reassigned, grants and
  assignments deleted, drives listed).

New `auth.fail` reasons: `invalid_scim_token` under `wardyn/scimAuth`, and `identity_deactivated`
under `wardyn/oidcCallback` (sign-in) and `wardyn/adminAuth` (a cookie, token or key at request
time). No new `authz.denied` reason is expected; a lane that adds one registers it in
`internal/authz/registry.go` (`TestAuthzDeniedReasonsAreDocumented`).

## Security model and residual risks

The SCIM token can remove anyone's access and, with DELETE, erase their stored credentials. It can
never grant access, rebind an identity or act as an operator.

Delegated portal tokens are covered too: `admit` is shared by the callback and the portal's token
exchange (`VerifySubjectToken`, `internal/auth/oidc/oidc_callback.go:330-332`), so the sign-in gate
refuses a deactivated identity there as well, and the exchange already refuses a cut session
(`session_revoked`, `internal/api/delegation_exchange.go:116`). What it protects against: a leaver
keeping a live session, token, key, run or captured credential after the identity provider has
removed them, on any replica.

Residual risks, disclosed in the docs:
- **A stolen SCIM token is a deprovisioning weapon.** It can suspend everyone, and a DELETE erases
  credentials at once. Mitigations: HTTPS only, rate limiting, an audit row per write, rotation
  without downtime. The purge delay does not apply to DELETE.
- **Email recycling.** Email aliases fan out removals, so an address reused by a new holder can
  have that holder's sessions cut by the old holder's suspension. A cutoff only forces a new
  sign-in; deactivation never follows an email.
- **Not yet seen since the upgrade.** A person with no sign-in since the upgrade and no API token
  is reached by the session cutoff only; their runs need `POST /runs/{id}/kill` until they sign in
  once.
- **Provisioning latency.** Removal is as fast as the identity provider's provisioning cycle. For
  an urgent leaver, `POST /sessions/revoke` and the existing per-person routes still apply; the
  leaver docs point to them.
- **Long-lived connections.** A suspension kills every live run, which ends its attach and SSH
  sessions. Other console streams end at their next authentication check or reconnect.
- **IdP-side demotions that are not SCIM group removals** still lag until re-login (the role-stamp
  TTL in the token-hygiene work narrows this).
- **A database writer** can clear `deactivated_at`, as it could any other row. The epoch only rises,
  so clearing the deactivation does not revive credentials minted before the suspension.
- **Non-Entra identity providers** (and multi-tenant or sovereign-cloud Entra issuers) get no SCIM
  routes; boot refuses a SCIM token on them. Their sign-ins still pass the per-principal gate.
- **Rate limits are per replica**, so an HA install's effective limit is the per-replica limit
  times the replica count.
- **Audit rows written before 0.8.6** stay plaintext and are not reached by purge; only retention
  or the legacy split removes them (AR design).

## Upgrade and compatibility

- Off by default: no token, no routes, no behaviour change.
- The migrations are additive. `principal_identities` starts empty and fills at each sign-in. A
  suspension for someone who has not signed in since the upgrade upserts their row, and the cutoff
  still covers their older sessions.
- The cookie gains `ae` with `omitempty`. An old cookie decodes as epoch 0, which stays valid until
  that identity's first suspension; no `SessionCodecVersion` bump
  (`internal/auth/oidc/session_codec.go:53`, as `MemberMode` did at `oidc.go:158`).
- `oidc.Config.OnLogin` takes a `LoginFacts` struct instead of positional arguments. It is an
  in-process interface, not a wire change. The token-hygiene role-stamp lane stacks on this change.
- The per-request identity check is folded into the existing revocation query, so it adds no
  round trip.
- A downgrade to 0.8.5 ignores the new tables and stops enforcing deactivation. The release notes
  say so.
- `README.md:273`, `ROADMAP.md:157` and the boot log lines at `cmd/wardynd/boot_deps.go:450,465`
  are updated, since SCIM now exists.

## Verification

- **Wire.** Replay every recorded Entra payload in the scim-a0 record, and the `rfc-*.json`
  fixtures, through the handlers; every one is accepted with the expected effect.
- **Rename then deactivate.** An official-style rename PATCH, and separately a PUT full
  replacement carrying the new `userName` and email, each followed by deactivation addressed by
  the new `userName`: the identity is suspended and the old name and email remain aliases.
- **Binding.** A PUT or PATCH changing `externalId` on a bound identity is 400 `invalidValue` with
  a denied `scim.user.write` row; combined with `active=false`, the suspension still lands.
- **Fan-out.** Deprovisioning reaches sessions, tokens and keys under the sub, email and
  `entra:<tid>:<oid>` forms.
- **In-flight sign-in.** Admission, then a suspension, then the callback completing on another
  server instance: no cookie and no captured credential works.
- **Portal exchange.** The delegated portal exchange (`VerifySubjectToken`) for a deactivated
  identity is refused with `identity_deactivated` on another server instance.
- **No people row.** A sub-keyed Entra user with no people row, deactivated over SCIM, cannot
  complete a fresh sign-in on another instance.
- **Login refused while deactivated**, for an Entra and a non-Entra issuer.
- **Durable jobs.** Injected runner, revoke and audit failures each return 5xx; the retry finishes
  the job, including a run already KILLED whose teardown failed. A run transitioning concurrently
  is killed once and confirmed.
- **Reactivation** does not restore tokens, keys or old cookies, and is refused on a purged tombstone.
- **Never signed in.** Suspending an identity whose principal is NULL leaves another person's token
  and SSH key working.
- **Mint during suspension.** A token or key minted by a cookie admitted before the suspension and
  committed after step 1 is revoked or refused, and stays refused after reactivation.
- **Purge.** DELETE and the sweeper each erase credentials through `erasure.Orchestrate`, reassign
  workspaces, delete user-subject grants and assignments, and list drives; the sweeper on two
  instances purges once, and a reactivation that commits between its candidate read and its purge
  leaves the person unpurged.
- **Movers.** A member removal revokes exactly the removed person's tokens whose snapshot holds the
  group, plus that person's truncated snapshots; another member's token and an unrelated person's
  truncated-snapshot token still authenticate; a group add changes no authorisation decision.
- **Routes.** The `authz_test.go` route matrix covers the new routes, and a SCIM-authenticated
  context is never an operator.
