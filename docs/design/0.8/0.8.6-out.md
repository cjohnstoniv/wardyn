# Wardyn 0.8.6 — run output capture and persistence

A headless run's printed output is the first thing a person looks for when the run fails, and
today Wardyn keeps very little of it: the last 8 KiB, only for `task_mode=exec` runs, only in
the memory of the `wardynd` process that dispatched the run, and only until that process
restarts. An adopter running Wardyn on a shared platform with no `kubectl` access asked for the
output of every run, kept across restarts, readable from the console and the CLI. This record
designs that: capture for every non-interactive run, one finalisation contract that every
terminal path goes through, a persisted and masked final row per run, a bounded snapshot of the
terminal pane for interactive runs that stop gracefully, and the read surfaces (API, SDK, CLI,
console).

It is one of the fifteen 0.8.6 design records. The work is tracked under the epic
"[Epic] 0.8.6: Run output capture and persistence" as six task issues, `out-o1` to `out-o5` plus `out-o2r`.
Every file and line reference below is to `origin/main` at `e0efee625` (v0.8.5).

## Where we are

**The capture.** `openExecOutput` gives dispatch a writer for the run's output only when output
is on and the run is `task_mode=exec` and not interactive (`internal/api/run_output.go:105-121`,
gate at `:106`; called from `internal/api/runs_dispatch.go:592`). The writer is a
`liveMaskWriter` (`internal/api/attach.go:811-817`) in front of an `outputRing` that keeps the
last `execOutputTailBytes = 8 << 10` bytes (`run_output.go:34,41-69`). An entry is released
`WARDYN_EXEC_OUTPUT_TAIL_TTL` (default 24h) after its last output and forgotten after twice that
(`run_output.go:36,89-101`). The file's own header says it plainly: memory only, so a restart
loses every tail (`run_output.go:29-30`).

**Both runners already drain the agent's output.** The Docker driver hijacks the agent exec's
TTY and copies it into the run's writer, or into `io.Discard` when the run keeps none
(`internal/runner/docker/driver_exec.go:170-181,193-198`); an exec-less agent's main-process log
is followed the same way (`driver_exec.go:203-217`). The Kubernetes driver follows the agent
exec container's log once the kubelet has started it (`internal/runner/k8s/exec.go:130-131,141-168`),
which needs `get` on `pods/log`, already granted by the chart (`deploy/helm/wardyn/templates/rbac.yaml:38`).
The writer reaches the drivers through `runner.SandboxSpec.ExecOutput`, whose contract is that
`Write` never blocks or fails (`internal/runner/runner.go:90-93`; stored at
`docker/driver_network.go:204,246` and `k8s/sandbox.go:359-360`).

**Exit is not end of output.** Each driver's `Wait` returns when the process exits
(`docker/driver_exec.go:312,325`, an `ExecInspect` poll; `k8s/exec.go:234`, a pod poll), and the
copy goroutine reaches EOF independently. A read of a finished run can still gain bytes after it
said `complete` (`run_output.go:157-162,195`); the SDK documents the race rather than closing it
(`pkg/client/families.go:409-411`).

**The masker holds bytes back.** `liveMaskWriter` withholds a trailing run of bytes that could be
the start of a registered secret until the next write completes or clears it
(`attach.go:816`). Only the read of a finished run releases it, masking a held-back run of
`secretmask.MinLen` (8) bytes or more against itself (`run_output.go:142-149`,
`internal/secretmask/secretmask.go:34`). Nothing persists that holdback today because nothing
persists at all.

**Terminal paths are many, and only some share a tail.** The completion watcher runs
`finalizeRunTail` after winning `RUNNING → COMPLETED|FAILED` (`internal/api/runs_lifecycle.go:147,173`,
tail at `:514-547`); so do the boot reconciler (`internal/api/reconcile.go:799`), the lease end
and lost kept runs (`internal/api/run_lease.go:275,288`) and the site-config probe
(`internal/api/site_config_probe.go:771`). Others do not:

- a watcher that loses the terminal CAS returns at once (`runs_lifecycle.go:100-103,155-158`);
- a watcher that finds the run kept returns before the CAS (`runs_lifecycle.go:141-143`);
- the kill runs its own tail, `KillSandbox` first (`runs_lifecycle.go:733,831-862`);
- the idle stop lives in `cmd/wardynd` as `lifecycleStopper.StopRun`, outside the API server,
  and runs CAS, approval cancel, `StopSandbox`, then the revocations
  (`cmd/wardynd/adapters.go:700-716,728-790`);
- a create or dispatch failure ends in `failAndRevoke` (`runs_lifecycle.go:562`).

**Reads.** `GET /api/v1/runs/{id}/output?tail=N` (`internal/api/routes.go:201`,
`run_output.go:167-208`) is owner-or-admin with `GET /runs/{id}`'s 404 for anyone else, refuses
interactive runs with `409 run_output_interactive`, and otherwise answers from memory with five
`run_output_*` reasons (`internal/api/reasons_routes.go:208-215`, documented at
`docs/sdk.md:381`). The SDK has `RunOutput` (`pkg/client/families.go:403-426`). The CLI has no
output command: `wardyn run logs` tails the audit trail and its help says no stdout capture
exists for a headless run (`cmd/wardyn/commands.go:836-849`), which is already untrue for exec
runs. The console has no output view (the run-detail tabs are overview, approvals, policy, audit
and recording, `ui/src/app/components/screens/run-detail.tsx:537-556`).

**Settings and docs.** `WARDYN_EXEC_OUTPUT_TAIL` (default on) and `WARDYN_EXEC_OUTPUT_TAIL_TTL`
(`cmd/wardynd/boot_flags.go:385-386`, `cmd/wardynd/main.go:416-417`,
`internal/api/server.go:381-387,807-808`), documented in `docs/ENV.md:153-154` and
OPERATIONS.md "Exec run output" (`docs/OPERATIONS.md:88-110`), which promises "nothing reaches
Postgres or a backup". That sentence changes in this release.

**Interactive runs and the credential-printing run.** An interactive run's terminal is the
recording's (`run_output.go:21-22`). The managed-harness sign-in run is interactive
(`internal/api/harnesscred.go:523-526`) and exists to print a long-lived credential that no
masking can catch, so its terminal is never recorded (`runIsUnrecordable`,
`internal/api/attach.go:650-662`; `harnesscred.go:398-407`).

## Goals

- Every non-interactive run keeps the end of its output, sized by a deployment knob (default
  64 KiB, max 1 MiB).
- The final output is masked and persisted once per run, survives restarts and is readable from
  any replica.
- One finalisation contract covers completion, failure, kill, idle and max-age stop and
  recovery, with a drain barrier, a flushed holdback, a fenced writer, a durable retry and an
  explicit record of what could not be captured.
- Interactive runs that stop gracefully keep a bounded, masked snapshot of their terminal pane.
- The settings define both what is collected and what old rows remain readable.
- Erasure of a person's run output is complete and stays complete.
- Read surfaces: the API, SDK `Source`, CLI `wardyn run output`, and a run-detail Output panel.

### What this is not

- Not a log pipeline. Wardyn keeps the end of a run's output, not a full log; a run that needs
  its full log writes it to its workspace.
- Not a recording. Interactive terminals stay the recording's; the pane snapshot is a bounded
  last screen, kept only on a graceful stop.
- No re-execution. When output cannot be recovered after a restart, the gap is recorded; the
  agent is never re-run to regenerate it.
- No terminal replay on reattach. That was considered for the terminal work and cut, because
  tmux repaints on attach.

## Design

### 1. Capture every non-interactive run (`out-o1`)

`openExecOutput` drops the `taskMode != "exec"` condition: every non-interactive run gets a
writer when the master switch is on. Headless agent runs (a task given to a harness) print
progress and errors to the same TTY the drivers already drain, so no driver change is needed to
capture them. The gate keeps two exclusions:

- interactive runs, whose terminal belongs to the recording (and to `out-o3`'s snapshot);
- any run `runIsUnrecordable` reports (`attach.go:660`), checked explicitly so a future
  non-interactive credential-printing run inherits the exclusion instead of relying on the
  sign-in run happening to be interactive.

The ring size comes from `WARDYN_RUN_OUTPUT_TAIL_BYTES` (default 64 KiB). Boot refuses a value
below 1 KiB or above 1 MiB, naming the variable. `?tail=` is capped at the configured size. The
`run_output_not_kept` and `run_output_interactive` messages stop saying "only a task_mode=exec
run".

*Rejected:* capturing interactive runs through the same writer. Their PTY is attached by a
person, and the recording already owns it, with its own masking boundary.

*Rejected:* a per-run `tail_bytes` field on the create request. Nobody asked for it, and a
per-run size makes the memory bound depend on callers.

**Memory.** With persistence on, a live or kept run's tail is held until its final row commits
and then released, so the bound is concurrent live and kept non-interactive runs × the tail size
(500 runs × 64 KiB is about 32 MiB; at the 1 MiB maximum it is about 500 MiB, which the docs
state). A live or kept run that is silent for longer than `WARDYN_EXEC_OUTPUT_TAIL_TTL` is not
expired while persistence is on; the TTL only governs the memory-only mode (section 3). That
live-runs-only bound holds only with persistence on. With `out-o1` alone, and with
`WARDYN_RUN_OUTPUT_PERSIST=off` afterwards, a tail is released only TTL after its last output
(`run_output.go:89-101`), so the bound is runs that printed within the last TTL, finished runs
included, × the tail size (2,000 runs a day × 1 MiB is about 2 GiB); the docs state both.

### 2. One output-finalisation contract (`out-o2`)

Persisting "once, in `finalizeRunTail`" is not enough on its own: the kill, the idle stop and a
watcher that loses the terminal CAS never reach it, and the exit that triggers it can precede the
last bytes. So persistence goes through one contract, in a new file
(`internal/api/run_output_final.go`; `runs_lifecycle.go` is 939 lines and `adapters.go` 976,
against the 1000-line cap in `scripts/check-file-size.sh`).

The contract has two halves, both idempotent per run:

- **before teardown** (`prepareRunOutput`): the interactive pane snapshot (section 4) on a
  graceful stop, or substrate recovery (below, `out-o2r`) when this process holds no tail for the
  run; until `out-o2r` lands, such a process writes a `capture_gap` row;
- **after the process has exited or the sandbox is gone** (`finishRunOutput`): the drain
  barrier, the holdback flush, the fence and the persist.

A per-run once-guard makes the first caller do the work; later callers return, or wait for the
first one to finish when they need the row (the read path never waits).

**Entry points.**

| Path | Where today | Pane snapshot | stdout |
|---|---|---|---|
| completion watcher wins the CAS | `runs_lifecycle.go:173` → `finalizeRunTail` | n/a (non-interactive) | finish before `StopSandbox` (`:521`) |
| exec never started | `runs_lifecycle.go:104` | n/a | finish (usually empty) |
| watcher loses the CAS | `runs_lifecycle.go:100-103,155-158` | n/a | finish (no-op if the winner did) |
| watcher finds the run kept | `runs_lifecycle.go:141-143` | n/a | no finish: the tail stays open (persistence on never expires it), because a kept run (`runIsKept`, `run_lease.go:340`) can be revived with its agent started again on the same run id (`run_revive.go:158,305`); the run is finished when it reaches a terminal state, through `stopKeptRun` → `finalizeRunTail` (`run_lease.go:288`) or any other listed path |
| lease end, lost kept run | `run_lease.go:288` → `finalizeRunTail` | STOPPED: yes, before teardown; FAILED: no | already final, or finish |
| boot and adoption finalize | `reconcile.go:799` → `finalizeRunTail` | no | recovery (`out-o2r`; covered runs only, bounded), then finish |
| site-config probe reclaim | `reclaimProbeRun`, `site_config_probe.go:765-773`: CAS to KILLED while the process may still run, then `finalizeRunTail` | no (KILLED) | finish after `StopSandbox`, as the kill path does, so a timed-out probe does not spend the drain barrier on a live process |
| kill | `killTeardownTail`, `runs_lifecycle.go:831` | no (KILLED never snapshots) | finish after `KillSandbox`, in a tracked goroutine after the revocations; the kill response never waits on output |
| idle stop | `lifecycleStopper.StopRun`, `adapters.go:728` | yes, after the revocations and before `StopSandbox` | finish after `StopSandbox` |
| max-age stop (`p-p4`; wired by `out-o3`) | the lifecycle reaper, not through `StopRun` (its CAS is idle-guarded, `UpdateRunStateIfIdle`, `adapters.go:742`) | as idle stop | as idle stop |
| create or dispatch failure | `failAndRevoke`, `runs_lifecycle.go:562` | no | finish |

`lifecycleStopper` reaches the server through a function field, the way it already reaches
`CancelTerminalRunApprovals` (`adapters.go:705-715`), so the reaper stays a thin adapter;
`adapters.go` grows only by that field and its call (≤15 lines), and the retention sweeper and its
adapter go in a new file, `cmd/wardynd/run_output_sweeper.go`. `p-p4`'s max-age stop cannot reuse
`StopRun`'s idle-guarded CAS, so `out-o3` (blocked by `p-p4`) wires it into both halves of the
contract.

In `finalizeRunTail` the contract runs after the revoke cascade and the approval cancel
(`runs_lifecycle.go:517-518`) and before `StopSandbox`, so the up-to-seconds of drain and
snapshot never extend a live credential. The exception is a caller that enters `finalizeRunTail`
having CASed the run to KILLED while its process may still be running (the site-config probe
reclaim): there the process has not exited, so the finish runs after `StopSandbox`, as on the kill
path. `lifecycleStopper` is reordered for the snapshot case to
match: revoke, then snapshot, then `StopSandbox`. The `run.complete` audit row stays first
(`runs_lifecycle.go:515`); `wardyn run logs` relies on it landing right after the state flips
(`cmd/wardyn/commands.go:865-870`).

**Drain barrier.** `SandboxSpec.ExecOutput` gains a second, optional contract: when the writer
also implements `io.Closer`, the driver calls `Close` once its copy goroutine returns, at EOF or
on error, including the Kubernetes follow loop's early returns (`k8s/exec.go:147-152,160-162`).
The tail counts open drains; `finishRunOutput` waits until the count reaches zero or
`runOutputDrainWait` (5s) passes. A run whose barrier timed out, or whose drain ended in an error,
is persisted with `incomplete = true`.

*Rejected:* waiting for silence (no bytes for N ms). It cannot tell a slow final line from the
end, which is exactly the failure being fixed.

**Holdback flush.** After the barrier, the writer's withheld bytes are released with the rule the
read path already uses (`run_output.go:142-149`): a held-back run of `MinLen` bytes or more is a
secret cut short and is masked against itself; a shorter one is ordinary output. The rule moves
into one helper both use.

**Fence.** Once finishing starts, the writer is sealed: later `Write`s are accepted (the driver
contract forbids failing them) and dropped, and a dropped byte marks the row `incomplete`. So a
"complete" row can never gain bytes after it was served. A byte dropped after the final UPSERT
committed is handled the same way: the finaliser issues `UPDATE ... SET incomplete = true` for the
run and writes a `run.output.finalize` audit row naming the late drop; it is not only logged.

**Persist and durable retry.** At dispatch, when persistence is on, a pending row is written for
the run (`captured_at IS NULL`). It is the durable record that a capture is owed. `finishRunOutput`
UPSERTs the final row; a failed write is retried with capped backoff while the bytes stay in
memory (bounded by the tail size per run), and each attempt refreshes the row's `claimed_at`.
If the process dies, the pending row remains. The retention sweeper resolves pending rows of
terminal runs whose claim is older than five minutes by recovery (below) or a capture-gap row. A
failed pending insert at dispatch is logged and does not fail the run; the final UPSERT still
writes the row.

**Recovery and the capture gap (`out-o2r`).** A process that finalises or adopts a run without
holding its tail asks the runner to recover it, through an optional interface:
`runner.OutputRecoverer.RecoverOutput(ctx, ref, w io.Writer) error`.

- **Coverage first.** Recovery runs only when this process is `Covered(runID)` (`ha-l2.0`):
  `prepareRunOutput` loads and certifies the run's manifest first (any replica may, without the
  watcher lease). If no complete manifest exists (a pre-0.8.6 run, or an incomplete one), no
  substrate read is made and the final row is written with `capture_gap = true` and no bytes; the
  sweeper resolves a stale pending row the same way. Otherwise a re-read in a process without the
  manifest would persist the run's dispatch-time secrets verbatim.
- **Bounded.** `RecoverOutput` runs under its own context, `runOutputRecoverWait` (10s), taken from
  the caller's deadline; on expiry the row is written with `incomplete = true` and whatever the
  ring holds. Recovery runs after the revoke cascade and never delays it, and stays inside
  `reconcileFinalizeTimeout` (`reconcile.go:740-747`), whose bound keeps the boot pass from
  blocking `/healthz`. A sandbox controls its own log size, so the re-read must not be unbounded.

- **Kubernetes:** re-read the agent exec container's log from its start into a fresh ring, with
  `PodLogOptions{Container: execContainerName, Follow: false}` for a finished run (`Follow` only
  when resuming a live adoption; today's follow is at `k8s/exec.go:159`). Ring
  semantics make this idempotent: re-reading replaces the tail, so nothing is duplicated, and
  kubelet log rotation only removes bytes older than the tail. On adoption of a live run
  (`reconcileWatch`, `reconcile.go:680`) the follow resumes, so output from before, during and
  after the handoff is all captured. This must happen before teardown, because `StopSandbox`
  deletes the pod.
- **Docker, exec-less agent:** re-follow the main process's log the same way
  (`docker/driver_exec.go:209`).
- **Docker, exec agent:** the TTY hijack cannot be re-attached after the process that held it
  died. `RecoverOutput` returns `runner.ErrOutputUnrecoverable` and the final row is written with
  `capture_gap = true` and whatever was captured after the gap (nothing, for an exec adopted after
  a restart).
- A runner without the interface, or a sandbox already gone, also yields `capture_gap`.

The agent is never re-run. *Rejected:* making `RecoverOutput` a required `Runner` method; every
fake and the conformance suite would change for a recovery-only path.

**Live chunks (`ha-l2.4`, W3).** When `run_output_chunks` lands, its rows follow this contract:
masked before insert by the dispatching replica; per-run chunk bytes capped at the tail size,
older chunks deleted as newer ones arrive (compaction), so a run never holds more than about one
tail of chunks; deleted in the transaction that writes the final row; checked against the
erasure tombstone on write; not written when persistence or output is off. Recovery prefers the
substrate re-read; chunks, deduplicated by `(run_id, seq)`, are the fallback when the substrate
cannot be re-read, with `capture_gap` covering what the dead replica never flushed.

### 3. The persisted row, reads, retention and erasure (`out-o2`)

**One final row per run** in `run_outputs` (data model below): masked bytes, `truncated`,
`incomplete`, `capture_gap`, `source` (`stdout` or `pane_snapshot`), `mask_scope`, `captured_at`.
A run that printed nothing gets an empty final row, so "printed nothing" reads differently from
"not kept". With persistence on, the in-memory copy is released when the row commits.

**Masking provenance.** `mask_scope` records whether the writer's process held the run's
complete masking manifest for the whole capture (`run` — `ha-l2.0`'s `Covered`) or not
(`globals_only`). The writer keeps a sticky flag, so a capture that was uncovered at any point
says so. A row with `mask_scope = globals_only` can arise only from a live capture whose writer
lost coverage mid-run, never from recovery (which requires coverage, section 2). `ha-l2.0`
refuses the live read of an uncovered run; a persisted row is served from the row on any replica, with no watcher lease and no live registry needed, which is what makes a
terminal run's output readable after every replica restarted.

**Read order.** After `getRunAuthorized` (unchanged, so the 404 for a stranger is unchanged):

1. an erasure tombstone for the run → `404 run_output_erased`;
2. output off → `409 run_output_off`;
3. a live tail in this process → `503 mask_state_unavailable` with `ha-l2.0`'s denied audit row
   when `!Covered(run)` (`ha-l2.0`'s refusal, kept exactly as it left it), else `200` from memory;
4. a final row → `200` from the row;
5. a pending row with no local tail (finalising, or live on another replica before `ha-l2.4`)
   → `409 run_output_not_kept`, with a message saying to read again shortly;
6. an interactive run with no snapshot → `409 run_output_interactive`;
7. no row, and the run ended (`agent_runs.ended_at`, migration 0092) longer ago than the
   retention window → `410 run_output_expired`;
8. otherwise → `409 run_output_not_kept`.

**`complete` changes meaning.** It becomes true only for a final capture: a final row, or a
memory tail whose barrier has closed. Today it means "the run has finished", and a read can still
gain bytes after it (`pkg/client/families.go:409-411`). *Rejected:* keeping `complete` and adding
a separate `final`; two near-synonyms on one body would be misread. Wardyn has no external users
to break, and the SDK comment and docs change with it.

**The response** gains `source`, `incomplete`, `capture_gap`, `mask_scope` and `captured_at`
(omitted while live). All are additive.

**What the settings mean, for collection and for old rows.**

| Setting | Collected | Rows already stored |
|---|---|---|
| `WARDYN_EXEC_OUTPUT_TAIL=off` (master) | nothing: no memory tail, no pending or final row, no chunks, no snapshot | not served (`409 run_output_off`); the retention sweeper still deletes them |
| `WARDYN_RUN_OUTPUT_PERSIST=off` (master on) | memory tail only, expired by `WARDYN_EXEC_OUTPUT_TAIL_TTL` as today; nothing reaches Postgres (no pending or final rows, no chunks); no pane snapshot, which exists only to outlive teardown | served until the retention sweeper deletes them |
| `WARDYN_RUN_OUTPUT_RETENTION_DAYS=N` | — | final rows older than N days are deleted; `0` keeps them forever |

*Rejected:* serving stored rows while the master switch is off. An operator who turns output off
after finding something in it expects it to stop being readable; deletion follows within the
retention window.

**Retention sweeper.** Hourly, it deletes final rows whose `captured_at` is older than the window
and resolves stale pending rows (section 2). Under HA it runs on the elected leader
(`SweeperLeaderLockKey`, `ha-l2.3`); its deletes are idempotent anyway. It records its tick for
`o-o2`'s `wardyn_sweep_last_tick_seconds{sweep="run_output"}`: `out-o2` adds `run_output` to
`o-o2`'s closed sweep label set, registered at its start site when `WARDYN_RUN_OUTPUT_PERSIST` is
on, with its hourly interval, and a row in `docs/operations/monitoring.md`. It needs only `o-o2`'s
backend (`sweep_ticks` and the registration API), not its M10 copy. A sweep that deletes anything
writes one `run.output.retention.sweep` audit row with the count, mirroring
`recording.retention.sweep` (`docs/AUDIT-ACTIONS.md:533`, `cmd/wardynd/adapters.go:930`).

**Erasure primitive.** This lane ships the deletion and its fence together, because the table and
its writers land here. `ar-l1.4` calls it from `erasure.Orchestrate`'s `run_outputs` scope; it does
not build a second tombstone.

- `EraseRunOutputs(ctx, runIDs)`, in one transaction: insert a tombstone per run into
  `run_output_erasures`, then delete the runs' `run_outputs` rows (and, once `ha-l2.4` lands,
  their `run_output_chunks`).
- Then, in the erasing process, zero and drop each run's memory tail and mark its finaliser
  fenced.
- Every final UPSERT, every retry, every pending insert and every read checks the tombstone in
  the same transaction, serialised against erasure by a transaction-scoped advisory lock keyed on
  the run. This lock is a leaf: it is taken last and never held while taking another
  (`ha-l2.2` lock order).
- A replica that still holds a tail for an erased run can neither persist it (the UPSERT sees the
  tombstone) nor serve it (the read checks the tombstone before memory), so no notification is
  needed for correctness.
- Any tombstone hit, at the pending insert, the UPSERT, a retry or a read, in any replica, zeroes
  and drops that replica's memory tail for the run and marks its finaliser fenced, so no copy
  outlives the erasure beyond the next touch; a retry loop stops on a tombstone instead of backing
  off.
- The existing `DELETE /people/{principal}/credentials` (`internal/api/credential_erase.go:49-118`)
  keeps meaning credentials only and never calls this.

`404 run_output_erased` deliberately breaks the handler's current rule that no other answer is a
404 (`run_output.go:164-166`). It cannot leak existence: only the run's owner or an admin gets
past `getRunAuthorized`, and they can already see the run; the reason code distinguishes it.

### 4. Pane snapshot for interactive runs (`out-o3`)

On a graceful stop of an interactive run, `prepareRunOutput` captures the tmux pane before
teardown and persists it as `source = pane_snapshot`.

- **When.** Only when Wardyn itself stops a live sandbox into STOPPED: the idle stop, the
  max-age stop and the lease end. KILLED never snapshots (a kill is immediate; it keeps any stdout
  already captured, which an interactive run does not have). FAILED and reconcile-finalised runs
  never snapshot: the sandbox is gone or untrustworthy.
- **Never for a credential-printing run.** `runIsUnrecordable` (`attach.go:660`) is checked first;
  for the sign-in run no exec is even issued, because its pane holds the credential it exists to
  print.
- **How.** `Runner.ExecStream` (`runner.go:279-282`) with
  `tmux capture-pane -p -J -S - -t wardyn` (the session name both drivers use,
  `internal/runner/docker/session.go:42`, `internal/runner/k8s/session.go:37`), no TTY, stderr
  drained concurrently as the streaming contract requires (`runner.go:236-240`). `-p` without
  `-e` emits plain text without attributes.
- **Bounds.** A 3s context; the stream is copied through the run's `liveMaskWriter` into a ring of
  the tail size, so the last bytes of the history are kept whatever the history length; the
  holdback is flushed as for stdout. A pane that never ends its output, a missing tmux, or a
  missing `wardyn` session yields no row and does not delay teardown beyond the bound.
- **Order.** Revocations first, then the snapshot, then `StopSandbox` (section 2), so the bound
  never extends a live credential.
- **Audit.** `ExecStream`'s contract requires the caller to record the principal. Each snapshot
  attempt writes `run.output.snapshot` with the system actor `wardynd`, the outcome and the byte
  count; never the content.
- **Persistence off** means no snapshot.
- **Who reads it.** A snapshot is a person's last terminal screen, the surface the recording gate
  protects. A `pane_snapshot` row is served only when `recordingReader` (`recording.go:65`) allows
  the caller: the owner or an operator (super admin). A security_admin, who passes
  `getRunAuthorized` through `ownsRunOrAdmin`'s incident-response widening, gets
  `409 run_output_interactive`, the same answer as no snapshot, so the row's existence is not
  revealed.

*Rejected:* snapshotting on every stop including kills. A kill is the control a person reaches
for when a run misbehaves; it must stay immediate and must not exec into the sandbox it is
killing.

*Rejected:* `capture-pane -e` to keep colours. Escape sequences from a sandbox-controlled pane
would have to be interpreted by every reader; plain text is safe to render anywhere.

### 5. CLI and SDK (`out-o4`)

- **SDK:** `RunOutput` gains `Source`, `Incomplete`, `CaptureGap`, `MaskScope` and `CapturedAt`; the
  doc comments drop "task_mode=exec" and the 8 KiB figure and describe the new `Complete`.
- **CLI:** `wardyn run output <run-id> [--tail N] [--json] [--raw]`. When stdout is not a
  terminal it prints the output exactly as stored. When stdout is a terminal, ESC, C1 controls and
  C0 controls other than `\n`, `\r` and `\t` are written as Go-quoted escapes unless `--raw` is
  given, because the bytes are sandbox-controlled and a terminal would interpret OSC 52 (clipboard
  write), title and CSI/DCS sequences; `pane_snapshot` rows are always filtered on a terminal. It
  prints a one-line notice on stderr when the row is truncated, incomplete, a
  capture gap or a pane snapshot. A refusal exits non-zero with the reason. `--json` prints the
  body. The command lives in a new file; `cmd/wardyn/commands.go` is 990 lines, so the only edit
  there is adding it to the existing `AddCommand` call (`commands.go:227-229`).
- **`wardyn run logs`** help stops saying no stdout capture exists (`commands.go:842-849`) and
  points to `wardyn run output`.

### 6. Output panel (`out-o5`)

A run-detail Output panel behind mock packet **M8**, which settles its placement (a sixth tab
beside `recording`, or a section of overview) and every string. It shows the output as plain
text in a monospace block (never HTML and never interpreted escape sequences), a label for the

CREATE TABLE run_outputs (
    run_id       UUID PRIMARY KEY REFERENCES agent_runs(id) ON DELETE CASCADE,
    output       BYTEA NOT NULL DEFAULT '\x',
    truncated    BOOLEAN NOT NULL DEFAULT false,

## Security model and residual risks

- **Output now reaches Postgres and its backups.** OPERATIONS.md's "nothing reaches Postgres or a
  backup" is replaced with what is kept, for how long, and the two switches. A deployment that
  turned recordings off so terminals are not kept should decide on these too.
- **Unregistered secrets.** Masking catches values the registry holds when they are printed. A
  token a command reads from a file, or one pasted into a task, is kept verbatim and served to
  whoever may read the run, as today, but now persisted. The docs say so in the same words as the
  recording docs.
- **Masking before insert.** Bytes are masked by `liveMaskWriter` as they are written and the
  holdback is flushed before the UPSERT; nothing is ever masked at read time. Tests inspect the
  stored row, not the API answer.
- **Coverage honesty.** `mask_scope = globals_only` marks a capture made without the run's complete
  manifest; the panel and CLI say so. Pre-0.8.6 runs have no row at all.
- **The pane is sandbox-controlled.** The sandbox runs as the tmux server's user and can make the
  pane, or the `tmux` binary itself, print anything. The snapshot is therefore untrusted text:
  bounded in time and bytes, masked, stored as bytes, rendered as plain text. It is evidence of
  what the pane showed only to the extent the sandbox did not lie, and the docs say so.
- **The sign-in run's credential.** Neither capture nor snapshot ever runs for a
  `runIsUnrecordable` run.
- **Erasure is fenced, not best-effort.** The tombstone is checked inside the writing and reading
  transactions; zeroing memory is the local half. Residual: bytes already copied into a database
  backup before erasure remain in that backup until it ages out, as for every other erased record.
- **Snapshot timing.** The snapshot runs after revocation, so it never extends a credential's
  life; it does extend sandbox teardown by up to 3s on a graceful stop.
- **Docker exec runs across a restart** lose their output and say so (`capture_gap`); Kubernetes
  runs recover it from the container log when the run's manifest is complete. The docs state the
  asymmetry.
- **Recovery never runs uncovered.** A substrate re-read happens only in a process that holds the
  run's complete manifest, and is bounded at 10s; otherwise the row is a capture gap.
- **The CLI on a terminal** escapes control sequences by default (section 5); the console renders
  plain text (section 6).
- **Storage.** 64 KiB × runs per day × 30 days: 2,000 runs a day is at most about 3.8 GiB. The
  docs give the formula.

## Upgrade and compatibility

- **Additive schema**, no ALTER of older tables; the migration takes the next free number.
- **Existing runs.** Runs that finished before the upgrade have no row and read
  `409 run_output_not_kept`. Runs alive across the upgrade restart have no masking manifest, so
  they get a capture-gap row and no substrate re-read, on both runners (Q-HA1).
- **Behaviour changes, listed in the CHANGELOG:**
  - every non-interactive run keeps output, not only `task_mode=exec`;
  - the default tail grows from 8 KiB to 64 KiB;
  - output is persisted for 30 days by default, so it is in Postgres and its backups;
  - `complete` means "final capture", not "run finished";
  - a new `404 run_output_erased`.
- **Turning it back to 0.8.5 behaviour:** `WARDYN_RUN_OUTPUT_PERSIST=off`,
  `WARDYN_RUN_OUTPUT_TAIL_BYTES=8192`.
- **Wire.** New response fields are additive; older CLIs and SDKs ignore them.

## Verification

- **Restart (end to end, `out-o4`'s kind walk):** on kind, a headless run completes, wardynd
  restarts, and `wardyn run output` returns the same masked bytes from Postgres.
- **Masked before insert:** a registered secret printed whole, split across two writes, and cut
  off as the last bytes before exit is absent from the stored `run_outputs.output` column (read
  with SQL, not through the API).
- **KILLED skips the snapshot:** a killed interactive run has no `pane_snapshot` row and issued
  no exec; a killed headless run keeps the stdout it had printed.
- **Delayed final bytes:** a fake driver writes its last line after `Wait` returns but within the
  barrier, and the row has it with `incomplete = false`; past the barrier, the row is
  `incomplete = true` and the late bytes are dropped, never appended after a `complete` read.
- **Every terminal path:** a table test over the entry-point table produces exactly one final row
  per run, including the CAS loser, the kill and the idle stop; a kept run revived and then ended
  has exactly one final row, `incomplete = false`, holding bytes from before the revive.
- **A → crash → B (`out-o2r`):** with output before, during and after the handoff, the Kubernetes
  fake's log re-read yields all three on B; the Docker exec case yields a `capture_gap` row; the
  agent is never re-executed (the fake counts execs). A run with no manifest gets a `capture_gap`
  row with no log read; a log that streams without end is cut at 10s.
- **Uncovered live read:** still `503 mask_state_unavailable` after `out-o2`.
- **Snapshot readers:** a security_admin gets `409 run_output_interactive` for a snapshot the
  owner and a super admin can read.
- **CLI on a terminal:** OSC 52 and CSI sequences print escaped on a pty, verbatim when piped or
  with `--raw`.
- **Durable retry:** Postgres refuses the first UPSERTs, then accepts; the row lands. The process
  dies with a pending row; the sweeper resolves it to recovery or a capture gap.
- **Settings matrix:** master off collects nothing and refuses old rows; persist off writes no
  rows and still serves old ones; a row past retention is deleted and reads `410`.
- **Erasure:** after `EraseRunOutputs`, reads answer `404 run_output_erased`; a finaliser blocked
  before its UPSERT, a retry, and a second replica holding the tail all fail to recreate the row;
  the behaviour holds across a restart.
- **Snapshot:** an idle-stopped interactive run has a masked `pane_snapshot` row; the sign-in run
  never snapshots; a pane that streams forever is cut at 3s and teardown proceeds; revocation
  precedes the snapshot.
- **Surfaces:** SDK round-trip of every field; the CLI on each refusal; the panel's e2e over
  live, final, truncated, incomplete, capture-gap, snapshot and refusal states, with an
  escape-sequence and markup fixture rendered literally.
