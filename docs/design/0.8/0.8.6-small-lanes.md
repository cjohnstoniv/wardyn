# Wardyn 0.8.6 — small lanes: first run, shared-cluster capacity, templates and token hygiene

An adopter running Wardyn on a shared, multi-tenant Kubernetes cluster sent two reports against
v0.8.5: a first run that fails without saying why, and a sandbox substrate that "assumes it owns the
cluster". Most of what they asked for is small. This record is the index for those small lanes: what
each one changes, the decision it rests on and the alternative it rejects, the schema, environment and
chart surface they add, and how each is proven. Each lane is one task issue on the `0.8.6` milestone.
There is no epic for this record: the B rows are plan-section lanes, not a design epic, so every issue
links here instead. Each lane id prefixes its issue title and names its branch.

Every file:line below is `origin/main` at e0efee625 (v0.8.5).

Some rows of the same plan section are owned elsewhere and are not repeated here: the preflight
sign-in, backend-row and no-model gates (F3, F4, F5) are in the auto-preflight record; G1 is the
prerequisite of profile composition; K1 and K2 are in the key-custody record; O1 and O2 are in the
fleet record; the OpenAI-dialect harness wiring fix (CX0) is in the Azure provider record.

## Decisions

### F1: reuse the R3 line in the one-candidate branch

When exactly one provider serves the picked agent, the rail renders the static name and residency line
and returns (`ui/src/app/components/screens/new-run/new-run-rail-credentials.tsx:208-217`). The
"not connected" warning and its door exist only in the select branch, so a person whose sole provider
is signed out learns it from the Launch 422. F1 renders `ProviderNotConnectedLine` after
`ProviderResidencyLine` in that branch. Its per-kind switch (`:110-164`) already covers all five kinds,
renders nothing when connected or `not_applicable` (`:120`), and opens the same door as the select.

Rejected: a new one-candidate sentence. It would be a second wording for the same state, and the
existing R3 cases in `new-run-rail-provider.test.tsx:162-301` already pin the copy and per-kind
behaviour that must be preserved.

### F2: renew at create, persist or refuse, never carry the credential in memory

Today create checks liveness with `refresh=false` (`internal/api/run_model_provider.go:306`), so an
expired access token with a live refresh token passes create as "renewable", and only dispatch renews it
(`internal/api/runs_dispatch_provider.go:337`). F2 gives `enforceRunModelProvider`
(`internal/api/run_model_provider.go:247`) a `renew bool`: create (`internal/api/runs.go:231`) passes
true, preflight (`internal/api/preflight.go:280`) passes false. The record session already calls
`providerLiveness` with false directly (`internal/api/record_model_provider.go:80`) and is unchanged.
Renewal applies to the Bedrock SSO arm only; the subscription arm keeps `PurposeStatus` at create
(`internal/api/runs_dispatch_provider.go:85-91`). A dead refresh token then gets the 422
`connectDenial{credential:true}` (`internal/api/provider_bedrock.go:128-136`) before any run row exists,
and the rail's door-and-relaunch (`ui/src/app/components/screens/new-run/new-run-rail.tsx:286-322`)
takes over.

The hard part is a redeem whose Put fails. `refreshAWSSSOBlob` today serves that run from the in-memory
blob and marks the old pair spent (`internal/api/awssso_refresh.go:408-414,551-565`). That cannot work at
create: the proxy's bootstrap re-reads the **persisted** pair (`internal/api/injection_awssso.go:224-238`),
finds the old one marked spent, and answers 423, so `buildInjector` fails the run after it was created.
An independent plan review reproduced exactly that with one redemption. So:

- create first proves the store will accept a write, before any refresh token is spent;
- after a redeem, the Put is retried up to 3 times **inside** `refreshAWSSSOBlob`, between the re-read
  under the owner lock and `markAWSSSOTokenSpent` (`awssso_refresh.go:551-565`). No caller writes back a
  blob it received from `refreshAWSSSOBlob`, so every write of the pair holds the lock an erase takes;
- if it still fails, create answers 503 with a "sign in again" sentence and writes no run row. The old
  pair is already marked spent, so the next launch gets the 422 door at once.

The write probe must not write the credential row itself. Writing back a copy read earlier could
restore a credential an admin erased in between, the hazard the re-read-under-lock rule exists for
(`internal/api/awssso_refresh.go:450-458`, #1478). It prefers a store health call that exercises the
write path, if the store has one. Otherwise it writes and deletes a value under one reserved name,
`wardyn-write-probe`, in the owner's namespace. That name joins the three reservation maps
(`internal/api/secrets.go:46`, `internal/broker/broker.go:850`, `internal/secretstore/secretstore.go:138`)
so the secrets API and the injection sink refuse it. The probe runs only on the renew path.

Rejected: carrying the renewed blob from create to dispatch and into bootstrap. It needs shared handoff
state across replicas, owner and provider binding, and erase and suspension fences for a case that is
rare. The persisted pair is already the one state every replica and every door reads.

The single-flight per owner stays in-process here (`lockAWSSSOOwner`, `internal/api/awssso_refresh.go:432-444`);
`ha-l2.2` makes it a cross-replica lock.

### F6: classify dispatch failures by a stamped reason, not by sniffing text

A sandbox-create failure is audited as `run.create`/failure with the raw error
(`internal/api/runs_dispatch.go:599-601`); an agent-start failure as `run.exec`/failure
(`internal/api/runs_dispatch.go:763-768`). The console grades a FAILED run only by `run.build` and
`run.selftest` (`ui/src/app/lib/api/audit.ts:186-189`), so both land as "unknown", and the status line
appends the platform's raw message (`withMessage`, `ui/src/app/components/screens/run-status-detail.ts:190`).

F6 stamps a machine `reason` on those two failure rows (`sandbox_create`, `agent_start`), the way the
model-credential refusal already stamps its class (the `llmRefusalAuditReason` pattern the comment at
`ui/src/app/lib/api/audit.ts:191-196` describes), and adds two `RunEndingKind` values with
`ENDING_COPY` entries (`ui/src/app/components/screens/run-detail/failure-block.tsx:61`). A stripper
removes the CRI `rpc error: code = … desc = …` wrapper. `withMessage` appends the platform message with
the wrapper stripped (keep the `desc` text, drop `rpc error: code = … desc =`): its sentences also render
in the run header, the runs list and the harness sign-in pane, which have no disclosure, and a stuck
image pull's `desc` is the only text that says what to do. The unstripped text moves behind the failure
block's "details" disclosure (`failure-block.tsx:286-292`).

Rejected: matching `run.create`/failure by message text. `run.create`/failure also carries provider
refusals and other failures, and the existing comment at `audit.ts:180-184` rejects guessing a cause from
an unclassified row for that reason.

The disclosure shows only text the viewer already receives today (`failure_hint`, the audit row's
`data.error`). Nothing new is fetched or widened.

### F7: documentation only

`wait_budget_sec` is how long a run's approval requests wait for a decision (`internal/api/run_limits.go:69-90`,
`internal/api/run_end_wait.go:19-27`, `internal/types/types.go:140`). The start deadlines are
`podIPWaitTimeout` and `canaryWaitTimeout` (`docs/OPERATIONS.md:4227-4245`). The field's descriptions
already call it the decision wait (`docs/operations/run-lifetime.md:32`, `ui/src/app/lib/types/runs.ts:186-188`,
`internal/types/types.go:140`), and OPERATIONS already names the start bounds. F7 adds the one missing
sentence, that it does not bound a run's start, with a link to the start bounds, in run-lifetime.md and
the TS comment. P6 owns the OPERATIONS paragraph.

### P2: one source for the default size

The 2000m/4096Mi default is read in three code places, `internal/composer/clamp.go:139-150`,
`internal/runner/k8s/naming.go:164-171` and `internal/runner/docker/hardening.go:490-497`, and named in a
fourth, the sign-in sandbox's comment (`internal/api/harnesscred.go:405-416`). P2 adds
`runner.EffectiveLimits()` beside the constants (`internal/runner/sandbox.go:33-37`), returning the
deployment's configured default or the constants; the three code sites call it and the comment names it. A deployment knob (`WARDYN_SANDBOX_DEFAULT_CPU_MILLIS`,
`WARDYN_SANDBOX_DEFAULT_MEMORY_MIB`; chart `runner.sandbox.defaultResources`) sets it. The proxy envelope
(500m/256Mi) becomes one value read by both substrates: k8s `proxyResources`
(`internal/runner/k8s/naming.go:260-271`) and docker `proxyResources`/`proxyMemoryMiB`
(`internal/runner/docker/hardening.go:33,469-477`). A Kubernetes-only value would leave Docker's proxy
at a size the Azure sizing rule below can outgrow.

The shipped chart default becomes **1000m/2048Mi** (Q-P2, approved). The daemon default without the
knob stays 2000m/4096Mi, so non-chart installs are unchanged. The sign-in sandbox keeps its own
500m/512Mi (`internal/api/harnesscred.go:417-420`).

Rejected: changing the compiled-in constants. That would move every Docker install too, and leave four
call sites free to drift again.

The proxy's memory value must also cover the Azure provider's 128 MiB in-flight body budget when that
provider is enabled. P2 records that sizing rule in the chart docs; the shipped proxy default is Q-B3.

### P1: one placement for the agent, proxy and canary pods

The chart's `nodeSelector`, `affinity` and `tolerations` (`deploy/helm/wardyn/values.yaml:742-744`,
`deploy/helm/wardyn/templates/deployment.yaml:701-712`) place wardynd only. The run pods are built with
none (`internal/runner/k8s/sandbox.go:207-209,302-303`), and neither is the boot canary
(`internal/runner/k8s/canary.go:154`). P1 adds a driver placement config carrying `nodeSelector`,
`tolerations`, `affinity`, `priorityClassName`, `podAnnotations` and `podLabels`, rendered from chart
values to one env var (`WARDYN_K8S_SANDBOX_PLACEMENT`), and applies it to all three pods. A canary
placed differently from the run pods would prove NetworkPolicy enforcement on nodes runs never use.

Arbitrary metadata never overrides reserved keys. `wardynLabels` writes the managed, run and component
labels after the caller's extras (`internal/runner/k8s/naming.go:75-86`), and the NetworkPolicy selects on
them. Placement labels go through the same path, and a placement that names a reserved key is refused at
boot, not silently dropped. Any annotation or label key whose prefix ends in `kubernetes.io/` or
`k8s.io/` is refused at boot too, except the allowlisted `cluster-autoscaler.kubernetes.io/safe-to-evict`.
Those keys can loosen confinement the PodSpec sets (an AppArmor `unconfined` annotation, for one).

Rejected: a pod template override (a full PodSpec patch). It would let a values file reach the security
context, service links and token automount that `sandbox.go` sets deliberately.

### P3: requests from a ratio, never from the run

`resourceRequirements` builds requests and limits from the same values (`internal/runner/k8s/naming.go:164-185`),
so every run pod is Guaranteed. `runner.Resources` gains `CPURequestMillis` and `MemoryRequestMiB`
(0 = equal to the limit, today's behaviour), filled from a deployment ratio knob. Boot refuses a ratio
outside (0, 1], naming the value; unset means requests = limits. The ratio applies to the agent pod
only: the proxy envelope stays Guaranteed, because it is the egress boundary and an evicted proxy ends
the run. Docker ignores them.
The `naming.go` comment is updated.

Rejected: a per-run request in the policy spec. A member could then shrink their request below what the
node can honour and push contention onto co-tenants; the ratio stays a platform decision.

### P4: reclaim a hung run in three independent ways

- **(a) Absolute max age.** `WARDYN_RUN_MAX_AGE` (default off) is a cap separate from idleness. The
  lifecycle reaper (`internal/lifecycle/lifecycle.go:4-18`) ends a run older than it and audits the stop.
  It is its own predicate on the run's age, not `ends_at` (which a person may extend) and not the idle
  compare-and-set.
- **(b) Pod deadlines.** `activeDeadlineSeconds` = max age + grace on both run pods (proxy,
  `sandbox.go:207`; agent, `sandbox.go:302`), set only when max age is set. The proxy is created first
  and its IP goes into the agent's PodSpec (`sandbox.go:285-288,307`), so the agent's UID does not exist
  when the proxy is created. The order is: create the proxy, create the agent, then **patch** the
  proxy's `ownerReferences` with the agent UID the create returned. The reference exists so that
  deleting the agent pod, by anything (Destroy, the sweep, an operator, a node drain), garbage-collects
  the proxy with it. That needs a `patch` verb on pods in the runner Role
  (`deploy/helm/wardyn/templates/rbac.yaml:181-183`), with a comment saying why. A crash
  between the steps is covered by the deadlines and the reconciler. `activeDeadlineSeconds` fails a pod
  and deletes nothing, so the per-run Secret and NetworkPolicies are reclaimed by the reconciler (c).
- **(c) Reclaim through the existing reconciler.** A pod failed by `activeDeadlineSeconds` reads as
  terminal (k8s `internal/runner/k8s/lifecycle.go:53`), so `sweepRunWatchers`/`reconcileWatch`
  (`internal/api/reconcile.go:405-480, 685-735`) finalizes the run and `teardownByRunID` deletes its
  pods, Secret and NetworkPolicies. `sweepOrphanedSandboxes` (`reconcile.go:192-237`) still reaps
  sandboxes with no run row. The reconciler already finalizes only on a definite terminal state and
  bounds probe errors with `reconcileProbeErrorCeiling`; P4 adds no second rule. Code is added only for
  a gap the lane's test shows red. P5's CPU signal is a different signal and is not used here.

Rejected: an owner reference on the proxy at creation by name. An owner reference needs the owner's UID;
a name is not enough.

### P4(d): a non-zero idle default, only once idleness is honest

`examples/policies/default.json:32` ships `auto_stop_after_sec: 0`. With P5 in place, a busy run is no
longer read as idle, so a non-zero default stops abandoned runs without killing working ones. The value
is Q-P1 (recommended 3600). Policies copied from `default.json` before the upgrade are unchanged. The
file is also the image's default `WARDYN_DEFAULT_POLICY` (`docs/ENV.md:166`), so a deployment that
points at the shipped file gets idle stop on upgrade; the upgrade note says so.

### P5: an activity signal from the substrate, one read per tick

The reaper reads `agent_runs.updated_at`; activity that never leaves the sandbox does not move it
(`internal/lifecycle/lifecycle.go:8-14`). `StampRunActive` moves a different clock, `active_at`
(`internal/store/store_run_pause.go:108-120`), which the pause reads and the reaper does not.

- On Kubernetes, the driver makes **one** `metrics.k8s.io` PodMetrics list per tick for the runs
  namespace, label-selected. That needs a `list` rule on `pods` in the `metrics.k8s.io` group.
  Without metrics-server, the CPU signal is off, a `/setup/status` row says so, and idleness falls back
  to today's attach and egress signal.
- On Docker, the existing pause sampler (`nextIdleSamples`/`runCPUQuiet`, `internal/api/run_pause.go:545-600`)
  is extended to cover auto-stop candidates, with one instrument for both: one-shot `ContainerStats`
  (`stream=false`), replacing `runCPUQuiet`'s in-sandbox exec. One reading per run per tick feeds both
  the pause and the stop decision against one threshold (`idleQuietCorePercent`), so they cannot
  disagree. N is `idleSamplesPerTick`, on the existing cursor. The walk/sample exclusion still holds.
- Activity above the threshold bumps `updated_at`, the clock the reaper reads, only through
  `store.TouchRun` (`internal/store/store.go:274-289`), whose non-terminal guard keeps the killed-run
  tail-upload grace closed.

Rejected: reading through the cockpit's in-sandbox exec (`internal/api/run_resources.go:7-14`). That is
one exec per run per tick, which is what this lane must not do at fleet scale. The cockpit keeps it for
one run on demand.

### P6: wait for room, under deadlines that span both pods

`canaryWaitTimeout` (3m) and `podIPWaitTimeout` (90s) bound a run's start
(`internal/runner/k8s/canary.go:26-32`). The proxy's IP wait fails at 90s on its own deadline
(`internal/runner/k8s/sandbox.go:536-560`), so replacing only the 3-minute constant would still fail an
unplaceable proxy at 90 seconds.

- `WARDYN_SANDBOX_START_TIMEOUT` (default 3m, today's value) replaces `canaryWaitTimeout` for sandbox
  start.
- When `podStuckReason` (`sandbox.go:459`) reports a capacity blocker (Unschedulable, Insufficient), the
  run stays STARTING with the existing "Waiting for a machine with room" line
  (`ui/src/app/components/screens/run-status-detail.ts:59`), with backoff, until
  `WARDYN_SANDBOX_CAPACITY_WAIT` (default 15m).
- Both are **absolute** deadlines across the proxy and the agent. The separate 90s IP wait is subsumed.
  A change of stuck reason never resets them.
- Image-pull and other terminal errors still fail fast (`proxyStartFailure`, `sandbox.go:584`).
- The boot canary keeps its **own** budget, which must fit inside the 450s startupProbe
  (`deploy/helm/wardyn/templates/deployment.yaml:569-573`).
- `/setup/status`, the UI's `RUN_START_OVERDUE_MS` (`run-status-detail.ts:135`, 270s today) and the
  provisioning lease (`internal/api/runs_dispatch.go:570-577,630-637`) follow the real deadlines.

Rejected: one shared timeout for start and boot. Raising it for runs would push the boot canary past the
startupProbe and restart wardynd mid-boot.

### P7: quota is a refusal, node size is advice

Preflight and create read the runs namespace's `ResourceQuota` objects and, optionally, node allocatable,
honouring P1's placement. Nothing reads either today.

- **RBAC.** `list` on `resourcequotas` (finding every applicable quota needs list, not get). Nodes are
  cluster-scoped, so reading them needs a ClusterRole, which a shared-cluster tenant may not be granted;
  it is optional and off by default. Empty, forbidden and unavailable are three different results.
- **What is counted.** Both pods (agent and proxy), the request and limit axes, and quota scopes
  (`Terminating` for `activeDeadlineSeconds`, `PriorityClass`).
- **What it means.** A hard quota breach is refused before dispatch. Node allocatable answers "does it
  fit on any node at all", an advisory, not free capacity: co-tenant pods in other namespaces are
  invisible to this Role, so the scheduler stays authoritative. Concurrent reads reserve nothing.

Rejected: treating allocatable minus visible pods as free capacity. It would refuse runs that fit and
admit runs that do not, depending on what other tenants run.

### P8: three small items

- **(a)** `cluster-autoscaler.kubernetes.io/safe-to-evict` and PriorityClass come through P1, with no
  annotation by default. `"true"` would let the autoscaler evict a live run. Documented.
- **(b)** A deployment-wide concurrent-run cap beside the per-principal `MaxConcurrentRuns`
  (`internal/api/runs_create_validate.go:566-592`). The per-principal cap is count-then-create and soft
  by design (`:583-586`); the deployment cap is atomic across replicas: the count of non-terminal runs
  and the insert happen under one transaction-scoped advisory lock. It is enforced at every creation door.
  New rows all go through the single `createRun` door (`internal/api/org_revocation.go:31-36`; its comment
  at `:22-27` lists POST /runs, harness login, record runs, source scans and site-config probes, the
  workspace launcher calls it at `internal/api/workspace_run_launch.go:601`, and
  `TestRunCreationRoutesThroughTheRevocationGate` fails a launcher that bypasses it). The plan's doors map
  onto these: create is POST /runs, record is the workspace launcher, and portal is a delegated POST /runs
  from a registered portal (stamped `created_via` at `internal/api/runs.go:318`, then `createRun` at
  `:321`). Revive
  re-dispatches a RUNNING row (`internal/api/run_revive.go:119,423`) that is already counted, so the cap
  never refuses it; a test pins that a revive at the cap succeeds. Default 0 = unlimited.
- **(c)** Docs: `PidsLimit` is not enforced on Kubernetes (`sandbox.go:298-301` warns).

Rejected for (b): a counter table. It drifts on every crash path that misses a decrement.

### G2: templates from the configured providers

`POLICY_TEMPLATES` is a constant list seeded with `api.anthropic.com` and an `api_key` grant
(`ui/src/app/components/wardyn/policy-panel.tsx:73-140`); the wizard seed hardcodes the same host
(`ui/src/app/components/screens/new-run/wizard-types.ts:615`) and the host helper knows two vendors
(`wizard-spec.ts:484-492`). On a Bedrock SSO install the starter template is wrong. G2 derives the
templates from `/setup/status` `model_providers`: a Bedrock SSO provider contributes its regional
endpoint host and no `api_key` grant; key kinds keep their vendor host and grant. `policy-lane.ts:14-17`
and both STARTER_SPEC users follow.

Rejected: a template endpoint. The comment at `policy-panel.tsx:57-59` already names that as the day a
deployment wants its own gallery; deriving from data the console already loads needs no new API.

### I1: token expiry with a deployment cap

`api_tokens` has no expiry (`internal/db/migrations/0045_api_tokens.sql:57-68`; `docs/OPERATIONS.md:2262-2272`
says so). I1 adds a nullable `expires_at`. `GetAPITokenByRaw` filters expired rows and returns
`ErrNotFound`, as it does for revoked ones (`internal/store/iface.go:170`), so `apiTokenAuth`
(`internal/api/apitokens.go:98`) answers its existing single 401 and expiry is no existence oracle. The mint request (`createAPITokenRequest`, `apitokens.go:203`) takes a TTL.
`WARDYN_API_TOKEN_MAX_TTL` caps it. Semantics:

- `expires_at` NULL means no expiry (every existing token).
- A TTL of zero or omitted at mint means the cap if one is set, else none.
- A TTL above the cap is clamped, and the clamp is recorded on the `token.create` row.
- The TTL is seconds; a negative value is a 400 before anything is minted.
- Default: no cap.

The console's mint form is unchanged in this lane; it sends no TTL and so gets the cap.

Rejected: a default cap. Every CI job holding a token would start failing on its own schedule after an
upgrade.

### I2: a role-stamp TTL, and the only way to refresh it is to sign in

Wardyn keeps no IdP refresh token, so a demotion made only in the IdP reaches Wardyn when the person
next signs in (`docs/OPERATIONS.md:2262-2272`). `WARDYN_ROLE_STAMP_TTL` (default off) bounds that:
a token whose role/group stamp is older than the TTL is refused with `role_stamp_stale` until its owner
signs in again. SSH keys already have this bound (`WARDYN_SSH_ROLE_TTL`, `docs/ENV.md:250`); I2 gives
API tokens and console sessions the same one.

- `api_tokens` gains `identity_stamped_at`, set at mint and at every re-stamp.
- `OnLogin` (`cmd/wardynd/boot_deps.go:437-439`) re-stamps through `refreshLoginStamps`
  (`boot_deps.go:833-839`). Today that is best-effort: a store error logs and the login succeeds. Under
  a TTL the re-stamp must be **atomic on a verified login**: if it fails, the person's tokens stay stale
  rather than half-stamped. The UPDATE keeps `revoked_at IS NULL` (`internal/store/store_apitokens.go:164-167`)
  and adds "not expired", so a login never revives a revoked or expired token.
- A console session whose `IssuedAt` (`internal/auth/oidc/oidc.go:143-145`) is older than the TTL is sent
  through re-login; the cookie's role (`oidc.go:138`) is checked against the same TTL. A session already
  ends at the IdP ID token's expiry (`internal/auth/oidc/oidc_callback.go:296`), so this check takes
  effect only when the TTL is shorter than that lifetime.

Rejected: re-deriving the role from the IdP on a timer. Wardyn holds no IdP credential to do it with.

The backfill is truthful: mint stamps the identity, and later re-stamps were not timed. A token

existing columns (`updated_at`, the run's creation time).

## Security model and residual risks

- **F2.** Every write of the AWS SSO pair happens under the owner lock an erase takes. The probe narrows, but does not close, the window between a successful redeem and a failed
  Put: a store that fails after the probe still costs one sign-in. Dispatch also renews
  (`runs_dispatch_provider.go:337`); a persist failure there still ends that run at bootstrap. With
  create renewing first, dispatch rarely has anything to renew. Erase racing create fails closed:
  bootstrap finds no pair and refuses.
- **F6.** The disclosure shows the same raw text as today. Whatever a CRI error already carries is not
  widened, and not removed either.
- **P1/P8.** Placement metadata is operator-supplied. Reserved labels, the NetworkPolicy selector and any
  `kubernetes.io/` or `k8s.io/` key other than `safe-to-evict` are refused, not merged. `safe-to-evict: "true"` remains possible if an operator sets it; the docs say what
  it costs.
- **P4.** The new `patch` verb on pods is not metadata-only: it also lets wardynd change mutable spec
  fields (container image, `activeDeadlineSeconds`, added tolerations) on any pod in the runs namespace.
  It already holds `create` and `delete` there, so it can already replace any such pod, but it is a new
  verb and the Role comment says what it reaches and why.
- **P5.** The metrics read is namespace-scoped and label-selected. A sandbox can fake activity by
  burning CPU, which keeps its own run alive; it cannot extend anyone else's. Max age (P4a) bounds it.
- **P7.** Quota reads say nothing about co-tenants. Node allocatable is advisory. The scheduler stays
  authoritative, so a run admitted here can still wait in P6.
- **I1/I2.** Both default off, so upgrading changes no token's validity. An operator turning I2 on
  forces one re-login for every holder. The console session check uses the cookie's own `IssuedAt`; a
  cookie without it is stale under the TTL.

## Upgrade and compatibility

- **P2.** Chart installs get the smaller 1000m/2048Mi default on upgrade. Set
  `runner.sandbox.defaultResources` back to 2000/4096 to keep the old size. Non-chart installs are
  unchanged.
- **P6.** An unplaceable run now waits up to 15 minutes instead of failing at 90 seconds. Set
  `WARDYN_SANDBOX_CAPACITY_WAIT=0` to keep failing fast.
- **P4(d).** Only `examples/policies/default.json` changes. Copied policies keep their value, but a
  deployment whose `WARDYN_DEFAULT_POLICY` is the shipped file (the image default, `docs/ENV.md:166`;
  `deploy/helm/wardyn/README.md:219-223`) stops idle runs after the upgrade.
- **P3, P1, P8, P4(a–c), P7.** Off or unchanged until configured. The new RBAC rules arrive with the
  chart upgrade.
- **I1/I2.** Two nullable or backfilled columns on `api_tokens`; existing tokens keep working. The
  `docs/OPERATIONS.md:2262-2272` paragraph ("no expiry column", "no TTL on the stamp") is rewritten.
- **F1, F6, G2.** Console-only behaviour; F6's new audit `reason` is additive.
- **Leaver docs.** The O1 scrape-credential docs and the leaver docs refer to I1 and I2 for expiry and
  re-login.
