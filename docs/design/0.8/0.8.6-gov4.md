# Wardyn 0.8.6 — four-eyes on governance writes (GOV4)

An adopter running Wardyn under a separation-of-duties rule asked that no single administrator be
able to widen what people may do. Today one security administrator can rewrite a governance
profile, repoint an assignment, add a capability grant, lift a restriction or change a role
mapping, and the change is live on the next request. 0.8.6 adds an opt-in switch,
`WARDYN_GOVERNANCE_SECOND_HUMAN`. With it on, an authority-changing write is stored as a pending
change and answered `202`; a second, distinct human with the authority to make that write approves
it, and only then does it apply. With it off, nothing changes.

This record is the design for epic GOV4 and its five lanes (`gov4-b1` to `gov4-b5`). Every code
reference is to `origin/main` at `e0efee625` (v0.8.5).

## What exists today

**Four-eyes already exists for approvals.** `WARDYN_EGRESS_SECOND_HUMAN` and
`WARDYN_CAPABILITY_SECOND_HUMAN` stop the creator of a run deciding its egress or Azure DevOps
escalation approvals (`internal/api/approvals_second_human.go:22,40`). The gate,
`requireSecondHuman` (`:170`), sets the rules GOV4 copies:

- the shared admin token bypasses it, and every bypass is audited (`:203`,
  `approval.second_human.bypass`, `docs/AUDIT-ACTIONS.md:316`);
- local mode refuses with a `503` that names the incompatibility, because local mode
  authenticates nobody and both operands of "is this a different human" are client-supplied
  (`:209-214`), and the daemon warns at boot (`cmd/wardynd/boot_flags.go:698,704`);
- a self-decision is refused with `authz.denied` reason `second_human_required`
  (`internal/authz/registry.go:39,102`; `approvals_second_human.go:239-246`).

That gate compares the principal only (`:234`). GOV4 compares principal **and** email (below).

**The governance writes are plain handlers that write and audit in one step.**

| Surface | Route and tier | Handler |
|---|---|---|
| Governance profiles | `POST /governance/profiles`, `PUT /governance/profiles/{id}`, `DELETE /governance/profiles/{id}` on `securityOps` (`internal/api/governance.go:55-57`, where the router parameter is named `operatorOnly`; the group is mounted on `securityOps` at `routes.go:582`) | `writeGovernanceProfile` (`governance.go:197-240`), `handleDeleteGovernanceProfile` (`:272-294`) |
| Governance assignments | `POST /governance/assignments`, `DELETE /governance/assignments/{id}` (`governance.go:58-59`) | `handleUpsertGovernanceAssignment` (`:375-417`), `handleDeleteGovernanceAssignment` (`:423-439`) |
| Capability grants | `POST /permissions/grants`, `DELETE /permissions/grants/{id}` on `securityOps` (`routes.go:774-775`) | `permissions.go:352`, `:400` |
| Enforcement map | `PUT /permissions/enforcement` (`routes.go:776`) | `permissions.go:433` (optional `If-Match`, `etag.go:30,49`) |
| Availability | `PUT /permissions/availability/{kind}/*` (`routes.go:779`) | `handlePutAvailability` (`permissions_availability.go:109`), which calls `SetCapabilityRestriction` (`internal/store/store_capabilities.go:198`) |
| User-type priority | `PUT /user-types/{id}` on `securityOps` (`user_types.go:33`) | `handleUpdateUserType` (`user_types.go:151`) |
| Role mappings | `POST /access/mappings`, `DELETE /access/mappings/{id}` on `operatorOnly` (`access.go:89-90`, mounted at `routes.go:549`) | `handleUpsertRoleMapping` (`access.go:579`), `handleDeleteRoleMapping` (`:715`) |

`isOperator` (`internal/api/http.go:554`) is the super-admin predicate. `isSecurityOperator`
(`http.go:598`) is admin or security admin. Both return true for a caller with no verified OIDC
human: the admin token, local mode, or no OIDC.

**Two of these routes widen without looking like it.**

- `PUT /permissions/availability/{kind}/*` with `restricted=false` deletes the restriction row
  (`store_capabilities.go:198-205`). Every person then reaches the value under the capability
  rules (`capabilities.go:627`) with no grant write at all.
- A user-type **priority** change can move a person who matches both a strict and a broad type onto
  the broad one at their next sign-in. `pickUserType` picks the highest-priority custom type
  (`internal/auth/oidc/user_type_derive.go:129`). No role mapping or assignment changes.

GOV4 covers both.

**The client cannot see a 202 today.** `Client.do` treats any 2xx as success and decodes the body
into the caller's output type (`pkg/client/client.go:724-735`). `ApplyGovernance`
(`pkg/client/families.go:711`) POSTs or PUTs each profile (`:740,742`). It then sends
assignments with the profile id from that response (`:773`) and, with `--prune`, deletes what the
file omits (`:790`). A pending body decodes into a zero profile, whose `uuid.Nil` id then reaches
the assignment write. `wardyn governance set` is a thin caller (`cmd/wardyn/governance.go:103`).

**File-size budget.** `governance.go` is 925 lines against the 1000-line gate
(`scripts/check-file-size.sh`). New code goes in new files.

## Decisions

### D1. Opt-in, one switch, default off

`WARDYN_GOVERNANCE_SECOND_HUMAN` (bool, unset by default) turns GOV4 on for every covered target.
Default off, for the reason the egress switch gives (`approvals_second_human.go:18-21`): turning it
on unprompted would deadlock every single-administrator deployment.

*Rejected:* a switch per target family. Partial four-eyes is the configuration an auditor
misreads. One switch covers one documented set.

*Rejected:* a console or site-config setting. A setting held in the database can be switched off
by the administrator it constrains. The switch is env-only, like the egress switches.

### D2. A covered write becomes a stored change and answers 202

With the switch on, a covered write is decoded and validated exactly as today, then stored in
`governance_changes` instead of applied. The response is `202 Accepted` with
`Location: /api/v1/governance/changes/{id}` and this body:

```json
{"pending_change": {"id": "…", "target_kind": "governance_profile", "op": "update",
  "target_key": "…", "state": "pending", "proposed_by": "…", "proposed_at": "…",
  "expires_at": "…", "diff": {"before": {…}, "after": {…}, "changed": ["ceiling.allowed_domains"]}}}
```

A second human approves the change and the target mutates; any authorised human rejects it; or it
expires after `WARDYN_GOVERNANCE_CHANGE_TTL` (default `72h`).

*Rejected:* write-then-revert, applying immediately and rolling back if nobody confirms. The
widening is live for the whole window, which defeats four-eyes.

*Rejected:* a precondition header (`Wardyn-Accept-Pending`) without which a covered write is
refused instead of queued. It would make old clients fail with a clear error instead of
mis-decoding a 202. But the console, the CLI and every script would have to send it, and old
clients already fail closed here: each follow-on write they make is itself covered (queued) or
refused (`profile_id: required`, `governance.go:320-321`). The old-client behaviour is documented
instead (Upgrade).

### D3. Handlers split into decode+validate and apply

Each covered handler is split into two parts.

- **decode+validate** reads the body and runs today's validation. That includes
  `decodeGovernanceProfileRequest` (`governance.go:133`), `validateGovernanceAssignment`
  (`:316`), `validateCapabilityGrant`, the user-type existence check and the role-mapping
  collision, posture-flip and acknowledgement checks.
- **apply** performs the mutation and its audit. It takes a store handle that is either the pool
  or a transaction.

For example, `writeGovernanceProfile` (`governance.go:197-240`) becomes
`decodeGovernanceProfileWrite` plus `applyGovernanceProfile`.

The same `apply` serves three callers: a direct write (switch off), a bypass or exempt write, and
an approval. **`apply` re-runs validation against the current state.** That includes
`governanceGrantsWithinCeiling` against the current `DefaultPolicy.EligibleGrants`
(`governance.go:208`), because `DefaultPolicy` is env-borne and can change between proposal and
approval. One code path means approval cannot apply something a direct write would refuse.

The **diff is rendered server-side** at proposal. It holds the target's current row and the
proposed row, both passed through `redactSpecForRead` (`policies.go:186`, as
`GET /governance` does at `governance.go:94-96`), plus the list of changed field paths. For an
assignment change, `diff.after` embeds the referenced profile as it stood at proposal
(`profile: {id, name, ceiling, limits}`), and the assignment's `base_hash` covers the referenced
profile row as well as the assignment row, so a rename or ceiling change after proposal makes the
change stale. The console
and the CLI show the server's diff and never compute their own.

### D4. What is covered

| `target_kind` | Operations | Lane |
|---|---|---|
| `governance_profile` | create, update, delete | gov4-b1 |
| `governance_assignment` | upsert, delete | gov4-b1 |
| `capability_grant` | upsert, delete | gov4-b2 |
| `capability_enforcement` | replace | gov4-b2 |
| `capability_availability` | set, when the stored `restricted` bit changes (either direction; a superset of "when it changes authority", adding no exemption) | gov4-b2 |
| `user_type_priority` | update, when `priority` changes | gov4-b2 |
| `role_mapping` | upsert, delete | gov4-b2 |
| `key_domain_assignment` | upsert, delete (the table comes from KEY lane `key-l3.3`, which registers the kind) | key-l3.3 |

**Exempt:** only metadata, or a change **proven narrowing by its resolved effect**. A metadata-only
profile write is exempt only when every stored field other than `name` and `description` is equal
to the current row, including `base_profile_id`, `overlay` and `overlay_limits`. A user-type name
or description edit with the same priority is metadata too. A PUT that changes nothing answers as today.

**"Delete" is not inherently subtractive.** Each of these widens:

- deleting a deny grant;
- deleting an assignment, which moves its subjects back to the deployment ceiling
  (`governance.go:419-422` says so);
- deleting a restriction row;
- turning enforcement on for a kind, because unenforced widening requests are refused
  (`capabilities.go:623-626`) and enforcement lets grants through.

So exemption is never decided from the shape of a row.

**Narrowing exemptions shipped in 0.8.6.** A profile update is exempt when the new effective
profile is `Leq` the current effective profile. `Leq` comes from COMP lane `comp-d2` and is
resolved through the base under composition. It must include the full git_pat dominance contract
from GPAT lane `gpat-g1`. No other target gets a narrowing exemption in 0.8.6. A future exemption
for another target needs a resolved-effect function and a test against the real decision code.
`gov4-b1` lands after `comp-d2`. If `comp-d2` slips, b1 ships with no narrowing exemption and
`comp-d2` adds it.

*Rejected:* exempt every delete, or every `effect=deny` write. Both are row-shape rules, and the
list above shows how they fail.

### D5. Who may approve: the per-target approver table

The approver must pass the predicate of the tier the write was proposed on, and never a weaker
one.

| `target_kind` | Proposed on | Approver predicate |
|---|---|---|
| governance profile, assignment | `securityOps` | `isSecurityOperator` |
| capability grant, enforcement, availability | `securityOps` | `isSecurityOperator` |
| user-type priority | `securityOps` | `isSecurityOperator` |
| role mapping | `operatorOnly` | `isOperator` |
| key-domain assignment (lane `key-l3.3`) | the tier `key-l3.3` mounts its write route on | the same predicate |

Two consequences follow, matching Q-GOV4 (c):

- A security admin may approve a super admin's grant or profile change. The tiers overlap on this
  surface (`http.go:569-571`).
- Only a super admin may approve a role-mapping change, because only a super admin may write one.
  A security admin who tries is refused with `authz.denied` reason `admin_surface`, the refusal
  `requireOperator` already gives.

The predicate is evaluated **inside the approval transaction**. For an API-token approver, the
token row is re-read by id with `revoked_at IS NULL` in the same transaction,
`IsSessionRevoked(principal, email, created_at)` is re-run, and the predicate is re-evaluated
against the re-read `role`. A revoked or expired token, one invalidated by the session-revocation
cutoff, or one whose role stamp no longer passes, is refused.

**The role-mapping lockout guard uses the approver's own facts.** Today `accessLockoutErr`
(`access.go:478`) checks the caller's own claim snapshot. Under GOV4 the caller that matters is the
human whose approval performs the write, so `apply` runs the guard against the approver's
snapshot. The proposer's facts are not consulted at apply: the proposer may have been demoted
since, and the second human is the safeguard against the proposer. The admin-token exemption is
unchanged (`access.go:479-482`), and remains the recovery path. The demoted-token revocation
(`access.go:682,777`) runs after the approval commits, as it runs after the write today.

The pending-change list filters by the same table: role-mapping changes are visible only to
`isOperator` callers. `/access` has no member-safe or security-admin view (`access.go:82-86`), so
the pending list must not create one.

### D6. Distinct human: compare principal and email

An approval is refused with reason `second_human_required` (target `governance.change`) when the
approver's principal equals `proposed_by`, **or** when both emails are non-empty and equal after
case folding. `requireSecondHuman` compares the principal only (`approvals_second_human.go:234`).
For governance writes, one person holding two principals (an SSO session and an API token
published through `withHumanIdentity`, `apitokens.go:196`, or two IdP subjects with one mailbox)
must not count as two humans. The email is captured from `oidcEmailFromContext` (`http.go:69`) at
proposal and approval.

The proposer **may reject** their own change. Withdrawal is not four-eyes-relevant: it applies
nothing. *Rejected:* a separate `withdraw` verb, which would be a second word for the same state.

### D7. The gates copied from `requireSecondHuman`

- **Admin token.** A covered write by the admin-token principal applies directly. An approval by
  the admin token applies the change. Both write `governance.change.bypass`, beside the target's
  own audit row, and the row records the outcome as the egress bypass row does. The token is the
  break-glass. Refusing it would lock an operator out of their own governance the moment SSO
  breaks.
- **Local mode.** With the switch on, every covered write and every approve or reject answers
  `503` with reason `governance_second_human_local_mode`, and boot warns, copying
  `boot_flags.go:698`.
- **Self-approval** is refused (D6).

### D8. One transaction per decision

Approve, reject and expiry each run as one transaction, in this order:

1. Lock the change row (`SELECT … FOR UPDATE`).
2. Require `state='pending'` and `expires_at > now()`. A lapsed row is moved to `expired` in this
   transaction and the caller gets `409`, reason `governance_change_not_pending`.
3. Re-check the approver's authority (D5) and distinctness (D6).
4. Recompute `base_hash` from the target rows, read with `FOR UPDATE` where they exist. Compare
   it, and compare `deployment_hash`, which is `computeETag` over the current `DefaultPolicy`. On
   either mismatch the row moves to `stale` and the caller gets `409`, reason
   `governance_change_stale`.
5. Run `apply` against the transaction (D3), including the lockout guard for role mappings.
6. Move the row to `applied` (or `rejected`), stamping the decider and the time.
7. Commit. Audit rows and the role-mapping token revocation run after commit.

Two approvers racing on one change: exactly one applies. A bypass write to a target between
proposal and approval changes the base, so the pending change goes stale. It never overwrites.

Proposal runs in a transaction too. It moves any lapsed pending row for the same target to
`expired`, then inserts. The partial unique index then gives a clean `409`, reason
`governance_change_pending`, naming the existing change id when a live one exists. No sweeper is
needed for correctness. Reads compute expiry from `expires_at`.

The existing store methods (`internal/store/governance.go:39,120`, `store_capabilities.go:198`,
and their siblings) call `s.Pool` directly today. They are refactored onto an exported
`store.Querier` interface (`Exec`, `Query`, `QueryRow`, satisfied by `*pgxpool.Pool` and `pgx.Tx`)
by gov4-b1/b2, so `apply` runs the same SQL either way and nothing in `apply` touches `s.Pool`. The in-process `capEnforcementMu` (`permissions.go:427-432`) is not
the serialisation point under approval, because HA runs more than one replica. The transaction
is.

*Rejected:* applying without the transaction and re-checking afterwards. A crash between
"target written" and "change marked applied" would leave a change that can be applied twice.

### D9. The switch cannot be enabled before every first-party client is pending-aware

`gov4-b1` adds a boot refusal: with this build, `WARDYN_GOVERNANCE_SECOND_HUMAN` set exits 2,
saying the switch is not yet available. The refusal stays in the tree until the SDK/CLI lane
`gov4-b5` has merged **with or before** `gov4-b1`. A tree with the 202 API and an SDK that
mis-decodes it never accepts the switch.

**Recommended, accepted at the recommended defaults (owner ruling 2026-10-03) (Q-GOV4 d):** lift the refusal only when `gov4-b2` (the rest of the
covered set) and `gov4-b3` (the console) have also merged. The lane that merges last of
b1/b2/b3/b5 removes it. Otherwise a tree in between advertises four-eyes while grants, role
mappings and availability are still single-human, and the console decodes a 202 as an ordinary
save. Everything ships in 0.8.6, so this costs nothing at release. It only closes the
intermediate trees. By the `blocked_by` edges that lane is `gov4-b3`.

The refusal precedes the local-mode warning (D7): while the refusal is in the tree, setting the
switch exits 2 in every mode, and the warning applies only once the refusal is lifted.

## Data model

One new table. The migration takes the next free number at merge: `0107_governance_changes.sql`
on today's `origin/main`, whose highest migration is `0106_attach_ticket_authority.sql`. A lane
stacked on a migrating parent takes the parent's number plus one, and the steward renumbers in
merge order. It creates a table and alters none, so it needs no OPERATIONS.md migrator-rationale
row.

```sql
CREATE TABLE IF NOT EXISTS governance_changes (
    id                UUID PRIMARY KEY,
    target_kind       TEXT NOT NULL,
    op                TEXT NOT NULL CHECK (op IN ('create','update','delete','upsert','replace','set')),
    target_key        TEXT NOT NULL,
    payload           JSONB NOT NULL,
    diff              JSONB NOT NULL,
    base_hash         TEXT NOT NULL,          -- computeETag of the target as read; 'absent' for a create
    deployment_hash   TEXT NOT NULL,          -- computeETag of DefaultPolicy at proposal
    proposed_by       TEXT NOT NULL,
    proposed_by_email TEXT NOT NULL DEFAULT '',
    proposed_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
    expires_at        TIMESTAMPTZ NOT NULL,
    state             TEXT NOT NULL DEFAULT 'pending'
                      CHECK (state IN ('pending','applied','rejected','expired','stale')),
    decided_by        TEXT NOT NULL DEFAULT '',
    decided_by_email  TEXT NOT NULL DEFAULT '',
    decided_at        TIMESTAMPTZ
);
CREATE UNIQUE INDEX IF NOT EXISTS governance_changes_one_pending
    ON governance_changes (target_kind, target_key) WHERE state = 'pending';
CREATE INDEX IF NOT EXISTS governance_changes_state_expires
    ON governance_changes (state, expires_at);
```

- **`target_kind` has no CHECK.** That follows the 0052 precedent
  (`internal/db/migrations/0052_governance_profiles.sql`, the `limits` comment): the closed set
  lives in one Go table, so `gov4-b2` and `key-l3.3` add kinds with zero DDL.
- **`target_key` is the target's natural key:**
  - the profile id (a create mints its id at proposal);
  - `subject_type` and `subject` for an assignment;
  - `(subject_type, subject, capability, value)` for a grant;
  - the constant `capability_enforcement`;
  - `kind/value` for availability;
  - the user-type id;
  - the role-mapping value;
  - the key-domain subject.

  A delete by id is resolved to the natural key at proposal, so a pending delete and a pending
  upsert of the same row collide on the unique index.
- **`payload`** holds the validated request, never a secret value. `validatePolicySpec` already
  refuses raw secret values in a ceiling (`governance.go:89-93`). `diff` is redacted (D3).
- **Retention.** Decided rows are kept as the governance history, like the audit rows that
  describe them. `proposed_by`, `proposed_by_email`, `decided_by` and `decided_by_email` are
  personal fields of the subject. `erasure.Orchestrate` (AR, `ar-l1.4`), the single erasure entry
  point, clears them under its `audit_personal_fields` scope. A pending row whose proposer is
  erased first leaves `pending` (to `expired`), so a change with no recorded proposer can never be
  approved. `gov4-b1`, the lane that adds the table, adds that integration atomically with it, and
  is therefore blocked by `ar-l1.4`.

## API

New routes are registered in a new file, `internal/api/governance_changes.go`, on `securityOps`,
with the per-target check inside the handler (D5):

| Route | Purpose |
|---|---|
| `GET /governance/changes?state=pending` | List changes. Role-mapping rows are filtered to `isOperator` callers. |
| `GET /governance/changes/{id}` | One change, with its diff. A role-mapping change answers 404 to a non-operator, the same hidden-404 parity the rest of the API keeps. |
| `POST /governance/changes/{id}/approve` | Approve (D8). |
| `POST /governance/changes/{id}/reject` | Reject, with an optional `reason`: trimmed, at most 512 characters, refused 400 when `controlCharFree` (`permissions.go:145`) is false; stored on the change row and in the reject audit payload only. |

The new error reasons are registered in `internal/api/reasons.go` (or `reasons_routes.go`) and
documented in `docs/sdk.md` (`TestReasonDocsMatchReasonsGo`):

- `governance_second_human_local_mode`
- `governance_change_pending`
- `governance_change_stale`
- `governance_change_not_pending`

The `authz.denied` refusals reuse the registered reasons `second_human_required` and
`admin_surface`, with the new target `governance.change`. They are documented under
`docs/OPERATIONS.md`'s denial table (`TestAuthzDeniedReasonsAreDocumented`).

**Audit actions**, each added to `docs/AUDIT-ACTIONS.md`
(`cmd/wardynd/audit_actions_doc_guard_test.go`):

| Action | When |
|---|---|
| `governance.change.propose` | a covered write was stored |
| `governance.change.approve` | outcome `success` beside the target's own row, or `failure` with an error class of `stale`, `not_pending` or `error` |
| `governance.change.reject` | a change was rejected (the proposer's own rejection included) |
| `governance.change.expire` | a lapsed change moved to `expired` |
| `governance.change.bypass` | the admin token wrote a covered target directly, or approved a change |

The target's existing row (`governance.profile.write`, `capability.grant.create`,
`access.role_mapping.write`, …) is still written on apply. Its actor is the approver, and it gains
`change_id` and `proposed_by`.

## SDK and CLI (gov4-b5)

The shared `do` path recognises `202` with a `pending_change` body and never decodes it into the
caller's output type. It returns the pending change instead, so no SDK method can see a zero-value
object as success. `GetGovernance` and `ApplyGovernance` get this handling.

`ApplyGovernanceResult` is added, following the `PutSiteConfigResult` precedent
(`pkg/client/families.go:238`). It returns:

- the applied document;
- the list of pending changes;
- the deferred writes.

`ApplyGovernance` keeps its signature and returns a typed pending-approval error when anything is
pending. An SDK caller written before 0.8.6 fails loudly rather than continuing.

Inside an apply:

- An assignment naming a profile whose write is pending is **deferred**, not sent. It is never
  sent with `uuid.Nil`.
- **Prune does not run** when any write in the apply is pending, because it would compare against
  a state that is not final. The result says so.
- Pending is the expected outcome under four-eyes, so `wardyn governance set` exits 0 and prints
  the pending and deferred lists. *Rejected:* a non-zero exit, which would make every governed
  apply in CI look like a failure.

New CLI commands:

```
wardyn governance changes list [--state pending|applied|rejected|expired|stale]
wardyn governance changes approve <id>
wardyn governance changes reject <id> [--reason text]
```

They are backed by `ListGovernanceChanges`, `ApproveGovernanceChange` and
`RejectGovernanceChange`, and the SDK coverage census (`pkg/client/client.go:12-70`) gains the
`/api/v1/governance/changes` family.

COMP lane `comp-d6` (W3) builds on this: under a 202 it defers dependent children and
assignments, and it tests a pending base approval.

## Security model

**What GOV4 guarantees.** With the switch on, SSO configured and the admin token held out of band,
three things hold:

- No single human changes the effect of a covered target through the governance, permissions,
  access or user-type API.
- Every change carries two named humans in the audit chain: a proposer and a distinct approver
  with the authority to make the write.
- Every change applies against exactly the state the approver reviewed, or not at all (D8).

**Residual risks, stated rather than discovered:**

1. **The admin token is the break-glass.** Its writes and approvals are single-human, and audited
   as `governance.change.bypass`. A deployment that wants GOV4 to bind holds the token out of
   band.
2. **Local mode cannot enforce GOV4.** It refuses with a `503` and warns at boot.
3. **The database is not four-eyed.** A database writer can change target tables directly. The
   audit chain then shows a target row with no `propose`/`approve` pair, which is detection, not
   prevention.
4. **Two authorised humans who collude defeat it,** as with any four-eyes control.
5. **Each change is reviewed alone.** Two separately approved changes can compose into a widening
   neither diff shows, for example a grant plus an enforcement flip. The diff shows the target, not
   every person it reaches; a group assignment's reach is the reviewer's judgment.
6. **Single-super-admin deployments** cannot approve role-mapping changes without a second super
   admin or the admin token.
7. **Pending governance changes do not notify anyone.** NOTIFY covers `approval_requests`, not
   `governance_changes`. Approvers find changes through the console tab or
   `wardyn governance changes list`.
8. **Approver authority is the stamped role.** For an SSO session that is the role stamped at
   sign-in. A person demoted only at the IdP keeps the role until the session ends; lane `i-i2`
   narrows this.
9. **Not covered in 0.8.6.** These governance-adjacent writes stay single-human:
   - `PUT /workspaces/{id}/approved-egress` and `PUT /workspaces/{id}/denied-egress`;
   - record-egress promotion;
   - `/policies`;
   - `/site-config`;
   - `/integrations`;
   - the approval `always` scope;
   - user-type create and delete. A new type takes effect only through a covered role-mapping
     write, and a referenced type cannot be deleted (`user_types.go:208-211`);
   - SCIM purge (`scim-a4`) deletes the person's user-subject governance assignments and
     capability grants directly, without a pending change. The IdP is the single authority for
     that write.

   `docs/OPERATIONS.md` and `threatmodel/THREAT-MODEL.md` list them.

## Upgrade and compatibility

- The migration adds one table and changes no existing row. With the switch unset, every covered
  route behaves exactly as in 0.8.5, byte for byte in status and body.
- **Old clients against a server with the switch on:**
  - a pre-0.8.6 `wardyn governance set` decodes the 202 as an empty profile;
  - its next assignment write is refused with `profile_id: required`;
  - or, if a pending profile's id is reused, that write is itself queued;
  - its prune deletes are each queued as changes rather than applied.

  Nothing applies without approval, but the old CLI reports a confusing error. Upgrade the CLI and
  any SDK callers before enabling the switch. `docs/ENV.md` and the upgrade notes say so.
- **Turning the switch off** leaves pending changes approvable and rejectable under the same
  rules, self-approval included. New writes apply directly.
- **A downgrade** follows the release's general rule: the migrator refuses a database with
  migrations it does not know. GOV4 adds one table to that.
