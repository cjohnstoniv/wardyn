New Run rail — the #542 gaps

Two shapes PR #1036 built with no line of their own. One small approval: say "approve packet 542-gaps", or name the strings you'd change.
Problem + decisionsThe statesCanon
The gapWhat ships silent today

PR #1036 drew R1–R4 and R6–R9 of the rail's provider picker, but two shapes reach the person with no sentence explaining themselves. First: when the admin's default provider is disabled, or this person has been granted none of the harness's providers at all, the picker falls through to R6's shape — no preselection, Launch just sits disabled — with nothing on screen saying why nothing was chosen for them. Second: R3's "you picked this, but it isn't connected yet" warning was drawn for exactly two provider kinds (bedrock_sso, custom_endpoint); the other three kinds a person can pick — an Anthropic API key, an OpenAI API key, or a Claude subscription — reach Launch with no warning line and no connect button at all.

Packet C already drafted R5b/R5c's sentences when it defined R1–R9 (frozen-strings table, §5.6) — the owner ruled R5 out of THAT build, not out of canon. This packet re-proposes those sentences unchanged, plus two new ones for R3's missing kinds, drawn from the same wire vocabulary the server's own model-provider refusal already uses (docs/design/model-providers-mock/canon.html's LLM_PROVIDER_REFUSAL states: "you are not signed in to Claude for it", "you have not added your key for it").

DecisionsAt most 3, each with a recommendation
  1. D1 · Does R5c name the admin who turned the default off, or just "your admin"?

    Recommended: just "your admin." SetupModelProvider carries no admin-identity field to name one, RAIL_PROVIDER.NOT_GRANTED and AGENTS.NO_PROVIDER already say "ask your admin" with no name, and an org with several admins has no single right name to print.

  2. D2 · One shared sentence for both API-key kinds (anthropic_api_key, openai_api_key), or one per kind?

    Recommended: one shared RAIL_PROVIDER.NO_KEY(name). model-provider-lane.ts's providerWhatWord/providerStateWord already treat every non-sign-in, non-token kind as plain "key" with no branch between the two — a second near-identical sentence would be the second answer to a question RAIL_PROVIDER.OPTION already answered once.

  3. D3 · Does the new anthropic_subscription line name the provider ("for {name}"), or drop the name the way the shell banner (BANNER.B5: "you're not signed in to Claude") does?

    Recommended: keep "for {name}." This sentence sits in RAIL_PROVIDER beside NOT_SIGNED_IN and NO_TOKEN, which both name the provider because a person can be offered more than one candidate of the same kind (two Claude subscriptions an admin set up differently, for instance). BANNER.B5 is one shell-wide banner with no list to disambiguate — a different surface, not a precedent to match.
