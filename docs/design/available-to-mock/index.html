What this isThe last four families still without their "Available to" control

You approved one "Available to" on every resource an admin sets up (user-types packet A, D1). #919 puts it on git providers, agents and org workspaces. #923 covers the other four: stored policies, model providers, integrations and base images. Two of those have an editor to put it in. The other two don't, and #923 asks for a mock round to decide where it goes.

When you approve, #923 loses needs-mock. The policy part can start once #818 lands, the model provider part once #537 lands and the kind is made restrictable, and the image part once #919's control is on main.

DecisionsFive, each drawn as recommended. Everything else follows packet A and #919.
  1. Where a base image's list lives. Drawn: a new Images tab on Workspace providers, after Agents. It has one row per image in the catalog that workspaces already fill (GET /base-images), each row with its control, and an Add image button that takes one reference. The other option is no Images page at all: images are listed for a type only from the type editor (UT-7a), where packet A already shows "Admins only · Images".

    Recommended: the tab. Images are admins-only until someone is listed, so without a page there is no place to see which images are open and to whom. The trade-off: a new tab and seven new strings.

  2. What the first choice says on an image. Drawn: Admins only / Only these, with packet A's line "Images are off for everyone until you list someone here." The other option is the same Everyone / Only these as every other family. But an image nobody is listed for can only be launched by admins, so "Everyone" would be selected on something almost nobody can use.

    Recommended: Admins only. It is what the server does, and packet A's type view already uses the words. It needs one extra line for the locked last chip: "Choose Admins only before removing the last one."

  3. Integrations get no editor of their own. Every integration the console shows is one of two things. The AI kinds become model providers in 0.8 (MP-15 removes them), and their list is on the provider editor. GitHub App and git host rows are git provider rows, which already have the control (#919). Drawn: a map of where each kind's list lives, and nothing new. The other option adds the control to Settings → Model provider for the card's integration, until MP-15 removes it.

    Recommended: no editor. A control on a kind that is going away would be taken out again within the release. Until then, the type editor can still set integration availability.

  4. A new policy, provider or image. Design §2.6 says a resource created after 0.8 asks on its creation form, starting at Everyone (Admins only for an image). It doesn't say how, and the control can only write once the resource has an id. Drawn: the form holds the choice, and Save creates the resource, writes the list, then turns Only these on. If the list is refused after the resource saved, the editor stays open on it with "Saved, but not who it's available to", the server's sentence, and "It is available to everyone until you set it again below." The other option leaves the control off creation forms: a new resource starts at Everyone, and the list is set once it has been saved.

    Recommended: as drawn, because it is what the approved design says. The trade-off: three new strings, and a partly failed save the admin has to finish. For a policy or a provider, both options leave it open to everyone between the two writes; an image starts admins-only, so there is no such gap.

  5. Each family's two lines. Drawn: policies and model providers follow the git provider's approved pattern. After "Only these" comes what someone not listed loses, plus "Runs already going aren't affected". Under the list comes "Security admins can change this list from the type editor too. The … itself is edited only by super admins." An image keeps only packet A's line, plus the note. The other option is no family lines, which is how #919 draws agents and workspaces.

    Recommended: as drawn. The only-these line is where the admin reads what taking someone off does, and no other state explains it. The trade-off: five new strings. "Runs already going aren't affected" still has to be checked on the model provider, where each model call might re-check the grant.

Settled without askingCalled out so none of them is a surprise
  • "None selected" is not a state. Choosing Only these with nobody listed is refused by the server, and its sentence is shown as sent (design §2.6). While Only these is on, the last chip's × is disabled (#919), so a list can't be emptied by removing people one by one.
  • Chips follow packet A. A user type shows its name, a group shows "(group)", and a person shows their email. #919 currently draws User type: developer, and the lane should change it to match.
  • The adder follows #919: User type / Group / User, a field, and Add. A typed name alone can't say whether it is a type or a group. The field's placeholder is packet A's.
  • A refused add is shown under the adder, not in a toast. A refusal is worth reading twice (CONSOLE-RULES §9). #919 uses a toast titled "Add".
  • Taking a type off asks for no confirmation. It can be undone, and runs already going keep what they have. Their next launch is where it bites: the server's list leaves the resource out, and naming it anyway gets #736's sentence.
  • Changes write at once, never through the editor's Save (#919). The one exception is a creation form (decision 4).
  • Only security admins and super admins see the control. The policy sheet is the only one of the four editors that anyone else can open, and for them the control is simply absent. The provider editor and the Images tab are for super admins only, so a security admin sets those lists from the type editor.
