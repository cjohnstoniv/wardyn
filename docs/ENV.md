# Wardyn environment variables

Registry of every `WARDYN_*` environment variable **read** by non-test Go in
this repo, with its type, default, and the binary that reads it.

The variable list is generated by grep (so it stays complete); a ratchet test
(`cmd/wardynd/envdoc_guard_test.go`) runs it **both ways** — a `WARDYN_*` literal
read in non-test Go but missing here fails the build, and so does a row here whose
last Go reader was deleted. To regenerate the raw list:

```sh
grep -rhoE '"WARDYN_[A-Z0-9_]+"' --include='*.go' --exclude='*_test.go' . \
  | tr -d '"' | sort -u
```

**What the ratchet does not check: the Default column.** It compares *names* only,
so a default that drifts from its `flagEnv`/`flagBool`/`flagDuration` call site goes
red nowhere — check the call site when you edit one. This file is deliberately
hand-written rather than generated: the generated columns are the ones already
correct, and generating it would cost the Notes column, where every load-bearing
caveat lives.

Most `wardynd` / `wardyn-tetragon-ingest` variables are the env form of a CLI
flag: the flag wins when both are set, and the env value only moves the flag's
default (`internal/cliutil`). Every parseable read through `internal/cliutil`
(bool / duration / int) is **loud** — an unparseable value exits 2 rather than
silently reinstating the default. Unset or empty (`docker run -e VAR` / compose
`VAR=`) keeps the default quietly.

Values that are secrets (tokens, DSNs, keys, base64 blobs) are marked 🔒 — never
log them.

## `wardynd` (control plane)

| Variable | Type | Default | Notes |
|---|---|---|---|
| `WARDYN_LISTEN` | string | `:8080` | HTTP listen address (flag `-listen`) |
| `WARDYN_ADMIN_TOKEN` 🔒 | string | **binary: empty**; compose: `demo-admin-token` | admin bearer gating the public API (flag `-admin-token`). Two layers, and they differ: `wardynd`'s own default is the **empty string**, and an empty token with no OIDC issuer on a loopback bind **auto-enables no-auth LOCAL HOST MODE** (`cmd/wardynd/boot_flags.go`) — so leaving it unset does not leave the API bearer-gated, it turns the gate off. The compose stack supplies `demo-admin-token` (`deploy/compose/docker-compose.yaml`) — nominally authenticated: that token is published here, so wardynd warns at boot when it is in use and refuses to start outright if the listen address binds a specific non-loopback interface. Note the recommended `make setup` containerized path additionally writes `WARDYN_LOCAL_MODE=true` into the compose env, so the flagship install runs the no-auth loopback local mode; the bare compose file's own default is the token. There is no `WARDYN_TOKEN` fallback here; that variable is CLI-only |
| `WARDYN_PG_DSN` 🔒 | string | (unset, required) | Postgres DSN (flag `-dsn`). pgx's own `pool_max_conns` DSN param, not a `WARDYN_*` var, so it is not its own row here — but multi-replica operators should size it **at least 3**: the lifecycle reaper borrows one connection per tick (transient, released immediately after), and the ground-truth rotator's leader-election lock (`db.GroundTruthRotatorLockKey`) holds one for the whole process lifetime once acquired — both on top of whatever the pool needs for its own request-serving queries |

| `WARDYN_RUNNER` | string | `none` | runner substrate: `none` or a registered confinement substrate (`docker` in `-tags docker` builds, `k8s` in `-tags k8s` builds — both may be registered in a `-tags docker,k8s` build; unknown/uncompiled names fail closed at boot) (flag `-runner`) |
| `WARDYN_RUNNER_TARGET` | `docker` \| `k8s` | (unset = the resolved target, `none` when no runner is configured) | **test harnesses only.** The substrate name **stored objects validate against** while `WARDYN_RUNNER` is `none`. A runner-less daemon resolves the target `none`, and a user drive names exactly one target that can mount its backend (`docker` for `docker_volume`/`host_path`, `k8s` for `k8s_pvc`/`k8s_pvc_static`), so without this every drive backend is refused with a 400 and no drive can be registered at all — which is the daemon `scripts/e2e-backend.sh` boots for the Playwright suite. It changes what may be **registered**, never what is **dispatched**: the runner is still nil, so every run still stays `PENDING`. **Ignored** whenever a runner *is* configured (the resolved substrate's own name is the only truthful target), and any other value fails boot closed (flag `-runner-target`) |
| `WARDYN_INTERNAL_NETWORK` | string | `wardyn-internal` | the docker network the runner attaches each run's proxy sidecar to; must match the compose control-plane network name (both derive from the compose namespace) or the sidecar lands on the wrong bridge |
| `WARDYN_ALLOW_UNENFORCEABLE_CAPS` | `1` only | off | escape hatch: allow a run to start on a host where the resource caps (memory/pids/cpu) can't actually be enforced. Off by default — the gate fails closed, since an unenforceable cap is a silently-broken guarantee. **Not a `cliutil` bool**: `register.go` compares against the literal string `1`, so `true`/`yes`/`on` do **not** enable it and a garbage value is silently ignored rather than exiting 2 |
| `WARDYN_K8S_NAMESPACE` | string | the pod's own namespace (read from `/var/run/secrets/kubernetes.io/serviceaccount/namespace`), else `default` | Kubernetes namespace the `k8s` substrate (`-tags k8s`) creates every sandbox's Secret/NetworkPolicies/pods in |
| `WARDYN_K8S_IMAGE_PULL_SECRET` | string | (unset) | optional pre-existing Secret name threaded onto `imagePullSecrets` for every pod the `k8s` substrate creates (agent, proxy, and the boot-time egress canary) (`-tags k8s`) |
| `WARDYN_K8S_ALLOW_UNENFORCED_NETPOL` | `1` only | off | escape hatch: allow the `k8s` substrate to boot when its boot-time egress canary proves the cluster's CNI does NOT enforce NetworkPolicy — CreateSandbox then proceeds with UNCONFINED egress instead of refusing to boot. Off by default (fail closed). The opt-out is never an invisible downgrade: it logs a loud warning at construction naming what is going unconfined, and `ClassSupport.NetworkPolicy`/`StructuralEgress` both still report `false` regardless — an opted-out substrate never reads identical to a genuinely confined one on `/healthz` (`-tags k8s`) |
| `WARDYN_K8S_ACK_AMBIENT_DEFAULT_DENY` | `1` only | off | on a managed cluster where a platform team already applies a baseline default-deny NetworkPolicy, phase A of the boot-time egress canary (which applies no policy of its own) fails in exactly that shape — the canary pod reaches Running and its own connect exits `1` — and construction refuses to boot with no override at all. This flag acknowledges that shape as an expected platform baseline rather than a Wardyn misconfiguration and lets boot proceed; phase B is skipped (behind an existing ambient deny it could only ever also exit 1, proving nothing). Any OTHER canary failure shape (never reached Running, a different exit code, apiserver unreachable) stays indeterminate regardless of this flag — it is scoped exactly to the one shape it explains (`-tags k8s`) |
| `WARDYN_DEFAULT_POLICY` | string | `examples/policies/default.json` | default RunPolicy spec path (flag `-default-policy`) |
| `WARDYN_UI_DIR` | string | (unset) | built web UI directory (flag `-ui-dir`) |
| `WARDYN_HOST_PROXY_B64` | string (base64 JSON) | (unset) | host-side proxy detection, captured by `scripts/up.sh` on the host and consumed by the Getting-started "Host proxy" step. **Diagnostics only.** Unset ⇒ the step honestly reports it could not look at the host. See [Four variables that need more than a table cell](#four-variables-that-need-more-than-a-table-cell) |
| `WARDYN_AUDIT_SINKS` 🔒 | string (JSON) | (unset) | audit sink config file/webhook/syslog (flag `-audit-sinks`). A webhook `bearer_token` requires an `https://` url — boot fails rather than replay the SIEM credential in cleartext on every POST. Schema: [Audit sinks](#audit-sinks-wardyn_audit_sinks) below |
| `WARDYN_AUDIT_SPOOL` | string | `./data/audit-spool.jsonl` | append-only JSONL fallback for failed audit writes (flag `-audit-spool`) |
| `WARDYN_AUDIT_SOURCE` | string | (unset) | #10: optional static string stamped as an extra top-level `"source"` field on every event a configured sink (file/webhook/syslog) serializes — never written to Postgres, sink payloads only (flag `-audit-source`). Lets one SIEM index ingesting from several wardynd instances/environments (staging vs prod, cluster A vs B) tell them apart without per-sink config. Empty (the default) is byte-identical to before this field existed. See [Audit sinks](#audit-sinks-wardyn_audit_sinks) below |
| `WARDYN_AGE_KEY` 🔒 | string | (unset) | age X25519 identity (flag `-age-key`) |
| `WARDYN_GEN_AGE_KEY` | bool | `false` | generate a fresh age identity and exit (flag `-gen-age-key`) |
| `WARDYN_LOCAL_MODE` | bool | `false` | LOCAL HOST MODE: bypass public-API auth (flag `-local-mode`) |
| `WARDYN_LOCAL_OPERATOR` | string | `local:<os-user>` | operator principal stamped in local-mode (flag `-local-operator`) |
| `WARDYN_LOCAL_TRUST_FORWARDER` | bool | **binary: `false`; compose: `true`** | accept a non-loopback peer under local-mode (flag `-local-trust-forwarder`) |
| `WARDYN_ALLOW_LOCAL_MODE_WITH_OIDC` | bool | `false` | override: allow boot with `-local-mode` explicitly set alongside a configured `WARDYN_OIDC_ISSUER` — i.e. silently disable the configured OIDC/SSO admin-member RBAC deployment and attribute every request to the fixed local operator — normally refused (`resolveLocalMode`, `cmd/wardynd/boot_flags.go`). The auto-enable heuristic (no explicit flag, no admin token, loopback bind) is unaffected — it already excludes a configured issuer on its own (flag `-allow-local-mode-with-oidc`) |
| `WARDYN_ALLOW_SHARED_SUBSCRIPTION` | bool | `false` | override: allow ONE operator's Anthropic subscription credential to be injected into runs on a daemon that is **not** `-local-mode` — e.g. the compose demo stack, which authenticates with a shared admin token rather than local mode. Does **not** waive the refusals on the k8s runner or a configured `WARDYN_OIDC_ISSUER`: those are multi-user by definition, and sharing one subscription there breaches the harness vendor's requirement that each end user authenticate with their own credential — putting the OPERATOR in breach, not Wardyn. Single-user demo boxes only; prefer a per-user API key (`wardyn secret set anthropic-api-key`) or Bedrock. See `subscriptionInjectPosture` in `cmd/wardynd/boot_posture.go` (flag `-allow-shared-subscription`) |
| `WARDYN_MEMBER_MODE` | bool | `false` | **member-mode desktop**: assert that the human using this daemon is a **member** and the operator authority is elsewhere (an org IdP / MDM-managed config). It adds no middleware — the admin/member split in `internal/api` already enforces everything — it makes the assumption *checkable*: boot is **refused** unless local mode is off (it bypasses public-API auth and would make the loopback developer an admin) **and** OIDC is configured (with no signed-in identity there is no role to derive, so every caller is an admin). See `validateMemberModePosture` (`cmd/wardynd/boot_posture.go`) and [docs/design/member-role-desktop.md](design/member-role-desktop.md) (flag `-member-mode`) |
| `WARDYN_MEMBER_WORKSPACE_ROOTS` | CSV (absolute paths) | (unset = **members may not mount host directories**) | the absolute host directories a **member's own** `local_dir` workspace source may live under. A member source is allowed only if its **canonicalized real path** (`filepath.EvalSymlinks`) is inside one of these — so a symlink *inside* a root pointing *out* of every root is refused — and never if it is or traverses a credential dotfile path (`.ssh`, `.aws`, `.claude`, `.wardyn`, `.gnupg`, `.docker`, `.kube`, `.config/gh`, `.netrc`, `.git-credentials`, `.git/config`), which holds even when a root is set too wide. Checked at onboarding, again at run-create on the resolved spec, and a **third** time in the docker driver immediately before the bind. Unset (the default) fails closed: a member can still onboard repos and use operator-owned workspaces. Point it at a dedicated projects directory — **never `$HOME` or `/`**, which boot WARNs about but permits. Operator mounts are never narrowed by it. (`internal/runner/member_mount.go`; flag `-member-workspace-roots`) |
| `WARDYN_MEMBER_WORKSPACE_ROOTS_MAP` | JSON | (unset) | per-member override of the list above, `{"<principal>": ["/abs/root", ...]}` keyed by lowercased OIDC `sub` **or** email (the same dual-key identity a `capability_grants` `user` subject uses). A principal with an entry uses **only** that entry — per-member **REPLACES** the shared list rather than unioning with it, because per-member exists to *narrow* and a union would make adding a row widen. An entry with an empty list means that member mounts nothing. Malformed JSON, an empty key, or a non-absolute/uncleaned path fails boot closed (flag `-member-workspace-roots-map`) |
| `WARDYN_MEMBER_WRITABLE_ROOTS` | CSV (absolute paths) | (unset = **no writable member mounts at all**) | where a member may mark **their own** mount writable, matched on the same canonicalized real path as the roots above. Unset means every member mount is read-only regardless of the source's `writable` flag — a writable bind widens the residual, so it is opt-in per subtree. Operators keep their unrestricted per-source writable opt-in (flag `-member-writable-roots`) |
| `WARDYN_MEMBER_WRITABLE_DENY` | CSV (absolute paths) | (unset) | carve-outs from `WARDYN_MEMBER_WRITABLE_ROOTS`. **Deny wins** over allow and is checked first, so a subtree inside a writable root can be pinned read-only for members (flag `-member-writable-deny`) |
| `WARDYN_USER_DRIVE_HOST_ROOTS` | CSV (absolute paths) | (unset = **no `host_path` user drive may be registered**) | the absolute host directories a **user drive** of backend `host_path` may be registered inside — typically the mount point of an NFS/SMB share the operator mounted **host-side** (fstab / systemd; Wardyn never performs the share mount and never holds a share credential). One level up from the member roots above: a drive's `host_root` is authored in the **database by an admin**, and its per-person subdirectories are bound into **other people's** sandboxes, so the ceiling over it is operator/MDM-set here rather than in a table the product itself writes — a console compromise then widens nothing. A `host_root` is accepted only if it passes the same host bind-mount deny-list every authored source does **and** its **canonicalized real path** (`filepath.EvalSymlinks`) is inside one of these — and, unlike a member mount source, it must actually **exist on this host** (fail-closed: authoring a drive over a path that is not there defers the failure to somebody else's run). Only that person's **subdirectory** is ever bound, never the root. Unset (the default) fails closed: Wardyn-managed volume drives are unaffected. Point it at the share's mount point — **never `$HOME` or `/`**, which boot WARNs about but permits. Malformed or non-absolute/uncleaned entries fail boot closed (`internal/runner/user_drive_mount.go`; flag `-user-drive-host-roots`) |

| `WARDYN_TLS_KEY` 🔒 | string | (unset) | TLS private key PEM path (flag `-tls-key`) |
| `WARDYN_TLS_TERMINATED` | bool | `false` | TLS terminates upstream; mark cookies Secure (flag `-tls-terminated`) |
| `WARDYN_ALLOW_PLAINTEXT_LISTEN` | bool | `false` | override: allow boot on a specific non-loopback bind serving plain HTTP with no TLS posture configured — normally refused (`refusePlaintextListen`, `cmd/wardynd/main.go`), for **both** listeners: `WARDYN_LISTEN` and `WARDYN_UI_SANDBOX_LISTEN`, which share one TLS posture; loopback and the unspecified bind (`:8080`, the compose topology) stay warn-only either way (flag `-allow-plaintext-listen`) |
| `WARDYN_OIDC_ISSUER` | string | (unset) | OIDC public issuer URL; enables human SSO (flag `-oidc-issuer`) |
| `WARDYN_OIDC_INTERNAL_ISSUER` | string | (unset) | server-reachable OIDC issuer (flag `-oidc-internal-issuer`) |
| `WARDYN_OIDC_CLIENT_ID` | string | (unset) | OIDC client id (flag `-oidc-client-id`) |
| `WARDYN_OIDC_CLIENT_SECRET` 🔒 | string | (unset) | OIDC client secret (flag `-oidc-client-secret`). **Optional**: PKCE S256 is sent on every login regardless, so leaving this unset registers a **public client** (a SPA/native-app registration with no secret at all — some IdPs refuse to issue one for a confidential client) and works exactly the same as a confidential one |
| `WARDYN_OIDC_REDIRECT_URL` | string | (unset) | OIDC redirect URL (flag `-oidc-redirect-url`) |
| `WARDYN_OIDC_EMAIL_DOMAINS` | CSV | (unset = any) | allowed email domains, exact match (list subdomains separately) (flag `-oidc-email-domains`). Entra ID tokens typically **omit `email_verified` entirely**, and this option fail-closes on that (every login denied) against an Entra tenant — prefer Entra App Roles (`WARDYN_OIDC_ROLE_MAP` against the `roles` claim) plus the app registration's "assignment required" setting there instead. An absent claim and an explicit `email_verified: false` are two distinct denials (`auth_error=email_verified_absent` vs `email_unverified`), each logged separately server-side; no opt-in flag relaxes either — allowlisting a self-asserted, unverifiable email would defeat the point of this list |
| `WARDYN_OIDC_OPERATOR_EMAILS` | CSV | (unset = **refused at boot** when OIDC is configured) | operator (admin) allowlist of the minimal member/admin role gate: a signed-in human whose session email is NOT listed is a **member** — owner-scoped: reads their OWN runs/approvals/audit and may launch/kill runs, 403 on configuring the deployment (harness-credential, policy, workspace, site-config **writes**), on **secret** writes/deletes, and on admin-only **credential**/**tool_call** approvals. A member still **decides** `egress_domain` approvals on, and **attaches** to, their OWN runs — both PTY lanes: the ticket mint (`POST /runs/{id}/attach-ticket`) and the attach WebSocket itself (`GET /runs/{id}/attach`), which falls back to session-cookie auth when no ticket is presented; a foreign run is a **404** (no existence oracle). `GET /secrets` (names only) stays readable. Full addresses, case-insensitive. Admin-token and local-mode callers are always admins (one shared credential, no human to key a role off). Leaving it empty with OIDC configured makes every SSO human admin-equivalent and is refused at boot — see `WARDYN_ALLOW_OIDC_NO_OPERATOR_LIST` (flag `-oidc-operator-emails`). Also doubles as a **legacy admin source** for the separate `WARDYN_OIDC_ROLE_MAP` role gate below: an email on this list always derives role `admin` there too, so an existing deployment adopting the role map keeps its operators as admins with zero re-configuration |
| `WARDYN_ALLOW_OIDC_NO_OPERATOR_LIST` | bool | `false` | override: allow boot with OIDC SSO configured but `WARDYN_OIDC_OPERATOR_EMAILS` empty — i.e. every signed-in human admin-equivalent — normally refused (`validateOperatorPosture`, `cmd/wardynd/main.go`). Unconditional, unlike the plaintext rule: a loopback bind bounds who can reach the port, not who the IdP authenticates. No effect without OIDC (flag `-allow-oidc-no-operator-list`) |
| `WARDYN_OIDC_ROLE_MAP` | CSV (`value=role` pairs) | (unset = role derivation off unless a console-managed mapping actually contributes to the merged map) | maps an Entra App Role (`roles` claim — the priority path), a `groups` claim entry, or an email — matched case-insensitively — to a Wardyn session role, `admin` or `member`, e.g. `Wardyn.Admin=admin,eng-team=member,alice@corp.com=admin`. If more than one entry matches, **any `admin` match wins** over a `member` match, regardless of which claim produced it. An email on `WARDYN_OIDC_OPERATOR_EMAILS` (above) always resolves to `admin` too — same top precedence. Console-managed mappings (Getting Started → People) merge with this map as additional entries at each login — same matching rules, and a chart entry here always wins on a duplicate key — this var remains the boot-time bootstrap those console rows merge on top of. No match at all falls through to `WARDYN_OIDC_DEFAULT_ROLE`, or denies the login when that is also unset. A bad role value, a non-ASCII key (matching is ASCII-only, so it could never match), a duplicate key, or non-empty input with no valid entry is a boot error naming the var. Derived once, at `/auth/callback` time (`internal/auth/oidc`'s `deriveRole`), and stamped into the signed session cookie — a cookie signed before this field existed decodes as no session, forcing a re-login. **Prefer `roles`/`groups` keys (IdP-signed) over email keys**: an email key is a second email-keyed privilege source riding an unverified IdP claim, same caveat as `WARDYN_OIDC_OPERATOR_EMAILS` above — `email_verified` is enforced only when `WARDYN_OIDC_EMAIL_DOMAINS` is also set (flag `-oidc-role-map`). **The same two claims do double duty**, with or without this var set: the union of `roles` and `groups` is also snapshotted into the session at callback as the caller's group identity, which is what a `subject_type=group` capability grant matches ([OPERATIONS.md](OPERATIONS.md) → "Capabilities: what one member, or one group, may do"). Lowercased, deduped, sorted, printable-ASCII only, and capped at 2048 payload bytes — dropped from the alphabetical END so the same human loses the same groups every login — which keeps the signed cookie under the ~4096 bytes a browser silently discards whole (~100 typical group names; past that, grant the user directly or prefer App Roles). It is a **login-time snapshot**: a directory change needs a re-login, while grants themselves resolve per request. A pre-0.6 cookie carries no groups at all and stays valid, reported as `groups_snapshot_stale` on `GET /me/capabilities` rather than as "holds no groups" |
| `WARDYN_OIDC_DEFAULT_ROLE` | string (`admin`\|`member`) | (unset = **deny the login**, this applies once the merged map — chart or console — is non-empty) | role assigned when a signed-in human's roles/groups/email matched none of the merged map's entries — the merged map is `WARDYN_OIDC_ROLE_MAP` (chart) plus console-managed mappings (Getting Started → People), so this var applies whenever EITHER source is non-empty, not only when the chart var itself is set. Unset denies that login with a message pointing the user at `WARDYN_OIDC_ROLE_MAP`. Ignored only when the merged map is itself empty — the chart var is empty AND no console mapping actually contributes to it: a console row that's empty/non-canonical or shadowed by the chart or `WARDYN_OIDC_OPERATOR_EMAILS` contributes nothing, the same as having no console rows at all, so the merged map can still be empty even with saved console rows present (flag `-oidc-default-role`) |
| `WARDYN_OIDC_ALLOW_EMAIL_MAPPINGS` | bool | `false` | opt-in for an email-shaped (contains `@`) value on a **console** People-step role mapping (`POST /access/mappings`) only — `WARDYN_OIDC_ROLE_MAP`'s own email-keyed entries above are unaffected either way (legacy, still boot-warned separately when `WARDYN_OIDC_EMAIL_DOMAINS` is unset). Refused by default (`EMAIL_KEY_REFUSED`, `internal/api/access.go`) steering an admin toward an App Role or group key instead — an Entra ID token typically **omits `email_verified` entirely**, so an email-keyed mapping rides an unverifiable claim the same way an email-keyed `WARDYN_OIDC_ROLE_MAP` entry does. Set it to allow the console write when this deployment has no usable App Role/group claim (flag `-oidc-allow-email-mappings`) |
| `WARDYN_DIRECTORY_PROVIDER` | string (`entra`) | (unset = **off**) | identity-directory connector behind the console's "who" autocomplete — the governance assignment **subject** and the People-step mapping **value** — so an admin picks a name and Wardyn stores the claim value (a group's `groups` claim carries its **object GUID**, not its name, and a hand-typed name binds nothing). Any value other than `entra` or empty is a **boot refusal** — a typo must not read as "off". See [OPERATIONS.md](OPERATIONS.md) → "Directory autocomplete" (flag `-directory-provider`) |
| `WARDYN_DIRECTORY_TENANT` | string | (unset = derived from `WARDYN_OIDC_ISSUER`) | Entra tenant id or verified domain for the connector. Unset, it is derived from the issuer's first path segment — commercial-cloud issuers only (`https://login.microsoftonline.com/<tenant>/v2.0`, or the v1.0 `https://sts.windows.net/<tenant>/`), since the connector talks to `graph.microsoft.com`; any other issuer is a **boot refusal** naming this var rather than a runtime failure against a tenant that does not exist. ### Audit sinks (`WARDYN_AUDIT_SINKS`)

The value is the JSON blob itself, not a path to one — so a webhook
`bearer_token` lands in the process environment. Omitting a top-level key
disables that sink; the whole variable unset disables fanout entirely (Postgres
stays the source of truth either way).

```json
{
  "syslog":  {"network": "udp", "addr": "localhost:514"},
  "webhook": {"url": "https://siem.example.com/ingest", "bearer_token": "...", "batch_size": 50},
  "file":    {"path": "/var/log/wardyn/audit.log", "max_bytes": 52428800, "keep": 3}
}
```

Defaults for the fields not shown: `file` rotates at `max_bytes` 100 MiB keeping
`keep` 5; `webhook` also takes `flush_interval` (`5s`), `buffer_size` (`4096`),
`max_retries` (`3`) and `retry_base_delay` (`200ms`) — see
`internal/audit/sinks/webhook.go`. The compose stack ships the `file` sink
pointed at `/data/audit/audit.log`.

Every event is one JSON object (NDJSON on the webhook sink — one line per
event per POST batch); `Data` is the per-action payload documented in
[AUDIT-ACTIONS.md](AUDIT-ACTIONS.md). `WARDYN_AUDIT_SOURCE` above adds a
`"source"` field to every one of them, for a multi-instance SIEM index.

#### SIEM recipes (`webhook`)

Two concrete `webhook` configs — swap in your real collector URL/token. Both
are just `WARDYN_AUDIT_SINKS`'s `webhook` block; nothing else changes.

**Splunk HTTP Event Collector (HEC).** HEC wants each line wrapped in an
`{"event": ...}` envelope, which this sink does not do — point it at a
lightweight HEC-shaped relay (or Splunk's own NDJSON-to-HEC forwarder) rather
than `services/collector/event` directly, and pass the HEC token as the
bearer:

```json
{
  "webhook": {
    "url": "https://splunk-hec-relay.corp.example:8443/ingest",
    "bearer_token": "<hec-token>",
    "batch_size": 100
  }
}
```

**Generic JSON webhook** (Datadog, Elastic, Chronicle, an in-house collector
— anything that accepts a bearer-authed NDJSON POST):

```json
{
  "webhook": {
    "url": "https://siem.example.com/ingest",
    "bearer_token": "<collector-token>",
    "batch_size": 50,
    "flush_interval": "5s"
  }
}
```

Both refuse to boot with a `bearer_token` set on a non-`https://` `url` (the
credential would replay in cleartext on every POST — see `NewWebhookSink`).
Watch `wardyn_audit_sink_drops_total{sink="webhook"}` on `/metrics`: a rising
count means the collector is slow/down and events are being shed after
`max_retries` — see [Monitoring](OPERATIONS.md#monitoring).

## Four variables that need more than a table cell

- **`WARDYN_HOST_PROXY_B64`** — a containerized wardynd is blind to every host
  detection tier (the OS/PAC tier dispatches on the *process's* `GOOS`, `git` is
  absent from the distroless image, `HOME` is unset so no shell profile or tool
  config is reachable), so without this seed the step would assert a false negative.
  It is deliberately **not** named `HTTP_PROXY`: Go's `net/http` honors the standard
  names process-wide, which would silently reroute wardynd's own OIDC discovery,
  audit webhooks, GitHub App minting and AWS credential chain through the corporate
  proxy. Values are credential-masked before capture; base64 because compose
  interpolates `$` inside `.env` values.
- **`WARDYN_NS`** — compose sets wardynd's `WARDYN_INTERNAL_NETWORK` from the same
  value; they **must** stay equal or each run's proxy sidecar joins the wrong bridge.
- **`WARDYN_UI_STAGE`** — when the in-image build fails, `scripts/up.sh` builds the UI
  on the host and retries with `ui-prebuilt` automatically. Setting it explicitly
  forces one stage *and disables that retry*.
- **`WARDYN_CI_PROJECT`** — the per-PID default guarantees concurrent invocations
  never collide, and that one job's `down --volumes` cannot tear down another's.
