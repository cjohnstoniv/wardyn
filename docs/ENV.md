# Wardyn environment variables

Registry of every `WARDYN_*` environment variable **read** by non-test Go in
this repo, with its type, default, and the binary that reads it.

The variable list is generated by grep (so it stays complete); a ratchet test
(`cmd/wardynd/envdoc_guard_test.go`) runs it **both ways** — a `WARDYN_*` literal
read in non-test Go but missing here fails the build, and so does a row here whose
last Go reader was deleted. To regenerate the raw list:

```sh
grep -rhoE '"WARDYN_[A-Z0-9_]+"' --include='*.go' --exclude='*_test.go' . \
  | tr -d '"' | sort -u
```

**What the ratchet does not check: the Default column.** It compares *names* only,
so a default that drifts from its `flagEnv`/`flagBool`/`flagDuration` call site goes
red nowhere — check the call site when you edit one. This file is deliberately
hand-written rather than generated: the generated columns are the ones already
correct, and generating it would cost the Notes column, where every load-bearing
caveat lives.

Most `wardynd` / `wardyn-tetragon-ingest` variables are the env form of a CLI
flag: the flag wins when both are set, and the env value only moves the flag's
default (`internal/cliutil`). Every parseable read through `internal/cliutil`
(bool / duration / int) is **loud** — an unparseable value exits 2 rather than
silently reinstating the default. Unset or empty (`docker run -e VAR` / compose
`VAR=`) keeps the default quietly.

Values that are secrets (tokens, DSNs, keys, base64 blobs) are marked 🔒 — never
log them.

## `wardynd` (control plane)

| `WARDYN_LISTEN` | string | `:8080` | HTTP listen address (flag `-listen`) |
| `WARDYN_ADMIN_TOKEN` 🔒 | string | **binary: empty**; compose: `demo-admin-token` | admin bearer gating the public API (flag `-admin-token`). Two layers, and they differ: `wardynd`'s own default is the **empty string**, and an empty token with no OIDC issuer on a loopback bind **auto-enables no-auth LOCAL HOST MODE** (`cmd/wardynd/boot_flags.go`) — so leaving it unset does not leave the API bearer-gated, it turns the gate off. The compose stack supplies `demo-admin-token` (`deploy/compose/docker-compose.yaml`) — nominally authenticated: that token is published here, so wardynd warns at boot when it is in use and refuses to start outright if the listen address binds a specific non-loopback interface. Note the recommended `make setup` containerized path additionally writes `WARDYN_LOCAL_MODE=true` into the compose env, so the flagship install runs the no-auth loopback local mode; the bare compose file's own default is the token. There is no `WARDYN_TOKEN` fallback here; that variable is CLI-only |

See `subscriptionInjectPosture` in `cmd/wardynd/boot_posture.go` (flag `-allow-shared-subscription`) |
| `WARDYN_MEMBER_MODE` | bool | `false` | **member-mode desktop**: assert that the human using this daemon is a **member** and the operator authority is elsewhere (an org IdP / MDM-managed config). It adds no middleware — the admin/member split in `internal/api` already enforces everything — it makes the assumption *checkable*: boot is **refused** unless local mode is off (it bypasses public-API auth and would make the loopback developer an admin) **and** OIDC is configured (with no signed-in identity there is no role to derive, so every caller is an admin). See `validateMemberModePosture` (`cmd/wardynd/boot_posture.go`) and [docs/design/member-role-desktop.md](design/member-role-desktop.md) (flag `-member-mode`) |
| `WARDYN_MEMBER_WORKSPACE_ROOTS` | CSV (absolute paths) | (unset = **members may not mount host directories**) | the absolute host directories a **member's own** `local_dir` workspace source may live under. A member source is allowed only if its **canonicalized real path** (`filepath.EvalSymlinks`) is inside one of these — so a symlink *inside* a root pointing *out* of every root is refused — and never if it is or traverses a credential dotfile path (`.ssh`, `.aws`, `.claude`, `.wardyn`, `.gnupg`, `.docker`, `.kube`, `.config/gh`, `.netrc`, `.git-credentials`, `.git/config`), which holds even when a root is set too wide. Checked at onboarding, again at run-create on the resolved spec, and a **third** time in the docker driver immediately before the bind. Unset (the default) fails closed: a member can still onboard repos and use operator-owned workspaces. Point it at a dedicated projects directory — **never `$HOME` or `/`**, which boot WARNs about but permits. Operator mounts are never narrowed by it. | `WARDYN_MEMBER_WORKSPACE_ROOTS_MAP` | JSON | (unset) | per-member override of the list above, `{"<principal>": ["/abs/root", ...]}` keyed by lowercased OIDC `sub` **or** email (the same dual-key identity a `capability_grants` `user` subject uses). A principal with an entry uses **only** that entry — per-member **REPLACES** the shared list rather than unioning with it, because per-member exists to *narrow* and a union would make adding a row widen. An entry with an empty list means that member mounts nothing. Malformed JSON, an empty key, or a non-absolute/uncleaned path fails boot closed (flag `-member-workspace-roots-map`) |
| `WARDYN_MEMBER_WRITABLE_ROOTS` | CSV (absolute paths) | (unset = **no writable member mounts at all**) | where a member may mark **their own** mount writable, matched on the same canonicalized real path as the roots above. | `WARDYN_OIDC_OPERATOR_EMAILS` | CSV | (unset = **refused at boot** when OIDC is configured) | operator (admin) allowlist of the minimal member/admin role gate: a signed-in human whose session email is NOT listed is a **member** — owner-scoped: reads their OWN runs/approvals/audit and may launch/kill runs, 403 on configuring the deployment (harness-credential, policy, workspace, site-config **writes**), on **secret** writes/deletes, and on admin-only **credential**/**tool_call** approvals. Full addresses, case-insensitive. Admin-token and local-mode callers are always admins (one shared credential, no human to key a role off). Leaving it empty with OIDC configured makes every SSO human admin-equivalent and is refused at boot — see `WARDYN_ALLOW_OIDC_NO_OPERATOR_LIST` (flag `-oidc-operator-emails`). | `WARDYN_OIDC_ROLE_MAP` | CSV (`value=role` pairs) | (unset = role derivation off; every SSO user is `admin`) | maps an Entra App Role (`roles` claim — the priority path), a `groups` claim entry, or an email — matched case-insensitively — to a Wardyn session role, `admin` or `member`, e.g. `Wardyn.Admin=admin,eng-team=member,alice@corp.com=admin`. If more than one entry matches, **any `admin` match wins** over a `member` match, regardless of which claim produced it. An email on `WARDYN_OIDC_OPERATOR_EMAILS` (above) always resolves to `admin` too — same top precedence. No match at all falls through to `WARDYN_OIDC_DEFAULT_ROLE`, or denies the login when that is also unset. A bad role value, a non-ASCII key (matching is ASCII-only, so it could never match), a duplicate key, or non-empty input with no valid entry is a boot error naming the var. Derived once, at `/auth/callback` time (`internal/auth/oidc`'s `deriveRole`), and stamped into the signed session cookie — a cookie signed before this field existed decodes as no session, forcing a re-login. **Prefer `roles`/`groups` keys (IdP-signed) over email keys**: an email key is a second email-keyed privilege source riding an unverified IdP claim, same caveat as `WARDYN_OIDC_OPERATOR_EMAILS` above — `email_verified` is enforced only when `WARDYN_OIDC_EMAIL_DOMAINS` is also set (flag `-oidc-role-map`). **The same two claims do double duty**, with or without this var set: the union of `roles` and `groups` is also snapshotted into the session at callback as the caller's group identity, which is what a `subject_type=group` capability grant matches ([OPERATIONS.md](OPERATIONS.md) → "Capabilities: what one member, or one group, may do"). Lowercased, deduped, sorted, printable-ASCII only, and capped at 2048 payload bytes — dropped from the alphabetical END so the same human loses the same groups every login — which keeps the signed cookie under the ~4096 bytes a browser silently discards whole (~100 typical group names; past that, grant the user directly or prefer App Roles). It is a **login-time snapshot**: a directory change needs a re-login, while grants themselves resolve per request. A pre-0.6 cookie carries no groups at all and stays valid, reported as `groups_snapshot_stale` on `GET /me/capabilities` rather than as "holds no groups" |

### Audit sinks (`WARDYN_AUDIT_SINKS`)

The value is the JSON blob itself, not a path to one — so a webhook
`bearer_token` lands in the process environment. Omitting a top-level key
disables that sink; the whole variable unset disables fanout entirely (Postgres
stays the source of truth either way).

```json
{
  "syslog":  {"network": "udp", "addr": "localhost:514"},
  "webhook": {"url": "https://siem.example.com/ingest", "bearer_token": "...", "batch_size": 50},
  "file":    {"path": "/var/log/wardyn/audit.log", "max_bytes": 52428800, "keep": 3}
}
```

Defaults for the fields not shown: `file` rotates at `max_bytes` 100 MiB keeping
`keep` 5; `webhook` also takes `flush_interval` (`5s`), `buffer_size` (`4096`),
`max_retries` (`3`) and `retry_base_delay` (`200ms`) — see
`internal/audit/sinks/webhook.go`. The compose stack ships the `file` sink
pointed at `/data/audit/audit.log`.

Every event is one JSON object (NDJSON on the webhook sink — one line per
event per POST batch); `Data` is the per-action payload documented in
[AUDIT-ACTIONS.md](AUDIT-ACTIONS.md). `WARDYN_AUDIT_SOURCE` above adds a
`"source"` field to every one of them, for a multi-instance SIEM index.

#### SIEM recipes (`webhook`)

Two concrete `webhook` configs — swap in your real collector URL/token. Both
are just `WARDYN_AUDIT_SINKS`'s `webhook` block; nothing else changes.

**Splunk HTTP Event Collector (HEC).** HEC wants each line wrapped in an
`{"event": ...}` envelope, which this sink does not do — point it at a
lightweight HEC-shaped relay (or Splunk's own NDJSON-to-HEC forwarder) rather
than `services/collector/event` directly, and pass the HEC token as the
bearer:

```json
{
  "webhook": {
    "url": "https://splunk-hec-relay.corp.example:8443/ingest",
    "bearer_token": "<hec-token>",
    "batch_size": 100
  }
}
```

**Generic JSON webhook** (Datadog, Elastic, Chronicle, an in-house collector
— anything that accepts a bearer-authed NDJSON POST):

```json
{
  "webhook": {
    "url": "https://siem.example.com/ingest",
    "bearer_token": "<collector-token>",
    "batch_size": 50,
    "flush_interval": "5s"
  }
}
```

Both refuse to boot with a `bearer_token` set on a non-`https://` `url` (the
credential would replay in cleartext on every POST — see `NewWebhookSink`).
Watch `wardyn_audit_sink_drops_total{sink="webhook"}` on `/metrics`: a rising
count means the collector is slow/down and events are being shed after
`max_retries` — see [Monitoring](OPERATIONS.md#monitoring).

| `WARDYN_DOCKER_SOCK` | string (path) | `/var/run/docker.sock` | which host Docker socket `wardynd` binds and drives. Persisted into `deploy/compose/.env` by setup |
| `WARDYN_WORKSPACES_ROOT` | string (path) | (unset = no host path exposed) | compose only — bind-mounts this host directory READ-ONLY at the *same path* inside the `wardynd` container so `local_dir` workspace onboarding (`internal/api/workspaces.go`) can see host source. Point it at the narrowest project directory you have — **never** your home directory (wardynd could then read `~/.ssh`, `~/.aws`, `~/.claude`, and staged Claude creds). The interactive prompt below enforces this itself — typing your home directory (or `~`) is refused with a warning and reverts to whatever was set before, not merely discouraged in copy. Unset means local-directory import stays unavailable rather than silently exposing anything. `scripts/setup.sh`'s containerized path prompts for it interactively (TTY only, and only when it is unset) and persists a non-empty answer into `deploy/compose/.env`; an already-exported env var wins silently and is persisted UNCHECKED — skipping the prompt (and its guard) entirely — and a bare Enter with no prior `.env` value leaves it unset/sealed — never the current directory |
| `WARDYN_MANAGED_DIR` | string (path) | (unset = nothing mounted) | compose only — bind-mounts this host directory READ-ONLY at the fixed path `/etc/wardyn` inside the `wardynd` container. Unlike `WARDYN_WORKSPACES_ROOT` above, only the HOST side varies — the container side is the literal `/etc/wardyn`, because the policy path comes from the MDM payload, not the operator. Every non-desktop deployment leaves it unset and mounts a harmless empty path |

## Four variables that need more than a table cell

- **`WARDYN_HOST_PROXY_B64`** — a containerized wardynd is blind to every host
  detection tier (the OS/PAC tier dispatches on the *process's* `GOOS`, `git` is
  absent from the distroless image, `HOME` is unset so no shell profile or tool
  config is reachable), so without this seed the step would assert a false negative.
  It is deliberately **not** named `HTTP_PROXY`: Go's `net/http` honors the standard
  names process-wide, which would silently reroute wardynd's own OIDC discovery,
  audit webhooks, GitHub App minting and AWS credential chain through the corporate
  proxy. Values are credential-masked before capture; base64 because compose
  interpolates `$` inside `.env` values.
- **`WARDYN_NS`** — compose sets wardynd's `WARDYN_INTERNAL_NETWORK` from the same
  value; they **must** stay equal or each run's proxy sidecar joins the wrong bridge.
- **`WARDYN_UI_STAGE`** — when the in-image build fails, `scripts/up.sh` builds the UI
  on the host and retries with `ui-prebuilt` automatically. Setting it explicitly
  forces one stage *and disables that retry*.
- **`WARDYN_CI_PROJECT`** — the per-PID default guarantees concurrent invocations
  never collide, and that one job's `down --volumes` cannot tear down another's.
