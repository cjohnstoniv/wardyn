# Runtime contract

What a run can rely on, promise by promise, on each of five runtimes, and the test that checks each claim.
It is for a platform team that offers Wardyn runs to its own consumers and must say what holds where.
[How to read a cell](#how-to-read-a-cell) explains the four verdict words.

## The swap proof

The CI job `conformance-k8s-agent-sandbox` in [`.github/workflows/ci.yml`](../.github/workflows/ci.yml) shows one contract holding over two runtimes.

- It runs the Kubernetes conformance suite, through the same make target as the `conformance-k8s` job, with the agent-sandbox backend on (`WARDYN_TEST_K8S_AGENT_SANDBOX=1`).
- Every Kubernetes runtime in the suite is built through one config function, [`k8sSuiteConfig`](../test/conformance/agentsandbox_k8s_test.go), which sets only the backend switch.
- So [`TestConformanceK8s`](../test/conformance/conformance_k8s_test.go) runs its cases unchanged against pods an agent-sandbox `Sandbox` made. [`TestAgentSandboxBackendIsReallyOn`](../test/conformance/agentsandbox_k8s_test.go) checks that each pod is controlled by its `Sandbox`.
- The job fails unless each of the backend's own named cases passed, so a skipped case fails it too.

Its limits:

- It runs only on pushes to main and on pull requests from `train/` branches, and skips when the `changes` job finds no backend change. It is not a required check, and it is not in the `gates` job.
- It covers one cluster setup: kind, Calico and `CC1` ([What is claimed](operations/kubernetes-agent-sandbox.md#what-is-claimed)).
- Docker, Docker through the runner protocol, and Kubernetes on either backend call one shared function, [`conformance.Run`](../test/conformance/conformance.go).
- Their options differ. Only the Docker suites pass a route probe, and only the Docker server suite a name-lookup probe, so `L0StructuralEgress` and `DNSAudit` skip on Kubernetes.
- The Docker suites run a stand-in proxy, so their `NoNetwork` case checks only that nothing gets out. Kubernetes runs the real proxy.
- Linux VM and macOS VM do not call it. Linux VM has its own suite, [`TestLinuxVMSandbox`](../test/conformance/vm/vm_test.go), in the `vm` job. The macOS live suite skips in the `macos` job, where no guest boots.

## How to read a cell

| Word | Meaning |
|---|---|
| **Holds** | The runtime keeps the promise, and the linked test checks it in hosted CI on that runtime |
| **Partly** | It keeps part of the promise, under a condition, or with no CI test. The cell says which |
| **Not held** | The runtime refuses the promise or lacks it. The cell names the refusal code where there is one |
| **Not stated** | No shipped page or test says either way. Do not rely on it |

- A test link's text is the test or case name, and its file holds the assertions. A page link names the rule the cell rests on.
- Docker cases run in the `conformance` job, and its `CC2` leg in the nightly gVisor job. Kubernetes cases run in `conformance-k8s`, agent-sandbox cases in `conformance-k8s-agent-sandbox`, and Linux VM cases in `vm`.
- No check that needs a real macOS guest has run in CI ([Not yet tested on a real Mac](operations/macos-vm-troubleshooting.md#not-yet-tested-on-a-real-mac)). So no macOS VM cell says Holds, and each links the page that states the rule.
- Kubernetes with agent-sandbox is an experimental backend, off by default and for server mode only ([The agent-sandbox backend](operations/kubernetes-agent-sandbox.md)).
- A Linux VM is a QEMU guest on a registered runner, a Docker runner unless the cell says otherwise. A macOS VM is a preview on a Mac's runner.
- Terms the control plane keeps for every runtime, such as a run's lease and its extension, are on [Run lifetime](operations/run-lifetime.md).
